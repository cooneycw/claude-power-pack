## Problem

When a Woodpecker agent restarts while a workflow is running on it, the server never reclaims or fails that workflow. It stays `running` indefinitely: service steps `running`, later steps `pending` or `running`, and the deploy step never runs. Because the list says `running`, **dead CI reads as slow CI**. On kyle's push pipelines, dev stays on the previous release until someone notices and kills the pipeline by hand.

## Evidence: a persisted agent id is not enough

This was first attributed to the agent registering a new id on every restart (#1551). The server data contradicts that. Both incidents ran on an agent whose id **is** persisted:

| kyle pipeline | event | agent_id | workflow state after manual kill |
|---|---|---|---|
| 3568 (T013, kyle#1821) | push | 93 (proxVMkyleci22, `host=kyleci`) | `running`, finished=null; postgres/redis `running`, deploy `skipped` |
| 3569 (kyle#1817) | pull_request | 93 | `running`, finished=null; postgres/redis/test-unit/test-playwright `running` |

Agent 93 was created at 1788610487 and still holds the same id. kyleci's compose (generated by `woodpecker/bootstrap-agent-host.sh`) mounts `./agent-config:/etc/woodpecker`. So the agent came back with the same id after the Proxmox reset (16:26 EDT, 2026-10-23) and after kyleci's resize reboot, and the server still left both workflows `running`.

Read via the server API: `/api/repos/<kyle>/pipelines/{3568,3569}` and `/api/agents/93`, on 2026-10-23.

## What is needed (a question, not a design)

Something that notices a workflow whose agent restarted, or whose containers are gone, and fails it. Possibilities, none measured:
- a post-boot reaper on each agent host: after the agent starts, find server workflows `running` on this agent id whose step containers are absent locally, and kill those pipelines;
- a server-side staleness check: `running` with no log or step progress for N minutes after its agent's last reconnect;
- whether a newer Woodpecker version reclaims orphaned work on reconnect (check upstream before building anything).

## Acceptance

- After an agent restart mid-run, the orphaned pipeline reaches a terminal state (killed or failed) without a human, within a stated bound.
- Negative control: a genuinely long-running workflow on a healthy agent is NOT reaped.
