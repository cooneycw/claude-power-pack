## Body as read
## Symptom

Every Codex session prints a wall of warnings like:

```
⚠ /home/cooneycw/.codex/skills/github-issue-close/SKILL.md: failed to read file: No such file or directory (os error 2)
⚠ /home/cooneycw/.codex/skills/secrets-rotate/SKILL.md: failed to read file: No such file or directory (os error 2)
... (one per CPP-generated skill)
```

and `~/.codex/skills` is left holding exactly two directories, `flow-auto` and `qa-test`, whose bodies read:

```
# Flow Auto

Run /flow:eli5 then /qa-test then /cpp:init.
Uses the EnterWorktree tool and scripts/helper.sh; also mentions
scripts/absent.sh which does not exist.
```

That is not a skill. That is `tests/test_codex_skill_sync.py`'s `tmp_repo` fixture body
(tests/test_codex_skill_sync.py:511-519), installed onto the host.

## Root cause

`tests/test_codex_skill_sync.py::test_the_two_success_lines_cannot_be_read_as_the_same_question`
(tests/test_codex_skill_sync.py:1111-1142) calls `codex_skill_sync.main(["--install"])` at line
1129 with the `tmp_repo` fixture but **not** the `tmp_home` fixture.

`tmp_repo` monkeypatches `REPO_ROOT` / `SOURCE_ROOT` / `SCRIPTS_ROOT` / `OUTPUT_ROOT` / `FAMILIES`.
It does not touch `install_dest_root()`, which returns `Path.home() / ".codex" / "skills"`
(scripts/codex-skill-sync.py:1193-1194). Every other `--install` test in the file uses `tmp_home`;
this one is the only call site that does not.

So `run_install()` executes against the real host with a two-skill fixture as its source:

1. copies the fixture `flow-auto` and `qa-test` into `~/.codex/skills`;
2. `find_installed_orphans()` then sees all 72 remaining real skills, each carrying the
   `GENERATED by claude-power-pack` marker, none of them in `source_names = {flow-auto, qa-test}`,
   and `shutil.rmtree()`s every one (scripts/codex-skill-sync.py:1236-1240).

The ownership predicate works exactly as designed — it is being handed the wrong source tree.

## Blast radius

The test is in the default `testpaths`, so **any** `make test` or `make verify`, in any checkout
or worktree, destroys the developer's installed Codex skills. On this host, two fleet worktrees
running `make verify` wiped `~/.codex/skills` twice inside six minutes (05:15 and 05:20) while
this was being diagnosed. A developer who runs `make verify` and then opens Codex sees the
warning wall every time, and has no reason to connect it to CPP's own test suite.

There is no data-loss beyond the install tree — `--install` regenerates it — but the user must
know to re-run it, and nothing tells them.

## Why no instrument caught it

- The test asserts on `capsys` output only. The host write is not part of any assertion, so it
  is invisible to the test that performs it.
- `scripts/check-cpp-host-writes.py` / `scripts/host-surface-observe.py` govern what the
  **scripts** declare they write. Nothing constrains where a **test** is allowed to write.
- `scripts/install-drift.sh` compares the install tree against the checkout, so it would report
  this as drift — but only if someone ran it after a `make verify`, and its report reads as
  "your install is stale", not "your test suite just deleted it".

## Proposed fix

1. Add `tmp_home` to `test_the_two_success_lines_cannot_be_read_as_the_same_question`. The
   assertions still hold, and get stronger: `install_root in install_line` then pins the
   *redirected* root, so the line is proven to name its actual destination rather than a
   constant that happens to appear.
2. Close the class, not the instance: an autouse `conftest.py` guard that fails any test which
   resolves `install_dest_root()` (or more generally writes under the real `Path.home()`)
   without opting in. A second call site added later must not be able to do this again.
3. Negative control for (2), per ADR 0008 — the guard's verdict is consumed by `make verify`,
   which nothing downstream re-derives: commit a case that writes to the real home under the
   guard and assert the guard **reds**. A guard that cannot fail is why this shipped.

## Also worth deciding

`run_install()` copies before it prunes, so there is a window in which the install tree is
half-populated. That is what turns this into a *warning wall* rather than a silent shrink: Codex
lists the directory, then reads each `SKILL.md`, and the ones already `rmtree`'d read as
`No such file or directory`. Pruning into a staging directory and swapping, or pruning before
copying, would make the tree never observably inconsistent — relevant to any concurrent reader,
not just this bug.
