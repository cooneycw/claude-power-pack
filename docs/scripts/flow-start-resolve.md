# `flow-start-resolve` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `flow-start-resolve`

- flow-start-resolve - deterministic `/flow` Step-1 resolver + `--verify` gate (#581): target-repo resolution (#578), issue fetch + state check, issue-anchored branch derivation, existing-work triage (`current-branch|fresh|resume|remote-pickup|local-pickup|cross-repo`), wraps the #503 live-driver guard + shipped-PR hazard, performs git-lane worktree creation (honoring `FLOW_WORKTREE_BASE`, #584), and emits a `key=value` contract - extracts the compound Step-1 bash the permission matcher could never auto-allow
- flow-start-resolve `COMPOSE_PROJECT_NAME` pin (#626) - the resolver emits a canonical compose-project pin in its contract so the WHOLE flow run inherits it, not just the Step-9 deploy #535 guarded. docker compose derives its project name from the cwd basename when unset, so any compose call from a worktree (the Step-4 test-loop `make docker-up`, a hand-run `make docker-*`) forks a parallel stack that collides on the published port and leaks `<basename>_*` orphans. Value precedence matches Step 9: an explicit `.claude/deploy.yaml compose_project_name:` override, else `basename "$TARGET_REPO"` lowercased - never the worktree basename; `auto.md` Step 1/Step 4 and `start.md` instruct pinning it in the same shell call as any `docker compose`
- flow-start-resolve shipped-PR probe on both lanes (#742) - the `PR_HEAD` probe was resume-lane-only, so a remote-pickup of a pushed branch with an OPEN PR reported `PR_HEAD=none` and sailed past the #503 hazard unconfirmed (the 2026-08-31 agentic-actuary run discovered PR #211 only when `gh pr create` errored at Step 6). The probe is now a shared `probe_pr_head()` run on the resume AND remote-pickup lanes, and names the target repo explicitly (`gh pr list --repo <owner>/<repo>`, parsed from origin's URL; cwd-based fallback for non-owner/repo remotes) so a cross-repo run can never let gh's cwd resolution drift
- flow-start-resolve `--session-cwd` - the session cwd is DECLARED, not inferred (#592): the Bash tool's cwd persists across calls and drifts on any earlier `cd`, so `CROSS_REPO` (and, with no PROJECT arg, `TARGET_REPO` itself) and the `current-branch`/`resume` lane detection are resolved from the path `auto.md`/`start.md` pass verbatim. `GIT_LANE` is always 1 now (worktrees are out-of-repo, issue #627), so omitting `--session-cwd` only risks a misdetected `current-branch`/`resume` lane, never a wrong-repo `EnterWorktree`; it still emits `SESSION_CWD_INFERRED=1` so the gap is visible
- flow-start-resolve existing-branch reuse guard (#793) - `create_worktree` used to reuse a pre-existing local branch of the derived name UNCONDITIONALLY, silently discarding the base ref it was told to branch from, while the `fresh` lane still reported `LANE=fresh` as if it had branched cleanly off `origin/<DEFAULT_BRANCH>`. A worker took this at face value and nearly built on top of another worker's unmerged branch tip (a pre-squash checkout of already-merged work). `create_worktree` now runs `git merge-base --is-ancestor <branch> <base>` before reusing an existing branch: an ancestor is content-safe reuse (nothing lost, so it proceeds, but the contract's new `WT_BASE` field names the reuse instead of letting `LANE` alone imply a fresh branch-off); a non-ancestor - unmerged, possibly another worker's - refuses via `fail()`, naming the branch, its short tip SHA, and that it is unmerged, rather than guessing. Also broadens the pickup probe (previously remote-tracking refs only) to a new `local-pickup` lane: a LOCAL branch matching `issue-<N>-*` with no worktree attached (case 2 only catches one WITH a worktree) is now found by issue-number pattern rather than requiring an exact match on the CURRENT title's derived slug, so a branch left over from before the issue was retitled is no longer invisible to it and does not sail past into the fresh lane under a second, duplicate branch name
- flow-start-resolve decides BEFORE it creates (#1258) - every pickup candidate is PR-probed before `git worktree add`: a MERGED branch is shipped history and is skipped (`SHIPPED_BRANCH=`), falling to the fresh lane on a free issue-anchored name; an OPEN one creates nothing and asks (`--allow-pickup`). An unwritable parent dir (a container repo at `/workspace`) falls back to `<repo>/.claude/worktrees/` only where git ignores it, else refuses before `-b`; a failed `-b` add deletes the branch it created. `COMPOSE_PROJECT_NAME` reads the compose file's own top-level `name:` before the checkout basename
- flow-start-resolve own-name upstream (#1221) - branching with `git worktree add -b <branch> <path> origin/main` made git record `origin/main` as the branch's upstream, so a bare `git push` exited 128 and git's FIRST suggested remedy was `git push origin HEAD:main`, which ships the branch onto the default branch past every gate. `create_worktree` now branches with `--no-track` and then sets `branch.<b>.remote=origin` / `branch.<b>.merge=refs/heads/<b>` on every creating lane, which also repairs a reused branch an older resolver pointed at the base. Until the first push `git status` shows the upstream as `[gone]`; a bare push creates it. The regression tests push for real and assert the ref on origin via `ls-remote`, and a pre-receive-rejected push is asserted never to print `HEAD:main`
