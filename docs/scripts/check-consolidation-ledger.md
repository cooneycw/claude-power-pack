# `check-consolidation-ledger` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `check-consolidation-ledger` (#1068)

- check-consolidation-ledger - derives the Codex-consolidation ledger's required population from a COMMITTED snapshot of codex-power-pack's open issues and PRs, and reports any that have no row in `.specify/specs/codex-consolidation/ledger.md` (#1068). The verdict is read by children #1069-#1076 to decide what may be moved, adapted or retired, and by #1076 to decide whether the repository may be archived at all. Nothing downstream re-derives it, which is what puts it inside ADR 0008's bound: a capability with no row is never reported as undecided, it is simply never considered again
- check-consolidation-ledger THE SNAPSHOT IS CAPTURED FROM GITHUB AND NEVER FROM THE LEDGER, and this is the design rather than a detail. A required-set built by scanning the ledger for `cxpp#N` tokens would compare the ledger against itself - every number present would be a number required, the check could never be red, and it would ship green forever while proving nothing. The snapshot file carries the two `gh` commands it came from in its own header so a later maintainer refreshing it cannot accidentally close that loop. `--refresh` re-captures it on a host with network and `gh`; a refresh that ADDS a number turns the gate red until the ledger accounts for it, which is the intended behaviour
- check-consolidation-ledger A CLAIM IS THE FIRST CELL OF A TABLE ROW, NOT A TOKEN ANYWHERE IN THE FILE, and the control caught this rather than a reviewer. The first cut matched `cxpp#<n>` anywhere, and `controls/ledger-completeness`'s known-bad fixture PASSED it: the fixture's prose explains that `cxpp#227` has no row, and that sentence contains the token, so the scan read the explanation of an absence as the account of it. Better prose makes a whole-file text scan MORE likely to pass, not less - the well-written ledger is the one most likely to discuss entries it never tabulated. The rejected rule is vendored as the control's anchor, so the blindness is a committed artifact rather than a remembered one. Same positional discipline as `scripts-inventory-check` (first backticked token of a heading) and `instrument-census-check` (first backticked token of column 2)
- check-consolidation-ledger IT IS ONE-DIRECTIONAL ON PURPOSE. It flags omission - an open entry with no row - and never the reverse, because the real ledger legitimately cites numbers outside the snapshot: PRs merged before the baseline (`cxpp#287`) and CPP issue numbers. A gate that went red on correct prose would be overridden inside a week and take the omission check down with it, which is the oscillation ADR 0009 predicts. It also never judges whether a disposition is RIGHT: `owner-approved-retirement` with no cited owner ruling is a defect this gate cannot see, and the spec leaves that to review
- check-consolidation-ledger AN ABSENT INPUT EXITS 2, NOT 0. A missing ledger, a missing snapshot, or a snapshot that parses to zero required entries are all UNKNOWN, never clean - exiting 0 there would make a deleted ledger indistinguishable from a complete one. `detect_signal` in the control keys on the `LEDGER_MISSING:` line rather than on exit status for the same reason: exit 1 is a finding and exit 2 is an unreadable input, and without the signal an unreadable input would score as a successful detection while nothing had been compared
