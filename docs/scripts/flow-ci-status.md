# `flow-ci-status` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `flow-ci-status`

- flow-ci-status - SHA-anchored CI verification as ONE audited allowlistable helper (#766, the #581 pattern): `/flow:auto` Step 8 was the last un-helpered step, inlining a `curl`+`jq` Woodpecker lookup gated on `WOODPECKER_API_TOKEN` already being exported - which it usually is not, since the token lives in an AWS secret rather than a shell profile. With no helper the model improvises, and on kyle flow:auto #516 the improvisation was a grep over `woodpecker-cli pipeline ls` that matched an unrelated PR pipeline from a DIFFERENT concurrent fleet session and reported `STATUS=failure` while the run's own pipeline was still queued. With several sessions merging into one repo that shared list is mostly other people's runs, so any positional grep is a coin flip. This helper selects on `.commit == <sha>` and cannot make that mistake
- flow-ci-status credentials + step naming - takes the token from `$WOODPECKER_API_TOKEN` when exported, else fetches it from AWS Secrets Manager (`essent-ai` / `us-east-1`, both overridable via `--secret-name` / `--region` / `CPP_WOODPECKER_SECRET`), and never lets it reach stdout, stderr, or a command line (`curl -H @-` feeds the header on stdin, so `ps` never sees it). A failure names the failed STEPS, because pipeline colour cannot separate a red test suite from a red deploy step - for kyle's push pipelines a transient SSH connect timeout in `deploy` and a genuine `test-unit` regression are the same colour and different problems
- flow-ci-status contract - `FLOW_CI_PROVIDER` / `FLOW_CI_REF` / `FLOW_CI_PIPELINE` / `FLOW_CI_URL` / repeated `FLOW_CI_FAILED_STEP` / `FLOW_CI_STATUS: success|failure|running|pending|not-found|unknown`. `--wait [SECS]` (default 600, 15s interval) replaces the hand-rolled poll loops Step 8 used to carry, `--event` picks among pipelines sharing a SHA (a merge commit usually has both a `push` and a `pull_request` run), and `--exit-code` turns a `failure` verdict into exit 1. GitHub Actions is the fallback provider where there is no Woodpecker. Fail-open everywhere else: no credentials, no network, no provider, no checkout all yield `unknown` and exit 0, so CI verification can never block a flow it cannot assess. The checkout is DECLARED via `--path`, never inferred from the Bash cwd (the #614 rule)
- flow-ci-status separates a PRE-CODE failure from a code failure (#1342). A red `clone` step - the checkout, before any of the change's code runs - used to read exactly like a red test suite. On `failure` it now emits `FLOW_CI_PRECODE_FAILURE: <step>` for each failed step whose provider TYPE is `clone`, and one `FLOW_CI_FAILURE_ORIGIN: precode | code | mixed | unknown`, both after the `FLOW_CI_FAILED_STEP` lines and before `FLOW_CI_STATUS`, which stays last; exit codes are unchanged. The decision is the step TYPE, never a list of names. The ORIGIN line exists so the marker's ABSENCE is not read as "code": GitHub Actions (checkout is a step inside a job), a step with no type, a failure with no failed step, and a `woodpecker-cli` whose separate `{{ .step.Type }}` call fails all report `unknown`. That CLI call is untested against a real CLI and is kept apart from the name|state call so it cannot erase the failed-step names
- flow-ci-status reads a stager's FETCH FAILURE as pre-code too (#1411). `ci-stage-jq.py`, `ci-stage-git.py` and `ci-stage-make.py` return 75 (`EX_TEMPFAIL`) only for a TRANSIENT network fault (#1462): HTTP 5xx or 429, a refused or reset connection, a DNS failure, a timeout, a truncated transfer. Everything else is 1 and reads as `code`: a hash mismatch, a scheme refusal, any other 4xx (a PR that bumped a pinned URL to an asset that does not exist), a TLS verification failure (classified on `URLError.reason`, because urllib wraps it), and any bug in the stager itself, which lives in the PR's own tree. A failed `*-stage` step whose provider `exit_code` is 75 is pre-code whatever its type; a 75 from any other step stays `code`, because EX_TEMPFAIL is a general code an application may use; an absent exit code changes nothing, and the CLI fallback lane, which carries none, keeps the type-only behaviour. `controls/flow-ci-status` pins exit 75 to `precode` and exit 1 to `code`.
- flow-ci-status `woodpecker-cli` fallback (#768) - when the HTTP API cannot resolve the repo, the helper asks the authenticated CLI for `--output go-template=` rows and filters on the exact commit SHA; failed step names come from machine-readable `pipeline ps --format` rows. This lane emits no URL because it does not have the numeric repo id, and falls through to GitHub Actions when the CLI is absent, errors, or prints nothing
- flow-ci-status (#1262) ANSWERS FOR THE DECLARED CHECKOUT AND THE REQUIRED LANE, AND SAYS WHICH. Three defects, each measured. The repository was resolved with `gh repo view` in the CALLER's cwd - invoked from a kyle clone with `--path` naming a CPP checkout it answered `cooneycw/kyle` - and the origin fallback's `[^/]+?` is not a lazy quantifier in ERE, so it kept `.git` and every lookup asked for `owner/name.git`; both now resolve inside `--path`, and `FLOW_CI_REPO` prints the answer. The preferred event was a hard-coded `push` while CPP and kyle require only the pr lane, so a SHA carrying both pipelines reported the push pipeline's verdict; without `--event` it is now DERIVED from the base branch's required status contexts (`ci/woodpecker/pr/*` alone -> `pull_request`, `push/*` alone -> `push`), and both, neither or unreadable falls back to the old `push` - `FLOW_CI_EVENT` names the source, so a repo whose protection cannot be read gets exactly what it always got and is told so. An expired `--wait` broke out with the same `not-found` a one-shot lookup prints; `FLOW_CI_WAIT: none | settled | expired (<N>s)` now separates "never registered in the window" from "one look found nothing". The STATUS values are deliberately unchanged, so no consumer's parse breaks
- flow-ci-status (#1552) tells DEAD CI from SLOW CI. An agent restart mid-run strands a Woodpecker workflow `running` forever with the agent id persisted (measured on 3.19.0 in cooneycw/woodpecker-baseline#2: no reschedule, the timeout does not fire, an API cancel leaves it `running`), so `--wait` used to sit out its whole window and report `running`. The repo `timeout` is enforced by the AGENT, per WORKFLOW, so a workflow the server still lists `running` more than `FLOW_CI_STALL_GRACE_MIN` (default 10) minutes past it - measured from that workflow's own start, after reconciling with the pipeline detail's status - was lost by its agent: the HTTP lane now reports the terminal `FLOW_CI_STATUS: stalled` with `FLOW_CI_STALLED: past-timeout (...)` and one `FLOW_CI_STALLED_STEP` per step still listed running, and a `killed`/`failure`/`error` pipeline whose children still read `running` keeps `failure` and gains `FLOW_CI_STALLED: terminal-pipeline-live-children`. `FLOW_CI_STALL_CHECK: checked | unavailable (<why>)` says whether the check ran, so an unreadable timeout or detail is never read as "not stalled". It reports only - it never cancels - and the woodpecker-cli and GitHub Actions lanes run no stall check. Control: `controls/flow-ci-status-stalled` (the 3374 shape at 71 vs 59 minutes; the pre-change anchor misses it)
- flow-ci-status (#1684) A `--wait` THAT DID NOT REACH A VERDICT IS NEVER EXIT 0. On kyle PR #2320 a 3000s wait returned with `FLOW_CI_STATUS: unknown`, `FLOW_CI_WAIT: none` and exit 0 while main's push pipeline ran; a lock-hold script read the exit code as "the wait ended" and released the merge lock. The output matches the `woodpecker-cli` lane's mid-wait re-listing failure, which ended the loop (read from the code, not reproduced); a found pipeline with an empty or unrecognised status ended it the same way on both Woodpecker lanes. Now both are polled to the deadline, and say why on a `FLOW_CI_RETRYABLE: <why>` line beside `unknown`. Every other `unknown` (no credentials, no provider, an all-skipped or capped Actions listing) is a final judgement and still ends the wait at once. Exit codes under `--wait` only: `unknown` exits 2, an expired wait exits 5 whatever it last saw (`running`, `pending`, `not-found`, a retryable `unknown`); without `--wait` the fail-open exit 0 is unchanged. The recorded dispatcher in `lib/cicd/flow.py` applies the same rule per lane, and its expired `not-found` moves from exit 2 to 5. `controls/flow-ci-status-wait` commits the case: an empty status that turns green must cost a second listing call; the pre-change script ends on the first look and is the blind anchor
- flow-ci-status (#1711) FOUR SMALL FIXES ON THE FALLBACK PATH, NO EXIT CODE CHANGED. (1) A failed step's error that spans lines is one step: the newline is folded to a space before the line-wise read, where the remainder used to be read as a second failed step with no type. (2) A stall-check answer is reset at the top of every poll, as the Actions loop already did; an earlier poll's `unavailable` was printed beside a later `success`. (3) The branch-protection reads keep stderr out of the list of required contexts; stderr is read only to recognise a 404. (4) A ref that is neither a commit in the checkout nor a full SHA (a PR number, a typo) answers `unknown` with "commit ref unreadable; name the full commit SHA", the recorded path's answer, and searches nothing; a full SHA the checkout lacks is still looked up. The header now says what `--exit-code` does today; that a STALLED pipeline exits 0 under `--exit-code` in fallback or pre-set-backend mode is a known defect, #1758. Control case `bad-fetch-failure-multiline-error`.
