# `flow-vantage` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `flow-vantage` (#959)

- flow-vantage - which side of the container boundary is THIS process on? (#959, the follow-on to #958's corrected prose.) Three contract lines every run - `FLOW_VANTAGE_BASIS:`, `FLOW_VANTAGE_SOURCE: measured|declared`, `FLOW_VANTAGE: host|container|unknown` - with one exit code per verdict (0 host, 3 container, 4 unknown), the #1027 shape. The lane INVERTS across that boundary: past it the mailbox is lane 1 and `SendMessage` addresses a population holding no fleet peer at all, so a wrong `host` is not a slower send, it is a silent non-delivery that returns success. Before this, every lane decision in CPP was made by an agent reading a paragraph and believing it - `SendMessage` and `ListAgents` appeared in `scripts/` only inside comments
- flow-vantage DERIVED, NEVER PASSED IN - a substrate-exported container indicator is the obvious shape and the wrong default, for three reasons the header states: ABSENT CANNOT MEAN HOST (CPP runs on hosts where nothing sets it, so a missing value is `unknown`, and a flag whose absence is indistinguishable from the negative case decides nothing); a DECLARED VALUE CAN BE STALE (an image rebuilt, a variable inherited, an export copied into a host shell, and the declaration keeps asserting yesterday's placement); and kyle's `KYLE_MASTER_PLACEMENT` PRECEDENT DOES NOT TRANSFER - that declares POLICY, where sessions should run, while this is a FACT ABOUT THE RUNNING PROCESS, and facts are derived. A derived answer also self-corrects when the substrate changes without telling CPP. `FLOW_VANTAGE_DECLARE=host|container` remains as a short-circuit, read FIRST and structurally apart, so there is no path on which a declared value can be blended into a measured basis; an unrecognised value is REFUSED as `unknown` with `SOURCE: declared` rather than silently falling through to measurement, because a typo that promotes itself to a measurement is the failure the separation exists to prevent
- flow-vantage TWO USABLE SIGNALS, UNEQUAL BY DESIGN, and the two that look decisive and are not. Measured on the host, harness 2.1.266, 2026-09-20, against the container rows established on 2.1.266, 2026-09-13 (#947, one container, kyle session 48): `readlink /proc/self/ns/pid` reads `pid:[4026531836]` on the host and `pid:[4026533495]` in the container - the GENERAL signal, and the only one that can say `host`, leaning on `4026531836` being the conventional initial pid namespace inode, a convention written down as one rather than passed off as a definition. `/etc/machine-id` is 33 bytes on the host and ABSENT in the kyle-session image - ONE-SIDED corroboration that can say `container` or stay silent, never `host`, because any other image ships one and a two-way reading would quietly generalise a fleet-specific fact. The two that do NOT discriminate are named in the header rather than merely omitted, since they are what people reach for first: `~/.claude/sessions/` in `/proc/self/mountinfo` is absent on BOTH sides (measured 0 matches), and the RECORD COUNT conflates a container with a lone host session - it is not even stable on one vantage (6 records on 2026-09-15, 5 on 2026-09-16, 7 on 2026-09-20, no fleet change between)
- flow-vantage `unknown` IS REACHED, NOT DOCUMENTED - it occurs two ways, both real: the namespace says host while machine-id says container (a host shipping no `/etc/machine-id`, which several minimal distributions do), or the namespace cannot be read at all, in which case one-sided corroboration may not speak for it. THE ROUTING COST IS DECIDED EXPLICITLY, because deciding it by omission is how a three-state contract decays into a two-state one: route to the MAILBOX on `unknown`. The asymmetry is the argument - a host session on the mailbox takes a durable-but-slower lane it did not need and fails quiet, while a containerised session on lane 1 addresses a population that returns success and delivers nothing. And because a default that is safe in every case is also one nobody notices firing, `unknown` STAYS VISIBLE at the routing site: `flow-wave-registry.sh` renders `vantage=unknown[route-mailbox]` on the roster row rather than absorbing it
- flow-vantage THE CONSUMER, so the contract is not write-only (#959) - `flow-wave-registry.sh register` derives vantage ONCE and STORES it on the role entry (`vantage`, `vantage_source`, `vantage_basis`), `get` reads it back, and `list` renders it in the per-role extras column beside `driver=`. Stored rather than re-derived because the orchestrator runs `get` on its OWN machine: a fact about somebody else's process cannot be recomputed from here, which is the same reason #1029's toolchain provenance is relayed at registration. An orchestrator therefore sees `vantage=container[lane1-empty]` BEFORE assigning through a lane that is empty, rather than after the silence. A missing helper reports `unavailable`, which is neither `unknown` nor a measured `host`
- flow-vantage CONTROLLED (`controls/flow-vantage/`, ADR 0008 row 95) - three committed cases (a host, a container, and a genuine signal disagreement) and a CONSTRUCTED anchor, because the gate is new and has no blind ancestor to vendor. The anchor reconstructs a check that was really RECOMMENDED: the mount-shaped reading of `~/.claude/sessions/` that `register.md` advised until 2026-09-16, which answers `host` on both sides and so misses both known-bad inputs while agreeing with the gate on the known-good one. #959's own suggested record-count anchor was rejected on a structural ground - it answers `container` on a lone host session, so it would disagree with the gate on the known-GOOD input and score INERT, proving nothing - and that blindness is pinned instead as a behavioural invariant in `tests/test_flow_vantage.py`: the verdict must not move when the record count does. `--fixture DIR` relocates the PATHS the script reads and supplies no verdict, so nothing in a case directory can hand over the answer it is meant to derive
