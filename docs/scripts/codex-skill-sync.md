# `codex-skill-sync` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `codex-skill-sync`

- codex-skill-sync - single-source -> per-harness SKILL.md generator (#555, CxPP epic cooneycw/codex-power-pack#64 story B1): emits checked-in per-command Codex skill dirs under `codex/skills/<family>-<cmd>/` (frontmatter name/description with front-loaded trigger words, Codex harness-adaptations block for detected Claude-only constructs, long bodies split to `reference.md`, referenced helper scripts bundled byte-identical); `--check` drift gate (pinned by tests/test_codex_skill_sync.py AND an explicit `codex-skills-check` step in `.woodpecker.yml`, #556), `--write` regen, `--install` copies to `~/.codex/skills/` and prunes managed orphans there so a dropped skill stops loading (#575; wired into `/cpp:init` Tier 5e and `/cpp:update` Step 7.9, which before #575 invoked it nowhere); editing any bundled `scripts/*` requires a `--write` re-run. Superseded the deprecated flat `codex/prompts/` surface + its `codex-prompt-sync.py` generator, both retired at the #556 cutover
- codex-skill-sync `--install` IS SAFE TO OBSERVE WHILE IT RUNS (#1235). It used to `rmtree` every managed skill and `copytree` it back, so a Codex start during an ordinary install listed a skill whose `SKILL.md` was momentarily gone and printed one `failed to read file` warning per skill with nothing wrong - the symptom that cost #1232 its diagnosis time. Each skill is now built in `~/.codex/.cpp-skill-staging/` (a SIBLING of the listed tree, same filesystem, removed after every run including a crashed one's leftovers) and swapped in with `renameat2(RENAME_EXCHANGE)`; a new skill arrives by one `rename`, an orphan leaves by one `rename` before its `rmtree`. Installers into one destination are serialized by an `flock` on `~/.codex/.cpp-skill-install.lock` held from stale-staging cleanup to the end, so a second install can never delete a live run's scratch as a crashed run's. Where atomic publication is impossible - no exchange (not Linux, a filesystem that refuses it), staging on another device, a rename refused with `EXDEV` despite equal `st_dev` (a same-filesystem bind mount), or a merge into an existing dir without the CPP marker - it writes non-atomically and SAYS SO in a `NOTE ... written NON-atomically (<reasons>): <skills>` line. An orphan deleted in place (rename refused) gets its OWN `NOTE ... orphan(s) deleted IN PLACE` line, so an orphan-only install cannot borrow its warning from an unrelated skill write. The lock file is a declared host surface (`write=append`, certified by `host-surface-observe`, which reds with the declaration removed). What is NOT closed: a reader that listed an orphan before its rename still finds it gone - inherent to removing a skill, and a whole-tree swap would not hide it from a reader that re-resolves paths. Negative control in `tests/test_codex_skill_sync.py`: an observer snapshots the tree after every mutation; it reports holes on the pre-#1235 installer (`test_the_observer_sees_the_pre_1235_installer`) and none on the exchange. Measured with a live reader over 10 installs: 134 read errors before, 0 after
- codex-skill-sync network adaptation (#1357) - a skill whose BUNDLED helpers invoke the network (`["gh", ...]` / `["git", "-C", p, "fetch"]` argv lists and `urllib.request` / `http.client` / `requests` imports in `.py`; `gh <subcommand>`, remote `git` verbs, `curl`, `aws` - literal or as a `"$GH_BIN"`-style variable - at a command position in `.sh`; comment lines skipped) gets a bullet telling Codex to run those helpers with escalated permissions, because its workspace sandbox has no network and a `gh` allow rule covers only a top-level `gh`, never one a helper runs. Decided by the bundle, not the command text: project-next's only `gh` call is in `lib/project_next/collect.py`. Field symptom: `project-next: cannot resolve GitHub repository: gh repo view: error connecting to api.github.com` while a bare `gh repo view` worked, read by Codex as an outage. `scripts/project-next.py` also appends a sandbox hint to a failed `gh` when `CODEX_SANDBOX_NETWORK_DISABLED=1` - in the unpinned entry point, not the hash-pinned engine, because a diagnostic is not a contract-version change. Red/green cases in tests/test_codex_skill_sync.py (`test_calls_network_*`) and tests/test_project_next_contract.py (`test_gh_failure_*_codex_sandbox_*`); heuristic limit: a command position inside a quoted shell string (`echo "retry; gh issue list"`) still matches, since telling it apart needs a shell parser
- codex-skill-sync visible-sibling worktree adaptation (#586) - the emitted Codex worktree bullet names the location convention both harnesses converged on (`git worktree add ../<repo>-<branch>`, honoring `$FLOW_WORKTREE_BASE/<repo>-<branch>` when set - ADR 0003/#627 on the Claude side, codex-power-pack#133 on the Codex side) instead of a generic `<path>` that stripped CxPP's hand-specialized sibling guidance on every `make codex-skills` refresh; CxPP picked the aligned text up at its next vendor pull (the #75 pull model - its own drift gate noticed staleness) until it went private and dormant on 2026-09-22 (#1076); regression to the bare placeholder pinned by test_worktree_adaptation_carries_visible_sibling_convention

- codex-skill-sync `--install` REFUSES A DESTINATION THE ENVIRONMENT DECLARES OFF LIMITS (#1232). `run_install()` writes outside the repository and its prune half deletes every managed skill the SOURCE no longer carries - correct on the real `codex/skills/`, catastrophic on a two-entry test fixture. One test in `tests/test_codex_skill_sync.py` reached it without the `tmp_home` fixture, so every `make test` and every `make verify`, in every checkout, installed that fixture over the developer's own `~/.codex/skills` and pruned the other 72 skills as orphans. Measured: 74 skills to 2, from one PASSING test - nothing it asserted had anything to do with the host, and the only visible symptom was Codex printing `failed to read file` for each deleted skill on every later session, with nothing connecting those warnings to CPP's test suite. `refuse_forbidden_install_dest()` now raises when `dest_root` IS the path named by `CPP_REFUSE_INSTALL_DEST`, which `tests/conftest.py` sets to that process's own `Path.home()/.codex/skills` in `pytest_configure`
- codex-skill-sync three choices in that guard, each of which the obvious alternative gets wrong. REFUSED AT THE WRITE, NOT AT `install_dest_root()`: three tests resolve that function read-only to assert which tree a success line names (#1029), so refusing to RESOLVE would break correct callers, and a guard that breaks correct callers is one the next person routes around. IT RAISES RATHER THAN RETURNING AN EXIT CODE: `main(["--install"])`'s return value is discarded at several existing call sites, so a guard reporting by code would be ignored by exactly the kind of test that needs stopping. THE VARIABLE NAMES A PATH, NEVER A MODE: a boolean "we are testing" would disable the one mode this script exists to perform for anyone who ever exported it, whereas a path can only ever block the single destination it names - which is also what keeps `host-surface-observe.py`'s sandboxed-`$HOME` run, and this guard's own control, working. The env var name is DERIVED by the conftest from this script's `REFUSE_INSTALL_DEST_ENV` rather than spelled twice, so a rename reports UNARMED instead of exporting a variable nothing reads
- codex-skill-sync WHAT THE GUARD DOES NOT COVER, stated so its silence is not read as coverage: it guards ONE destination. It says nothing about any other write a test might make under the real `$HOME`, by this script or any other. CONTROLLED by `tests/test_codex_skill_sync.py::TestHostInstallDestinationIsUnreachableFromTheSuite` rather than by a `controls/` entry, because the instrument is a pytest fixture and that framework invokes shell/python gates through a `control.json`. Three committed cases, all run through a REAL pytest sub-run over a COPY OF THE REAL `tests/conftest.py`: the host destination is refused and creates nothing, a redirected destination still installs (a guard wedged at "refuse" passes the first half alone), and a conftest that could not ARM the guard prints `host-install guard: NOT ARMED` instead of rendering as a clean run. The sub-run gets its own `$HOME` in a temp directory, which is what makes the red case SAFE: with the refusal deleted the inner test installs into that temp path and the control reds, destroying nothing. Measured red on all three - refusal removed (`DID NOT RAISE`), `pytest_configure` removed (`KeyError` plus the missing NOT ARMED line), and `tmp_home` removed from the original call site, where the exact code that destroyed 74 skills now fails and leaves all 74 in place. The conftest anchors its checkout on the IMPORTED `tests` package, not on `__file__`, because a copied conftest's `parents[1]` is the temp directory and every repo-relative lookup would silently find nothing
- codex-skill-sync THE MIRRORS ARE BUILD OUTPUT AND THE INSTALL IS THE FIDELITY GATE (#1670, ADR 0013). `codex/skills/` is ignored; only its README is tracked, so an ordinary PR no longer rewrites a script's copies and their `SHA256SUMS`. `--output-root DIR` reads and writes the tree elsewhere. A bare `--install` builds into a private temp tree and publishes that, never reading the checkout's tree; `--write --install` and `--output-root DIR --install` check the named tree against the sources first and REFUSE on any difference (exit 1, destination untouched), always across ALL families because the publish step prunes what its source tree lacks. `--check` on a tree with no generated skill exits 3 `NOT GENERATED`, which is not drift. CONTROLLED by `controls/codex-skill-install-fidelity`: a bundled script altered with its manifest RECOMPUTED is refused, and the gate at dca1ac6b is measured publishing those bytes. Does not cover copies already installed (install-drift), nor authenticity of the checkout.
- codex-skill-sync `--install` PUBLISHES WHAT IT VALIDATED (#1715). `skill_files()` left `__pycache__` out of the check and the five `copytree` calls carried it anyway, so a `.pyc` in a NAMED tree (`--write --install`, `--output-root DIR --install`) passed the check and reached the host unexamined. A bare `--install` builds into a fresh directory and never had one. Every copy now takes `_PUBLISH_IGNORE`, derived from the same `_GENERATED_BYTECODE` tuple the check uses; a test compares the published file set with the validated set, both ways, on all three install routes.
- codex-skill-sync's "N skill(s) in sync" line says `both IN-CHECKOUT` only when the compared tree is inside the checkout (#1715). For `--output-root` outside it, and for the private build a bare `--install` checks, it names the real path and says `an output root OUTSIDE the checkout`. The in-checkout form is unchanged byte for byte.
- codex-skill-sync DOES NOT HONOUR `CODEX_HOME`, AND SAYS SO (#1715). `--install` writes `~/.codex/skills`, its declared host surface, which consumers pin verbatim. When `CODEX_HOME` is set and is not `~/.codex` it prints one stderr `NOTE` that the install did not use it; stdout and the exit code are unchanged. Installing into `$CODEX_HOME/skills` is a change to the declared surface and is recorded as a feature request, not done here.
- A COMMAND DESCRIPTION IS NEVER SHORTENED SILENTLY (#1715). `derive_description` truncates past `DESCRIPTION_MAX` unless the skill is in `DESCRIPTION_MAX_EXEMPT`, so a test pinning a source description could pin text Codex never received (#1380). `tests/test_codex_skill_sync.py` now fails when an explicit description exceeds the cap without an exemption, and when an exemption is stale (its skill has no description, or no longer exceeds the cap). It does not cover descriptions DERIVED from a title and first paragraph, which are capped by design.
