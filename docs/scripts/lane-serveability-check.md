# `lane-serveability-check` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `lane-serveability-check`

- lane-serveability-check - can a local-model lane actually SERVE, as opposed to having the model registered (#895, the #581/#613 pattern). `/qwen:auto` and `/gemma:auto` gated delegation on `GET /api/version` plus `GET /api/tags`, which answer *is the daemon up* and *is the model in the manifest*. Neither asks whether the weights can be LOADED, and those are different facts: on 2026-09-13 the qwen host passed both in ~13ms, the run proceeded, and it died ~18s later inside the delegated call with `{"error":"llama-server process has terminated: signal: killed"}` - an error naming an internal process rather than a lane. `/gemma:auto` carried the identical gate and therefore the identical latent defect, unfired only because that host was healthy. The helper is the discriminating probe: one single-token `POST /api/generate`, the only check that separates registered from serveable
- lane-serveability-check contract - `LANE_SERVE_LANE` / `_ENDPOINT` / `_MODEL` / `_HTTP` / `_ELAPSED` / optional `_DETAIL`, then `LANE_SERVE_STATUS: serving|dead|unreachable|unknown`. Age mode emits `LANE_SERVE_FRESHNESS: fresh|stale|unknown`. Exit 0 serving, 1 dead, 2 usage, 3 unreachable, 4 unknown. LANE/ENDPOINT/MODEL/HTTP/ELAPSED/STATUS are always emitted; DETAIL is omitted when there is nothing to say, the convention `delegated-run-check` set for the same reason
- lane-serveability-check treats `unreachable` as a refusal, not a milder verdict, because the failure shape is NOT deterministic. Six probes at the same endpoint with the same request bytes produced three shapes: HTTP 500 carrying the server's error text (17.4s / 18.2s / 18.6s), HTTP 000 with curl exit 52 and an empty body (16.5s / 17.1s), and an immediate HTTP 000 with curl exit 56 (0.008s) when a probe landed right after a prior failure. A helper keyed on the 500 alone would have cleared that host on a third of the samples, and the sub-second reset is the trap inside the trap - it reads as a network blip and is the same dead loader. Both `auto` documents are pinned to refuse on either verdict
- lane-serveability-check probes `/api/generate`, and the tidier story for why is wrong. Two `/v1` samples both dropped the connection, which looked like an endpoint property until `/api/generate` produced the same drop - the shape is not determined by the endpoint. It is probed anyway for reasons that survive the correction: it is ollama's native endpoint whatever transport a harness uses, `/qwen:status` already probed it, and the error text was observed there and never on `/v1` - a weak preference on small samples, recorded as one
- lane-serveability-check timeout is 120s and is deliberately NOT the discriminator. Measured across both hosts: warm and GPU-resident 0.067-0.085s; cold reload 7.0s and 12.2s; healthy but with 7.18 GB spilled from VRAM to CPU 18.5-67.3s; BROKEN 17.4-18.6s. The last two rows overlap completely, so no deadline separates a degraded-but-working lane from a dead one - only the response does. A "fail fast" ceiling would have condemned a lane that was serving real work slowly, which is the mirror-image bug #895 named in advance. 120s is a hung-socket backstop past the slowest healthy observation; the failure path never approached it
- lane-serveability-check sends no `keep_alive`. A request-level value overrides the server's policy, so a probe sending one would reconfigure the host it only meant to observe. When this was written the gemma host was recorded running `OLLAMA_KEEP_ALIVE=-1` to pin a 19 GB model in VRAM, where a probe shipping `"5m"` would quietly un-pin it and hand the next real run a cold load. That setting has not been re-read since, and a 2026-09-24 owner ruling says to treat the serving hosts as unpinned (see age mode below, #1272); the rule holds either way. Caught in review of the change that introduced it, whose first draft did exactly that. A preflight reports on the server; it does not reconfigure it
- lane-serveability-check `unknown` (exit 4) is the empty-population state from [the detector contracts](../agents/detector-contracts.md): no `curl` means no observation, and reporting that as either verdict would assert over zero probes. It prints "unchecked, not clean" and `/qwen:status` renders it as a third summary state, `UNVERIFIED`, which may only ever weaken a `true` - a missing harness is a decided NOT READY and uncertainty must not soften it into a maybe
- lane-serveability-check age mode has two callers, the Step-6 fix loops of `/qwen:auto` and `/gemma:auto` (#921 half 2). Before each re-execute they `--check-age` the Step-4 verdict; `stale`/`unknown` probes ONCE immediately before the call, and `dead`/`unreachable`/`unknown` stops the loop. There is no timer and no free-standing re-probe, by owner ruling: treat the serving hosts as unpinned, where every cold probe is a full weight load. A probe is load-neutral only when the call behind it would load the model anyway. The keep_alive note above records gemma as once pinned (`OLLAMA_KEEP_ALIVE=-1`, unverified since); the ruling supersedes that as a planning assumption, and the design is correct either way - on a pinned host the extra probe is merely cheap
- lane-serveability-check does NOT cover tool calling, and on the gemma lane that is the gap that matters most: gemma4 on ollama `/v1` silently drops tool calls past a ~1,600-token system prompt (ollama/ollama#14958) while OpenCode's own prompt is ~6,900, so a model can serve a token here and still produce prose instead of edits on every run. That question is answered by `/gemma:status` Step 4, which runs a real `opencode run` past the threshold; a raw curl smoke test passes on both `/v1` and native `/api/chat` and would prove nothing
