## `check-test-binary-guards` (#831 inversion)

- check-test-binary-guards inverted DIRECT lane (#831) - the gate enforced CLAUDE.md's "a test that shells out to a real binary must use a `shutil.which` skip guard" for exactly FOUR names (`git`, `docker`, `gitleaks`, `jq`), so every other binary was not under-detected but OUTSIDE what it examined: the DIRECTIVE was broad, the GATE was narrow, and the gate is what a reader trusts. #830 is the bill - a test ran `subprocess.run(["pgrep", ...])`, `make verify` passed, the gate said ok, and CI went red on `FileNotFoundError` because `pgrep` ships in procps and `uv:python3.11-bookworm-slim` omits it. The tell that this was a defect rather than a missing entry: `ps` was not on the list either, yet `tests/test_flow_wave_mailbox.py` carried a `requires_ps` guard - it existed because someone REMEMBERED, not because anything checked. The default is now inverted against `CI_IMAGE_BINARIES`, a list of what the validate image PROVIDES, so a bare argv[0] outside it needs a guard and "a binary nobody thought about" becomes a state the check can represent; `CI_IMAGE` is pinned against the image named in `.woodpecker.yml`, because the exempt list is a claim about ONE image and nothing else in the repo would notice the pipeline moving. `GUARDED_BINARIES` survives as the script-hop scan list and as an explicit always-guard override (the union decides), which is what keeps #838's `timeout` oracle - a widening harness that substitutes that constant - measuring the direct lane rather than only the hop
- check-test-binary-guards: the inversion is NOT applied to the script hop, and the reason is measured (#831) - in shell text a binary and a shell FUNCTION occupy the same "command position", and so do many variable and heredoc fragments. Scanning this repo's own `scripts/*.sh` for any command-position token and subtracting a generous exempt list leaves 141 uses of `jq` beside 107 of `usage_fail`, 116 of `s` and 75 of `issue`. Telling those apart needs a shell parser, which this file states outright it is not, so the hop keeps an explicit list - widened past the original four to `pgrep`, `ps`, `tmux`, `flock`, `curl`, which is only safe now because #833 and #838 fixed the case-label and quoted-text false positives that widening exposes. A guess that cries wolf costs more than the false negative it removes
- check-test-binary-guards KNOWN RESIDUAL: a fail-soft script use (#831, not fixed) - the hop drops a binary when every use in the script is fail-soft (stderr silenced, in a condition, or with a `||` fallback), because such a script genuinely survives the binary's absence. That is the right answer to the question the hop asks - *can the SCRIPT do its job without this binary?* - and a reader takes it for *can the TEST pass without this binary?*. They diverge exactly when a script degrades gracefully and a test asserts the degraded-versus-not distinction, which is a GROWING pattern here since every `unknown`-vs-`clear` lane produces one. Live in tree: `scripts/flow-wave-mailbox.sh` reaches `ps` only as `$(ps -eo pid,ppid,args --no-headers 2>/dev/null)` so the hop drops it, while `tests/test_flow_wave_mailbox.py` needs `ps` to exercise that lane and carries a hand-written `requires_ps`. Measured: widening `GUARDED_BINARIES` to include `ps` AND deleting those guards still yields ZERO findings, so #831's inversion does not close this. Deliberately not fixed by widening - believing the fail-soft declaration is what keeps the hop from crying wolf (scanning for mere mentions produced 266 findings, ~250 false), so per `docs/agents/detector-contracts.md`'s "when widening is not the remedy" the larger question needs its own channel. Pinned as a property by `tests/test_test_binary_guards.py::test_a_fail_soft_script_use_is_a_known_blind_spot`

## `check-test-binary-guards` (#906 direct-invocation hop)

- check-test-binary-guards direct-invocation hop (#906) - the #789 one-hop scan required argv[0] to be `bash` or `sh`, so a test that ran a repo script DIRECTLY on its shebang (`subprocess.run([str(HELPER), ...])`) entered no hop at all and the script was never scanned. Every helper in `scripts/` is executable and carries `#!/usr/bin/env bash`, so direct invocation is the NATURAL spelling: a test author following the repo's own conventions got no coverage, while one writing the less natural `["bash", SCRIPT]` did - reinstating, for the commonest shape, exactly the local invisibility the gate exists to remove. The trigger now also fires when argv[0] itself resolves to an executable file inside the checkout, reusing the existing resolver and scanner. Only the TRIGGER widens: the scan it feeds is the same `binaries_in_script()` against the same explicit `GUARDED_BINARIES`, so the function-versus-binary collision that made inverting the hop unworkable (#831) stays out of reach - a shell function is mistakable for a binary only when scanning for arbitrary tokens, and nothing here does. Bounded by an ownership boundary (argv[0] resolving OUTSIDE the checkout is ignored - a system script is not ours to scan) and by executability (the shape covered is "run on its shebang"; a non-executable path cannot run, so scanning it would read a file the test never executes). Verified by control rather than assertion: on a synthetic tree with a script that hard-requires `jq`, the pre-#906 checker finds 1 of 3 invocation shapes and the new one finds 3 of 3
- check-test-binary-guards: #906's own 11-of-12 is TWO stacked gaps, and only one is closed (#906, #831) - the issue attributes its measurement (11 of 12 `curl` tests in `tests/test_lane_serveability.py` invisible) to the trigger alone. Reproduced exactly, then re-measured WITH the trigger fixed: still 1 of 12. The trigger fires; `binaries_in_script(scripts/lane-serveability-check.sh)` returns empty, because that script preflights `command -v curl` and reports `unknown` when it is absent - it genuinely degrades, so the hop CORRECTLY drops curl. That is the #831 residual by name: the hop answers "can the SCRIPT do its job without this binary?" while a reader takes it for "can the TEST pass without this binary?", and they diverge wherever a test FORCES the degraded lane, as these twelve do by stubbing a server and asserting real HTTP outcomes. #906's acceptance criterion is met (it is correctly worded, "where the script hard-requires a guarded binary"); its narrative attribution is not. Those twelve keep their hand-written `requires_curl` and the header's caveat list now names this case
- check-test-binary-guards heredoc masking (#906, cascade step six) - widening the trigger took the tree from `ok` to 31 findings, ALL false, ALL from ONE line of prose. `scripts/delegated-run-check.sh` embeds a Python program at lines 225-442 via `python3 - <<'PYEOF'`, and a docstring inside it reads "a model that tries \`git commit\` once and moves on is behaving exactly as designed". Those are MARKDOWN backticks - but a backtick opens a command substitution in shell, and `SHELL_BINARY_RE` counts one as a command-position separator, so the sentence read as an invocation of `git`. `_mask_noncode` resolves comments, quoting, arithmetic and command substitution and had NO heredoc handling. A quoted-delimiter heredoc body is now blanked before the shell-quoting pass: it is literal text the shell hands to another program and never executes as shell, and a nested interpreter's needs are a SECOND hop this checker states outright it does not follow - so this is consistent with the existing depth rule rather than a new exception. Only QUOTED delimiters: an unquoted `<<EOF` body IS parameter-expanded and command-substituted by the shell itself, so its `$(...)` really are this script's invocations and masking them would be the undercount direction. This is `#831 -> #833 -> #838 -> #840 -> #841` one step further, and it could not fire before #906 because that script is only ever invoked directly by its tests - the gap masked the bug. The coupling is not a choice: removing the mask reddens the two existing #838 widening oracles, so the trigger change cannot land without it

## `check-test-binary-guards`

- check-test-binary-guards - gate for the "guard tests that shell out to `git`/`docker`/`gitleaks`" core directive (#602), which had failed three times as prose (#451, #489, #577) because it is invisible locally - the dev box HAS git, so only a red pipeline could ever report it. Stdlib-only `ast` walk over `tests/`: flags any `test_` reaching a guarded binary through a statically resolvable `subprocess`/`os.system` call, DIRECTLY or transitively via a module-level helper, without a matching `shutil.which` guard (decorator, module alias, class marker, `pytestmark`, or in-body `pytest.skip`). Since #789 it follows ONE more static hop: `subprocess.run(["bash", str(SCRIPT)])` where SCRIPT resolves from a module-level `Path` constant is opened, and the test is flagged for whatever guarded binaries that script HARD-REQUIRES - the transitive case #716/#717 documented as a known blind spot and #783 then walked into (green locally, red in CI). "Hard-requires" is narrow on purpose, because a naive "mentions jq" scan measured 266 findings on this repo of which ~250 were false: a binary is discounted when the script's own `command -v` preflight says it degrades without it, when an exiting preflight is nested and so scopes the need to one branch, or when every use is fail-soft (`|| fallback`, an `if`/`!` condition, or stderr discarded). A dynamic argv is deliberately unresolved - the gate is a floor for the shape that has actually failed, not proof of total coverage. `# binary-guard: allow <reason>` is the escape. `make binary-guards-check`, folded into `make verify`, and asserted by `tests/test_test_binary_guards.py` so it also runs in the CI `validate` step it defends
- check-test-binary-guards a `case` label read as a command invocation (#833) - `SHELL_BINARY_RE` matches a guarded name at "command position": after a newline, `;`, `&`, `|`, `(`, backtick, `$(`, `&&`, `||`, or an anchor keyword. A `case` PATTERN LABEL sits at exactly that position too - `scripts/flow-wave-mailbox.sh:720`'s `ps)   watcher_roles_ps_fallback "$wave" ;;` follows a newline the same way a real command would, and the label's own closing `)` satisfies the trailing `\b` the same way a real command's argument list would - nothing in the regex's surroundings tells "the next token is a case arm" from "the next token is this command's first argument", because that distinction lives in what comes AFTER the matched word, not in the word or what precedes it. Latent since none of the four then-guarded binaries (git/docker/gitleaks/jq) is a label anyone writes; widening toward `ps` (the change #831 proposes) makes it fire immediately - **101 findings, all one label**, across `test_flow_wave_mailbox.py` (91) and `test_flow_wave_registry.py` (10), each one a `binaries_in_script()` result that would have taught the suite a false `ps` dependency `flow-wave-mailbox.sh` (which picks its scan lane with `[ -d /proc ]` and does not need `ps` on any host the suite runs on) does not have. Fixed with a SECOND regex, `CASE_LABEL_RE`, matching a `case` label's shape (one or more `|`-joined glob tokens from line start, then `)`) - `_is_case_label()` checks whether a `SHELL_BINARY_RE` match's binary token falls inside that label span, and skips it if so. A structural check rather than "is the very next character a `)`", specifically so a pipe-joined label (`a|ps|b)`) is caught too, not only the single-pattern shape actually in the tree - none of the three real-binary-name labels found in a repo-wide sweep (`ps`, `timeout`, `rev`) happens to be pipe-joined today, but the fix should not need re-deriving the moment one is. Verified with the exact oracle the issue measured: `GUARDED_BINARIES` widened to include `ps`, findings **101 -> 0**. Tested in both directions per review (the undercount direction is the unsafe one, same principle as the unreadable-`/proc/<pid>/environ` note on #832): the real invocations at `:845` and `:894` (both fail-soft, stderr-silenced) are pinned as STILL detected, using the REAL lines from `flow-wave-mailbox.sh` as the fixture rather than a constructed one, per review's explicit ask - a real in-tree instance is evidence, a hand-written `case` block is illustration. Two ADDITIONAL false-positive mechanisms for the same at-risk names were found while verifying `timeout`/`rev` specifically and are explicitly OUT OF #833's scope (case labels only) - filed as **#838** rather than fixed here: `rev=0` / `rev="$(...)"` (a bash variable ASSIGNMENT, not a label, misread the same way for the same structural reason - the assignment sits at command position too) at `flow-wave-mailbox.sh:634,729,900,1381,1383,1393` (widening `GUARDED_BINARIES` to `rev` measures **234 findings**, via `flow-wave-mailbox.sh` and `flow-wave-registry.sh`), and `"fail (timeout: ...)"` (a guarded name appearing as plain TEXT inside a double-quoted string literal, preceded by `(` which the regex cannot tell from a real command-position `(` because it has no shell-quoting awareness at all) at `scripts/flow-finish-gate.sh:306` (widening to `timeout` measures **42 findings**, all via `flow-finish-gate.sh`). Both mean `#831` widening to `timeout` or `rev` specifically is not yet safe even after this fix; widening to `ps` alone is

- check-test-binary-guards an assignment, an arithmetic expansion, and quoted text all read as command invocations (#838) - the two mechanisms #833 found and scoped out (`rev=0`/`rev="$(...)"`; `"fail (timeout: ...)"`), plus a THIRD found empirically while fixing them: `$(( rev + 1 ))` arithmetic expansion, where the second `(` of `$((` satisfies `SHELL_BINARY_RE`'s bare-`(` separator at ANY nesting depth (`$(( (rev) + 1 ))`'s inner `(` too), not only the outermost one. A precision correction to #833's own framing of the six cited sites: `flow-wave-mailbox.sh:634,729,900` are NOT bash assignments - they are an AWK program's own `rev = 0` embedded verbatim inside `awk '...'`, single-quoted TEXT the shell never interprets, misread for the same reason as the quoting mechanism, not the assignment one; only `:1381,1383,1393` are real bash, and `:1393` (`rev=$((rev + 1))`) carries BOTH the assignment and the arithmetic bug on the same line. Case-label ambiguity resolves from a fixed window around the match (line-start shape, or - new here - the immediate next character: `ASSIGNMENT_RE` excludes a name glued directly to `=` (not `==`), unambiguous bash assignment grammar with no #833-style trap, since `word=` never spells a real invocation's own attachment to its first argument). Quoting and arithmetic do not: whether a position sits inside either depends on everything since the region opened, so both are resolved by one new state-tracking pass, `_mask_noncode`, applied before every regex runs - blanking quoted/arithmetic text while carving out and recursively re-scanning any LIVE `$(...)`/backtick substitution nested inside either (`"...$(git status)..."`, `$(( $(count) + 1 ))` both still detected; the undercount direction stays the one guarded against). Comment-stripping is folded into the SAME pass rather than run as a separate step before or after it, because the two questions are mutually dependent - a `#` inside a real quote is not a comment, and an apostrophe inside a `#` comment is not a real quote open - and running them independently in either order gets one of those wrong; the second attempt at this function is what caught its own `# the orchestrator's side`-shaped comment misreading its apostrophe as opening a single-quoted region that would not close until the next apostrophe anywhere later in the file, against this script's own source, via `make verify`'s full run. Verified against both of #833's own oracles restated: widening to `rev` was **234 findings, now 0**; widening to `timeout` was **42, now 1** - not 0, because one of the 42 was never a false positive: `tests/test_delegated_run_check.py::test_a_real_forced_timeout_reaches_the_helper_as_124` genuinely shells out to `timeout` directly with no guard, and correctly stays a finding (the undercount direction proven the same way #833's `$(cat)`/`$(uname)` pins were - detecting a real invocation is the harder direction to get right, and the one silence cannot be told apart from). Deliberately not a general shell tokenizer: no command boundaries, no redirection, no glob expansion, and explicitly no here-doc awareness - a known, separate, unaddressed gap a here-doc body is not masked against
- check-test-binary-guards a heredoc-opener-SHAPED token inside a quoted string OR a comment masked everything after it to EOF (#1407) - `_mask_heredocs` runs before `_mask_noncode` (quoting and comments are not resolved yet when it scans), so `echo "usage: cat <<'EOF' > file"` and a `#:`-prefixed doc-comment line carrying the identical shape both opened a REAL mask on text that was never a heredoc. `_heredoc_opener_is_live()` adds a same-line-only lookback before a candidate is trusted: it tracks single/double-quote spans (backslash escapes only inside double quotes) and treats an UNQUOTED `#` that BEGINS A WORD - preceded by whitespace, by position 0, or by a shell operator that ends a word the same way whitespace does (`WORD_BOUNDARY_CHARS`, `;&|()`; counter-model review caught `echo ok;# <<EOF` being missed by a whitespace-only check) - as a comment start, while a `#` glued to non-whitespace (`${x#prefix}`) is not one. Deliberately same-line only - a quote or comment opened on an EARLIER line is outside what a scan running before the real state machine can see, the same boundary this function's own docstring already draws for cross-line reach. Measured LIVE, not hypothetically: `scripts/cpp-host-write.sh:207` carries exactly this shape in a usage-example doc-comment and left the file's heredoc state unclosed at EOF - confirmed consequence-free there only because the real `jq` uses the mask would otherwise have swallowed are ALSO independently fail-soft via the unrelated `||`/`if !`-anchor heuristics, not because the masking bug wasn't real. The quoted-string shape and the `;#`-boundary comment shape are each pinned by their OWN control case (`bad-heredoc-quoted-string`, `bad-heredoc-comment-boundary`) rather than one combined fixture, per counter-model review: a combined fixture carrying both shapes reds through EITHER one, so reverting only one half still leaves it red and the control cannot tell "fixed both" from "fixed one" - load-bearing-ness for each was proven by patching a scratch copy to disable only the corresponding half (quote-tracking only; `WORD_BOUNDARY_CHARS` only) and confirming that case alone goes undetected while the other two (including `bad-if-bang-preflight`) still detect, with the historical anchor still blind to all three
- check-test-binary-guards a TOP-LEVEL, unconditionally-exiting `command -v` preflight was misclassified `scoped` (#1407) - `_preflight_declarations`'s nesting check (`line[: match.start()].strip()`) read ANY non-whitespace text before the match as evidence of nesting, which conflated two different shapes: text that genuinely gates the preflight from outside (`[ -n "$X" ] && command -v jq`), and the preflight's OWN condition-opening keyword (`if !`), which is not nesting at all - `scripts/lane-serveability-check.sh:507`'s `if ! command -v curl >/dev/null 2>&1; then ... exit 4; fi` sits at column 0 but was read as scoped purely because "if !" precedes the match on the same line. `CONDITION_OPENER_RE` exempts a stripped prefix that is exactly `if`/`while`/`until` plus an optional `!` and nothing else, falling through to the (correct) indentation check instead. DELIBERATELY EXCLUDES `elif` (counter-model review, after an earlier draft of this fix included it): unlike `if`/`while`/`until`, each of which OPENS a new conditional or loop, an `elif` is a CONTINUATION of a prior `if` - it runs only when an earlier sibling branch's condition was false, which the line's own indentation cannot distinguish from a genuinely unconditional entry point (`if true; then :; elif ! command -v curl ...; then exit 1; fi` sits at column 0 exactly like a real top-level preflight, but only runs if the first branch's condition failed). A SECOND, independent bug compounded the first on this exact script: the later `curl -s ... 2>/dev/null` use was ALSO read as fail-soft by the unrelated stderr-silenced heuristic, even though the preflight had already exited if curl were absent - `_preflight_declarations` now also returns `hard_required` (a TOP-LEVEL exiting preflight's binaries, minus any ALSO marked `degrades`), which `binaries_in_script` consults to OUTRANK a use's own fail-soft markers, matching the absorbed finding's own suggested direction verbatim. `hard_required`/`scoped` are still tracked as file-wide sets keyed by binary name rather than per call site, a pre-existing limitation (not introduced by this fix) filed as a Nit Store finding rather than fixed here: [claude-power-pack#864](https://github.com/cooneycw/claude-power-pack/issues/864#issuecomment-6034344770). Measured the full blast radius across `scripts/*.sh` before writing either fix: of 4 files sharing the top-level `if ! command -v X` shape, only `lane-serveability-check.sh` changes (`[] -> {curl}`) - `branch-protection.sh` already reported `jq` via an unrelated direct use, `npm-global-upgrade.sh`'s `$BINARY` is a variable `PREFLIGHT_RE`'s literal-name group cannot match, and `flow-ci-status.sh`'s own `jq` preflight genuinely DEGRADES (no `exit` in its failure branch, by design - "a missing formatter must never be the thing that stops a merge") rather than sharing the bug. Surfaced 22 previously-unguarded `tests/test_lane_serveability.py` functions, all guarded with the file's own pre-existing `@requires_curl` marker in the same commit, per the standing "fix both the classifier and its fallout" directive. The `good-elif-conditional-preflight` control case pins the elif exclusion directly: the exact shape above, with curl correctly left optional
