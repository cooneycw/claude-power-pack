# `ci-stage-git` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `ci-stage-git` (#1171)

- ci-stage-git - stages a CONTENT-PINNED `git` into `.ci-bin/` for the CI steps that need one (#1171). `flow-finish-gate.sh` derives counter-model enrolment, which needs `rev-parse` and `merge-base --is-ancestor`, and the pipeline image `uv:python3.11-bookworm-slim` HAS NO GIT - measured, and the same fact `check-test-binary-guards.py` has recorded about that image since #451. `check-control-ci-deps.py` then reports SEVEN registered controls as needing git, because `counter-model-enrolment` and the six `flow-finish-gate*` registrations all invoke that one script, and the harness REFUSES to skip a control it cannot run - a red, not a silence. ONLY ONE OF THE SEVEN NEEDS IT AT RUNTIME and that is recorded so nobody deletes the stager after measuring the other six: with jq and make staged and no git, `counter-model-enrolment` is UNSIGNALLED while `flow-finish-gate`, `-resume` and `-derivation` all PASS, because their cases carry no receipts directory so the gate takes the not-enrolled path where its one git call is already `|| true`. The six are staged for anyway because that checker derives REQUIRED from what a script can REACH rather than from what a control's cases execute. TEN .debs, NOT ONE, which is why this is longer than its siblings: jq is one static binary and make is one .deb whose only shared-library dependency is present by construction, while `apt-get install --no-install-recommends git` pulls SEVENTEEN packages including perl and git-man. What is staged is the minimal closure that actually runs the operations the controls perform - git plus its shared libraries, no perl, no git-man. THE ENVIRONMENT IS SCOPED BY A WRAPPER, NOT EXPORTED. An extracted git needs LD_LIBRARY_PATH and GIT_EXEC_PATH, and setting those in the step would apply them to every process in it - all 42 controls running under an altered loader environment to satisfy one. `.ci-bin/git` sets both on its own exec line instead; measured in the image, both variables read UNSET in the step while git, and a python `subprocess` call to it, both work. So `.ci-bin` on PATH stays the entire interface and `check-control-ci-deps` keeps deriving PROVIDED exactly as before. IT STAGES THE CLOSURE, NOT THE MANUAL, and that is a CI finding rather than tidiness. Everything extracted lands in the WORKSPACE, which later pipeline steps walk - so the first cut, which unpacked each .deb whole, put git's documentation and contrib into the tree and turned two unrelated CI steps red: `undeclared-import-audit` tried to parse `usr/share/doc/git/contrib/fast-import/import-zips.py`, which is PYTHON 2, and reported UNKNOWN; `shellcheck` scanned contrib shell and reported errors in `git-new-workdir` and `spatchcache`. Neither file is executed by anything; they were merely unpacked. Extraction is now restricted to `usr/bin/`, `usr/lib/git-core/` and `usr/lib/x86_64-linux-gnu/` - the binary, its helper programs and the shared libraries - which also takes the staged tree from 49MB to 33MB and leaves zero .py and zero .sh files under `.ci-bin`. The general lesson is that a stager's blast radius is every gate that WALKS the workspace, not just the step that runs the binary: jq and make never surfaced it because a single binary has no source for a scanner to find. THREE PINS: each archive, and the EXTRACTED `usr/bin/git` separately, because an archive can be repacked around identical contents and it is the binary that executes. AND IT RUNS WHAT IT STAGED - `git --version` plus a real init/commit/rev-parse/`merge-base --is-ancestor` smoke before reporting success, because `--version` passes on a git whose helper binaries are unreachable, and the ancestry call is the one this issue's match predicate depends on
