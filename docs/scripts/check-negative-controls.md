# `check-negative-controls` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `check-negative-controls` (#924)

- check-negative-controls - runs every gate's registered NEGATIVE CONTROL and proves the control can fail (#924). Seven open CPP issues are one defect in different gates: an instrument returning a confident verdict it is not entitled to, where a green from a blind gate and a green from a working gate are the same bytes. The catching PRACTICE already existed - a hand-run mutation at review time, performed on every merge of 2026-09-13 (#912, #913, #914, #917, #920) - and left NO ARTIFACT: no registered control, no CI step, nothing that reddens when a control stops discriminating. The reviewer's own words: "if I stop doing it, nothing notices"
- check-negative-controls reads unavailability BEFORE detection, and that order is the #1117 design rather than a preference. MEASURED by removing one binary at a time from an otherwise identical PATH: gitleaks absent made `controls/secret-scan` UNSIGNALLED, shellcheck absent made `controls/shellcheck-gate` UNSIGNALLED, and jq absent made `controls/flow-driver-retirement-check` **BLIND** - because that gate reports `RETIREMENT: unknown - jq is not installed` and its `detect_signal` legitimately includes the `unknown` branch, so its unavailability message is a member of its own detection pattern and detection-first cannot separate them. A declared `unavailable_signal` (optional, unlike `detect_signal`) is therefore consulted first, and three refusals keep that from being a fail-open: it may not match empty output, may not match the gate's real clean-run output, and may not report the tool absent on one case while another ran cleanly through the same gate - a missing binary is missing for every case, so that contradiction is what catches a pattern loose enough to swallow a genuine finding
- check-negative-controls asserts three things per control. DISCRIMINATION - `gate(known-bad) == BAD` **and** `gate(known-good) == GOOD`, both directions, because a gate wedged at "fail" passes the known-bad half alone. ANCHOR - the control run against a vendored blind artifact must FAIL, i.e. the artifact must MISS the known-bad input; that is acceptance step 4 executed on every run instead of once by hand, and an anchor that CATCHES the bad input proves the control is not load-bearing. ANCHOR SANITY - the anchor must agree with the current gate on the known-GOOD input, or it differs for reasons beyond the blindness under test. Each of the three reads the gate's OUTPUT as well as its exit code: a non-zero exit counts as detection only when the manifest's `detect_signal` is present, since a crash exits non-zero too (#946)
- check-negative-controls contract - `NEGATIVE_CONTROL_GATE` / `_CONTROL` / `_SOURCE` / `_DETAIL` (repeatable) / `_PROVENANCE` / `_VERDICT`, plus a run-level `NEGATIVE_CONTROL_REGISTERED` / `_UNIVERSE` / `_UNAVAILABLE`. `_CONTROL` names the control directory and exists because a gate may carry several registrations (#986 made discovery see them all, and #1117 was the first to use it): without it two blocks for one gate are identical in their only identifying field. `_UNAVAILABLE` is a count printed on every run including zero, since a line that appears only when non-zero cannot be told from one nobody emitted. Seven verdicts: `PASS`; `BLIND` (the gate stopped discriminating - an alarm about the GATE); `INERT` (the anchor did not miss the known-bad input, so the control would not notice a regression); `UNRESOLVED` (a path the registration names is not in this checkout, the manifest is incomplete, or an anchor cannot be CONFIRMED to have missed the known-bad input - NOT a gate failure, and it presents identically to `BLIND` while needing the opposite response); `UNPROVEN` (registered and discriminating but carrying no anchor, so nothing has demonstrated it can fail); `UNSIGNALLED` (the gate exited like a finding and said nothing that identifies one - also an alarm about the GATE, but a different one from `BLIND`, which sends a reader into detection logic for a gate that is throwing, #946); `UNAVAILABLE` (the gate reported that ITS OWN TOOL is not installed, so it could not look here - the only verdict that is a fact about the MACHINE rather than about the control or the gate, #1117). `--strict` exits non-zero on anything that is not `PASS`, `UNAVAILABLE` included; `--allow-unavailable` additionally tolerates that one verdict, naming every unexamined control and dropping it from the discriminating numerator. CI passes bare `--strict` because it stages pinned gitleaks, shellcheck and jq on purpose; `make negative-controls` (in `make verify`) passes both, because a developer box may legitimately lack them
- check-negative-controls treats UNPROVEN as the load-bearing state, and it is what makes step 4 MECHANICAL rather than remembered. A control with no anchor does not go quiet, it reddens the build - so forgetting to demonstrate that a control can fail produces a red instead of a silence. Without that the framework is only the reviewer's habit relocated into a script nobody runs
- check-negative-controls vendors its anchors instead of fetching them with `git show`, because **git is not in the CI image**. `CI_IMAGE_BINARIES` in `check-test-binary-guards.py` does not list it, and that file's own header records the rule as "forgotten three times (#451, #489, #577)" and structurally invisible locally, since the dev box HAS git and `make verify` can never reproduce the failure. A `git show <sha>^:<gate>` anchor would have worked where it was written and been INERT where it gates - this issue's own defect class, inside the tool built for it. Verified by running the step under `env -i PATH=<no-git>`: `PASS`, provenance `unverified`
- check-negative-controls keeps PROVENANCE on a separate axis from the verdict and never folds it in: `ok` only after a byte comparison of the vendored anchor against its recorded sha via git history, `unverified` when git was unavailable, `MISMATCH` when the bytes disagree. `unverified` must never print as `ok` - the same rule as "unknown is not 0" (#903, #569)
- check-negative-controls reads the CHECKOUT and never `~/.claude/scripts`. Measured 2026-09-13: of 54 installed helpers 51 were byte-identical to main, 3 were not, 0 were dead mounts - so `st_nlink == 0` corpse-checking reports clean while stale helpers serve. `check-test-binary-guards.py` was one of the three and was byte-identical to `c6df826`, the very pre-fix artifact used here as an anchor, so a control pointed at the installed copy would have produced a REAL RED that looked like a successful demonstration: right about the file it read, silent about main. Every output line carries `NEGATIVE_CONTROL_SOURCE: worktree-at-<sha>`
- check-negative-controls registration is ONE line in the gate itself - `#: NEGATIVE-CONTROL: <control dir>` - so deleting the gate deletes the registration, and a directive naming a directory that is not there is `UNRESOLVED` rather than a skip. The manifest's `gate` field is authoritative for what is INVOKED; the directive's location only says how the control was DISCOVERED, and a registration living beside a different gate than it declares is refused. Reading the discovered file instead was a real defect in the first cut, caught by this script's OWN negative control, which reported `BLIND` for an absent gate - the exact collapse the verdict vocabulary exists to prevent
- check-negative-controls first consumer is `check-test-binary-guards` against #906, whose fix (1fa3560, parent c6df826) was written by someone who had never heard of this control - a control tuned against a fix being written in parallel proves much less. The known-bad fixture's helper HARD-REQUIRES `jq` with no `command -v` preflight, deliberately: a fail-soft helper is dropped by the hop ON PURPOSE (the #831 residual the gate's header documents as a remaining, accepted blindness), so a control written against that residual would fail against main while looking like a demonstration
- check-negative-controls manifest - `control.json`, one per control directory, is the half of the registration that does not fit on the directive line, and this is its whole schema. `gate` - repo-relative path to the instrument, and AUTHORITATIVE for what is invoked; the directive's location only says how the control was DISCOVERED, and a manifest declaring a gate other than the file carrying the directive is refused. `invocation` - the argv, with `{gate}` and `{case}` substituted and cwd at the repo root; use `python3` from PATH and never `sys.executable` or an absolute interpreter, because this manifest is read inside the CI image as well as on a dev box. `good_exit` - the exit code meaning GOOD. `detect_signal` - REQUIRED since #946, a regex (multiline) the gate's own stdout-plus-stderr must carry for a non-zero exit to count as detection; without it a crash and a finding are the same evidence, and a control that omits the field is `UNRESOLVED` rather than silently scored on the exit code alone. Anchor the pattern on something a CLEAN run cannot print - `^binary-guards: [0-9]+ unguarded test` includes the count for exactly that reason. Declaring the field is not enough and the harness refuses two ways of declaring it uselessly, both of which restore the old blindness while wearing the fix's own field name: a pattern that matches EMPTY output (`.*`, a trailing `|`, a bare `^`) makes every non-zero exit a detection again, and one that ALSO matches the gate's known-GOOD run identifies a clean run as readily as a finding. The second is checked against that run's real output rather than the author's intention, and only when the gate exited clean - a gate WEDGED at "fail" prints its finding line on the good input too, and that is `BLIND`, a fact about the gate, not about the regex. `cases[]` - `{name, input, expect}` where `input` is a directory relative to the control dir and `expect` is `GOOD` or `BAD`; register at least one of each, since the GOOD case is the only thing separating a working gate from one wedged at "fail"
- check-negative-controls anchors - `anchors[]` entries are `{kind, sha, origin, path, sha256}`. `sha` and `origin` name the historical commit and the path within it, `path` is the vendored copy relative to the control dir, and `sha256` is the digest of the HISTORICAL BYTES (`git show <sha>:<origin>`), NOT of the vendored file - hashing the vendored copy into its own manifest would only prove nobody edited it since someone wrote the digest down, which is not the claim provenance makes. Omitting `anchors` is legal and yields `UNPROVEN`, which `--strict` refuses: that is the state that makes acceptance step 4 mechanical rather than remembered
- check-negative-controls scored a CRASHING gate as detection until #946: the verdict came from the exit code alone, so a gate that fell over on the known-bad fixture was indistinguishable from one that reported it whenever the crash exited with anything but `good_exit` - and `check-test-binary-guards` exits 1 both ways, so for the one control that existed they were not separable at all. The harness printed `PASS`, exit 0, and "1 control(s) discriminate" for a gate that discriminated nothing, with the CI step green while it happened. Closed by making the manifest declare `detect_signal`: a non-zero exit is detection only when the gate also SAID something, otherwise the verdict is `UNSIGNALLED`. The same misscore lived on the anchor side and is fixed with it - an anchor that crashes on the known-bad input was reported as having CAUGHT it (`INERT`, which accuses a healthy anchor of not being blind) and is now `UNRESOLVED`, the narrower and honest claim. The committed control is `tests/test_negative_controls.py::test_a_gate_that_crashes_on_the_known_bad_input_is_not_a_pass`, which reports `PASS` on the pre-#946 harness
- check-negative-controls does NOT yet prove a mutation landed on an EXECUTED path. That matters only for a MUTATION anchor; a historical anchor is a real artifact that really was blind, so the "mutation that did not mutate" failure mode cannot arise. Every one of the seven first consumers has fix history, so no v1 consumer would exercise a mutation anchor - and shipping an unexercised fallback inside the framework for unexercised instruments is the thing this issue forbids. Recorded as a named gap: stdlib `trace`/`sys.settrace` for Python gates (`coverage` is not in the dev extras), `BASH_XTRACEFD` for shell
- check-negative-controls lets a case REGISTER A REFUSAL since #1129, and that is a third registrable expectation rather than an eighth verdict. Every gate here answers in three branches - clean, a finding, and "I could not look, or could not look COMPLETELY" - and the third could not be registered: a case exercising it exits non-zero with a message `detect_signal` does not match, so it scored `UNSIGNALLED` and took the WHOLE control down. `cases[].expect` now also takes `UNKNOWN`, recognised by an optional declared `unknown_signal`. WHY THIS IS REGISTRABLE WHEN `UNAVAILABLE` IS NOT: UNAVAILABLE is a fact about THIS MACHINE (the gate's own tool is absent), so it stays an observation and is never scored against an expectation; a refusal is caused by the CASE INPUT, deterministic given the committed tree, so a case may demand it and IS scored against it - a mismatch either way is `BLIND`, and the sentence names which direction. The #1117 cross-case contradiction check deliberately does NOT apply: a missing binary is missing for every case, but a refusal is per-input by construction, so "refused here, clean there" is what a CORRECT pair looks like. PRECEDENCE is `unavailable_signal`, then `unknown_signal`, then `detect_signal` - most specific first, and load-bearing rather than tidy, because `shellcheck-gate.sh` reports its absent linter AND its other refusals through one `UNKNOWN - ` marker, so the tool-absent line is a strict SUBSET of the refusal marker and the reverse order turns a missing binary back into a gate alarm. Three refusals keep the new field from being a fail-open, each checked against REAL output: it may not match empty output, may not match the gate's clean run, and may not match output `detect_signal` also matches - a marker identifying a finding as readily as a refusal is #946 undone. An anchor must AGREE on an UNKNOWN case exactly as on a known-GOOD one, which has a real cost worth knowing before adding a case: an anchor frozen from before a gate's refusal branch existed reports clean there, lands `INERT`, and forbids any UNKNOWN case on that control while it stands SINCE #1157 A CASE MAY ALSO DECLARE WHAT ITS ANCHOR MUST DO, with `anchor_expect: clean`, and the field is fail-closed: absent means "must agree", which is what every case meant before it existed. It exists because the agree-rule had a cost that fell on exactly the branch it was meant to protect - an anchor frozen from before a gate's refusal branch reports clean where the gate refuses, lands INERT, and forbade any UNKNOWN case on that control. MEASURED at the time of the change: 45 controls, 190 cases, UNKNOWN = 1. A `clean` declaration requires a recorded `anchor_expect_reason` naming why the anchor cannot derive the population, without which the field would be an escape hatch for any inconvenient disagreement; it is refused on a BAD case, where only GOOD and UNKNOWN reach the sanity loop so the declaration would govern nothing; and a declaration that stops being true reds as UNRESOLVED - the manifest is stale, not the anchor - rather than decaying into silence. A case `input` that resolves outside its own control directory is refused in the same pass, symlinks included: a control is a unit, and a case reaching out with `../..` survives a directory move as a registration that still looks valid.
- check-negative-controls leaves DERIVED BYTECODE out of its tracking axis, and only that (#1239). A case that runs Python writes `__pycache__/*.pyc` beside itself, so every run after the first in a checkout reported the control UNTRACKED on files no clean clone needs - which failed every `/flow:auto` Step 7 re-gate in kyle while CI, one fresh run, stayed green. The exclusion is by NAME (`__pycache__/`, `*.pyc`, `*.pyo`), not by ignore status: dropping every gitignored path would blind the axis to the #964/#953 shape it exists for, a load-bearing `case.json` swallowed by the blanket `*.json`. `test_an_ignored_LOAD_BEARING_case_file_still_reads_as_UNTRACKED` is the case that fails if the exclusion widens, measured with an ignore-everything mutant
- check-negative-controls typed make-target gates (#1276, ruling: option B, one kind) - a gate that was not a top-level `scripts/` file could not be registered by any arrangement: `discover` read only `scripts/*` and `evaluate` required the gate to be the file carrying the marker, so kyle's `make verify` (a real discriminating pair) scored `UNRESOLVED`, and the only way to raise the count was a `scripts/` shim whose anchor tested exit-code propagation. A marker directly above a Makefile rule (only comment lines between; a blank line breaks adjacency) is now discovered, and its manifest declares `gate: {kind: make-target, file: Makefile, target: <t>}`, which must name the rule the marker sits above. The schema is CLOSED - an unknown `kind` or key is refused, never ignored - and the one parser (`parse_gate`) lives in the shared census rule module, so `check-control-ci-deps.py` and `mutation-probe.py` read `gate` the same way (a refused gate is a note / UNRESOLVED there, never an absent path read as "needs nothing"). `NEGATIVE_CONTROL_DISCOVERY_SCOPE` is derived from that module's `DISCOVERY_SOURCES` and names both kinds. A registered make-target gate with no census row prints `NEGATIVE_CONTROL_CENSUS_NONMEMBER_REFUSED` and FAILS a `--strict` run; a `scripts/` non-member keeps today's named-not-failed behaviour, which is #1268's decision. `lib/` modules and `scripts/` subdirectories are still not read. THE COMMAND IS BOUND STRUCTURALLY (#1276, orchestrator review of #1334): the invocation must be a plain `make` argv - no `sh -c`, `env` or other wrapper - parsed as GNU make parses it, whose GOALS are exactly `{target}` and whose makefile is `-f {gate}` (at most once) or the default; `-C` and `--eval` are refused and an unparseable option is refused. A substring test was not enough: `sh -c "make -f {gate} {target} seer"` credited a neighbour's verdict to the declared target. What is NOT bound is the declared rule's own recipe - a recipe running `$(MAKE) other` is that target's behaviour
- check-negative-controls #1268 harness half - (1) the census DENOMINATOR is `census_rows` from the shared rule module: the numbered rows of THE census table, header to first non-table line, so a numbered row in any other table no longer joins it (`ADR_ROW_RE` over the whole document is only the fallback when the rule cannot load). (2) RULING R1: a registered gate named by the EXCLUSIONS table is `NEGATIVE_CONTROL_CENSUS_EXCLUDED_CONTROLLED` - named, not failed, and the headline says "excluded from the census but controlled" instead of "outside the census"; a registration in NEITHER table prints `NEGATIVE_CONTROL_CENSUS_NONMEMBER_REFUSED` and fails `--strict`, whatever its kind (superseding #1276's make-target-only refusal). A green census gate makes that unreachable for `scripts/`; `test_a_registration_in_NEITHER_table_fails_when_the_census_gate_is_bypassed` pins it anyway. (3) `anchors[].kind` is read: one of historical, constructed, synthetic, vendored; a historical anchor needs a hex sha and an origin; checked after provenance is recorded so an early return never discards a MISMATCH. (4) Anchor diagnostics name the anchor path, its kind and the case (`anchor anchors/x.py (constructed) on case bad-y`), not the sha field, which read `n/a` for every constructed anchor. (5) RULING R4: a CLOSED top-level schema - `CONTROL_KEYS` is the 14 keys found by scanning all 61 controls at 5fd91de (`limits` canonical, `_comment` an accepted alias, `mutations`/`battery`/`battery_cwd` for mutation-probe, `subject_kind` for reporters); any other key is UNRESOLVED, and `test_every_real_control_stays_inside_the_closed_schema` keeps the tree inside it
- check-negative-controls `good_signal` (#1350) - the GOOD-side mirror of #946's declared detection signal. A gate whose clean answer is a WARN exits non-zero on its known-good input, and every warn shares that code, so scoring GOOD by `good_exit` alone accepted any warning: `controls/flow-finish-gate-resume` stayed PASS through #1341 while its good case's warn changed from `carried, unverified` (the resume signal it tests) to an unrelated `zero coverage`. A control may now declare `good_signal`; a run at `good_exit` without it is UNSIGNALLED, and the message names `good_signal` rather than the detection signal so a reader opens the right regex. OPTIONAL and keyed on PRESENCE: unset scores exactly as before, while a declared-but-empty or empty-matching pattern is refused, since either would restore exit-only scoring under the field claiming to remove it. Applied at all three `_observe` sites - cases, anchors on the known-bad input, and anchor sanity - which was MEASURED safe for the resume control before shipping (its anchor prints the same marker on both cases). The red cases: `controls/check-negative-controls` case `bad-good-exit-wrong-warning` (mutating `_observe` to ignore the field turns that control BLIND), and `tests/test_negative_controls.py::test_the_real_resume_control_judges_its_good_case_by_the_resume_signal`, where the resume good case without its fixture source reads PASS on the pre-#1350 manifest and UNSIGNALLED on the current one - and PASS again with a match-any-warn regex, which is what shows the pattern's specificity does the work. `controls/counter-model-enrolment` (good_exit 4, six GOOD cases) has the same shape and is not yet converted
- check-negative-controls typed `lib-module` gates (#1394), the same shape #1276 gave Makefile targets - a gate implemented under `lib/`, not `scripts/`, could not be registered by any arrangement: the concrete motivating case was CPP's own `lib.security gate` (ADR 0008 row 61), which has no `scripts/` entry point at all. `discover` now also reads `scripts/` RECURSIVELY (the OTHER half of #1394's acceptance - a marker in a `scripts/` subdirectory is discovered too) and `lib/**/*.py` for the marker; the gate stays the plain `file` kind (no new typed-object schema, unlike `make-target`) because its census subject is a STRUCTURAL function of the file's own path (`lib_module_subject`, in the shared census rule module: the file's immediate package, dotted - `lib/security/cli.py` is about `lib.security`), not a second thing a manifest has to declare and keep in sync. `registration_subject`/`census_membership` gained a `root` parameter to recover that relative path. The real control is `controls/lib-security-gate`: its invocation imports `lib.security.cli` by dotted name rather than running `{gate}` as a script, because `cli.py` uses package-relative imports that fail outside package context, and seeds `sys.path` from `{gate}`'s own path so the anchor substitution actually swaps which copy gets imported - the anchor's `lib/security/__init__.py` is load-bearing for this, not boilerplate: without it `lib` (a namespace package) merges the anchor's and the real tree's `lib/security/` portions and Python still resolves to the real one's `__init__.py` regardless of sys.path order (measured while building this control: the anchor read INERT, having silently never run, until that file was added). `tests/test_negative_controls.py::test_a_marker_in_a_scripts_subdirectory_is_not_discovered` is now `..._IS_discovered` - its own docstring, written at #1276, named exactly this inversion as the sign the widening had landed
- check-negative-controls path-form census subjects normalize to a basename (#1394) - `registration_subject` has always resolved a plain-file registration to `path.name`; cpp-w2's comment on #1394 measured that kyle's own census cites the full relative path (`scripts/check-skills-install.py`) where this repository cites the basename alone, so EVERY one of that repository's registered controls printed as `NEGATIVE_CONTROL_CENSUS_NONMEMBER` once its ADR path resolved (#1264) - a confident, wrong answer, not an unknown. `subject_of` (the shared extraction rule both readers import) now strips a `/`-containing head word to its final segment; a `make:`/dotted `lib.<pkg>` subject has nothing to strip and this is a no-op for it
