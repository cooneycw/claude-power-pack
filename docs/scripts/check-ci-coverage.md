# `check-ci-coverage` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `check-ci-coverage` (#1146)

- check-ci-coverage - answers whether the PIPELINE runs what `make verify` runs, per prerequisite (#1146). `make verify` chained 27 gates and `.woodpecker.yml` ran 16; nothing in the tree recorded which 11 were missing, so #1144 merged green over a gate that was in `verify` and absent from CI and `main` was red from the moment it landed - in front of whoever pulled next rather than at PR time in front of its author. The accounting that failed was an ABSENCE read as fine, so the remedy is not a second registry of what CI runs (a registry drifts from the pipeline exactly as the pipeline drifted from the Makefile) but a DECLARATION beside each gate whose BOTH SIDES are read. Three populations, all derived: `verify`'s prerequisites from the `verify:` rule, the step names in `.woodpecker.yml`, and the `ci:` clause of each `## verify-coverage:` directive. Four findings: `UNDECLARED` (a prerequisite with no clause), `MALFORMED` (a clause that is not exactly `ci: runs <step>` or `ci: excluded <reason>`), `ABSENT-STEP` (a `ci: runs` naming a step the pipeline has not got), and `ORPHANED-CLAUSE` (below)
- check-ci-coverage names an ORPHANED CLAUSE by file and line - a `## ci: ...` written on its own line instead of on the directive - and that finding exists because the notation reintroduced the defect it removes. Found when #1071 and #1146 met at merge: a worker who branched before the inline form existed wrote `## verify-coverage: gate agents-md-budget-check - <reason>` and `## ci: runs agents-md-budget-check` on two lines, plausibly, and two readers confirmed it matched. Such a line READS AS A DECLARATION TO A HUMAN AND IS INVISIBLE TO A GATE THAT PARSES ONLY DIRECTIVES, which is #1146 one level in. Left to surface as `UNDECLARED` it is worse than silence: the remedy says "say `ci: runs <step>`" to someone looking straight at a line reading exactly that, and from where they sit it is indistinguishable from a broken gate - the same false-diagnosis shape as the list-form pipeline above. The cause is printed BEFORE the symptom, and the orphan is never credited as the target's declaration. Anchored on the LINE START, because writing about the notation is ordinary: this Makefile's own explanation of the gate contains "`ci: runs <step>` is a claim" mid-sentence, the good control case carries a line of that shape, and a loose pattern would red the repository over its own documentation
- check-ci-coverage keeps the SHAPE strict and the VOCABULARY open, and the pair is the point. Nobody can enumerate in advance why a gate cannot run in a slim container, so an exclusion reason is free text; but a parser lenient enough to honour that turns "an unrecognised reason still passes" into "a malformed declaration still passes", which is the defect wearing the feature's clothes. `ci: run validate` and a bare `ci: excluded` are both committed bad cases, and they are SEPARATE cases: they fail different halves of the grammar - an unrecognised keyword and a missing argument - and a parser matching on the first word alone catches the typo and passes the other
- check-ci-coverage binds a declaration by NAME, never by position, and inherits that decision rather than re-deriving one: `## verify-coverage:` directives name their target so a comment block that drifts away from its recipe cannot silently re-point at the target below it. `controls/ci-coverage/cases/bad-declaration-bound-to-a-ghost-target` is what holds the inherited decision - a well-formed clause naming `beta-chek` sitting directly above the real, undeclared `beta-check`, which a positional reader scores clean. The Makefile PARSER itself is IMPORTED from `verify-coverage-check.py` rather than copied, because two readers of one format drift and both stay green while they do
- check-ci-coverage is a SIBLING of `verify-coverage-check` rather than a branch inside it, on the contract rather than on size: that gate's verdict already stands for two populations at once (every Makefile target is classified, every file in `scripts/` is accounted for) and its own docstring calls it "a TRIPWIRE, not a coverage enumeration". This is a third pair - `verify` prerequisites against pipeline steps - and it IS an enumeration: per-prerequisite, exhaustive, green only when every member is dispositioned. Folding it in would make one green stand for two unrelated claims, which is the reading failure #1146 is about, one level up. The two cover each other's blind side: a gate dropped OUT of the `verify:` list leaves this gate's population entirely, and `verify-coverage-check` is what reds on it, because the target is still declared `gate` and `verify` no longer reaches it
- check-ci-coverage treats an EMPTY population as `UNKNOWN` (exit 2), never `ok`, and the `ok` line states its counts so a reader can see the population the green rests on. The gate exists because an absence was read as fine, and a derivation returning zero members is an absence; two ways that arrives with nobody editing the script are a `verify:` rule reformatted past the continuation join and a `.woodpecker.yml` converted to YAML's list form. Both are REGISTERED control cases since #1157, at `controls/ci-coverage/cases/unknown-*`, and they also keep their pytest coverage in `tests/test_ci_coverage_check.py` - the registration asserts the anchor relationship, the tests assert the exit code and the NAMED population, and neither subsumes the other. They could not be registered before, and the reason is worth keeping: `expect: UNKNOWN` routes a case to the anchor-SANITY loop where the anchor had to AGREE, and for this gate the anchor's blindness under test IS that it never derives the prerequisite population - an anchor that refused an empty one would have to derive it and would then catch the undeclared-gate case. Mutually exclusive by construction. What resolved it was measuring what the anchor actually says: `ok - 2 declaration(s) found: 1 run in CI, 1 excluded` over a population the gate refuses to judge with `the population is empty, so a clean verdict would rest on nothing`. A confident COUNT, not a silence - which is the blindness the cases exist to show, so they now declare it with `anchor_expect: clean`.
- check-ci-coverage is a MEMBER OF ITS OWN POPULATION and declares `ci: runs ci-coverage-check` on itself. Stdlib-only, git-free and offline - it opens two repo-relative files - so `make verify` and the slim CI image give the same verdict, and a check that audits "does the pipeline run what verify runs" while being itself absent from the pipeline would be the class it audits. Registered in `controls/ci-coverage`, whose constructed anchor is the declaration-COUNTING framing this issue itself used at `a9408bc` before the gate existed: it counts clauses and checks neither side, so it misses all five bad cases and agrees on the good one
