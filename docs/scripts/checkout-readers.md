# `checkout-readers` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `checkout-readers`

- checkout-readers - name the processes holding files in the checkout, and separate the ones executing code that no longer exists (#1029, specimen 2). A `flow-wave-mailbox.sh __supervise_daemon` was found running for 3 days 09:54 with `fd 255 -> .../flow-wave-mailbox.sh (deleted)`: `git checkout`/`merge`/`pull` UNLINK and CREATE rather than rewriting in place (inode 4828759 -> 4828784, verified across a fast-forward), which is what makes the swap safe for a running reader AND what makes it partly ineffective - the process keeps executing the old inode indefinitely while `ls`, `git status` and `sha256sum` all describe a different file. Mixed-version supervision follows: the daemon re-arms `watch` as a child, the child opens the script fresh and gets the NEW code while the parent runs the OLD. One walk answers both halves of the remedy - `stale` (deleted inode: the swap did not reach it; re-arm these) and `live`/`busy` (current inode or cwd inside the tree: a pull now hot-swaps instruments under a running gate). `clear` IS the declared safe moment for the pull
- checkout-readers CARRIES THE PID, which the first form could not. As posted to the nit store it was `ls -l /proc/*/fd | grep '<checkout>.*(deleted)'`, and `ls -l` emits a `/proc/<pid>/fd:` HEADER line that `grep` discards - so a stale reader was proven to EXIST with no way to say which one, and the only action a hit calls for is "re-arm that supervisor". The corrected form was supplied and both controls re-run against it BEFORE the detector was first relied on (POSITIVE: pid 21206, known stale, FOUND; NEGATIVE: pid 3452895, a live daemon on a current inode, correctly not flagged), which is the only time a correction to an absence claim is cheap. Both are committed as `tests/test_checkout_readers.py`
- checkout-readers states its two limits rather than documenting them away. (1) UNREADABLE `/proc` entries are COUNTED, not swallowed by `2>/dev/null` - a scan that inspected nothing reports `unknown`, never `clear`, and the bound is printed on EVERY verdict INCLUDING `clear` and INCLUDING `--quiet`, because the quiet line is the one that reaches a session start and a bare "clear" hiding 390 uninspected processes is a blind instrument's green. A fifth verdict `partial` (fire whenever any SAME-USER process is unreadable) was built and rejected on measurement: `(sd-pam)`, systemd's per-session PAM helper, is same-user with an unreadable `/proc/<pid>/fd` on EVERY systemd session - 390 unreadable of 580 scanned on the reference host, 389 root-owned and exactly one `(sd-pam)` - so `partial` would be permanent and `clear` dead code, which is the oscillation ADR 0009 predicts. The counts stay split by owner in `--json` so that decision can be revisited from data. (2) It sees only processes alive at the instant it runs: correct IMMEDIATELY after the replacing operation, wrong if anyone later treats it as an audit. The caller's own ancestors are reported as live readers, because they are, and broken out as `self_tree` so a caller subtracts them deliberately - "ignore the processes that look like mine" is how a detector stops seeing a sibling session
- checkout-readers contract - `CHECKOUT_READERS: stale | busy | clear | unknown`, plus `CHECKOUT_READERS_UNREADABLE: <n> (<m> same-user)` whenever anything was uninspectable. `--quiet` / `--json` / `--path <dir>`; the tree is DECLARED, never inferred from a drifting Bash cwd. `make checkout-readers`
