# `tools-check` - reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `tools-check` and the verify dependency set (#987)

- tools-check - `make verify` acquired TWO undeclared hard dependencies in ONE DAY: shellcheck at 07:00 (#960) and gitleaks at 19:00 (#935, reached indirectly through `make test` -> `test_negative_controls.py` -> `controls/secret-scan`). Neither appeared in README Requirements, `/cpp:init`, `/cpp:update`, `/cpp:status`, `docs/HOST_MANAGED_ARTIFACTS.md` or `.pre-commit-config.yaml` - measured as zero occurrences in all six. A clean clone could not pass the repository's own documented gate while CI stayed green, because the pipeline images supply the tools
- tools-check THE DEFECT IS NOT "A TOOL IS MISSING" - make already said that. It is that make says it about the FIRST missing tool and stops, so a developer installs one, re-runs five minutes of gate, and meets the next. `tools-check` runs first in `verify` and reports the WHOLE set in one pass, naming what each tool is for and the pinned digest that would satisfy it. Demonstrated two-sided by SHADOWING rather than by trusting the host: on a PATH carrying neither shellcheck, gitleaks nor docker it names both; with git also shadowed out it names three; with all present it prints `ok`. Shadowing was the only route to a measurement because the original repro had been destroyed twice that day by installing the tools to unblock the wave
- tools-check AND `verify`'s MEMBERSHIP ARE BOTH MUTATION-GUARDED, per the standing practice that after a repair you mutate THE REPAIR. Five mutations applied and killed: removing `oscillation` from `verify:`, dropping gitleaks from the declared set, adding `--exit-on-finding` to the oscillation recipe, and two CI shapes that slipped an earlier guard - `make -j2 verify` and a YAML block scalar containing `make verify`. The `verify` membership list is a TRIPWIRE and says so: it cannot know what the aggregate SHOULD contain, only fail loudly when something that is there stops being there. That failure has a live instance - `check-negative-controls` is absent from `verify` today and nobody decided it, which is why every worker in this wave read a green `make verify` as "the gates are healthy"
- tools-check DOCKER DOES NOT SUBSTITUTE EQUALLY, and the first cut claimed it did. `make shellcheck` and `make secret-scan` fall back to a pinned image, so docker covers them; `make test` does NOT, because it runs registered controls that invoke `scripts/shellcheck-gate.sh` and `scripts/secret-scan-check.sh` DIRECTLY with no fallback. Reporting "available via docker" for the test path was the overclaim this target exists to remove, inside the target that removes it. The declared set is now two classes - `TOOLS_HARD` (git, python3, uv: required, no fallback) and `TOOLS_NATIVE` (shellcheck, gitleaks: docker covers the standalone targets only) - and the report says which
- tools-check DOES NOT GATE. Absence is reported and `verify` continues to the target that actually needs the tool, which is where the honest verdict lives - the shellcheck gate's own `command -v shellcheck || unknown` exit 2 is UNTOUCHED. Naming a missing tool early is diagnosis; deciding what its absence MEANS belongs to the instrument, and #987's scope note is explicit that the fix is to supply the tool and never to soften the gate
- shellcheck target gained the docker fallback `secret-scan` has carried since #935, pinned to `koalaman/shellcheck-alpine:v0.10.0@sha256:5921d946...` - THE SAME DIGEST `.woodpecker.yml` PINS, so the pin has one source. Strictly better than an install instruction here: apt supplies 0.9.0 and CI pins 0.10.0, and `.woodpecker.yml` already records why that matters ("running the gate under two different linters would make the control's verdict depend on which container reached it"). An install instruction would reintroduce the exact skew #960 designed around; the fallback gets version parity for free
