Per-script history, indexed from [the scripts inventory](../scripts.md).

## `npm-global-upgrade`

- npm-global-upgrade - upgrade a global npm harness and report the VERSION TRANSITION rather than the install command's exit code (#1022). `/cpp:update` Step 5d.2 ran `npm install -g @qwen-code/qwen-code`, read exit 0, and composed `Tier 6 refreshed`. On a host running node 20 that install does nothing: npm resolves `latest` down to the newest ENGINE-COMPATIBLE release, and 0.24.0 declares `engines.node >=22.0.0`, so npm reinstalls the 0.15.10 already present and exits 0 with no error. A real upgrade and a silently-capped one were the same bytes, and the Step 10 summary that quotes them is read by the operator and by later sessions, none of which re-derive the version. Measured on the box the issue was filed from: installed 0.15.10, published latest 0.24.0, node v20.20.2 - nine minor versions behind, reported as refreshed on every run. The same offer for `opencode-ai` in Step 5d.3 goes through the same helper, not because that package stalls today (it upgraded 1.18.29 -> 1.18.31 on the same run) but because the two were indistinguishable from their output alone
- npm-global-upgrade contract - `NPM_UPGRADE_LABEL` / `_PACKAGE` / `_BEFORE` / `_INSTALL_EXIT` / `_AFTER` / `_LATEST` / `_ENGINE` / `_NODE`, then `NPM_UPGRADE: <verdict>`. Exit 0 `upgraded` (the installed version moved FORWARD) and `current` (it did not move and already IS the published latest); exit 1 `downgraded` (it moved BACKWARD), `capped` (behind latest, and latest's `engines.node` excludes this host's node), `not-upgraded` (behind latest with no constraint that explains it) and `failed` (the install command exited non-zero); exit 2 `unknown` (a version could not be read, so the transition is UNVERIFIED). `--package` and `--binary` are required; `--npm`, `--node`, `--sudo` and `--skip-install` cover the host variations. POSIX sh, so it gives the same verdict on a dev box and inside the slim CI image
- npm-global-upgrade callers must NOT treat a non-zero exit as fatal. `capped` is a truthful report about a host, not a broken update run: `/cpp:update` prints the verdict, carries it into the lane status, and continues. What it may no longer do is compose an unqualified "refreshed" over it - there is no such value in the Step 10 vocabulary any more, which is the half of the fix that survives someone rewriting the helper
- npm-global-upgrade invents no reason, and evaluates a constraint WHOLE or not at all. `capped` requires the text after `>=` to be a bare dotted-numeric version that this host's node fails on the full major.minor.patch triple, with absent components read as 0 so `>=22` means 22.0.0; anything else (`^22 || ^20`, and equally `>=22.0.0 || >=20.0.0`, which merely BEGINS with `>=`) is quoted verbatim, labelled not evaluated, and the verdict stays `not-upgraded`. The counter-model review reproduced both halves of the prefix-matching error before reporting it: `>=22.0.0 || >=20.0.0` on node 20 read as `capped` although the disjunction admits that host, and `>=22.12.0` on node v22.1.0 read as "no engine constraint explains it" although it is the entire reason. A move is likewise not an upgrade: `after != before` was the whole test, so an install replacing 1.6.0 with 1.5.0 reported `upgraded` and exit 0 - the same defect class the helper exists to remove, inside the helper. Ordering drops a prerelease or build suffix WHOLE and compares the numeric cores; when the cores are equal and the strings are not, the direction is not established and the verdict is `unknown`, never a guess. The second counter-model pass found both halves of that too: `cut -d. -f2` prints the whole line when it holds no delimiter, so `>=22` read as 22.22.22, and `tr -cd '0-9'` kept a suffix's digits, so `1.5.0-rc1` read as patch 01. The tempting shortcut - blame `engines` whenever the version did not move - is wrong in a direction nobody checks, because a plausible reason attached to a verdict nobody re-derives ends the investigation instead of starting it. `controls/npm-global-upgrade/cases/bad-unevaluable-engine` is that input, and node 20 satisfies the `^20` branch of its constraint
- npm-global-upgrade is an instrument whose verdict is consumed without re-derivation, so it carries a committed negative control (ADR 0008, enumerated row 64): `controls/npm-global-upgrade/` holds eleven known-bad cases (engine-capped, silent no-op with engines satisfied, an unevaluable constraint, a compound constraint the host satisfies, a minor-version engine ceiling, an abbreviated `>=22` requirement, a backward move, a prerelease move in each direction, a failed install, and an unreadable registry) and two known-good ones - six of the eleven contributed by the counter-model review across two passes, which is worth recording: a case set whose author chose every input is weaker evidence than one a second reader added to. The second GOOD case is the one that is easy to omit: a host already on the published latest does not move either, and a check phrased as "did the version change" reports it as a problem - an instrument that cries wolf on every up-to-date machine is switched off, which returns the lane to #1022 by a different route. Each case is a `bin/` of stub `npm`, `node` and harness programs; the REAL helper runs over them unmodified, so no npm or node is needed in CI. The anchor is `constructed` - the blind version was never a script, it was inline bash in `/cpp:update` - and reproduces it exactly: install, exit 0, report refreshed. It misses all five bad inputs and agrees on both good ones
- npm-global-upgrade migrated onto gate-lib (#1127) - `gate_map upgraded=0 downgraded=1 unknown=2 error=3` and `gate_arg_value` for the FIVE value-taking flags. `--sudo` and `--skip-install` stay exactly as they are: `gate_arg_value` answers "was a value supplied" and a boolean flag has none to supply, so converting them would be a module adopted past the question it answers. USAGE EXIT MOVED, {1 under bash, 2 under sh} -> 64: the bash value was this gate's own `downgraded` code, so a dangling `--package` reported as "the installed version moved BACKWARD". `--package ""` is now accepted and caught by the existing `[ -n "$PACKAGE" ]`, exit 2, before anything reaches npm
