# `flow-wave-registry` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## Re-registration work moves (#1762)

Owner ruling, 2026-11-13, verbatim: "1762 yes yes yes". A re-brief keeps an
omitted issue or repo. Explicit empty values clear them; cwd and branch still
rewrite. `--force` concerns ownership only. A work-reset refusal uses the
existing `refused` verdict and exit 1, leaves the registry byte-identical, and
names the missing consent. Usage 2 and I/O 3 remain unchanged. The decision
uses the entry snapshotted under the same lock as the write.

Each identity dimension has seven states. This table applies independently to
issue and repo; "named" means the supplied value after normal repo resolution.

| Stored | Supplied | Effective | Move contribution |
|---|---|---|---|
| absent | omitted | absent | no |
| absent | named | named | yes |
| present | omitted | stored | no |
| present | same | stored | no |
| present | different | supplied | yes |
| absent | explicit empty | absent | no |
| present | explicit empty | absent | yes |

Either dimension moving makes the combined identity move: 33 of the 49 pairs
move, 16 keep identity. The following four outcomes apply to every pair. Here
"supplied" includes empty `--files`; an observation is complete only with all
three `--pr`, `--base`, `--diff` flags. Partial observations remain usage errors.
The table assumes the role holds both an active lane and an observation.

| Identity | Files | Observation | Outcome without reset consent |
|---|---|---|---|
| kept | omitted | omitted | keep both and their overtake count |
| kept | supplied | omitted | replace lane; keep observation/count |
| kept | omitted | complete | keep lane; replace observation using existing count rules |
| kept | supplied | complete | replace both using existing count rules |
| moved | omitted | omitted | refuse, unchanged |
| moved | supplied | omitted | refuse, unchanged |
| moved | omitted | complete | refuse, unchanged |
| moved | supplied | complete | replace both, count zero |

These are all 196 combinations; the 99 refusals are the 33 moves times three
incomplete restatements. Their exact inputs and chosen outcomes are committed
in `tests/fixtures/flow-wave-reregister-cross-product/cases.json`. The older
matrix repeats selected cases in a checkout, linked worktree and plain cwd.

Consent is per component: empty `--files` clears the lane; `--clear-pr` clears
the whole observation; neither authorizes losing the other. `--allow-work-reset`
authorizes resetting omitted components on a move, while supplied components
still win. With no active component there is nothing to protect. Released
legacy rows are history, not active claims. Same PR/new base/same diff still
increments the overtake count; a changed diff preserves it, and a changed PR
or observation repo resets it. A new work identity always starts at zero.

Every successful re-registration changing a lane or observation prints a plain
line naming the change. The role stores one plain `work_note`, also shown in
human `list` and nested inside that role in `list --json`. It is the most recent
work change, retained across unchanged re-briefs and cleared on role reuse;
there is no structured event line or change-history object. Withdrawals say
"merge observation withdrawn". Existing file-delta lines remain. Consumers of
exit 1 must read the diagnostic and must not automatically retry with `--force`.
The output lexicon and existing verdict values are unchanged.

The committed `controls/flow-wave-reregister-work` has independent missing-lane
and missing-observation witnesses. The old helper accepts both. Mutation tests
remove only each witness's guard: its case becomes accepted while the other
still refuses. No test or control reads a live wave registry.


## `flow-wave-registry`

- flow-wave-registry - role -> address registry for multi-session flow waves (#638, companion to the #637 wave loop): `register`/`list`/`get`/`verify`/`release`/`close`/`self-address` verbs over a flock-atomic, wave-namespaced JSON roster at `$XDG_RUNTIME_DIR/cc-flow-wave/registry.json` - OUTSIDE any repo (never shared mutable repo state, the #635 hazard class) and outside transcripts (survives a worker `/clear`; the runtime dir dies at reboot, exactly when every session socket dies too). Self-derived sockets (ancestor-pid walk) are bootstrap only: `verify --from` reconciles against the transport-observed `from=`, and the OBSERVED address replaces the self-derived one as canonical - never the reverse. The non-matching outcomes are SPLIT (#674): a recorded `unknown` filled in by observation is the documented fallback succeeding and reports `address_filled` unflagged (`list` renders `filled`, a fully verified state and not a lesser grade than `verified`), while only a recorded REAL address contradicted by the observed one is flagged `mismatch-corrected`; both exit 0. Role conflicts against a LIVE session refuse (exit 1) without `--force`; dead owners read stale and are taken over, mirroring #597 claim semantics. `list` warns on lane overlap only for the useful signal (same repo + same issue, same branch, same/nested worktrees among LIVE entries) - same repo alone is the normal wave shape and stays info-level, and roles that DECLARED NO LANE are exempt from the pairwise checks entirely (#683: the `orchestrator`, plus any live role with no issue, no branch and a shared-parent cwd; announced in the roster, never silent, and lapsing the moment a lane is declared). `list` also reconciles `flow-claim` worktree locks (#687), since registration is opt-in and orthogonal to `/flow:auto`: a LIVE lock no live registry entry accounts for renders as a claim-derived row and PARTICIPATES in overlap detection (contactable but never a role - separate `unregistered_claims` key in `--json`, never a `verify`/`release` target), its address OBSERVED rather than derived from the pid, and coverage bounded to repos the wave already knows about plus an explicit `--repo` - a host with nothing registered has nothing to scan
- flow-wave-registry close (#1562) - `close --wave W [--archive DIR] [--dry-run] [--force]` archives the entire runtime wave directory and `registry-entry.json`, verifies the contents and registry round-trip, then removes only that wave under registry, mailbox and verdict-ledger locks. Whole-wave watcher enumeration is independent of registrations and heartbeat files, and watcher arming shares the mailbox lock. An inaccessible source refuses even with force. Live/unknown roles and unknown watcher counts refuse unless explicitly forced; a confirmed watcher always refuses, even with force. Existing archives get a non-colliding suffix. `FLOW_WAVE_ARCHIVE` and `FLOW_WAVE_BYTES_FREED` describe the result. `/flow:cleanup` previews and offers each eligible wave separately; `/flow:wave` records the archive in its final summary. Committed controls in `tests/test_flow_wave_close.py` cover live role, consuming watcher, verification failure preservation, clean retirement and other-wave preservation.
- flow-wave-registry loud default + cross-wave visibility (#671) - an omitted `--wave` lands in wave `default` with a clean verdict while every named-wave roster stays empty, the #638 silent-addressing-failure class one namespace level up (both sides read success; the 2026-08-11 incident took a raw-JSON dig to diagnose). Now `register`/`get`/`verify` into `default` without an explicit `--wave` print one advisory stderr line, `register` names the likely intended wave when exactly one other wave has a LIVE orchestrator (suggestion only - never auto-join), and `list` appends a `note:` line for LIVE entries parked in OTHER waves (stderr in `--json` mode so stdout stays parseable). Advisory only: verdicts and exit codes are byte-for-byte unchanged
- flow-wave-registry honest address bootstrap (#672) - the 2026-08-11 wave deadlocked with every session recording `socket: unknown` while the helper reported that the orchestrator's `verify` would supply it later; it could not, because `verify` needs an observed `from=`, which needs a delivered message, which needs an address somebody already holds - so the promise named a fallback that was structurally dead, and ~2h were lost to both sessions standing by on a healthy-looking verdict. Three properties close it. Failure NAMES its cause (`FLOW_WAVE_SOCKET_REASON`): `no-sock-dir` (the socket dir is created LAZILY - the same host had none at 07:52 and self-derived successfully at 10:27, so `unknown` is point-in-time, not a permanent verdict, and a re-register adopts the real address) vs `no-match` (dir present, no ancestor pid owns a socket - a retry alone will not fix it). `FLOW_WAVE_BOOTSTRAP: ok|deadlock` on register/get/list says blocked-not-pending and prints the three lanes that do not depend on self-derivation (re-register, `register --socket <addr>` - which already shipped in #638 but was documented nowhere - and a user-relayed hello). And a failed derivation NEVER downgrades a recorded address to `unknown` (`SOURCE=preserved`): re-registering is the documented cheap re-brief, so the #638 trust model read in its other direction - a known address outranks a failed assertion, since `unknown` cannot be messaged. `FLOW_WAVE_SOCKET_SOURCE` (`explicit|self|preserved|unknown`) reports which lane produced the address; the ancestor walk now starts at `CLAUDE_PID` (`$PPID` alone starts a hop low and was reached only by luck). Companion to #670's order-independent registration, which named this gap as the residual it could not cover
- flow-wave-registry wave-policy tiers (#699) - the registry recorded a role, an address and a lane; everything else a wave RUNS ON - implementation authority, gate policy, who judges, the ledger format, the authority model, merge and deploy policy, and the per-worker FILE LANE - lived in prose the orchestrator retyped into every message, which is both where the 2026-08-11 wave's orchestration errors happened and the one thing that does NOT survive a worker's `/clear` (the registry's stated purpose). Now declared data in two tiers: wave-level via `policy set` (a MERGE that bumps `rev`, so amending one field is a one-flag call; `--authority` implement|file-issues-only and `--authority-model` orchestrator-only|user-and-orchestrator are enum-validated because a typo there reads as declared and answers 'may this wave write code?' with garbage, the rest free text) and role-level on `register` (`--model`, `--permission-mode`, `--files`, `--capacity` - preserved across the omit-everything re-brief, cleared only by an explicit empty value). A DECLARED POLICY NOBODY READS IS DECORATION, so four readers are pinned by test: `register` REPRINTS the policy (the compaction-proof re-brief - a `/clear`ed worker recovers the protocol by re-registering), an undeclared policy reports `FLOW_WAVE_POLICY=absent` instead of passing silently (the failure where implementation authority took a user round-trip and both workers correctly refused to infer it from an issue number), a role briefed on a superseded rev reads `brief=STALE` in `list`/`get` and is named at `policy set` time, and declared FILE LANES join the ONE `report_overlap` predicate - exact-match on declared paths, below the branch/worktree arms and above the shared-repo info, so the collision class that was 100% of the reference wave's real conflicts stops being checked by hand. `policy_absent` is a STATE and exits 0 (#674's rule: a new verdict is never a new exit code); `list --json` gains a `wave_policy` sibling key only when one is declared, so a policy-less wave is byte-identical to pre-#699. Covers declared STATE; #701 covers the state TRANSITIONS
- flow-wave-registry jq-1.6 update trap (#699) - a `?` anywhere inside a `|=` body makes jq evaluate the update as a backtracking path expression, and `_modify` then DELETES the key it was told to update: exit 0, no stderr, the whole policy object gone, `with_lock` reporting success. The same `$pid | tonumber? // $pid` coercion is safe in the object CONSTRUCTOR `register` uses (a plain `=` assignment) and unsafe in `policy set`'s `|=` - exactly the difference that gets copied across by hand, so it is commented at both sites and pinned by a test asserting the STORED object rather than the verdict
- flow-wave-registry watch-state join (#778) - a role could read `[live, verified] brief=current` and be completely DEAF: arming the #676 mailbox watch was the one element of participation that left NO trace in the roster when it was missing, so `list` reported a healthy worker while nothing sent to it would ever arrive. In the `kyle-completion` wave on 2026-09-05 a worker skipped step 4 of `/flow:register`, sat that way for over an hour, and never saw a six-issue assignment - the orchestrator's ledger said assigned, the worker's roster entry said `free - no active lane`, BOTH sides looked healthy, and the only tell was `flow-wave-mailbox.sh list` showing `CURSOR 0 / UNREAD 2`, found by accident during a sweep prompted by an unrelated question. The existing `flow:wave` guidance ("an idle session is not a stalled one"; check the mailbox before diagnosing a stall) was correct and had been followed all evening: it requires the orchestrator to REMEMBER to cross-reference two tools, per worker, continuously, against a failure that is silent, has no deadline, and looks identical to a worker legitimately holding. Now `list` renders it: `watch=armed`, `watch=stale(42m)` or `watch=ABSENT` per LIVE role, `unread=N since <ts>`, and a loud `** NEVER READ **` for a cursor at 0 against a non-zero rev - the unambiguous "has consumed nothing, EVER" case, which a count alone does not state - plus `WATCH:`/`UNREAD:` summary lines naming who, and `FLOW_WAVE_WATCH_UNARMED` / `FLOW_WAVE_UNREAD` contract lines emitted on every `list` path so 0 deaf roles is distinguishable from not-reported. THREE BOUNDS, each deliberate. Data comes from ONE call to the sibling `flow-wave-mailbox.sh list --json`, never from parsing box files here - the mailbox owns that format and a second parse would drift into reporting a healthy wave that is not one, the exact failure class this closes. That call FAILS OPEN in every mode (missing sibling, non-zero exit, unparseable output): watch state becomes `unknown`, renders nothing, warns nothing, since a broken mailbox must never break the roster - the #701 lexicon rule in the other direction. And rendering is gated on the mailbox lane being IN USE in that wave (at least one box or one heartbeat), because in a wave that never uses it every role would read ABSENT - a flag firing on 100% of the fleet, which is #674's zero-signal failure that this repo has already paid for once; a mailbox-free wave emits byte-identical text and JSON to pre-#778, the promise #687's `unregistered_claims` and #699's `wave_policy` both made. Scoped to LIVE roles (a dead role's watch is moot) and deliberately NOT added to `get`: the deafness gap is a property of the roster SWEEP, while `get` answers "where do I send to this role?". Companion to #687 - same class of blindness, the other direction: that one surfaced sessions the roster could not see, this one surfaces roles the roster shows but cannot reach. SUPERSEDED IN PART by #801: the three states this entry describes were derived from the heartbeat stamp alone, so `watch=armed` was rendered for a role whose one-shot watch had already exited - see the #801 entry under `flow-wave-mailbox` for the fused state (`armed`/`stale`/`dead`/`absent`/`unknown`) the roster renders now
- flow-wave-registry unscoped-lane reporting (#800) - overlap detection's same-issue and FILE-LANE arms compare `$ra` = `$rb` before anything else, because the same relative path (or issue number) in two different repos is not a collision. An EMPTY repo therefore matched nothing: the arm could not fire, the shared-repo `info:` arm below it could not fire either, and the pair dropped out of the report in silence - indistinguishable from "checked, and clean". The trigger is the documented cheap re-brief itself: `--files` is PRESERVED across a re-register that omits it while `repo` is REWRITTEN, so a worker re-registering with only `--files` to extend its lane keeps the lane and loses its scoping key, and the act of declaring a lane becomes the act that stops the lane being checked. Found in a live `docker-list` wave and reproduced with a positive control in both directions: two workers held the same two files for ~40 minutes against a roster that showed no warning at all, and passing `--repo` on the re-register fired it immediately. Now `list` NAMES such live roles (`UNKNOWN: overlap NOT computed for live role(s) with a declared lane and NO repo`), counts them in `FLOW_WAVE_OVERLAP_UNSCOPED` - emitted as a VALUE on every exit path including `0`, the empty roster and `--json`, so "none" is distinguishable from "not reported" - and says on stderr that the roster CANNOT be read as clean; `register` says it at the moment it records the lane (the #683 shared-parent advisory's placement, for its reason: one re-register fixes it, and otherwise nobody notices because there is nothing to notice) and `register`/`get` answer it per role as `FLOW_WAVE_LANE_SCOPED=yes|no|-`. Deliberately NOT fixed by preserving `repo` across a re-register, the issue's other option: `repo` is a LANE fact and lane facts go stale (the #683 trap), so preserving it would make a worker that moved repos cry wolf, and it would still leave a never-declared repo silent - failing loud makes an unscoped role visible instead of invisible. The reported symptom was the file-lane arm; the same-issue arm carries the identical guard and the identical hole, so both are covered, while the branch and same/nested-worktree arms are repo-independent and untouched. The `orchestrator` is excluded because the pairwise checks exempt it unconditionally. No exit code changes (#674): advisories add lines, never verdicts. Same instrument-fails-toward-"no problem here" shape as #801's mailbox watch-state stamp, fixed alongside it
- flow-wave-registry release clears the lane (#1222) - `release` set `released` and cleared nothing, so a role whose session had ended still advertised a closed issue, a merged PR and an eight-path file lane, and an orchestrator granting from `list` could not tell a held lane from an abandoned one. Release now moves `issue, pr, branch, base, diff, obs_repo, files, overtaken` under `released_lane` - a key no lane reader consults - and blanks the live keys; `released`, `released_ts`, identity and `repo` (which the #687 claim scan reads from every row) survive, and a second release keeps the first record. Re-registering onto a DIFFERENT non-empty issue now resets every preserved lane fact the call does not supply, so a row can no longer blend one issue with the previous issue's PR and base. A re-brief that omits `--issue` is deliberately not an issue change, or it would wipe the #989 starvation baseline.
- flow-wave-registry another host's owner is `unknown`, not `stale` (#1014 Part 2, ruling RA) - an entry recorded on another host read `stale other-host`, and `stale` is the one state `register`/`release` treat as a proven death, so any session on this host took over or released a role that a session on another host might still be driving, with no `--force` and no warning beyond "taking over stale role". The registry cannot observe a remote pid - it did not look, because it cannot - so the entry now reads `unknown other-host`: `register` and `release` refuse it (exit 1) naming the holding host, `--force` still takes it with the "NOT confirmed gone" line, and `list` counts it in `FLOW_WAVE_LIVENESS_UNDETERMINED`. A same-host dead owner is unchanged (`stale pid-gone`, taken over automatically). The local pid table is never consulted for a remote entry, because a local pid with the same number says nothing about the remote process. Consumers: every `= live` reader is unaffected (neither state was live); `flow-driver-retirement-check` now sees a remote role as `unknown` - which it already refuses to clear on - instead of `stale`, which it cleared: the conservative direction. A registry.json that is readable but not JSON used to reach those rules as an EMPTY entry whose blank host "was not this host"; with the change it would have been refused as held by a host named "", so `register`/`release`/`get`/`verify` now report it as `error` (exit 3, "could not be parsed") before any liveness is computed - measured by `test_a_corrupt_registry_update_emits_a_verdict`, which caught it. Negative control `controls/flow-wave-registry-takeover`
- flow-wave-registry the socket file is corroboration, never proof (#869) - `kill -0` has two failure modes behind one return code, ESRCH (the process is gone) and EPERM (it exists, we merely may not signal it), and the liveness rule collapsed them. The socket file used to be sufficient on its own, and was evaluated AFTER the pid had already been reported dead: `uds:*) [ -S "${sock#uds:}" ] && { echo live; return; } ;;`. The kernel does not unlink a unix domain socket when its owner dies, so the file outlives the process and the WEAKER evidence overrode the STRONGER one: a SIGKILLed session kept reading `live` for as long as its socket sat on disk. What #675 actually asked for is preserved. Its words are that the socket file is "a SECOND, independent proof, covering a pid the helper cannot signal" - that is the EPERM case, and `pid_state` now answers it directly and correctly from the errno. What is removed is only the socket's power to override a DEFINITE ESRCH, which #675 never claimed and which was a bug in the mechanism rather than in the intent. #689 then made the branch uds-only and recorded that transports without sockets get one factor, "a property of the design, not an oversight"; that asymmetry is now GONE rather than documented, because errno needs no socket and every transport gets the same primary evidence. The socket survives only in the liveness BASIS (`pid-undeterminable-socket-present` and its siblings), where it corroborates an already-undeterminable pid and changes no verdict. `register` and `release` take an ALLOW-LIST of the states that free a role (`stale`, `released`), never a deny-list, and `list` counts roles of undeterminable liveness in `FLOW_WAVE_LIVENESS_UNDETERMINED`; `FLOW_WAVE_UNKNOWN_PIDS` is the test hook that reaches the undeterminable branch on a `/proc` host. The #1014 other-host reading below (`stale other-host`, where any session on this host silently took over a role a session on another host might still be driving, without --force) was the #869 defect - weaker evidence read as a death - reached by a different road: we did not look, because we cannot
- flow-wave-registry declared-directory containment, `lane-check` and the one lane splitter (#985) - file-lane overlap was exact-match only (the #683 lesson: prefix-GUESSING invents collisions the roles never declared). Live case: a role declared the bare `codex/skills` and thereby claimed three other roles' mirror trees while the predicate reported no overlap at all. The same file already did containment for CWD comparison (`case "$ca/" in "$cb"/*`) and refused it for file lanes, so the codebase had decided both ways in one file; a rule applied to one half of a comparison and refused for the other is not a policy, it is an accident. Now a declared DIRECTORY contains the paths under it, tested against an explicit separator (`scripts/foo` does NOT contain `scripts/foobar`), everything else stays exact, and the reversal trigger sits at the predicate. `lane-check <role> [--base REF]` compares the NAMES a role's diff touches (against the MERGE BASE, never the moving tip) with its declared lane and refuses a path the role never claimed; no declared lane is `unknown`, never a pass. A live over-claim in the wave that built it was invisible to both detectors: too wide for the diff check to have run on, and invisible to exact-match. `lane_split` is the one comma splitter. The previous guard was `set -f` around each loop with an unconditional `set +f` on the way out. That restores globbing ON rather than to the caller's state, so the first lane_covers call re-enabled expansion for every loop after it, and the unused-lane scan expanded `*.md` into real filenames and reported those invented paths as unused - and could report them CONTESTED against another role (Codex pass 2 on #985). `read -ra` splits on IFS and never globs; its reversal trigger (#936) sits beside it
- flow-wave-registry read-back lines, the lane lapse and the merge-strict shelf life (#1026) - each of these was a declaration that was stored and never reported, so a broken declaration and a working one printed identically. `--files` REPLACES a lane wholesale, so a role re-registering for its next issue silently un-claimed whatever the new list omitted; `register` now prints `FLOW_WAVE_FILES`, `FLOW_WAVE_FILES_DROPPED` and `FLOW_WAVE_FILES_ADDED` and says the drop on stderr (reported rather than prevented: replacement is the right mechanism, its SILENCE was the defect). Counter-model review of that stderr line: the earlier wording claimed "nothing else holds these paths now" - a ROSTER-WIDE fact that `register` never looks up, and which another live role may flatly contradict. The per-role delta is what was measured; who holds a path now is `list`'s question, so the reader is sent there rather than handed a fabricated answer. `register` stored `--driver` and emitted nothing, so a silently-accepted flag and a silently-IGNORED one were byte-identical; it now echoes `FLOW_WAVE_DRIVER` and its capability lines, and `list` counts live roles with no driver under a wave whose policy declares one (`FLOW_WAVE_DRIVER_UNDECLARED`, with `FLOW_WAVE_DRIVER_POPULATION` as its denominator, `-` when the wave declares none). `policy set --merge-strict` became a reading with a shelf life (`FLOW_WAVE_MERGE_STRICT_TTL`, default 86400 seconds): an expired or unstamped `no` no longer switches starvation detection off, and `FLOW_WAVE_MERGE_STRICT_SUPPRESSING` says whether it did. Counter-model review pass 2 on #1026 found the empty-roster path returned before reaching the place these were derived, so `list` on an empty wave omitted FLOW_WAVE_MERGE_STRICT_SUPPRESSING while `list --json` on the SAME wave emitted it; they are computed above every render branch now, for the same reason #800 counts unscoped lanes above the `--json` split. `--authority-model` gained `user-only`, the most restrictive value, and `lane-check --granted A,B` compares the declared lane against the GRANT that authorised it (`FLOW_WAVE_LANE_UNGRANTED` refuses, `FLOW_WAVE_LANE_UNCLAIMED` is loud data)
- flow-wave-registry pid start-time witness (#1094) - pid EXISTENCE alone is not pid IDENTITY: a registered pid that exits and is later reused by the kernel for an unrelated process read `alive` either way. `register` records `pid_started` (field 22 of `/proc/<pid>/stat`, clock ticks since boot) and liveness compares it: recorded-and-equal is `live pid-present`, never-recorded is `live pid-present-witness-absent`, current-unreadable is `live pid-present-witness-undeterminable`, and only a proven mismatch is `stale pid-recycled` (orchestrator ruling: the witness can only ever ADD a positive finding, never subtract one, so every entry written before the field existed stays `live`). The stat line is split on the LAST `)`, never with a positional `awk '{print $22}'`: `comm` may itself contain spaces or parentheses, so a naive split silently shifts every field after it. Measured directly: this read a start time from BEFORE the process could have existed, for exactly this reason. `FLOW_WAVE_PID_STARTTIMES` and `FLOW_WAVE_PROC_ROOT` are the test hooks
- flow-wave-registry a refusal announces itself, and a failed write does not report success (#1190) - `usage_fail` now emits the `FLOW_WAVE: error` verdict (one function behind about 45 call sites; the exit code is unchanged). The three failure paths of `with_lock` exit 3 inside a SUBSHELL, and nothing used to read that status, so the script carried on and emitted its own verdict. Measured before the fix: with a corrupt registry.json, `register` printed `FLOW_WAVE: registered` and exited 0 while the update had failed and NOTHING was recorded. That is worse than the missing verdict this issue is named for: the line is present, well-formed, and says the opposite of what happened. So exit 3 never reached a caller at all, and "preserve the exit code" had no behaviour to preserve. Surfacing it necessarily changes the observed exit from 0 to 3 on a path that was already broken. `self-address` stays verdict-free on purpose, because its stdout IS the address. Adding the detail block and a `FLOW_WAVE:` line there was tried during #1190 and reverted. Two long-standing tests pin the contract - `test_self_address_names_why_it_failed` and `test_self_address_walk_starts_at_the_session_pid` both assert `stdout.strip()` equals the address EXACTLY - and they caught it. They are the contract, not an obstacle to it. The same issue added `overlap_cwd_is_artefact`: a same/nested-worktree match that is only an artefact of registering before a worktree existed no longer silences the file-lane arm for that pair. Observed in production, not hypothesised: an orchestrator granted `docs/scripts.md` to three roles at once and told a worker in writing that two files were free while another role held them, then concluded it had failed to re-read the roster between grants. The roster could not have told it. That a real checkout holding two submodules satisfies the two-child-checkouts heuristic too was found by counter-model review; the nested-worktree guard test used empty directories and could not see it, hence `_is_inside_checkout`
- flow-wave-registry an unreadable registry is unknown, and the orchestrator is exempt only while it declares no lane (#1260) - the registry half of the #1260 entry under `flow-wave-mailbox`. A registry file that EXISTS but cannot be read used to read as `{}`, so "I could not look" rendered as "nobody is registered" - an empty roster, `no-roles-registered`, a free role. Every verb but `self-address` now refuses it (`error`, exit 3; `list --any-live` answers `undeterminable`), and `path_state` asks `stat` for the errno because `[ -e ]` is false both when a path does not exist and when a parent directory denies traversal. The overlap exemption used to be keyed on the role NAME alone, so an orchestrator registered with --files, an issue or a branch - one that really was holding a claim - was still skipped, under a notice promising the skip lasted "until they declare one". The orchestrator is now exempt only while it DECLARES no issue, branch or file lane, and a lane it declared with no repo counts in `FLOW_WAVE_OVERLAP_UNSCOPED` exactly like a worker's
- flow-wave-registry the lane delta is taken under the write lock (#1266) - `register` read the current entry before the lock and reported `FLOW_WAVE_FILES_DROPPED` against it, so when a concurrent registration committed in between, the delta described an entry that was not the one replaced. Measured with the test seam (`FLOW_WAVE_REGISTRY_TEST_PAUSE_REGISTER`): the delta reported DROPPED=b.py against the stale read when the lane actually lost c.py. `with_lock` now snapshots the entry it replaces and the entry it writes inside the same lock, the after-snapshot from the CANDIDATE before the rename, so a snapshot failure (`FLOW_WAVE_REGISTRY_TEST_SNAPSHOT_FAILS` routes it to /dev/full) refuses before anything is committed. Also from #1266: a lane path may not contain a newline; `--clear-pr` withdraws a whole merge observation; the same issue number in a DIFFERENT repo is a move to other work and resets the preserved lane facts; and the toolchain warning names WHICH checkout was measured (`FLOW_WAVE_TOOLCHAIN_CHECKOUT`) - the warning used to say "this session's CPP toolchain" and name nothing, so it was read as a fact about whichever checkout the reader had in mind
- flow-wave-registry observed writes join overlap detection, and a malformed registry is refused (#1403) - a worker writing into a directory it never declared was invisible to the overlap detector, because that detector compared only DECLARED lanes against each other (a Nit Store finding). `list` now computes each live role's own `git diff --name-only` against the merge base, once per role (`observed_touched`, the algorithm `lane-check` uses, `-C`-scoped because the roster asks about ANOTHER role's cwd), and warns when a touched path lands inside another role's declared lane; an unreachable cwd is `unknown`, never "no writes", and `FLOW_WAVE_LANE_UNDECLARED_WRITES` counts roles whose diff touches a path no live role declared. Counter-model review moved the computation out of the pairwise calls (a role with zero or one live peer never reached a comparison at all, so its notice never printed) and replaced a substring membership test with exact per-token and per-line comparison. Separately, a registry that opens fine but is not exactly one JSON object document is refused by `list` and `lane-check` (`error`, exit 3) instead of rendering as an empty roster; negative control `controls/flow-wave-registry-malformed`
- flow-wave-registry toolchain provenance at registration (#1029) - registration is where a session declares its vantage, and until this change vantage meant address, lane and policy - never which VERSION of the instruments it holds. On 2026-09-15 a wave ran for eleven hours on a shared checkout 21 commits behind `origin/main`: every helper resolved, every gate was green, and none of the merged work those commits carried was reachable from any of it. The gap was found only when a worker tried to use a flag that had shipped and did not exist here. `register` now relays `toolchain-provenance.sh --json` as `FLOW_WAVE_TOOLCHAIN` (the helper's `current`, `behind`, `ahead`, `diverged` or `unknown`, or `unavailable` when no helper is installed or the helper printed nothing `register` could parse) with `_BEHIND`, `_UPSTREAM`, `_AGE` and `_CHECKOUT`; advisory only, no verdict or exit code moves
- flow-wave-registry a zombie LEADER with live threads is a live owner, and a small tidy (#1691) - `pid_state` read state `Z` in `/proc/<pid>/stat` as death, but a process whose main thread exited while another thread runs reads `Z` too; its role read `stale` / `owner-zombie` and a second session could take it without `--force`. `Z` now counts as dead only when the thread count (field 18 after the comm) is 1, 0 or unreadable, the rule `flow-worktree-claim.sh` has carried since #1709; `X` is unchanged. The same change removed the uncalled `_is_checkout_root`, folded `close_path_state` into `path_state` and two repeated print blocks into `emit_claim_rows` and `emit_driver_lines`, and corrected the two printed lines that said `--files` is always preserved by a re-register. Every printed line was compared against the scripts as they were at `4f34005f` in a one-off run of about 190 scripted steps, on raw bytes, recorded in the change's pull request; that comparison is not kept in the tree. `tests/test_flow_wave_owner_liveness.py` holds the liveness cases.
