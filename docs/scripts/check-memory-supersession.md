# `check-memory-supersession` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `check-memory-supersession` (#1440)

- check-memory-supersession - reports Claude Code auto-memories (`~/.claude/projects/<project>/memory/*.md`) that link `[[slug]]` to a SUPERSEDED memory and were last modified before the supersession (#1440). The defect is a propagation gap: a changed fact is corrected carefully in the one memory that holds it, and the memories that link to it keep asserting the old rule until a session acts on one. `--root DIR` is repeatable; with none it checks every `~/.claude/projects/*/memory`. `MEMORY.md` is the index and is never treated as a dependent
- check-memory-supersession THE MARKER GRAMMAR IS STRICT, and writers can rely on it: a memory is superseded only when a body line begins `**Superseded YYYY-MM-DD.**` (the period optional), or its frontmatter carries `metadata.superseded: YYYY-MM-DD` (or a top-level `superseded:`). When a memory carries several markers, the LATEST date is the supersession, because a dependent must postdate the most recent change, and any one marker with an invalid date makes it undecidable. The word "superseded" in prose does NOT count. Measured on the store that motivated the issue: of three memories using the word, one meant "this memory's rule changed" and another described a ruling changing INSIDE one memory, which has no dependents to go stale - matching prose would flag it. The cost is stated in every clean verdict: supersession written only in prose is not examined
- check-memory-supersession FOUR VERDICTS: `clean` (exit 0), `stale` (1), `unreadable` (2: a missing or unlistable directory, or a store with no memory files - zero examined is not zero found), `unknown` (3: a dependent with no `modified` date, one modified the SAME day as the day-granular marker, a memory whose frontmatter does not close, an explicit marker whose date is not a real date such as `2026-02-30`, or a link to a slug that more than one memory claims when one of them is superseded). A memory FILE that cannot be read (permissions, not UTF-8) makes its store `unreadable`: an unseen part of the population is a different fact from a seen memory whose order is undecidable. The last three were Codex's pre-PR findings - picking the first memory to claim a slug made the verdict depend on file ordering, an uninterpretable explicit marker read as no marker and so as clean, and a file that could not be read was folded into `unknown`. A second Codex pass found two more, both fixed: only the first of several markers was read, so a later supersession was hidden; and the dependent was removed from a slug's claimants BEFORE ambiguity was decided, so a dependent that itself claimed the slug turned a two-way ambiguity into a confident `stale` Precedence across stores is stale, unreadable, unknown, clean, so an actionable finding is never hidden behind another store's inability to be read. On its first real run it found a stale dependent the person who filed the issue had missed, and reported five undated ones as `unknown` rather than clean
- check-memory-supersession HYGIENE FINDINGS ARE INFO ONLY (`MEMORY_SUPERSESSION_INFO:`) and never change the exit code: a dangling `[[slug]]` (legitimate in this convention - it marks a memory worth writing later), an index line naming a missing file, a memory absent from the index, a `name:` that differs from the file stem
- check-memory-supersession BOUNDED to the explicit link graph. It cannot see a contradiction between two memories that do not link each other, and Kyle's substrate memory is a different store. Not in `make verify`: CI has no `~/.claude/projects`, so `.claude/verify-coverage.json` accounts for it as `tested` by `tests/test_check_memory_supersession.py`; `controls/check-memory-supersession` registers synthetic stores (public repository - no real memory content) with a CONSTRUCTED anchor that drops the marker detection and reads clean everywhere
