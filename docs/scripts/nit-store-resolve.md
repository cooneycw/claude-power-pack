## `nit-store-resolve` (#1272, #1273)

- nit-store-resolve IS THE ONLY COPY OF THE REPOSITORY-TO-NIT-STORE MAP. It was a `case` block pasted into three command documents (flow/finish.md, flow/auto.md, codex/code_review.md) that agreed with each other and not with GitHub: codex-power-pack still mapped to #227 after #227 was CLOSED, and nothing checked a number before a finding was posted into it. The resolver reads the repository from `origin` (never the directory name, since the step runs from a per-issue worktree), and answers `NIT_STORE=<n>` / `NIT_STORE_STATUS: ok` only after `gh issue view` confirms the issue is OPEN and titled exactly "Nit Store". A mapped issue that is closed or retitled is `none` (exit 1, "file the finding as a normal issue"), never the number. An unmapped repository is searched by EXACT title, and exactly one open match is required: zero is `none`, two is `unknown`. `unknown` (exit 3) is anything GitHub could not answer, and it is kept distinct from `none` because "I could not ask" is not "there is no store". Red case: the pre-#1273 block, run against a stub reporting #864 CLOSED, printed `WOULD POST INTO #864`; the resolver answers `none`. Pinned by `tests/test_nit_store_resolve.py` and, per surface, `tests/test_nit_store_routing.py`
- nit-store-resolve NO LONGER MAPS THIS REPOSITORY (#1673). claude-power-pack's store rolls over monthly ([the rollover procedure](../agents/nit-store-rollover.md)), and a mapped number is wrong the moment its issue is closed: with #864 CLOSED and a successor OPEN the mapped resolver read #864, answered `none`, and never searched, so every finding after a rollover would have been filed as a normal issue. The entry is removed and this repository is found by the exact-title search like any unmapped one. kyle and skillc stay mapped. The cost is the search path's two fail-closed answers: two open stores is `unknown`, and a successor GitHub's search index has not caught up with is `none`. Red case: `test_after_a_rollover_the_successor_is_the_answer_not_864` fails on the mapped resolver
- nit-store-resolve A SEARCHED NUMBER IS READ DIRECTLY BEFORE IT IS ANSWERED, like a mapped one (#1673, counter-model finding). The search is an index and an index lags: just after a rollover the listing can still offer the closed predecessor, and the search branch answered it unread, `NIT_STORE=864` with exit 0. The single candidate now goes through the same `gh issue view` state-and-title check; a stale hit is `none`, an unreadable one `unknown`. Red case: `test_a_stale_search_hit_on_the_closed_predecessor_is_never_answered`
- A RECORD KEPT AS AN ISSUE OR NIT STORE COMMENT IS CORRECTED BY POSTING A NEW COMMENT, NEVER BY EDITING THE OLD ONE IN PLACE (Nit Store #864, absorbed into #1499). `gh` exposes no reliable, repository-local signal that a comment was edited after the fact (GitHub's own `updated_at != created_at` is upstream API behaviour, not something this repository's tooling reads or surfaces anywhere), so an amended record is indistinguishable from an original one to anything that later reads it - including a resolver or a session relying on "what the comment says" as ground truth. If a decision or disposition needs correcting, post the correction as its own new comment naming what it supersedes; optionally strike through the superseded text in the original with Markdown (`~~like this~~`) so a reader scrolling the thread sees both the original and the correction without needing GitHub's edit history. A reader or tool surfacing an `(edited)` marker is a nice-to-have, not required by this rule - add it only where doing so is cheap for the surface already reading the comment.
