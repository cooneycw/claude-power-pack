# `gh-pr-merge` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `gh-pr-merge`

- gh-pr-merge - layout-aware PR squash-merge used by `/flow:auto` + `/flow:merge`; polls mergeability to wait out a transient `UNKNOWN` right after push (#485); bounded refetch+retry when the squash fails on `Base branch was modified` (sibling merge race, #502); opt-in `--admin` flag plus a single admin-gated auto-retry when a squash is rejected by branch protection on an owner merge (#517)
- gh-pr-merge explicit admin retry opt-in (#1489 narrowing #517) - an administrative protection block no longer gets a silent `--admin` retry just because the actor is a repo admin; each invocation must opt in with `--admin` (admin from the first attempt) or `--allow-admin-retry`. Without either, the block is a failed merge (non-zero exit, "did not merge") and `--admin` is never invoked. The known caller relying on the old implicit default is `/flow:merge` (`.claude/commands/flow/merge.md` and its Codex mirror `codex/skills/flow-merge/reference.md`), which calls `scripts/gh-pr-merge.sh "$PR_NUMBER" "$BRANCH"` without admin-related flags. This PR does not change that call site: a human or orchestrator running `/flow:merge` who wants the old retry behavior must now pass `--allow-admin-retry` (or `--admin`) explicitly; silently reinstating it there would defeat this issue.
- gh-pr-merge `--admin` narrowing + required-check wait (#577, ADR 0004) - before the squash it resolves the BASE branch's required status-check contexts and polls the PR head until they are green (bounded, `GH_PR_MERGE_CHECK_ATTEMPTS` x `GH_PR_MERGE_CHECK_DELAY`); a red required check, and one that never reports, are hard stops. A required-check block is EXCLUDED from the #517 `--admin` auto-retry - auto-overriding it would defeat the required check on every run - while a review block (#517's actual case, and #579's) is unchanged; an explicit `--admin` from the caller still skips the wait, the documented break-glass
- gh-pr-merge required-context resolution reads BOTH protection mechanisms and believes only a 2xx (#610) - the #577 resolver read classic branch protection alone and discarded gh's exit code, so a 404 body (`{"message":"Branch not protected"...}`, which `gh api` prints on STDOUT with `--jq` unapplied) became a "required context" that could never report, and the wait timed out into a refusal. It fired both when a repo had no protection AND when `main` was guarded by a repository RULESET, which the legacy endpoint cannot see. Resolution now unions `/branches/{b}/protection/required_status_checks` with `/repos/{o}/{r}/rules/branches/{b}` and reports one of three states: `declared` (wait, exactly as #577), `none` (a source answered, nothing required -> skip the wait outright), `unresolved` (neither readable -> fall back to the checks the PR itself reports: green merges, RED is a hard stop, pending waits then FAILS OPEN). Enumeration failure no longer outranks observed reality, and the client-side wait is defence in depth - GitHub enforces a ruleset server-side at squash time, so a plain `gh pr merge --squash` cannot bypass the posture. Cost before the fix: 25 flow:auto runs, ~4h of wall-clock, every one worked around by hand
- gh-pr-merge review gate + exit-3 clean stop (#579) - a required human review is a handoff, never an automated bypass: before the squash the helper reads `reviewDecision` and on `REVIEW_REQUIRED`/`CHANGES_REQUESTED` exits 3 (a FIRST-CLASS CLEAN STOP: PR left open/current/green, message prints the PR URL + "approve or merge on GitHub, then /flow:merge"); a review-family rejection at squash time hits the same stop as belt-and-braces. This retires the #517 auto-`--admin` retry for review blocks - the retry survives only for the residual ADMINISTRATIVE family (protected-branch/push-authorization/base-branch-policy), so automation now bypasses neither a required check (#577) nor a required review; an explicit human-typed `--admin` remains the break-glass and skips both gates. Fail-open on an empty/unreadable `reviewDecision` (GitHub enforces server-side). `auto.md` Step 7 + `merge.md` document exit 3 as not-a-failure (leave worktree/branch intact, no cleanup, never self-escalate to `--admin`)
- gh-pr-merge explicit squash subject/body (#655) - the squash always passes `--subject "<PR title> (#N)" --body "<PR body>"` derived from the PR, because with no `--subject` GitHub may title the squash from the branch's FIRST commit and #635's commit-first discipline makes WIP-first branches routine (a 1045-line feature landed on main as "WIP: ..."); fail-open - an unreadable or empty title omits BOTH flags together and merges exactly as before, so the merge is never hostage to a metadata read; the #517 --admin retry inherits the flags via BASE_FLAGS
- gh-pr-merge deletion surfacing + post-merge completeness (#657) - a collapse onto a moved base (`reset --soft origin/main` + commit, the #655-thread workaround, now marked superseded) silently records deletions of a sibling's merged work with a conflict-free merge and honestly-green CI, so before the squash the helper prints `GH_PR_MERGE_DELETIONS: <n> <paths...>|0|skipped` (opt-in `GH_PR_MERGE_STRICT_DELETIONS=1` turns any deletion into a clean exit-4 pre-squash stop, PR untouched) and after a confirmed merge prints `GH_PR_MERGE_COMPLETENESS: ok|violation|skipped` (landed squash vs the PR's own file list; violation is loud but never flips the exit code - the merge landed); both fail open per component, all reads ref-scoped `git -C <root>` with full refs (never bare relative pathspecs, the #657 companion trap); honestly scoped: completeness catches base-race/squash contamination, NOT collapse damage inside the file list - that guard is the auto.md Step-6 safe-collapse recipe (merge-base target + staged-deletion check)
- gh-pr-merge tested-tree trailer (#716) - poker-measure's push-to-`main` pipeline re-runs the full suite on every squash because its shared 2-worker Woodpecker agent leaves effective PR-verification concurrency at roughly one (poker-measure#236); when this PR's branch was up to date with its base at squash time (`git merge-base --is-ancestor origin/<base> HEAD`), the squashed tree is provably identical to the PR head CI already tested, so the helper appends `Woodpecker-Tested-Tree: <sha1 of HEAD^{tree}>` to the squash body (via `--body` alone when the #655 title-derived path is empty). Deliberately NOT a boolean trailer - an unrelated commit's stray `Woodpecker-Skip-Full-Test: true` text would otherwise propagate into any squash body gh composes and silently skip a real full run; the tree hash is self-verifying, since the consumer recomputes the same hash locally on what it actually checked out and only skips on an exact match. Fail-open per component (unreadable base, unresolvable ancestry, or a branch behind base all omit the trailer - the push pipeline then runs the full suite, the safe default)
- gh-pr-merge Woodpecker queue-wait (#717) - the required-check poll's fixed 60-attempt window counts from when polling starts, not from when the pipeline is actually picked up, so a PR queued behind others on the same shared 2-worker Woodpecker agent burns the same budget as one that is genuinely stuck (measured: 8 of 8 poker-measure merges one night needed exactly one retry, a deterministic tax). GitHub's classic commit-status API - what Woodpecker posts as `ci/woodpecker/pr/woodpecker` - has no queued-vs-running distinction in its `state` field (only GitHub Check Runs expose that), so instead of trying to read that distinction off the rollup, the helper asks Woodpecker's OWN pipeline API: when `WOODPECKER_API_TOKEN` is set (the same credential `/flow:auto` Step 8 already uses for post-merge CI verification), it waits out a `pending` (queued) pipeline on its own bounded budget (`GH_PR_MERGE_QUEUE_WAIT_ATTEMPTS` x `GH_PR_MERGE_QUEUE_WAIT_DELAY`) before the existing check-poll budget starts counting. Entirely fail-open and additive: no token, no `curl`/`jq`, an unresolvable repo id, or no matching pipeline all fall straight through to the unchanged pre-#717 poll, and an explicit `--admin` skips the queue wait exactly as it already skips the required-check wait
- gh-pr-merge base-move guard across the required-check wait (#767) - snapshots the fetched `refs/remotes/origin/<base>` tip before the non-admin queue/check wait and re-fetches it after checks turn green; unchanged tips and moved tips already contained in `HEAD` proceed, while unreadable snapshots print `GH_PR_MERGE_BASE_MOVED: skipped` and fail open. A new base tip not contained in `HEAD` prints the old/new marker and exits 6 as a clean pre-review, pre-squash stop, leaving the PR untouched so the branch can be synced, re-gated, pushed, and merged again; `--allow-base-move` is the loud per-invocation override, and explicit `--admin` skips the guard with the waits
- gh-pr-merge negated close-keyword refusal (#726, #772) - GitHub's literal issue-linking matcher still auto-closes `#N` when close/fix/resolve prose is negated (for example, "does not close #N"), so immediately before either squash path the helper scans the assembled title and body, trims each keyword prefix at sentence and clause boundaries, and treats only an adjacent negation with at most two intervening alphabetic words as a clean exit-5 stop with the issue number and surrounding text printed, leaving the PR untouched; `--allow-negated-close` is the conscious per-merge escape hatch, but stays loud by printing the same detection plus an override-consumed audit line before proceeding
- gh-pr-merge incidental close-keyword refusal + commit-subject scan (#794) - GitHub matches close/fix/resolve + `#N` by proximity, ignoring grammar, so a keyword that is not negated but also is not a directive - an adjective ("...the resolved #N/topic finding"), or one governing a different noun ("closes #N's investigation...") - still closes on squash; #726's negation-only guard does not see either shape. `close_keyword_scan_sources()` now gathers title, body, AND every commit subject on the PR branch (`gh pr view --json commits`) into shared arrays both close-keyword guards scan, because the squash composes its message from the PR's own commits whenever neither `--subject` nor `--body` is supplied (#716) and GitHub's own closing-issue linking already reads every commit in the PR independently of that - a `git commit -m` typed inline is exactly as much a closing surface as the PR description. `guard_incidental_close_keywords` flags a match when `#N` is immediately followed by a possessive or slash-compound, OR the keyword is not clause-initial AND those preceding words are not a recognized adjacent negation (that exclusion keeps the two guards from both firing on one negated match under two different exit codes) - clean exit-7 stop, own `--allow-incidental-close` escape hatch, same loud-override-audit shape as #726. Before trusting a clean scan the guard runs `_incidental_close_selfcheck()` against fixed known-hit/known-miss inputs (issue number 0, which can never exist on GitHub, so the fixtures are inert even if ever echoed) and hard-exits 8 - never conflated with "no hazard found" - if the classifier's own answer ever changes; this immediately caught a real bug in development (`grep` sees zero lines, never a match regardless of anchors, on a zero-byte stream, so an empty prefix/suffix must be piped through `printf '%s\n'`, never bare `'%s'`)
- gh-pr-merge stacked-child retarget before branch deletion (poker-measure#405) - during the 2026-08-20 poker wave merge drain, squash-merging PR #375 through this helper deleted its branch and GitHub auto-closed open stacked PR #382, whose base was that branch, in the same second; the automatic retarget happens only in GitHub's web-UI merge flow, not through the API/CLI squash-and-delete path used here. Before any squash attempt, the helper now lists every open PR based on the parent branch, resolves the repo's real default branch, and runs `gh pr edit <child> --base <default>` before deletion can occur; the child's temporarily inflated diff self-corrects after the parent's squash lands because only its base pointer changed. It prints `GH_PR_MERGE_STACKED_RETARGET: <n> <PRs...>|0|skipped`; enumeration or default-branch lookup failure is `skipped`, and an individual edit failure warns while the remaining edits and merge continue, preserving the #610 fail-open posture
- gh-pr-merge (#1262) four corrections, each a place the helper spoke confidently about something it had not measured. (1) COMPLETENESS read `gh pr view --json files`, which stops at 100 entries silently, so a 150-file PR's paths 101-150 read as OUTSIDE its own file list - a false `violation`. It now reads the paginated REST listing and checks its length against `changedFiles`; a short listing is `skipped (file list incomplete: X of Y)`, because an incomplete population cannot convict a landed path. (2) An ALREADY-MERGED PR hit `GH_PR_MERGE_BASE_STALE` forever - a squash puts the work on the base under a new sha, so the branch never contains its own landed commit - and the printed remedy sent the caller round a merge-and-re-gate loop on a closed PR (seen four times in thirty minutes). The PR's state is now read first; MERGED prints `GH_PR_MERGE_ALREADY_MERGED: <n>`, skips every guard and the squash, and runs only the post-merge tail (now the `finish_merged` function, so both paths run one implementation). (3) BASE_STALE names the directory, the HEAD sha and the base tip it compared, so "invoked from the wrong checkout" is self-diagnosing. (4) EXIT 9: a worktree on this host holding the PR's head branch at a sha other than the PR head is a clean stop - GitHub's BEHIND+green cannot tell an abandoned PR from one a session is mid-finish on, and merging then lands the stale head. It sees this host only; `--allow-local-divergence` is the override
- gh-pr-merge (#1300) A WAIT THAT RAN OUT IS ITS OWN VERDICT, AND THE BASE IS RE-READ AT THE SQUASH. CI here takes 15-20 minutes and the required-check wait was a fixed 60 x 10s; on expiry it printed "never reported" and exited 1 - the same code as a red check or a failed merge, and the wrong words for a pipeline that was visibly running. Expiry is now exit 10 (CLEAN STOP, never a merge) in every declared path, naming contexts still RUNNING apart from any that never POSTED a status; `--wait-ci[=SECS]` (bare: 1800; it never consumes the next argument, since the PR number is numeric too) makes the wait a deadline, read through `GH_PR_MERGE_CLOCK` so tests drive it without sleeping; `GH_PR_MERGE_CI_WAIT: green|red|expired (<budget>)|none-required|none-observed|observed-fail-open` reports every wait (an empty observed rollup is `none-observed`, never `green`). The #610 observed path keeps its deliberate fail-open. The base is re-read IMMEDIATELY before `run_squash` (`GH_PR_MERGE_BASE_AT_SQUASH`), because the post-wait read was followed by several network reads in which a sibling merge could land; and the #502 "Base branch was modified" retry now re-checks that the branch CONTAINS the new tip immediately before squashing again (after its sleep and re-poll) - it used to retry after a refetch alone, landing a tree nobody gated, which defeated #767. No auto update-branch (a CI-budget decision the caller owns) and no merge queue. Caller audit: `/flow:merge` and `/flow:auto` Step 7 are the only surfaces that branch on the exit code; both document 10 (and merge.md gained the 9 that #1262 had documented only in auto.md)
- gh-pr-merge cross-repo closing keyword (#1412) - both close-keyword guards' shared `keyword_re` matched only a bare `#N`, so GitHub's cross-repo syntax `owner/repo#N` matched NOTHING: "Does not close cooneycw/kyle#99" was invisible to the #726 negated-close guard, and the merge proceeded, silently closing a DIFFERENT repository's issue on merge despite the disclaimer - the exact #726 hazard, just unreachable by the regex rather than defeated by negation. Both guards' `keyword_re` now accept an optional `(?:[\w.-]+/[\w.-]+)?` repo qualifier before `#`; the trailing `${match##*#}` issue-number extraction is unaffected (it strips to the last `#` regardless of what precedes it), so no other guard logic changed. A plain (non-negated, non-incidental) cross-repo directive still merges normally.
- gh-pr-merge base-move exit-6 message (#1412) - the literal ask ("tell a genuinely moved base from ordinary churn on a busy repo") was DECLINED after measuring, not guessed at: merging PR #1417 was itself refused by GitHub with "the head branch is not up to date with the base branch", so CPP main's own branch protection already enforces the up-to-date rule the guard exists to anticipate - relaxing exit 6 for a disjoint (non-overlapping) base advance would only move the identical refusal from this helper to the server, with a worse message. The ancestry check (#767/#1300) is unchanged and still the sole determinant of the exit code. What changed is legibility: a new shared `_report_base_advance()` prints the old/new tip, the commit count and one-line subjects of what moved, and - INFORMATIONAL ONLY, never altering the exit - whether any of those commits touch a file this PR's own branch also changes, before the existing remedy (fetch + merge the base, re-run). Tested in isolation against a real git repo (`_report_base_advance` extracted from the script text and sourced directly), since the rest of this file's tests drive a fully synthetic git/gh stub with no real commit graph to diff against.
