# `project-next-ownership` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `project-next-ownership`

- project-next-ownership - CPP's ownership pin for the project-next engine (#1069), succeeding `project-next-vendor` when CPP took the engine over from codex-power-pack. The question changed with the ownership: the retired gate asked "does our copy match what upstream published", and after the transfer there is no upstream to be correct against - CxPP goes private and dormant, and `lib/vendor.py` carries no auth to reach it afterwards. This gate asks instead whether the engine can change WITHOUT its `contract_version` changing, which is the consumer-facing pin: it validates `.project-next.json` through `templates/project-next.schema.json`, it is the runtime pin `/project:next` reads, and it is rendered into every report as `decision policy: contract v<N> (project-next engine)`
- project-next-ownership `check` is a stdlib-only, git-free, network-free hard gate (`make project-next-check`) over 11 pinned paths, hashing each separately so a failure names the exact file. `--repin` recomputes the pins after a deliberate engine change (`make project-next-repin`) and refuses when no contract version can be read; it now shells out to git (#1398, see below) - a developer/session-time operation only, since CI never passes `--repin`. `--root DIR` aims it at another tree, which is what makes a committed control case possible
- project-next-ownership `--repin`'s baseline is the manifest as committed at `merge-base(HEAD, origin/main)`, not the working tree's own current file (#1398). Before the fix, a branch's FIRST repin already advanced the working-tree manifest to the new version and hashes, so a SECOND repin on the same branch compared the engine against itself and was refused as "N engine module(s) changed while ... still states contract version ..." even though the branch's version genuinely differs from origin/main - reproduced and confirmed red pre-fix. An unresolvable `origin/main` REFUSES rather than silently falling back (the same "unknown is not agreement" rule the unreadable-baseline guard already followed); `--baseline <ref>` is the explicit override for a shallow clone, a detached checkout, or CI. A `--root` fixture carrying no git history at all (the committed control, the pre-existing offline tests) falls back to reading the working-tree file directly - there is no branch history to find a shared ancestor in, and that file is the only baseline such a fixture can supply
- project-next-ownership carries three invariants beyond the per-file hash, each with its own failure message: the manifest's key set is checked against the HARDCODED contract before any hash is compared (so a dropped pin is refused rather than read as one fewer thing to check), an unpinned `.py` module inside `lib/project_next` is reported (so the package cannot grow a file no version bump accounts for), and the contract version is DERIVED from `docs/project-next-contract.md` and compared with the manifest rather than trusted from it (so re-pinning an edited engine cannot quietly keep the old version)
- project-next-ownership had three defects found by the #1069 POST-MERGE counter-model review (codex/gpt-6-astra), which ran only because the Step 6 review had been skipped on that issue. Two were in this gate and both made it report clean over exactly what it exists to catch. (1) `--repin` recomputed every hash and re-derived the version from the contract document, so editing the engine and re-pinning succeeded at the SAME version - the module docstring claimed that was refused and nothing implemented it. The guard now compares against the manifest as recorded BEFORE the re-pin and refuses when an engine module's hash moved while the derived version did not; it is scoped to `lib/project_next/**` deliberately, because the contract document is where the version lives and a schema or LICENSE repair should not demand a behaviour-version bump. (2) the unpinned-module scan was `glob("*.py")`, immediate children only, so `lib/project_next/rank/__init__.py` left all eleven pins byte-identical while Python resolved the PACKAGE ahead of the pinned `rank.py` - the scan is now recursive. Neither was catchable by a committed case: one is a TRANSITION and the other a nested tree, and a case carries one state
- project-next-ownership registers its committed control at `controls/project-next-ownership`, which holds two 11-path fixture trees plus a constructed blind anchor. The anchor is the plausible weaker check - confirm every pinned path is PRESENT and call that owned - which catches a deleted file and is blind to one edited in place; it misses the known-bad case and agrees on the known-good one. The cases are NOT the retired control's, edited: those encode the upstream-fidelity question and this gate asks a different one, so they were rebuilt. Their content is placeholder bytes, except that the contract document must carry a derivable version line or the good case fails on the version path instead of passing on the hash path
