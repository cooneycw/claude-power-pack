# `maintain-loop-indicator` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `maintain-loop-indicator` (#1085)

- maintain-loop-indicator - reports whether findings this repository already records are reaching the backlog, and how fast, from data CPP already writes: the Nit Store and `.claude/friction.jsonl`. It is a REPORTER, not a gate - #1085's words, "this issue produces a number a person reads" - so no build surface invokes it and `make verify` does not run it. A gate would have to decide whether the number is acceptable, which is a BAND, and #1085 defers the first threshold to ADR 0009
- maintain-loop-indicator THE PARTITION IS THE METRIC, not a number with a denominator attached. It reports `attributable` (a finding whose filing event can be identified), `excluded` (explicitly dismissed - not a finding that took forever), and `UNDETERMINED`, and the median delay is computed over the attributable subset ONLY. On the real population that subset is a minority, so a median presented as the headline with the partition beneath it would claim more than the input supports. UNDETERMINED is never folded into the denominator and never renders as zero
- maintain-loop-indicator THREE INPUT STATES, NOT TWO, and the distinction is the whole acceptance. A capture that PARSES and declares its lists - even as `[]` - is an OBSERVED empty population and reports zero. A ZERO-BYTE file is what a failed `gh ... > capture.json` leaves behind and is UNKNOWN; so are unparseable JSON and a document that never declares a population. #1085: "a broken extractor's zeros look exactly like real ones, and this is a measurement whose whole purpose is to be believed later by someone who did not watch it run"
- maintain-loop-indicator THE FRICTION LEDGER IS IN THE POPULATION AND UNDETERMINED BY CONSTRUCTION. Measured across every record, its keys carry no filing linkage - `run` names the issue the RUN was about, not what the finding became. Matching on signal text would be inference dressed as measurement. Leaving it OUT of the population instead would shrink the denominator and make the attributable share look better than the repository's record-keeping supports
- maintain-loop-indicator AN INVERTED PAIR IS ITS OWN NAMED CATEGORY - not in the median, not undetermined, not silently dropped. A citing issue created BEFORE the finding is a REFERENCE to existing work rather than a filing event, so folding it in biases the median with a number that is not a delay. Measured on the real capture: exactly one, at MINUS NINE SECONDS, which is the ordinary "file the issue, then record the nit" order. That is why it is a category and not a refusal - refusing would red on an everyday workflow, and separating an ordinary inversion from a faulty one needs a threshold, which is a band
- maintain-loop-indicator ITS CONTROL IS THE FIRST REGISTERED `subject_kind: reporter` (#1204, #1207) and declares NO `detect_signal`. A reporter has no finding to mark, so every pattern it could declare is dishonest: one that matches its own measurement output, or one that can never match. The marker requirement is carried by `unknown_signal` instead. THE ANCHOR TEACHES THE SAME THING FROM THE OTHER SIDE - A BLIND INSTRUMENT DOES NOT REFUSE, because refusing is the capability it lacks. An earlier anchor exited 2 with an unmarked "no capture to read" and the harness correctly reported it could not tell that from a crash; it now answers every unreadable input with a confident `0 finding(s) recorded`, which is this gate's own thesis turned into a fixture
- maintain-loop-indicator THE STORE IS RESOLVED, NOT A CONSTANT (#1673). It held `NIT_STORE = 864`; after a monthly rollover `--capture` would have kept reading the closed predecessor, a capture that parses and has silently stopped growing. `--capture` now asks `nit-store-resolve.sh` for the current store and is UNKNOWN, writing nothing, when the resolver does not answer `ok` - it never falls back to a remembered number. `--nit-store N` names a store explicitly, which is how a closed predecessor is still read. A capture covers ONE store; a delay series across a rollover is two captures
