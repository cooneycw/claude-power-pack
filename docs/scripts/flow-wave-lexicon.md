## `flow-wave-lexicon`

- flow-wave-lexicon - reserved vocabulary for wave STATE TRANSITIONS (#701), the transitions half of #699's declared state and the fourth sibling in the wave dir (#638 says who, #676 says it arrived, #699 says the rules, this says what a message DOES). The wave protocol was strict machine-to-machine and free prose agent-to-agent, and every miscommunication in the 2026-08-11 reference wave happened in the prose layer while `FLOW_WAVE:` markers never once misfired: a LANE grant read as a GATE approval (an unjudged gate stopped only by a worker's caution), a lane FENCE read as its own inverse, four state broadcasts accurate when composed and wrong when read, a merge predicate retyped ad hoc four times. Tokens cover ONLY transitions with a wrong-answer cost - `GATE: GO|HOLD|GO-WITH-CONDITIONS #N`, `LANE: GRANT|SET|REVOKE <role> <paths>` (`EXTEND` is refused BY NAME, #1026: the registry's `--files` REPLACES a lane, so the token named the inverse of the mechanism and a role re-registered on one silently dropped every path the new list omitted), `MERGE: AUTHORIZED #N when <named check>`, `STATE: as-of <commit>`, `RATIFY`/`OVERRULE`, `PUSHBACK`, `LEDGER` - line-anchored (the #607 rule, so a mention is never a declaration) and each requirement traceable to a specific failure. **Quoting is not issuing (#980):** a token at column 0 outside a fence ISSUES; one inside a ``` / `~~~` fence or behind a `>` prefix is a CITATION - inert, and REPORTED (`FLOW_LEXICON_CITATIONS=<n>` plus a `FLOW_LEXICON_CITATION=` line per token, surfaced by `send` on a successful delivery, since inert and dropped otherwise look identical); one merely INDENTED is REFUSED as ambiguous, naming both remedies, because reading it as cited would silently drop a transition typed with a stray leading space and a dropped `GATE: HOLD` fails OPEN. Before this a draft written to WITHDRAW a merge authorisation parsed as a fresh `MERGE: AUTHORIZED #243` under the predicate being withdrawn, and a quoted `GATE: HOLD` blocked the planner on a phantom hold whose recorded reason was the quoted text; the reasoning stays prose by design, since the reference wave's highest-value messages were a worker's design rulings and its catch of the crossed lane/gate message, none of which survive schematisation. **The anti-decoration contract** (the issue's own kill condition - a reflexive `GATE: GO` prints what a considered one prints): two readers, both load-bearing. `flow-wave-mailbox.sh send` validates every body, so a malformed transition cannot be DELIVERED (exit 6, `refused`, box untouched) - while a message with NO token always delivers and a missing/broken validator FAILS OPEN, since a wave stalling on its own linter is the #676 failure in a different hat; and `record` DERIVES the #645 ledger entry from the parsed `GATE:` token (ruling, `holds_behind`, `serializes:` -> `adds_serialized`) instead of accepting a hand-written one, so a gate cannot be recorded as judged without a parseable verdict. Because `flow-wave-plan.py --verdicts` exits 4 on an unsuperseded hold and unions `adds_serialized` into `serialized_resources`, an unparseable verdict changes PLANNER OUTPUT rather than a log line - pinned by tests that run the real planner twice and assert the two results differ, plus two mutation checks measured on the suite as it stands: a refuse-nothing validator turns 34 of 95 tests red, and an over-wide skip that reads every column-0 token as a citation turns 58 red (the #980 fail-open direction). Both were re-measured for #980 - the prior 23-of-49 figure described a suite that no longer exists, which is what a count written in prose does from the next appended test onward; re-measure these rather than adjust them
- flow-wave-lexicon `MERGE: PRIORITY #N <argument>` (#989) - #N merges before every other open PR in the wave. Under branch protection `strict: true` a PR must be up to date with base to merge, so every merge invalidates every other open PR; `main` is a serialized resource and the PR with the longest verify keeps losing its place: #982 was overtaken four times in one wave, each time after a full green run, burning four suite runs on rebases that changed not one line of its diff. The remedy that worked was a merge hold declared in PROSE, which means it was unvalidated, absent from `verdicts.json`, and invisible to the planner. The token is that remedy as a transition. The verb is `PRIORITY` so that #N denotes the same referent as in `MERGE: AUTHORIZED #N`; `HOLD`, `BLOCK` and `FREEZE` are refused BY NAME because each reads as its own inverse. `record` does not write it to the ledger, which holds GATE rulings only
- flow-wave-lexicon issueless subjects, and a HOLD must state why (#1189) - a GATE verdict may name a lowercase kebab slug of at least two parts (`journal-false-red`) for work that deliberately has no issue; a bare number and a single word are refused. A HOLD is the one verdict that keeps an issue out of the assignment pool for every LATER session, and before this it was also the one with no guard on its reason: GO-WITH-CONDITIONS refuses an empty harvest and `MERGE: PRIORITY` refuses a missing argument, but a HOLD whose argument was typed as prose beneath the token was stored as `GATE: HOLD (no reason given)` while `record` printed success. The enforcement survived and the argument did not, so a successor inherited an unexplained standing hold with no way to tell a terse ruling from a misplaced one. A HOLD now needs its reason on the token line or as `- ` lines beneath it. A slug ruling is recorded under a `subject` key, which `flow-wave-plan.py` reads and ignores for planning (#1223)
- flow-wave-lexicon a HOLD cannot be held behind itself (#1403) - the behind-list scan cannot tell the last real blocker from the first word of a reason that happens to start with `#N`, so a HOLD reason beginning with an issue reference gets that reference silently absorbed into the blocker list. Observed 2026-09-15: `GATE: HOLD #208 behind #194 #208's own body declares "Parent: #194 ..."` recorded holds_behind:[194,208] - #208 held behind itself, which can never be satisfied, and neither `validate` nor `record` flagged it. The subject's own issue in its `behind` list is now refused, naming the `--` separator; a reason that starts with a DIFFERENT issue reference remains a declared, unfixed gap
- flow-wave-lexicon the citation skip carries its reversal trigger (#936, ADR 0009) - reading a fenced or `>`-quoted token as a citation (#980) is a two-sided change whose other side's pain is a DROPPED transition, so the trigger is committed in the script header beside the grammar rather than left to a later judgement: if a wave ever loses a real transition because its author fenced or blockquoted a line they meant to issue, AND the `FLOW_LEXICON_CITATION=` report did not stop them, move the fenced and quoted contexts to REFUSE as well
- flow-wave-lexicon no subprocess in the LEDGER and vague-predicate checks (ci-concurrency) - `has_section` was `printf '%s\n' "$block" | grep -Eq "..." || missing="$missing $sect"`, three forks per LEDGER token. `grep` reports "no match" with exit 1 - and a `grep` that CANNOT BE STARTED also exits non-zero. Under load the two are the same answer, so the `||` fired and a section that was plainly present was reported missing. Measured in CI on 2026-09-23: pipelines 2504 (push) and 2505 (pull_request) built the SAME commit, their `validate` steps started in the SAME SECOND on a single agent running WOODPECKER_MAX_WORKFLOWS=2, and 2505 failed with `LEDGER is missing section(s): delivered` on a body that contained it. Reproduced exactly with a `grep` shim that fails to exec on its Nth call: fail call 1 -> "delivered", call 2 -> "in-scope", call 3 -> "residual". ONE section, never three, which is what distinguishes a failed fork from a truncated body and is how the mechanism was found. The vague-predicate check in `parse_merge` was the SAME CONFLATION AS parse_ledger, POINTING THE OTHER WAY. This was `bare="$(lower "$pred")"` plus `[ -z "$bare" ] || printf '%s' "$bare" | grep -Eqx "$VAGUE_PREDICATES"`, and the two forks fail in OPPOSITE directions: `grep` cannot run -> the pipeline exits non-zero -> the OR is false -> the `if` does NOT fire -> A VAGUE PREDICATE IS ACCEPTED (false negative: the guard silently stops guarding under load); `tr` cannot run -> `bare` is empty -> `[ -z "$bare" ]` is TRUE -> the error FIRES -> a perfectly specific predicate is called vague (false positive, from the same root, in the same statement). One defect, two directions, which is why it was fixed together with the `parse_ledger` site rather than after it (the script comment said "fixed with :759", a line number that has since drifted): fixing either alone leaves the other, and the two are harder to recognise as one thing once they are no longer adjacent in a diff. Both sites now use bash `=~` and `${x,,[A-Z]}` with no process to start. The `[A-Z]` range is load-bearing (counter-model review): bash's unrestricted `${x,,}` is LOCALE-AWARE and folds beyond ASCII, while `tr '[:upper:]' '[:lower:]'` does not. Measured under LC_ALL=C.utf8 on `DELIVERED` spelled with U+0130 (dotted capital I): tr yields `del\u0130vered`, `${x,,}` yields `delivered`. End to end that flipped a body from `invalid` to `ok` - a silent change in WHICH ledgers validate, from a change that was supposed to swap the engine and not the meaning. The 17-spelling pin did not catch this because every spelling in it was ASCII; the pin was sound and its POPULATION was too narrow
- flow-wave-lexicon `LANE: EXTEND` in the field (#1026) - the token names the INVERSE of the registry mechanism (`--files` REPLACES a lane), so a sender who reads it as written produces the opposite of what they intend. It fired twice in one day, the second time by an orchestrator who had reported the first occurrence two hours earlier, which is why `EXTEND` is refused BY NAME with a message naming the mechanism rather than left to the unknown-verb arm
