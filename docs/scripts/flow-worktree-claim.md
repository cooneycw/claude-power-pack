# `flow-worktree-claim` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `flow-worktree-claim`

- flow-worktree-claim - cross-session OWNERSHIP claim on a flow worktree (#597), the half #503 could not cover: the live-driver guard protects a session ENTERING a worktree, but nothing protected an active worktree from being REMOVED by a sibling session, whose Step-7 cleanup deleted an issue-N checkout by name and destroyed uncommitted work with no signal but the user noticing. Rides git's own `git worktree lock --reason "flow-claim issue=N pid=... session=... host=... ts=..."`, so the claim is a real barrier (`git worktree remove --force` refuses a locked worktree) rather than an advisory note, and is readable from `git worktree list --porcelain`. `claim`/`check`/`release` verbs; ownership is pid + session, liveness is `kill -0` trusted only when the recorded host matches, and a claim whose owner is gone is STALE and auto-taken-over so the mechanism can never wedge a repo. A lock this family did not write is FOREIGN and never stolen. Staked in `flow-start-resolve.sh --verify` - the hook point running INSIDE the worktree on every lane - and read by resolve mode via `check --issue N` BEFORE any worktree is created, so two sessions handed the same issue stop instead of racing. Fail-open everywhere except the case it exists for: claiming against a live owner exits 1
- flow-worktree-claim pid-IDENTITY witness (#1032) - liveness was `kill -0 <pid>`, which answers "some process has this number", not "the owning session is alive". Linux recycles pids - the space wraps in hours on a busy host - so a dead session's claim read HELD forever, and `FLOW_CLAIM_MAX_AGE_HOURS` aged out only claims from ANOTHER host, so a same-host claim on a recycled pid had no bound at all. That fails in the UNSAFE direction: the reading that BLOCKS recovery, leaving `--steal` - the override meaning "I am overriding a genuinely live owner" - as the only way to clean up after a dead one, at which point the safe path and the deliberate override are the same flag. The claim now records `start=<ticks>`, field 22 of `/proc/<pid>/stat`: a pid can be reused, a pid paired with its start instant cannot. `FLOW_CLAIM_OWNER_WITNESS` reports HOW liveness was decided - `matched` (alive, decisive), `mismatched` (the pid exists but is a DIFFERENT process -> stale, the reading that fixes this), `absent`/`unreadable` (identity could not be established). The witness may only DEMOTE on a positively read CONFLICTING value; an unreadable one never yields `stale`, because a check that cannot read identity has not disproved it. The age bound now applies to any claim whose identity could NOT be established, same-host included, so nothing can wedge a repo permanently - and NOT to a matching witness, so a session legitimately working one worktree for days is never evicted by the clock. That asymmetry is what makes the threshold change one-sided: the case that would argue for moving it back cannot occur, and `test_a_verified_owner_is_never_aged_out` pins it. Field 22 is read by consuming through the LAST `') '` rather than splitting the line, because `comm` is process-controlled and may contain spaces - measured on this host, a process named `npm exec tavily` yields 11 from `awk '{print $22}'` and the true start-time from this extraction. `FLOW_CLAIM_PROC_ROOT` is the test seam making both witness lanes reachable on a host whose /proc works. Sibling gap, deliberately NOT widened into here: `flow-wave-registry.sh` liveness is pid-identity-blind the same way, and #1033 item 3 owns it by name
- flow-worktree-claim owner of a Codex session, and what state `Z` proves (#1709) - three changes, each of which moves a claim from `stale` to `held` and none of which moves one the other way. (1) In a Codex session (`CLAUDE_PID` unset, `CODEX_THREAD_ID` set) the claim names the nearest ancestor process called exactly `codex`. It used to name `$PPID`, which there is a tool shell that exits with the command, so a working session's claim read `stale` to everyone else a moment after it was written. The match is by name and not "the first ancestor that is not a shell": a walk that stopped at a login shell would hold the worktree for days after its owner left. A miss records `$PPID` exactly as before. (2) The session field falls back to `CODEX_THREAD_ID`, so the session's own later commands read the claim as `self`; Claude's id wins when both are set. (3) State `Z` in `/proc/<pid>/stat` counts as a dead owner only when the thread count (field 20) is 1 or unreadable. A process whose main thread has exited while other threads still run also reads `Z`, and before this it was called `stale` (owner-zombie) although it could still write to the worktree - the direction that loses work. Measured on a real process: state `Z`, 2 threads, `kill -0` succeeds. `tests/test_flow_worktree_claim_owner.py::test_no_scenario_moves_towards_stale` runs 1,215 combinations of what the classifier reads through the helper before and after and asserts that nothing the old helper called held, foreign or unknown is called stale now. KNOWN OVER-HOLD: where one long-lived `codex app-server` hosts several threads and is the nearest `codex` ancestor, a claim outlives its thread and reads `held` until the server exits. That blocks cleanup and loses no work. Clear it, once you are certain the thread is finished, with `flow-worktree-claim.sh release <worktree> --force` or `worktree-remove.sh <worktree> --steal`. The zombie-owner report of 2026-11-11 (a zombie read as `held`) was reproduced against the real zombie with both copies: this helper reads it `stale`, the copy at `85e9b03a` reads it `held`; that report came from a checkout pinned before #1635
- flow-worktree-claim, two findings from the counter-model review of #1709, both in the direction that loses work. (1) Once a Codex caller's pid resolves to the `codex` process, the older rule "same pid and the claim names no session means it is mine" would have called a session-less claim on a shared Codex server `self` for every thread that server hosts, and `self` makes `worktree-remove.sh` drop the claim and skip its in-use check. A pid found by the ancestor walk can name several sessions, so it no longer satisfies that rule alone; a Claude session's pid names one and still does. (2) `claim` and `release` each read the lock, decide, then unlock, and between the read and the unlock another session could take a stale claim over, so the unlock removed the NEW owner's lock. Both verbs now run their read-decide-write under one mutex per repository (`flock` on `flow-claim.mutex` in the common git dir, 10 second wait, held until exit), and `release` re-reads the lock immediately before unlocking and stands down if it is not the lock it judged; `check` takes nothing. A second review pass tightened both: a verb that finds the mutex held past the wait (`FLOW_CLAIM_MUTEX_WAIT`, default 10 seconds) now STANDS DOWN, reporting what it sees and changing nothing, because proceeding there is the race with a witness; and every unlock in `claim` (stale takeover, self refresh, `--steal`) re-reads the lock first, as `release` does. KNOWN RESIDUAL: on a host with no `flock` at all the verbs still run unserialized, and the re-read narrows the window to the instant between that read and the unlock without closing it. Standing down there too would leave such a host unable to release even its own claim. `release --force` is unconditional by design `tests/test_flow_worktree_claim_owner.py` poses the interleaving with a `git` wrapper, with and without `flock`
- flow-worktree-claim, what a reader of its output can now see that it could not (#1709; coordination issues kyle #2361, skillc #706, kyle-candidate #9). No verdict word, stale-reason word or exit code is new. Two existing words appear in new positions when a writer STANDS DOWN (the mutex was held past the wait, or the lock changed under it on a host without `flock`): `claim` can end `FLOW_CLAIM: stale` or `FLOW_CLAIM: free` with exit 0 having claimed nothing, where it could only end self, held, foreign, unsupported or unknown; and `release` can end `stale` or `self` with the lock untouched, where it ended `free`. `flow-start-resolve.sh --verify` passes the first through as `CLAIM=stale` or `CLAIM=free`; the claim is advisory there and never a precondition. `worktree-remove.sh` discards `release`'s output and then asks git to remove the worktree, which git refuses while it is locked. Also: for a Codex session `CLAIM_PID` is the `codex` process and `CLAIM_SESSION` the thread id, where they were the tool shell's pid and `-`. The mutex descriptor is closed for every git child, because a flock belongs to the open file and a background child that inherited it (`git gc --auto`, an fsmonitor daemon, a hook) would hold the mutex after the helper exited, leaving every later claim and release to wait out its timer and stand down. `FLOW_CLAIM_MUTEX_WAIT` that is empty or not a number falls back to 10
