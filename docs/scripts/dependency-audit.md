# `dependency-audit` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `dependency-audit` (#961)

- dependency-audit - the repository's own gate over its own locked dependency sets (#961). CPP ran no dependency audit at all: both sets of advisories it carried were found by a person looking - #922 on the root lock ("tracked by no issue") and #943 on `mcp-evaluate` - which is a practice, not a gate. Both are resolved: #922 upgraded the root lock, #943 retired the `mcp-evaluate/` subproject outright. `lib/security/modules/pip_audit.py` is NOT that gate and is not replaced by it: that adapter runs only inside `/security:scan` (`scan_full` / `scan_deep`), appends to `skipped` when the binary is absent, and reads `requirements.txt`, a file CPP does not have - so with pip-audit installed it audits the ambient environment rather than this project's lock, and `lib.security gate` runs the quick scan, which never reaches it (ADR 0008 row 61)
- dependency-audit inherits ADR 0008's third-party-tool shape verbatim from `shellcheck` (#960), which that ADR states is the shape #961 and #962 take. The lock population is DERIVED by walking the tree with a declared prune list, never globbed or hardcoded, and the run prints `source=walk` (or `source=capture`). The denominator - files examined, packages examined - prints on EVERY run including the clean one, because `0 findings` means nothing beside an unstated number of files, and a zero-file population is UNKNOWN rather than clean
- dependency-audit posture, decided rather than defaulted because #961 asks for it explicitly: a gating finding exits 1, a stale suppression exits 1, and UNKNOWN exits 2 - pip-audit unreachable, `uv` absent, the advisory feed down, a zero-file population, or an unreadable allowlist. **Unknown is never a pass**, the same rule the shellcheck gate holds for a missing binary, and the two outcomes are distinguishable in the output by construction: `dependency-audit: ok - ...` is a statement about the dependency set, `DEP-AUDIT-UNKNOWN: ...` is a statement about this run. The tempting `command -v pip-audit || exit 0` goes green on every machine lacking the tool, which is the dormant-instrument failure ADR 0008 exists to prevent and which the `lib/security` adapter already demonstrates one door down
- dependency-audit residual lives in `.dependency-audit-allow`, tracked and printed. ADR 0008 requires suppressions to be visible or not happen - a disabled check is invisible, a filed issue is not - so each line is `advisory <path> <package> <version> <advisory-id> <issue>` (one finding, pinned to the exact version, so a bump or a NEW advisory does not match) or `deferred <path> <issue>` (one file, while an issue owns its whole dependency set). Today: NO lines at all. The ledger carried exactly one, a `deferred` for `mcp-evaluate/uv.lock` (#943), deferred rather than enumerated because a gate that blocks every pull request on day one is one that gets switched off, and switching it off is itself an oscillation (ADR 0009). It came out when #943 retired the subproject on 2026-09-19 - not by anyone remembering, but because the gate reports a line that accounts for nothing as `DEP-AUDIT-STALE` and reddened until it was removed, which is the second time that rule has fired on a change its author did not make. An empty ledger is still PRINTED as a count on every run, so it reads as examined rather than as absent. The root lock's two advisories were suppressed here while this gate was written and are gone: #922 landed mid-review and upgraded both packages, the gate reported both lines STALE, and they were removed - the rule doing its work on its first real occasion, against a change made by someone else. `docs/security/dependency-advisory-dispositions.md` (#922) is the companion, not a replacement: it records per advisory id WHY this repository is or is not exposed, while the ledger records WHICH findings the gate is not failing on, and a disposition of "not exposed" is a reason to write a ledger line rather than a substitute for one. Whole-line comments only: `#` also opens every issue reference, and `line.split("#")[0]` silently ate the `#922` off the first record written against this gate
- dependency-audit treats an allowlist line that accounts for NOTHING as a RED (`DEP-AUDIT-STALE:`), not a quiet no-op. That is the direction that keeps the residual honest: without it a suppression outlives the advisory it records and becomes a permanent blindfold nobody re-reads, and it is what forces this repository's own two lines out when #922 lands. The other side is NOT solved - nothing here stops the list growing - and that is named rather than hidden
- dependency-audit `--all-extras` is load-bearing on `uv export`, and `--frozen` is load-bearing in the other direction. The default export omits dev dependencies, where BOTH root-lock advisories live, so the narrower export reports the tree clean while it carries two known advisories; without `--frozen`, `uv export` may re-resolve and REWRITE `uv.lock`, and an instrument that mutates the tree it measures is not an instrument
- dependency-audit has three inputs because a control must be valid where the harness runs (ADR 0008). LIVE (default) walks and audits, needing `uv`, pip-audit and the network. `--from-capture` replays a committed capture of pip-audit's own JSON - stdlib-only, offline - and is what `controls/dependency-audit` exercises, the same move `controls/check-oscillation` makes by feeding its detector committed `git log` captures because git is absent from the CI image; a control reaching the network would report UNSIGNALLED on a blip, an environment failure wearing the diagnosis "the gate stopped discriminating". `--selftest` covers the half replay cannot - that pip-audit is invoked, and against the file we meant - by auditing a 2019 PyYAML pin that must report and a clean pin that must not, and the CI step runs it BEFORE the real audit so no clean verdict is issued by a scan never shown able to find something. Neither half is sufficient alone
- dependency-audit refuses to count a SKIPPED dependency as an audited one (counter-model review of #961, HIGH). pip-audit emits `{"name": ..., "skip_reason": ...}` for a record it could not resolve - a package absent from the advisory service, an editable or local install - with no `version` and no `vulns`, which reads exactly like a package audited and found clean. Measured on the first cut: a report containing one skipped dependency and nothing else produced `ok - ... 1 package(s), 0 gating finding(s)` and exit 0. It is UNKNOWN now, with the package and the reason printed, because unlike a platform exclusion this is not a decision anyone made - it is the audit failing on part of its own population
- dependency-audit states the PLATFORM on every verdict and NAMES what the audit never reached. pip-audit resolves environment markers against the host it runs on, so `colorama==0.4.6 ; sys_platform == 'win32'` is dropped before the advisory lookup and never appears in the report; measured 2026-09-16, a two-line file pinning that colorama and `six` came back with `six` alone, and both CPP locks carry such entries (5 in total, including `pywin32==311`). The narrow answer is deliberate - CPP's CI is Linux and a lane per environment is a different ticket - so the claim is BOUNDED rather than widened: every dropped requirement line is printed by name, the count appears in the summary, and `platform=` appears on clean runs too. `--all-groups` accompanies `--all-extras` on the export for the same reason one level over: extras and PEP 735 dependency groups are different namespaces, and CPP declares no groups today, so the omission would have surfaced only when someone added the first one
- dependency-audit keeps UNVERIFIED apart from STALE, and the two carry different exit codes (counter-model review pass 2). A suppression for a Windows-only package is never matched by a Linux audit, so collapsing them made the gate exit 1 and tell the reader to REMOVE a legitimate suppression on the strength of a run that never looked at its package - a guard firing on a window rather than a cause. "The advisory is gone" (stale, exit 1, remove the line) and "this run could not see it" (unverified, exit 0, keep the line) need opposite responses. The distinction is bounded rather than an amnesty: an entry for a package the audit DID reach, with no matching advisory, is stale exactly as before, and `test_a_residual_this_platform_DID_audit_is_still_stale` is what stops `unverified` widening into one
- dependency-audit coverage is keyed on `(package, version)`, never the package name, and `--selftest` proves it EXAMINED its fixtures before reading a verdict off them. Both were pass-1 fixes that reintroduced the pass-1 defect through a different door: a lock pinning two conditional versions of one package had the unaudited line vanish from the coverage report, and a pip-audit returning `{"dependencies": []}` for the clean fixture passed the positive control and printed its success message. A skipped record never counts as a covered pin either, so the HIGH fix cannot leak back in through `audited_pins`
- dependency-audit anchor is CONSTRUCTED and permanently `unverified`, which ADR 0008 pre-ruled for this ticket: a gate introduced by its own pull request has no blind ancestor on main and its anchor commit dies with the squash, so integrity is established by sha256 and historicity is not. The anchor is the plausible weaker gate - confirm the audit produced a report with a `dependencies` list and treat that as coverage - which is the shape `lib/security/modules/pip_audit.py` already has. Six mutations of the real gate were applied and all six killed: never inspect `vulns`, never report stale, deferral ignores its path, wedged at fail, unaccounted finding counted as suppressed, and allowlist matches anything
