# `undeclared-import-audit` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `undeclared-import-audit` (#1041)

- undeclared-import-audit refuses a MODULE-LEVEL import whose package no `pyproject.toml` dependency or extra declares (#1041). It exists because `dependency-audit` one section down asks OSV about what `uv.lock` **pins**: a module imported directly and declared nowhere is never queried, so it cannot appear in any advisory row however vulnerable it is, and the scan that never looked prints the same clean line as one that looked and found nothing. The gap was stated as a blind spot in `docs/security/dependency-advisory-dispositions.md` before it was closed; stating it is not the same as gating it
- undeclared-import-audit was built for one reported instance and found twelve. #1041 named `scrape_reddit.py:11` (`import requests`, with only `types-requests` - the type **stubs** - in the lock). Run over the tree, the same question returned **three** module-level instances (`scrape_reddit.py`, `fetch_reddit_posts.py` importing `praw`, `woodpecker/bootstrap-secrets.py` importing `boto3`) and **nine** guarded ones across six packages, several inside `lib/creds/` - this repository's own credential retrieval and secrets UI. One was found by reading the issue; the other eleven were found by building the instrument
- undeclared-import-audit's own positive control was hardened TWICE by the counter-model review, each time against the same substitution one level down. The first cut compared exit codes only, so a bad fixture whose planted import had stopped being detected but whose ledger had gone stale still exited 1 and the selftest printed "reported the planted import". Requiring the expected text fixed that and introduced a narrower version: the path and the package name were searched independently across the JOINED report, so a `scraper.py` finding about some other package plus a stale entry mentioning `requests` supplied one half each and scored as the detection. One line must now carry both. An unrelated failure standing in for the intended detection is what `UNSIGNALLED` exists to refuse one harness over, and it arrived inside the control built to prevent it
- undeclared-import-audit's classification of what RUNS ON IMPORT was wrong in nine contexts on its first cut, and the counter-model review found all nine. A `finally:`, a `try`'s `else:`, an `except ImportError:` handler's own body, a module-level `with`/`for`/`while`, a class body, the `else:` of `if TYPE_CHECKING:` and the body of `if not TYPE_CHECKING:` all execute during import and were all reported clean; the last two were one mistake twice, because the TYPE_CHECKING exemption was decided by searching the test expression for the NAME. Only three things are deferred now - a function body, a `try:` guarded by an ImportError handler, and the BODY of `if TYPE_CHECKING:` - and an `if` whose condition the gate cannot classify fails CLOSED. This is the shape of the defect the gate exists to prevent occurring inside the gate: the success line claimed a population the collector did not cover
- undeclared-import-audit asks about imports that RUN ON IMPORT, and #1041 resolved the rest rather than leaving them to a gate boundary. An import inside a function body, inside a `try:` with an `ImportError` handler, or under `if TYPE_CHECKING:` cannot crash an importer and is not a finding - but guarded is not the same as **declared**, and those nine sites were invisible to the advisory scan exactly like the three hard ones. The six packages behind them (boto3, botocore, python-dotenv, psycopg, fastapi, uvicorn) are now `[project.optional-dependencies]` extras, so `uv` resolves them into `uv.lock` and the advisory scan sees them while `uv sync --extra dev` still installs none of them. Had they been left undeclared the gate would have been green over them, which is why the boundary is written down rather than assumed
- undeclared-import-audit reads COMMITTED METADATA ONLY and never the ambient environment. `importlib.metadata.packages_distributions()` would map import names to distributions exactly, and is deliberately unused: it reports what happens to be **installed**, so the verdict would be green on a developer box that has boto3 for unrelated reasons and red in CI - the ambient-scan failure #1044 closed one gate over. Resolution is an exact compare of PEP-503-normalized names, then a small committed `IMPORT_ALIASES` table for the naming irregularities (`yaml` ships as `pyyaml`, `dotenv` as `python-dotenv`), then a finding. That last step is fail-CLOSED: a new package whose import name differs from its distribution name reds with the alias to add rather than passing quietly
- undeclared-import-audit compares NORMALIZED NAMES, not substrings, and the registered anchor is the version that does not. `types-requests` contains `requests`, so a gate asking "does this name appear in the dependency list" reports #1041's own tree clean. `controls/undeclared-import-audit/anchors/constructed-substring-matcher.py` is that plausible first cut - it shares the real gate's population, stdlib screen and first-party screen and differs in exactly two places, so the demonstration is isolated - and `cases/bad-stub-only-declaration` is the case it misses. CONSTRUCTED and permanently `unverified` under `--verify-provenance`, the ADR 0008 rule for a gate introduced by its own PR
- undeclared-import-audit's ledger has a STALE direction, and it fired on its own author on the first run. `.undeclared-import-allow` records a file deliberately run outside the project environment, one line per `(path, import name)`, tracked and printed on every run; an entry that accounts for nothing exits 1. #1041 intended to record `woodpecker/bootstrap-secrets.py` importing boto3, then declared boto3 as the `aws` extra in the same change - which resolved that import too - and the stale check reported the entry as accounting for nothing before it was ever committed. The ledger caught a false record being written and the entry was deleted; the file is empty today, and earning that emptiness is what the header comment records. KNOWN BLIND SPOT, bounded rather than widened: a line is `(path, name)` and accepts that import in that file however many times it appears, because a line number is invalidated by every edit above it and a ledger that reddens on unrelated edits gets switched off (ADR 0009)
- undeclared-import-audit derives its population with a DENY list, not a hardcoded root list, so a new top-level directory is scanned rather than silently skipped. The prunes - `mcp-second-opinion` (its own pyproject), `controls` (fixtures that are undeclared on purpose), `codex/skills` (byte-identical generated copies), the #953 paired case trees - print on every run, so narrowing is a visible decision. First-party names are derived too, and with DIFFERENT SCOPES: the root is a global `sys.path` entry because `[tool.pytest.ini_options] pythonpath` declares it, while a `src/` directory - the conventional `sys.path.insert` target, and what stops `tests/fixtures/delivery_pilots/` reporting its local `retry` and `slugify` as third-party - is scoped to the directory that inserts it. The counter-model review forced both halves: the first cut made every `src/` stem first-party EVERYWHERE, so an unrelated fixture suppressed a production `import retry` anywhere in the tree, and it tested the ABSOLUTE path's components, so a checkout living under any directory named `src` turned every file's stem into a global exemption and the verdict became a property of where the repository sat on disk. A `src/` exemption needs TWO conditions together, which took a second review pass to get right: the importing file must live under the directory holding the `src/`, AND must itself manipulate `sys.path` - subtree scoping alone still exempted `tool/check.py`'s bare `import requests` because `tool/src/requests.py` existed, with no insertion anywhere. The name granted is the IMMEDIATE CHILD of the source root, a module stem or a package DIRECTORY name, because collecting every descendant's stem was wrong in both directions: `tool/src/acme/requests.py` is importable as `acme.requests`, so recording `requests` masked an unrelated import, while `tool/src/acme/__init__.py` recorded `__init__` and left a legitimate `import acme` reported as undeclared. Virtual environments are pruned by their `pyvenv.cfg` MARKER rather than by name, because `.venv` and `venv` are two spellings of many and an `env/` that slipped the list put a neighbour's whole site-packages tree into the population
- undeclared-import-audit states what a static import scan cannot answer rather than counting it clean: a dynamic `importlib.import_module(name)` or `__import__`, and a declared package whose code is never reached. The success line reports the population it examined - files, distinct third-party names, undeclared, accepted, stale, and the count of guarded names outside its question - so the claim is bounded by construction
- undeclared-import-audit posture: a finding exits 1, a stale ledger line exits 1, and UNKNOWN exits 2 - no `pyproject.toml`, a file that will not parse, an unreadable directory, an unreadable or malformed ledger, or a zero-file population. **Unknown is never a pass**, the same rule the shellcheck and bandit gates hold. It IS in `make verify` where `dep-audit` is not, and the asymmetry is the reason: this gate is stdlib-only (`ast` + `tomllib`) and needs neither the network nor a synced venv, so a bare `python3` gives the same verdict on a plane, in `verify`, and in the slim CI image
