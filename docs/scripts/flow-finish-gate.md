# `flow-finish-gate` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `flow-finish-gate` re-run verdict (#900)

- flow-finish-gate / runner re-run verdict (#900) - the #769 targeted re-run appends `--last-failed`, so the second execution runs ONLY the failed ids, alone. Passing alone is the signature of a flake AND of an order-dependent real failure, because the re-run changes TWO variables at once - WHEN it ran and WHAT ran before it - so the experiment cannot separate them. `lib/cicd/runner.py` resolved that ambiguity in the reassuring direction: it logged "first attempt was a flake" and recorded the outcome as `passed`. An order-dependent failure in cooneycw/kyle survived WEEKS of being cleared by it (`tests/test_enrollment.py` asserted `"tok" not in rendered` against an ssh argv whose absoluteness depended on whether an earlier test had imported `core.fleet_authz`; alone green, in company red)
- flow-finish-gate: the gate was ALREADY honest, and that is what made the defect survivable-looking (#900) - the issue reports that the gate says `ok`. Measured against the real runner JSON shape, it does not: `flow-finish-gate.sh` has reported `warn (rerun passed: ...)` since f6c6071, the #769 commit itself, and its warning already offers both causes ("either these are the documented host-state flakes, or you have a real intermittent failure"), pinned by `test_runner_rerun_passed_reports_warn_and_ids`. So the issue's second remedy was already implemented. What remained is the mechanism the issue could not explain - why a warning that exists was cleared every time it fired: THE NARRATION PRE-EMPTS THE WARNING. The runner's confident sentence prints FIRST and names one cause; the gate's hedged sentence prints after. A reader meets the explanation before the warning and reads the warning as already accounted for. The warn was never missing - it was DEFUSED
- flow-finish-gate re-run token renamed `passed` -> `passed-in-isolation` (#900) - the narration fix closes what a HUMAN reads in the moment; the token closes what a LATER READER greps, and #900's own evidence is a defect that survived weeks, by which point the record is all that is left. `RERUN_PASSED_IN_ISOLATION` in `lib/cicd/runner.py` is the single producer-side constant (the emit site, the step-success branch and the qualifier filter all read it, so those three cannot drift from each other); `flow-finish-gate.sh`'s awk is the one cross-language copy and matches it with an ANCHORED regex. That anchoring is why the rename needs a both-directions pin rather than trust: a half-landed rename does NOT fail loudly - the gate stops emitting `RERUN_PASSED`, the warning never prints, and the marker reverts to `ok`, which is #900's exact symptom restored by the fix for it. `tests/test_runner.py::test_the_rerun_token_matches_what_the_gate_greps` parses the token out of each source and requires equality, failing in both directions. Deliberately NOT touching the `--last-failed` selection: a discriminating re-run would have to preserve the original selection and order, and the point of #900 is that isolation CANNOT distinguish the two causes, so building a detector for it would be the error the issue is about
- flow-finish-gate / runner re-run graded on the NAMED ids, not the invocation (#915) - the invocation-failed branch of the #769 retry decided "the failure reproduces" from `rerun_result.success`, i.e. the re-run PROCESS's exit code. The re-run executes the whole test target, so any unrelated failure in it named the retried id as reproducing - an id that had passed (kyle #1176: the retried Playwright id passed, a different test failed because another repository moved under the run, the verdict named the innocent id). `lib/cicd/runner.py` now compares failed-id SETS and records three facts on the rerun entry, independently: `reproduced` (retried ids in the re-run's failed set -> verdict `failed`), `appeared` (ids that failed but were not retried -> named whether or not anything reproduced; verdict `new-failures` when nothing did), and `unobserved` (retried ids absent from the failed set -> reported with reproduction status UNKNOWN, never as passed: a collection error elsewhere leaves them unexecuted). A failed invocation with no readable id at all is `failed-unattributed`. The gate clears only on an anchored `passed-in-isolation` match, so all three stay `fail` by construction (pinned in `tests/test_flow_finish_gate.py`). Two parser fixes came out of the cross-model review the change went through: failed ids are read from BOTH stdout and stderr on both attempts (`_failed_ids_from_both_streams`, not `parse(out) or parse(err)`), and `parse_failed_node_ids` reads an id up to pytest's ` - <reason>` separator instead of the first space, because `\S+` collapsed `test_v[hello world]` and `test_v[hello there]` onto one id - cosmetic while ids only labelled a re-run, a false "reproduced" once sets are compared. The suite-SUMMARY parser in `steps.py` has the same `or` shape and is #939, deferred because its fix changes the #621/#900 semantics. Each fix carries a regression that fails against the code before it (`tests/test_runner.py::TestRerunFailedTests`, `tests/test_cicd_outcomes.py::TestFailedNodeIds`)

## `flow-finish-gate` verdict channel (#1027)

- flow-finish-gate exit codes: every verdict gets its OWN code (#1027) - the invocation discipline the flow commands state is *"helpers print their own status markers and exit codes carry the result"*, and that was true of `fail` and false of every `warn`. All six `warn` verdicts exited 0, so `$?` separated `fail` from `{ok, warn}` and NEVER `ok` from `warn`: a caller following the documented `if gate; then proceed; fi` / `gate && git push` shape waved through all six - including `warn (carried, unverified: ...)`, which #804 added precisely to catch a run whose tree the runner could not verify, and `warn (not run by fallback: ...)` / `warn (skipped gates: ...)`, both of which report that stages DID NOT EXECUTE. `skipped` shared the same 0, so in a container - where the degraded path is the ordinary state, not an edge case - `skipped` and `passed` were indistinguishable. Now `ok` 0, `fail` 1, usage error 2, `warn` 3, `skipped` 4. `warn` and `skipped` are deliberately DIFFERENT codes rather than one shared non-zero: "ran, passed, something is soft-bad" and "did not run, no evidence" are different facts a caller must branch on separately, and sharing one would fix the ok/warn collision while creating an identical warn/skipped collision a level down. 2 is left alone because it already means "usage error" in THIS script, not UNKNOWN as it does in `shellcheck-gate.sh` / `dependency-audit.py` - colliding them would make a mistyped flag indistinguishable from an unrunnable gate
- flow-finish-gate `warn (zero coverage: ...)` - per-stage coverage for the gates that are not test steps (#1027) - `step_details` carried coverage evidence for `test` alone, so the standing "grade per-stage, not the rollup" procedure was unfalsifiable for three stages of four: `lint`, `typecheck` and `security_scan` emitted `{id, status}`, and `status: "success"` was returned both by a stage that examined the whole tree and by one that no-opped. `lib/cicd/coverage.py` parses whatever the tool said about its own coverage into three states - `covered`, `zero`, `unknown` - carried on `StepResult`, in `step_details`, and as a top-level `coverage` object the gate greps. Only `zero` warns; `unknown` is RECORDED but never graded on, the same bound `runner.py` already draws for an unparseable test summary, because warning on silence would fire on every Go/Rust/shell harness CPP cannot parse, on every run, which is how a warning stops being read. Reachability differs sharply by tool and is stated rather than implied: mypy gives a reliable positive count on both verdicts (`checked N source files`); CPP's own `SECURITY_GATE:` line now carries `secrets-scanned=`, named for the CHECK it measures rather than the stage, because that gate runs several checks and only the secrets scanner counts files - the number travels with a `scope` so a component's zero can say "the secrets scan examined nothing" and cannot say "this gate proved nothing", which would be a claim about the gitignore and permissions checks it never looked at (cross-model review); **ruff can do neither** - it states no positive count, and its `No Python files found` warning is SUPPRESSED whenever a `pyproject.toml` exists (measured across four tree shapes, with and without a `[tool.ruff]` section), so the detector is blind in exactly the population the gate runs against and `lint` reports `unknown` in practice. That was found by running the control, not by reading the code: parser and gate were both green. A real lint number would mean measuring the stage's INPUT rather than parsing its output, which is a different design and is filed (#864) rather than half-built here. The fallback lane detects the same markers directly, because in a container that lane is the ORDINARY path and a runner-only fix would leave the measured case blind

## `flow-finish-gate`

- flow-finish-gate - the deterministic quality-gate invocation as ONE audited allowlistable helper (#613, the #581 pattern): resolves the CPP checkout, checks `uv`, runs `lib.cicd run --plan <name>` under the #430 `PYTHONPATH` / `uv run --project` contract, degrades to the same Makefile gates the runner plan declares (`make lint`, `make test`, `make typecheck` and, since #1147, `make verify`) when the runner is unavailable, and ends with `FLOW_FINISH_GATE: ok|fail|warn|skipped`; `--check-summary` covers the advisory `lib.cicd check --summary` shape. Invoked BARE at `~/.claude/scripts/` by `/flow:auto` Step 6 + the Step-7/`/flow:merge` re-gate, `/flow:finish` Steps 2/2c and `/flow:check` Step 5 - the inline `PYTHONPATH=... uv run ...` line those docs carried could never match a permission prefix rule and prompted CODE-EXEC on every finish and merge
- flow-finish-gate typecheck parity (#617) - the `finish`/`check` runner plans AND this helper's Makefile fallback all run typecheck, because every shipped CI template (`templates/workflows/ci-python.yml`, `ci-node.yml`, `woodpecker-python.yml`, `woodpecker-node.yml`) runs `make typecheck` as a hard step and `PipelineConfig.branches["pr"]` defaults to `[lint, test, typecheck]`. Without it the gate reported `ok` on trees CI then rejected - twice in agentic-poker, after the PR was already open. Each step is `skip_if`-guarded on its Makefile target, so a repo without `typecheck:` is unaffected; `tests/test_runner.py::TestPlansCoverCITemplates` pins the plan-vs-template invariant so a step added to the templates cannot silently skip the local gate again
- flow-finish-gate skipped-suite qualification (#621) - a runner verdict of `completed WITH WARNINGS` (a test step that exited 0 having executed no tests) surfaces here as `FLOW_FINISH_GATE: warn`, exit 0, with the runner's JSON tee'd through untouched. Without it this helper - the layer the flow commands actually read - would flatten the careful qualification back to a bare `ok` and re-hide the false green one level up, the #617 layering trap repeating
- flow-finish-gate Makefile-less coverage + skipped-gate warn (#628) - a gate is no longer silently skipped just because a `make <target>` is absent: the `finish`/`check` runner plans (`BUILTIN_PLANS` + `generate_manifest` for Python/Django) and this helper's fallback each prefer the Makefile target but fall back to `uv run --extra dev <ruff|pytest|mypy>` when `pyproject.toml` configures the tool, and `skip_if` skips ONLY when NEITHER a target nor the tool exists. A gate that genuinely cannot run is surfaced, never hidden: the runner names it (`completed WITH WARNINGS - SKIPPED GATES: ...`), carries it in `RunResult.skipped_steps` -> the JSON `skipped` array, and `flow-finish-gate.sh` reports `FLOW_FINISH_GATE: warn (skipped gates: ...)` (exit 0) rather than `ok`. `ok` now means every gate actually executed. This supersedes the #617 "a repo without `typecheck:` is unaffected" framing - it is now surfaced as `warn`, not a silent pass (a Makefile-less repo that fully configured ruff/mypy/pytest was the #628 repro: oneninety-budget flow:auto #2). CPP itself is unchanged (its Makefile has all three targets, so the `make` branch always wins); `GATE_STEP_IDS` in `lib/cicd/steps.py` is the gate set, pinned by `tests/test_runner.py::TestSkippedGateReporting`
- flow-finish-gate gate set derived, and the shell filter kept equal to it (#890) - `GATE_STEP_IDS` was a hand-written literal `{"lint", "test", "typecheck"}` that omitted `security_scan` for three releases, so a run whose security scan skipped reported a bare `ok`. The omission was NOT an oversight: it was a deliberate #628 exemption, recorded affirmatively in `tests/test_runner.py::TestSkippedGateReporting`'s docstring ("A skipped NON-gate step (security_scan) is a legitimate skip and must NOT trip the warning") and using `security_scan` by name as its worked example, so #890 is a REVERSAL that has to be argued rather than a hole to fill. The exemption rested on a CATEGORICAL reading - a gate is one of the three #617 quality gates - where the question the set is consulted for is what a SKIP MEANS. `security_scan`'s `skip_if` is `! python3 -c 'import lib.security'`, so it skips exactly when the scanner is NOT INSTALLED, which is the same thing #628 says about a skipped lint or test and precisely when a warn is warranted; a containerised session has no CPP checkout, so it could run its finish gate, skip the scan and report `ok` with no mention. Not permanent noise either: `PYTHONPATH` points at the CPP checkout wherever it is, so the step RUNS for any target repo while CPP is reachable. `GATE_STEP_IDS` is now DERIVED from a `gate=True` declaration on `StepDef`, so a gate cannot be declared and left out of the set - there is no second place to update. Deriving cannot catch a new step that never declares `gate=` and takes the `False` default, so `tests/test_runner.py::TestGateDeclarationIsExhaustive` requires every builtin step to be a declared gate or carry a named reason for not being one, fails on a stale exemption for a step no plan defines, and fails when one id is declared a gate in one plan and not another (the set is keyed by id, and a disagreement between two declarations of one id would otherwise resolve silently). The worked example used to be `security_scan`, which appeared in both `finish` and `deploy`; since #1155 ids are globally unique across BUILTIN_PLANS and the deploy step is `deploy_security_scan`, so no id repeats today - the invariant is unchanged and is precisely what makes inheritance-by-id safe
