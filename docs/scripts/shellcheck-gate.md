# `shellcheck-gate` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `shellcheck-gate` (#960)

- shellcheck-gate: membership is DERIVED, never globbed (#960) - the issue states the population as "96 tracked .sh files" and both halves of that are wrong as a file list. `git ls-files '*.sh'` cannot see `scripts/cpp-memory`, a TRACKED bash script with no suffix (`#!/usr/bin/env bash`, `file` confirms it), and a tracked-only list cannot see untracked scripts at all. The gate derives from `git ls-files --cached --others --exclude-standard` filtered on extension OR shebang, falling back to a pruned `find` where git is absent, and prints `source=git|find` so a reader knows which ran. The two derivations agreed at 96 on adoption, which is the only reason that number is worth anything
- shellcheck-gate: the two surfaces have DIFFERENT blind spots and neither sees the whole universe (#960) - a CI clone contains no untracked files, so an untracked script is visible ONLY to `make shellcheck` on a working checkout; conversely shellcheck is frequently absent locally, where the gate then reports UNKNOWN and examines nothing, while CI always has it via the pinned image. Local sees untracked and may not run; CI always runs and cannot see untracked. Reporting a green from either without naming which surface produced it overstates the coverage
- shellcheck-gate: a missing binary is UNKNOWN (exit 2), never a pass (#960) - `command -v shellcheck || exit 0` is the obvious guard and it goes green on every machine lacking the tool, including the host this was written on. Same for a zero-file match: `0 examined` is not `0 findings`. Both exit 2 and say so, per #952 as amended - a zero is a denominator and reads UNKNOWN unless the instrument can show it was looking in the right place
- shellcheck-gate: adopted at `severity=error` with ZERO suppressions and no `.shellcheckrc` (#960) - the first run over 97 files produced 181 findings (6 error, 31 warning, 144 note). The 6 errors were 2 distinct SC1087 defects mirrored 3x through `codex/skills/`; both were fixed at source and the mirrors regenerated with `make codex-skills`, never hand-patched, because six independently edited copies is how a vendoring contract dissolves. The 175 remaining sit below the gate's severity and are a counted residual with a filed issue rather than a config line - a disabled check is invisible and an issue is not. #972 reviewed that residual to zero - each finding fixed or suppressed on its own line with its reason - and raised the default to `severity=style`; `controls/shellcheck-gate/cases/bad-note-severity` is the case that reports BLIND if the default reverts to `error`
- shellcheck-gate: excluding a fixture DIRECTORY is not suppressing a check (#960) - `controls/*/cases/**` holds deliberately-bad inputs whose whole function is to be bad, and they are still linted, by the negative control invoking this same gate with `--root`. `controls/*/anchors/**` holds frozen byte-identical copies of historical gates whose sha256 IS the provenance; editing one to satisfy a linter destroys what the control rests on, so a finding there is left alone by design
- shellcheck-gate: `--verify-provenance` can pass from the REFLOG, which does not generalise off the box (#960) - during adoption a rebase rewrote the branch SHAs, and the anchor entry still recorded the pre-rebase commit. `--verify-provenance` reported `ok` anyway, because `git show` resolved that commit as an UNREFERENCED object surviving in the local reflog, reachable from no branch. A fresh clone would have failed. The green was produced entirely by local state that exists nowhere else - the vacuous-in-one-environment shape, inside the machinery built to detect it. Repointed to a commit confirmed an ancestor of HEAD rather than a reflog survivor. The general lesson: a provenance `ok` from a rewritten branch says the object is reachable HERE, not that it is reachable
- shellcheck-gate: a comment opening with the linter's own name is parsed as a directive (#960) - the first draft carried a prose line beginning `# shellcheck and find, but NO bash...` and shellcheck read it as a malformed directive, failing the gate on its own source with SC1073/SC1072. Reworded rather than suppressed. Worth knowing before writing any comment whose first word after `#` is the tool's name
- shellcheck-gate migrated onto gate-lib (#1127) - `gate_map ok=0 findings=1 unknown=2` and `gate_arg_value` for `--root`/`--severity`; NOT `gate_emit`, whose `KEY: verdict - detail` shape does not fit lines like `shellcheck-gate: N file(s) scanned at severity=...`, and reshaping them is the change that slice forbids. USAGE EXIT MOVED, {1 under bash, 2 under sh} -> 64: the bash value was this gate's own FINDINGS code, so on any host whose /bin/sh is bash a dangling `--root` reported as "shellcheck found problems". No ok/findings/unknown code moves. `--root ""` is now accepted as supplied-but-empty (#1126's count semantics) and caught by `[ -d "$ROOT" ]` as UNKNOWN, exit 2 - measured, and it does not reach the good verdict
