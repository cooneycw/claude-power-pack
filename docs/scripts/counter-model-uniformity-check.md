# `counter-model-uniformity-check` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `counter-model-uniformity-check` (#1091)

- counter-model-uniformity-check UNIFORMITY IS AN OBSERVATION, NOT A DEFECT. A sweep once found 13 of 13 counter-model receipts recording the identical reviewer `codex/gpt-5.5` - the signature of a copied literal, not 13 independent observations (#1048, now fixed at the writer). But if one model genuinely reviewed every change in a period, "N of N identical" is the *correct* reading of a correct corpus. This checker distinguishes the two by cross-verifying a uniform corpus against independently supplied exec-log evidence, rather than treating uniformity itself as a finding
- counter-model-uniformity-check THE EVIDENCE LINK IS SUPPLIED, NEVER GUESSED, deliberately not a schema change to `scripts/counter-model-receipt.py`: real receipts written before #1269 carry no EXEC-LOG or thread_id field (since #1269 a `ran` receipt records `reviewer_evidence.thread_id`), so the manifest route cannot reach anything already on disk, and adding provenance now would help nothing already landed. NOTE (#1048): "structurally impossible" was how this read until 2026-09-20, and it was wrong - a receipt's `branch` names the worktree a rollout records as its own `cwd`, which is an association real receipts do carry. `counter-model-reviewer-attribution.py` uses it; the 13 are attributed in `docs/measurements/counter-model-reviewer-attribution.md`. The premise blocked that disposition for as long as it stood, which is the cost of writing an impossibility claim where a limitation was meant (filed to the Nit Store, claude-power-pack#864, rather than fixed here - re-touching #1048's shipped schema for a benefit that helps nothing on disk was judged out of scope). An `X.evidence.json` manifest is the only way a receipt becomes cross-verifiable, and nothing populates one for the real corpus today
- counter-model-uniformity-check FIVE VERDICT STATES, not two, checked in a fixed order: a disagreement between a stored reviewer and independently-derived evidence is a FINDING regardless of diversity (the strongest signal); a corpus that genuinely varies is OK; a uniform corpus verified against at least one piece of evidence with no disagreement is OK; a uniform corpus with zero verifiable evidence is UNKNOWN (today's real state for the actual corpus, and the case a gate wedged at "always trust uniformity" or "always distrust it" cannot separately pass); an empty population is UNKNOWN. The denominator - `examined=<n> verifiable=<m> distinct=<k>` - is printed on every verdict including the clean ones, so `0 mismatches` is never read next to an unstated population
- counter-model-uniformity-check ADVISORY, NOT GATING, and not wired into any Makefile target or CI step in this repository: a gating version would block on the 13 landed receipts' disposition, which is an OWNER decision this checker does not make, act on, or annotate (`docs/measurements/counter-model/` is read-only to it). ADR 0008 row 83 registers it as class X regardless - the operator eventually reading its verdict when deciding the 13's disposition will not independently re-derive the fact, which is what the bound turns on, not whether a machine currently blocks on it
- counter-model-uniformity-check REUSES `scripts/counter-model-receipt.py`'s own `_derive_reviewer_from_exec_log` via `importlib` rather than a second implementation of the thread_id -> rollout -> model lookup, so the two cannot silently drift apart on how a reviewer is derived
- counter-model-uniformity-check `--selftest` reads the FIVE COMMITTED CASES straight out of `controls/counter-model-uniformity/control.json` and asserts each one's exact exit code and output, so the self-test and the registered negative control cannot drift apart into two things that used to agree
- counter-model-receipt `head` is DERIVED, never asked for (#1171) - the receipt records the commit its review was taken against, and the writer derives it with `git rev-parse HEAD` rather than taking a `--head` value. The only write call site is in `.claude/commands/flow/auto.md`, so a required flag would make the field depend on a document being edited in lockstep with this script - the same "a marker written by the thing being measured" trap #1048 removed from `--reviewer`. `--head` survives as a test override. The field is OPTIONAL in `validate()` and that is load-bearing: all 50 receipts committed before #1171 carry no `head`, and requiring it would have invalidated the entire corpus at once, so absent means "written before this field existed" and is read by the gate as not satisfying enrolment rather than as a malformed receipt. A head that cannot be derived is reported on stderr rather than left for the gate to surface as a bare `missing` later
- counter-model-receipt `skip-reasons` prints the committed set one per line, and exists so `flow-finish-gate.sh` can validate a `skipped: <reason>` against ONE declaration instead of a second copy in shell - the cross-language drift #890 and #1147 kept removing, which fails in the dangerous direction here: a shell copy still naming a retired reason would accept a skip the committed set refuses, which is exactly how `explicit-opt-out` would return without anyone re-adding it
- counter-model-uniformity-check `--enrolment-scan [REF]` derives the population from HISTORY instead of from the receipts that exist (#1171), so a landed change with no receipt is a FINDING rather than a smaller corpus - the thing `scan()` structurally cannot report. CPP squash-merges, so every first-parent commit is one PR and its subject carries the reference; the trailing `(#N)` GitHub appends is the PR number and is deliberately NOT counted as an issue, or the check would invent enrolments nobody owed. UNATTRIBUTABLE IS NOT MISSING: a commit naming no issue is counted and reported separately, and a range that attributes nothing reports UNKNOWN - an unrun check, never a clean one. Measured on this repository at the time it landed: 16 of the last 23 first-parent merges had no receipt, including both merges of 2026-09-21
- counter-model-uniformity-check enrolment REPORTS STATUS, and says what its keying can and cannot support (#1171, both found by this change's own counter-model review). Keying on "a receipt mentions this issue" counted an explicit `skipped: codex-absent` as a completed review and then said "recorded a review" - the skipped-versus-reviewed ambiguity #1171 exists to remove, recreated inside the instrument built to remove it. The summary now splits `reviewed=` from `skipped=` and names skips in the success line, and a receipt whose status is neither is a FINDING rather than coverage. Coverage is keyed per ISSUE and an `ENROLMENT-NOTE` says so on every run, naming any issue named by more than one commit: one receipt satisfies every commit referencing its issue, so two changes closing #11 both read as covered while only one was reviewed. Per-change correlation is not derivable from this data - a receipt records an issue and a branch, not a squash sha - so the keying is DECLARED rather than the number being quietly read as a per-change claim. The three verdicts are named with the exact invocation that produces each in the `enrolment_scan` docstring, using fixed SHAs rather than HEAD~N
- flow-finish-gate counter-model status is checked POSITIVELY (#1171, counter-model review HIGH) - the first cut accepted every matching receipt whose status was not exactly `skipped`, so a receipt with `"status": "garbage"` or no status field satisfied the gate while recording neither a review nor an allowed skip. Only `ran` is a review now; anything else is UNKNOWN and reds, pinned by the control case `bad-receipt-with-unusable-status`. The helper is resolved BESIDE THE GATE FIRST, which fixes two things at once: a generated Codex skill bundling this gate on a host with no Claude paths and no CPP checkout now finds its own bundled copy instead of reporting UNKNOWN and blocking finishing, and a gate running from a worktree validates against that worktree rather than through the stable path's symlink into the primary checkout. The control fixtures pin their branch with `git init -b`, because `init.defaultBranch` is host configuration and without it the control's verdict was a property of the box rather than of the instrument - verified by re-running the whole control under `init.defaultBranch=main`
- flow-finish-gate CANNOT-ANSWER IS NOT ANSWERED-NO, and the permissive half is gated on an ESTABLISHED cause (#1171). `git merge-base --is-ancestor` exits 0 for yes, 1 for no and 128 when it CANNOT ANSWER - the commit is not in this repository. The first cut treated every non-zero as "not an ancestor", so a review that demonstrably happened was reported as `missing`, a review that did not: unknown collapsed into NEGATIVE, inside the instrument whose entire subject is that those two must be distinguishable. But 128 has TWO causes and only one is benign - a SHALLOW clone, where the object is simply elsewhere (CI clones `--depth=1`, so this is every pipeline run), and a FULL clone whose receipt names a commit that exists nowhere, which is a wrong or fabricated receipt. Letting every 128 pass would be the same defect inverted and failing OPEN. `git rev-parse --is-shallow-repository` separates them: shallow reports `undecidable` and PASSES loudly - never as `ok`, never as a receipt id, and the line says the enrolment decision was NOT made here - while a full checkout reports `unresolvable` and REDS. Both halves are pinned, by `good-shallow-clone-is-undecidable` and `bad-receipt-names-a-commit-that-exists-nowhere`; without the second, `undecidable` would be a blanket escape reachable by any cause
- flow-finish-gate `--enrolment-only [--branch NAME]` is the CI pull_request step's check (#1452). The finish-mode enrolment ran only when someone ran this gate, and 7 of the 40 merged PRs before #1452 never did. The CI step deepens the depth-1 clone, then runs this mode with `--branch "$CI_COMMIT_SOURCE_BRANCH"`: exit 0 for a receipt, a committed skip or a non-participating repo; 1 for missing or unresolvable; 5 for undecidable, which is never a pass here. Without `--branch`, a detached checkout matches by ancestry alone and accepts another branch's receipt. **No review could run? One command records the skip** and must be committed: `python3 scripts/counter-model-receipt.py write --status skipped --reason <codex-absent|reviewer-unavailable> --issue <N> --branch <branch> --head "$(git rev-parse HEAD)"`. Since #1461 the mode also fails a matched default-direction `ran` receipt that carries no `scope`: the CLI refuses to write one, and `validate()` requires it only from `SCOPE_REQUIRED_FROM`, a compatibility window that a hand-built receipt could backdate. The merge boundary evaluates the PR's own receipt whatever date it claims. `controls/counter-model-enrolment-ci` scores the mode. The three historical reviews (#1162, #1165, #1166) stay a permanent gap per #1269, and nothing is backfilled.
- flow-finish-gate names the failing test (#1258) - the runner records `tests.<step>.failed_ids` for every step whose parsed outcome failed, whether or not the #769 re-run applied (an aggregate like `make verify` failing at its `test` prerequisite recorded a count and no id), and the gate relays `FAILED_IDS:` above its fail verdict; an EMPTY list is said out loud (`none readable`) rather than looking like nothing failed. The runner-JSON temp file is removed by the EXIT trap, so an interrupted gate no longer leaks one. The typecheck fallback honours a declared mypy `files =` (`[mypy]`/`[tool.mypy]`) by running bare `mypy`, else `mypy .`
- flow-finish-gate the skip allowlist is addressed with `--` (#1171, counter-model review pass 2) - `grep -qxF "$reason"` read a reason of `-ecodex-absent` as the OPTION `-e codex-absent` and matched, so a reason absent from the committed set passed the allowlist that exists to close exactly that door. Reproduced against the matcher before the fix and refused after; pinned by the control case `bad-skip-reason-shaped-like-a-grep-option`. An allowlist that can be addressed with its own matcher's flags is not an allowlist
- counter-model-uniformity-check enrolment validates a SKIP and classifies by the WEAKEST evidence (#1171, counter-model review pass 2) - the scan accepted every `"status": "skipped"` receipt without reading `skip_reason`, so `explicit-opt-out` and a receipt with no reason at all both produced ENROLMENT-OK while the finish gate reds on precisely those: a historical report certifying what the gate refuses. It now reads `SKIP_REASONS` from the same already-loaded `RECEIPT` module the file already uses, never a second copy. And a commit's classification takes the WORST status among the issues it names rather than the union preferring `ran`, because a commit naming a reviewed #11 and a skipped #12 reported `reviewed=1 skipped=0` - the skip vanished behind its sibling. Disagreeing issues are NAMED in an `ENROLMENT-NOTE` (`#11=ran, #12=skipped`) instead of being rounded either way
