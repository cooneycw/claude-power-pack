## `flow-driver-capability`

- flow-driver-capability - what each lifecycle driver CAN do, as declared data (#783). The ELI5 gate (#775) and the delegated drivers' Step 3 gate (#774/#784) both answer "should this work be done, and is this the right plan?"; nothing answered "can this driver do this work AT ALL?", and for three of the four the answer is structurally NO for whole classes of issue - `/codex:auto`, `/qwen:auto` and `/gemma:auto` each wrap their model in an IMPLEMENTATION-ONLY execution fence (so the deliverable can only be a source diff, never a finding), and none can reach a live source (`codex --sandbox workspace-write` blocks network for shell commands; the `gemma-implementer` profile DENIES `webfetch`/`websearch` by name; the Qwen lane simply configures no retrieval tool - recorded as an absence of provision rather than a denial, because a matrix that overstates a block is worse than one that admits a soft edge). Observed twice in one evening on the `kyle-completion` wave (2026-09-05) by two workers on two drivers, both caught only because the worker read its own fence and refused - discipline, not mechanism, and the fences live inside PROMPT-CONSTRUCTION instructions written for a different purpose (#735 exists to stop a model self-directing into the lifecycle, not to describe what work suits it), so a worker checking capability reads a document that never set out to answer that question and an ORCHESTRATOR has nothing to read at all. Four axes - `scope` (general | implementation-only) and `web` (yes | no), each traced to one of the two observed refusals, plus `container` (yes | no, added by #835) and `meta` (yes | no, added by #877 - may the driver read and edit THIS repository's own `.claude/commands/**` and `.claude/skills/**`? `no` for all three delegated drivers, whose #735 fence forbids reading the very files a CPP-meta issue requires editing; the fence block is byte-identical across codex/qwen/gemma, so this is a property of delegation and not a codex quirk) - each `no` (or, for `container`, a conditional `yes`) carries a `_basis` field recording HOW it is enforced, since the drivers reach these verdicts for materially different reasons; preconditions (`auto` needs a filed issue and an existing checkout, #758) are a DIFFERENT axis and deliberately not duplicated. **`container` does not track `scope`/`web`**: qwen:auto is implementation-only and web=no, yet reaches docker unconfined, because #749 already skips its sandbox for a remote endpoint - the same conditional #749 recorded for its `web_basis`. Added when a real assignment routed a CI-image docker inventory to gemma:auto and the run came back a clean, tool-call-denied "success" (#831 groundwork, #836) - the driver's own permission profile denies `docker*`/`kubectl*`/`terraform*` at the same tier as `git commit*`/`gh *`. Every value across all three axes is MEASURED by actually running the probe command through each driver's real harness rather than inferred from its config and assumed - reading gemma's `opencode.json` and running the docker call through it gave different confidence, which is the reason #835 measured rather than inferred, and codex's `container: no` was confirmed the same way (`docker version` under `--sandbox workspace-write` returned a socket permission denial; the identical command unsandboxed for the same user succeeded). `show`/`list`/`check <driver> --needs implementation|research|web|container|meta`, with needs DECLARED by the caller out of a closed enum and never inferred from issue prose - a classifier guessing at text would invent mismatches nobody declared, the #683 failure where an overlap warning stops being believed - and an unknown need is a usage error (exit 2) rather than a silent `fit`. Because needs are declared, a caller who does not ASK about an axis cannot be answered on it, so `check` also emits `FLOW_DRIVER_UNDECLARED` - the incapacities this call left unasked - and says so in words on a narrow fit: #877 is the case where `--needs implementation` returned `fit` for a driver the fence forbade, and the reader had nothing in the output to notice it with. **The anti-decoration contract**: a capability matrix nobody reads is prose with extra steps (#701's kill condition about its own lexicon), so it is READ BACK by three consumers rather than merely published - `flow-wave-registry.sh` DERIVES the roster's `driver=gemma:auto[impl-only,no-web,no-container,no-meta]` annotation and the `FLOW_WAVE_DRIVER_CANNOT` line from it (so the mismatch is visible when the orchestrator ASSIGNS, not when the worker refuses), each driver's own skill file states the contract so a worker's Step 2 pre-flight reads a stated contract, and `tests/test_driver_capability.py` derives the expected matrix from the driver documents themselves so a driver that loses its fence or whose sandbox flag changes turns the suite red instead of leaving this file quietly lying. Fail-open throughout: an unknown driver reports `unknown` and exits 0, because failing closed on a name it has never heard of would block a wave over a downstream driver, and the routing question is then simply unanswered - where every driver stood before this existed
