# `step3-record-guard` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `step3-record-guard` (#1083)

- step3-record-guard - a `PreToolUse` hook that REFUSES an edit in a flow worktree carrying no approved-plan record (#1083). In a checkout whose branch is `issue-<N>-<slug>`, an edit is refused unless `docs/flow-runs/issue-<N>.md` exists AND records `Approval: granted`, and the block message names what is missing and the route to obtaining it - a refusal that is not recoverable is one people route around
- step3-record-guard exists because #775 was ASSERTED AND NOT ENFORCED. #775 says no flag, trailer, marker, environment variable or governance tier may let `/flow:auto` Step 3 proceed without a reviewer approving the plan, and that none may be added; it is among the most forcefully stated rules in this repository and, until #1083, the `.claude/hooks.json` CPP then shipped carried one SessionStart notice and two output-masking declarations and nothing checked it (the file itself was removed in #1206, since Claude Code never loaded it). The strength of prose is not evidence about the strength of a control
- step3-record-guard IS A FLOOR AND DOES NOT ENFORCE #775, and that wording is load-bearing rather than modest: it establishes that an ARTIFACT IS PRESENT, never that an APPROVAL OCCURRED, and only on the tool paths it is matched against. Anything able to write the record can write itself an approval line. Meeting the issue's full acceptance needs `/flow:auto` to RECORD Step 3 where a hook can read it before the first edit - a command-document change with a different blast radius, ruled out of that lane before any code was written and left as the named residual
- step3-record-guard's COVERAGE DIFFERS BY AUDIENCE by an order of magnitude, and both halves ship. In THIS fleet it is near zero: sessions are steered to make file changes through Bash - "with sed, heredocs, or short scripts, rather than using the dedicated Read, Edit, or Write tools" - so the path it cannot see is the INSTRUCTED DEFAULT rather than an escape from it, measured as three plan records across three runs of one session with zero via `Write`. Where CPP SHIPS it, coverage is genuinely useful, because that steering is a property of how this fleet is operated and not of the hook mechanism. A reader here must not take its silence as evidence
- step3-record-guard commits that blindness as a CASE rather than a sentence: `controls/step3-record-guard/cases/good-BLIND-bash-redirection-is-NOT-SEEN` is the same recordless fixture edited by Bash redirection, expecting the hook NOT to fire, with a `WHAT-THIS-CASE-COMMITS` file telling a future maintainer not to "fix" it - a committed known-gap looks exactly like a committed bug to someone who does not know why it is there. If the steer changes or the matcher grows, that case flips and the flip is the notification; prose cannot do that
- step3-record-guard reads the branch with `git symbolic-ref --short HEAD` and NOT `git rev-parse --abbrev-ref HEAD`, because two states produce the same word from `rev-parse` and need OPPOSITE answers. An UNBORN branch - `git checkout -b` before the first commit, which a fresh flow worktree briefly is - makes `rev-parse` FAIL and print the literal `HEAD`, so the branch went undetected and the guard ALLOWED: a refusal rendering as a permission, on the one behaviour #1083 calls non-negotiable. Its own control caught that before it shipped. A genuinely DETACHED head is DETERMINED rather than unreadable and must ALLOW, since refusing there would block every edit in every detached checkout including CI
- step3-record-guard exempts EXACTLY ONE PATH, the record's own, and the block message says so. The record is written BY an edit, so a guard without that exemption blocks the write that would unblock it and every run deadlocks on its first edit. The exemption is keyed on the ISSUE NUMBER and not on the directory - `docs/flow-runs/issue-9999.md` is still refused - because location would exempt every worker's artifact where provenance exempts only this run's. It is also a hole, and given the Bash bound it is subsumed by a wider one rather than being the marginal risk
- step3-record-guard is OPT-IN, shipped through `templates/hooks/step3-record-guard.md` and installed by nothing. CPP ships to other people's projects and a hook that blocks edits must not arrive unannounced. The installable block lives inside that document rather than a sibling `.json` because `.gitignore` carries a blanket `*.json` and every template JSON here survives only via an individually-named `!` negation; one file also means the matcher and its documentation cannot drift, and a test pins that they agree and that the document does not overclaim
