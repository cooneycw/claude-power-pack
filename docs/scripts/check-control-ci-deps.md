# `check-control-ci-deps` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `check-control-ci-deps` (#1036)

- check-control-ci-deps - flags a registered negative control that needs a binary the battery's CI step does not have (#1036), at REGISTRATION time and in `make verify`, rather than at gate time on CI. The failure it prevents is not hypothetical: a control registered committed BARE GIT REPOSITORIES as its cases, `git` is not in the `negative-controls` image, and because `check-negative-controls.py` REFUSES to skip a control it cannot run - correctly, since a skipped control and a passing one must never print the same thing - that one control made the gate every other control's verdict is read through the thing that could not report. One unmet dependency takes the whole battery down
- check-control-ci-deps is structurally invisible without a gate like it. The offending control passed `make verify`, `--strict`, sixteen killed mutations and two review passes locally, because every local instrument had `git` on PATH; the dev box cannot reproduce the condition unless someone constructs it deliberately (`env -i PATH=<no-git>`). It is discoverable only on CI, only after the commit, and only as a red on a step that names a different control than the one at fault. The repository records the same class as forgotten three times already: #451, #489, #577
- check-control-ci-deps derives the PROVIDED set rather than listing it. The step is found by what it RUNS (`check-negative-controls.py`), not by its name, so renaming the step cannot silently point the gate at the wrong image; that step's `image:` is compared against `CI_IMAGE` in `check-test-binary-guards.py`, which is where this repository already records what the image CONTAINS, and a mismatch is a RED rather than a fallback - a contents list describing a retired image is the hand-maintained-number failure one level up from the one this gate catches. `CI_IMAGE_BINARIES` is IMPORTED from that file, never copied, for the reason #1060 recorded about census parsers: two lists of one image's contents drift apart silently while both keep printing verdicts
- check-control-ci-deps counts staged binaries two ways, and the second is not a nicety. `cp "$(command -v gitleaks)" .ci-bin/gitleaks` is a literal a regex can find; `jq-stage` runs `python3 scripts/ci-stage-jq.py`, whose destination is built as `DEST_DIR / "jq"`, so NO `.ci-bin/jq` string exists in the yaml or the script. Read the pipeline alone and jq is invisible, the provided set silently loses a binary that IS on PATH, and the first control to need it gets a false red in `make verify`. The `scripts/ci-stage-<name>` convention resolves it, and a dependency step neither rule can read is printed as `CI_DEPS_UNRESOLVED_STAGE:` so the provided count reads as a FLOOR rather than a total. Found by reading this gate's own output - it printed `CI_DEPS_STAGED: 2` beside a battery step that depends on three staging steps
- check-control-ci-deps examines THREE surfaces and its success line names all three, so the green cannot be read as "every dependency is satisfied": the `invocation` command (with `env` and its `VAR=VALUE` assignments unwrapped, since reading `env` as the dependency checks a binary present in every image while missing the one that might not be); the gate's shebang interpreter; and, for a `sh`/`bash` gate only, the binaries it HARD-REQUIRES via `binaries_in_script` in `check-test-binary-guards.py` - the audited extractor that already powers the binary-guards gate and drops anything a script declares it degrades without. NOT examined: what a PYTHON gate shells out to, and what a case FIXTURE needs. Both need the AST and shell analysis that file spends 1,500 lines on, aimed at a different population, and a looser scan measured 266 findings there of which ~250 were scripts that run fine without the tool
- check-control-ci-deps contract - `CI_DEPS_STEP:` and `CI_DEPS_STAGED:` on every run (plus `CI_DEPS_UNRESOLVED_STAGE:` when a staging step cannot be read), then `CI_DEP:` per control finding and `CI_PIPELINE:` per pipeline finding, then `CONTROL_CI_DEPS_REGISTERED:` / `_EXAMINED:` / `_PROVIDED:`. Exit 1 on any finding, and exit 1 with "This is UNKNOWN, not clean" when the CI environment could not be derived at all - an underivable environment must never read as a satisfied one
- check-control-ci-deps the walk tracks EXECUTION SCOPE, not `tree.body` membership (#1168, counter-model review) - the first cut asked whether an import node was a direct child of the module body, and `if True: import x`, a `try/except ImportError` fallback and a class-body import are not, while all three RUN on load. Each was demonstrated reporting `ok` with the import counted as deferred: the original failure recreated inside the check built to catch it. Everything is now reached except the bodies of functions and lambdas, which run on call. The same review found the package resolution incomplete in both directions - `import a.b` executes `a/__init__.py` first, and `from a import b` executes `a/b.py` when b is a module - so a dependency in a parent initializer or an imported submodule was missed, both reporting clean. A PEP 420 namespace directory is NOT an external requirement: `lib/` here has no `__init__.py`, and requiring every chain step to resolve to a file reported `from lib.vendor import ...` as needing a distribution called `lib`, a false red on the only control importing first-party code. Resolution also searches the gate's OWN directory first, as python does, so a sibling import is not reported as an external package and a root-level file of the same name cannot shadow it
- check-control-ci-deps the walk is attributed only to an invocation that RUNS the gate (#1168) - any command starting with `python3` used to walk the declared gate whatever followed, so `["python3", "{case}", "{gate}"]` - which runs the CASE - was reported as the gate examined, and `-m`/`-c` forms were attributed to a file they never execute. The script argument must now BE `{gate}`; anything else counts as a non-python invocation rather than a walked one, which is the difference between a bound and a guess
- check-control-ci-deps TWO STATED BOUNDS on the python side, neither fixable here (#1168) - the stdlib set is the HOST interpreter's `sys.stdlib_module_names`, not the pinned image's, so it names platform-specific modules that do not import on Linux and may include names a newer host has and the image lacks; and `make battery-in-ci-image` copies the host's gitleaks and shellcheck, proving they RUN but not that they match the versions the pipeline's stagers pin. Both make this side generous, which is the safe direction for a NECESSARY check - it can miss, it does not invent - and both are answered by running the battery under the pinned digest instead
- check-control-ci-deps a PYTHON gate's module-level imports are examined too (#1168) - it read the invocation, the shebang and a SHELL gate's binaries, and said so; what a python gate IMPORTS was never examined, and 26 of this repository's 41 controls invoke python. One module-level import of something the image lacks takes the whole register down, because the battery refuses to skip a control it cannot run. MODULE LEVEL ONLY, which is a bound and not a shortcut: a module-level import is UNCONDITIONAL, an import inside a function is conditional on a call path this reader cannot decide, and #1163 deliberately created seven such imports in `lib/cicd/cli.py` that the gate's own `run` path never reaches - following them would report a requirement that is false and red a control that works. Deferred imports are COUNTED instead, in four counts printed on every run including the clean one: `CI_DEPS_PY_GATES_WALKED`, `_IMPORTS_RESOLVED`, `_DEFERRED_UNFOLLOWED`, `CI_DEPS_INVOCATIONS_NOT_PYTHON`
- check-control-ci-deps NECESSARY, NOT SUFFICIENT, and the success line says so (#1168) - a green means no examined surface names something the step lacks; it does not mean a control RUNS there. #1163's case reached `lib.cicd` through a case FIXTURE - the one surface this gate declines by name - so no static reading of it could have caught that, and a green that let a reader believe otherwise would be the overclaim this file spends its length refusing. The line names the sufficient instrument instead
- check-control-ci-deps a control invoked through a WRAPPER rather than the declared gate directly was walked as if the wrapper WERE the gate, and never walked at all itself (#1407 fallout, orchestrator ruling) - `check-test-binary-guards.py`'s own #1407 fix corrected `scripts/lane-serveability-check.sh`'s own curl requirement from `[]` to `{curl}`, which this gate had never been able to see either, for the same reason; fixing it surfaced that `controls/lane-serveability-check`'s invocation runs `run-case.sh`, a WRAPPER that stages a throwaway curl stub on PATH before the real gate ever runs (issue #1281) - so the gate's own `command -v curl` is satisfied by the wrapper's own PATH injection, never by `.ci-bin`. The orchestrator surveyed main: 26 of this repository's registered controls invoke a wrapper this way, so walking the WRAPPER INSTEAD OF the gate (the rejected direction) would drop every binary the gate needs that a wrapper happens not to stub, across all 26 - the more dangerous direction, where a control goes UNAVAILABLE or CI breaks with nobody noticing. The fix is additive: the wrapper's OWN `sh`/`bash` hard-required binaries (via the same `binaries_in_script`) are ADDED to the gate's, never substituted for them, and a control may self-declare `ci_deps_provided_by_invocation` to name a binary its own wrapper demonstrably stages - `_verify_provided` requires the wrapper's text to WRITE a file ending in `/<name>` AND prepend that same directory expression to PATH somewhere in the same file, textually, never trusting the declared key as free text. Only `controls/lane-serveability-check` carries the key today, citing #1281 in its own `limits`. Four committed cases pin the shape: a wrapper-invoked control without the key still reports its gate's need (today's real failure, reproduced); the same control WITH a verified key scores clean; a key naming a binary the wrapper never creates is refused as a stale claim; and a gate needing a SECOND binary the key does not name is still reported, pinning that this is the additive direction and not the rejected one
- battery-in-ci-image A FAILED PREFLIGHT INVALIDATES THE RUN (#1168, counter-model review) - the first cut printed the unusable-binary warning and then ran the battery anyway, returning only its exit status. A success would have overridden the failed preflight, which is unexamined reading as clean. It now refuses before scoring anything: measured, the positive control prints `jq(does-not-run)`, exits 2 and emits ZERO battery verdicts. The digest selector also stops at the NEXT step and requires an `@sha256:` pin, because an inherited or missing image made the old selector take a neighbour's image and silently defeat the pipeline boundary the target exists to hold; measured, a battery step with no image exits 2 rather than running under something else
- battery-in-ci-image THE SUFFICIENT HALF, and a copy that lands is not a tool that runs (#1168) - `make battery-in-ci-image` answers "would this control run in CI" by running the battery under the pipeline's OWN image digest, read from `.woodpecker.yml` rather than retyped, with `--network none` and a read-only workspace. Its first run reported one control BLIND, and the cause was the TARGET rather than the control: staging by `cp "$(command -v jq)"` produced a file that exists, is executable, satisfies `command -v` and fails on exec, because the host's jq is dynamically linked against `libjq.so.1` which the image does not carry. gitleaks and shellcheck survived the same treatment because they are static builds, which is why only one control moved and why it looked like a property of that control. CI never copied jq - it stages a content-pinned static build via `scripts/ci-stage-jq.py` - and the target now does the same, on the host where network exists, with the battery still running with none. It also RUNS `--version` on every staged binary inside the image before trusting the verdict, and when one cannot run it says `STAGED BUT UNUSABLE IN THE IMAGE` and that the resulting UNAVAILABLE is unexamined, NOT a gate that stopped discriminating. Without that sentence this instrument's failure mode is to accuse a healthy control of blindness - the misdiagnosis `check-negative-controls.py` already refuses for anchors (#946), reproduced one level up by the tool built to check it
- check-control-ci-deps runs nothing and needs no staged binary: it READS `.woodpecker.yml` and the manifests. That is not incidental - a gate ABOUT CI dependencies that itself needed a binary CI lacks would be this issue's own defect one level further in. It is in `make verify` PRECISELY BECAUSE the battery is not: `negative-controls` sits out of `verify` for an environment reason, so without this target the whole subject is unexamined locally. Controlled at `controls/control-ci-deps`, whose two BAD cases are a gate hard-requiring `git` behind an unremarkable `sh` invocation, and a pipeline running an image the contents list does not describe; the constructed anchor reads `invocation[0]` and stops, so it misses both
- check-control-ci-deps the SECOND battery (#1268) - the mutation-probe CI step runs the batteries of every control that declares `mutations`, and only the negative-control step's environment was derived. Now `mutation_environment` finds the step that RUNS `mutation-probe.py` (the `uv run ... python` chain; a mention is not a run) and gives it the battery step's staged environment ONLY when it runs after that step, on the same image, with `.ci-bin` on PATH - literally true in this pipeline, because Woodpecker shares the workspace. Otherwise it is the image's own binaries, or UNKNOWN (a finding, never clean). Each command is classified on its own, a quoted script path is an invocation, and a compound command (`&&`, `||`, `;`, `|`, `$(`, a backtick) mentioning the probe is UNKNOWN - its second invocation would not inherit the first's command-local PATH. No step running it is ABSENT, not unknown: no mutation runs in CI, so none can fail for want of a binary
