# `flow-plan-record` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `flow-plan-record`

- flow-plan-record - the `/flow:auto` plan record and as-read issue snapshot, as one helper (#1211): `reconcile` (Step 1: restore the last COMMITTED record from HEAD or remove scratch, #1080), `read-issue` (Step 1: store the body as read, with digest and read time, in the git dir, #1081), `approve` (Step 4: write `docs/flow-runs/issue-<N>.as-read.md` and stamp the record's digest as the Step-5 baseline, #1081/#1082), `drift` (Step 5: `ISSUE_DRIFT: clean|drift|unresolved`), `compliance` (Step 5: `PLAN_COMPLIANCE` + `PLAN_RECORD_STABILITY`, reports and never blocks, #1082) and `head-check` (Step 5: `FLOW_PLAN_RECORD: present|absent|unverified`, the STOP when the record did not ship, #1080). Exits 0 ok / 1 error or absent / 2 usage / 3 finding / 4 unknown, so no cannot-answer state shares a code with clean. `--body-file`, `--live-file` and `--head` replace only the `gh` call so tests drive the real entry point without stubbing `gh`. It replaced roughly 5,700 words of pasted programs and prose in `auto.md`; the reasoning moved to `docs/agents/flow-plan-record.md`, which the procedure links as background rather than required reading
- flow-plan-record lanes check (#1731) - `approve` refuses a record whose run section has no `### Lanes for this change` table, or leaves a lane listed in `.claude/lanes.md` without one of the four answers, through the existing `FLOW_PLAN_RECORD: error - ...` line and exit 1, before anything is written. Three plans had been approved without the table in the first afternoon of the rule and one merged that way. Silent and byte-identical where the project has no lane file. An unusable lane file is `unknown` and refuses; it never reads as no lanes. `Lanes: none - <reason>` is accepted and announced on stderr. The stability digest is untouched (its code is identical to the helper before the change, which a test asserts): what a run demonstrated goes in `docs/flow-runs/issue-<N>.lanes-demonstrated.md`, a file of its own, and `compliance` names on stderr each `will test` lane with no row there, without changing its verdict. An earlier cut kept those rows in the record and exempted them from the digest; three review passes each found a way to hide a plan edit in the exempt part, so nothing is exempt. The helper reads the lane file itself (the Codex `flow-auto` bundle ships it without `lane-file.py`). Committed cases: `controls/flow-plan-record-lanes`, whose blind anchor is the helper at `6b6cc29e`. Background in [the plan-record reference](../agents/flow-plan-record.md)
- flow-plan-record lanes on the verdict line (#1767) - `compliance` puts `, LANES NOT DEMONSTRATED (<count>)` or `, LANES NOT CHECKED` (a state and a count; no lane name and no reason, so nothing on the line needs delimiting) directly after the `PLAN_COMPLIANCE` verdict word when a lane the plan answered `will test` has no row in `docs/flow-runs/issue-<N>.lanes-demonstrated.md`, or the lane file or that file cannot be read. One function, `lanes_at_close`, decides one of four states (nothing owed, all shown, missing, not checked) before any verdict is printed; the clause and the stderr note are both generated from it. Exit codes are unchanged and the line is byte-identical where nothing is owed (no lane file, a waived plan, no `will test` answer). The stderr note says what to do in each state and is where `/flow:auto` Step 5 sends a run. Where a lane result is owed, the demonstrated file is excluded from the touched files, like the plan record and the as-read snapshot (anywhere else a file at that path is an ordinary touched file, as before): counted, it turned `agreement` into `divergence` for every run that wrote it, a defect of #1731. Committed cases: `controls/flow-plan-record-lanes-verdict`.
- flow-plan-record lanes bound to the approval (#1821) - `approve` writes a lane stamp (`flow-plan-lanes-<N>` in the worktree's git directory, beside the baseline) recording the run, the approved section's digest, whether `.claude/lanes.md` existed, and the `will test` lanes. `compliance` takes what is owed from that stamp and never reads the lane file at close, and counts only rows below this run's own `<!-- lanes-demonstrated run=<id> plan=<digest> -->` line in `docs/flow-runs/issue-<N>.lanes-demonstrated.md`, up to the next such line (one outside a code fence); the stderr note prints the exact line. Two false greens found reviewing d90712ee: run 2 was satisfied by run 1's unchanged rows, and deleting the lane file after approval silenced the line (a test then required it). A first cut compared row text with the file at approval and upstream; counter-model review showed text cannot say which run wrote a row, so the run names itself. A missing, foreign, unreadable or malformed stamp, or a section changed since approval, reads `NOT CHECKED` where `will test` lanes are owed; a plan owing nothing is unchanged, a damaged stamp included. The delegated-driver core says to write rows under that line. New committed cases in `controls/flow-plan-record-lanes-verdict`: `bad-previous-run-evidence`, `bad-lane-file-deleted-after-approval`; case `demonstrated.md` files carry a `{{LANES_MARKER}}` placeholder the runners fill from the stamp.
- flow-plan-record lane results and named values (#1823) - a `docs/flow-runs/issue-<N>.lanes-demonstrated.md` row is `| <lane> | <result> | <evidence> |` (the evidence may follow the result in the same cell), the result one of `passed` / `failed` / `not run` / `refused as expected`, matched as a whole phrase; only `passed` or `refused as expected` with evidence counts, a lane's last row is its result, and the stderr note names every other owed lane with why (no row, no result state, `failed`, `not run`, no reference). `will refuse` lanes are owed at close too: the lane stamp is version 2 (a version-1 stamp is read as it was written). `approve` refuses a `will test` row that names none of its lane's `Values` (split on ` / ` and `;`, parentheticals dropped, emphasis/case/spacing ignored); a lane with no values is not checked. Found reviewing d90712ee: any non-empty cell counted (`row[1].strip()`), so `TODO` and `failed` passed the check. New committed cases: `bad-result-state-todo`, `bad-passed-no-reference`, `bad-will-refuse-no-evidence`, `good-will-refuse-refused-as-expected` in `controls/flow-plan-record-lanes-verdict`, and `bad-will-test-names-no-values` in `controls/flow-plan-record-lanes`; each BAD case passes on the pre-#1823 helper.
- flow-plan-record run verbs (#1849) - `start` (reconcile, then read-issue), `approve --plan FILE` (checks the plan in memory - no run marker, a Section C with at least one parseable file line, the lanes table - then begin-run, append, approve; nothing written on a refusal) and `finish` (drift, compliance, head-check, every one run, each verdict line printed, then `FLOW_PLAN_FINISH: <verb>=<exit> ...`). A wrapper's exit is the worst inner one (error over unknown over finding over ok) and an inner crash is an error, so success is never reported over a failed or unavailable result. They dispatch from `COMPOSITE_VERBS`, which `check-driver-parity.py` reads to expand a wrapper into the verbs it runs; a tree whose `/flow:auto` drops `finish` loses `compliance` and stays `unknown`. Plain `approve` and every old verb are unchanged for the delegated drivers. `/flow:auto` uses the three and its eight-call assembly left it in the same change. Tests: `tests/test_flow_plan_record_wrappers.py` (each red case fails on the pre-#1849 helper) and the run-verb cases in `tests/test_driver_parity.py`

- Optional provenance validation (#1877, owner option A) - `finish ISSUE --provenance-file FILE` reads the exact closing or PR text already written by the caller. Both `Origin:` and `Missed because:` must have one nonempty canonical value; identical repeated lines are allowed, conflicting values are refused. The closed lists are read from `docs/agents/closing-report-contract.md` under the helper's own package root, never from the consumer checkout or a copied list in code. The package must ship that contract beside its scripts. `FLOW_PROVENANCE: valid` (0), `invalid` (1), or `unknown` (4) appears only when the flag is supplied, and `provenance=<exit>` joins the finish summary's worst-of result. Drift, compliance and head-check still all run. An unreadable input or unreadable/malformed contract is UNKNOWN. Without the flag, output and exit behavior are unchanged and no provenance check is claimed. This is an optional report-only capture point, not a required fix-work gate, a backfill, or a claim that the account is true or was published. Tests drive the real finish entrypoint and feed the same captured text to the real review-yield reader. Committed controls: `controls/flow-plan-provenance` (invalid, missing, conflicting, valid, unavailable contract); its constructed anchor mistakes readable text for valid values while preserving UNKNOWN.
