# `flow-wave-mailbox` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `flow-wave-mailbox`

- flow-wave-mailbox `ps -ww` argv widening (#904) - the `ps` watcher lane read `ps -eo pid,ppid,args --no-headers`, and without `-ww` procps caps every line at the terminal width, or at `$COLUMNS`, WHICH A CLAUDE CODE SESSION SETS AND EXPORTS (120 on the host this was found on). A watcher's argv carries the absolute path of `flow-wave-mailbox.sh`, so whether the `--role` and `--wave` fields survived the cut depended on how long the checkout path was. Measured on one host, same moment, same processes: plain capped every line at 120 and found 2 watchers; `-ww` gave max line 2576 and found 5. The orchestrator independently measured a 4x undercount (1 vs 4) on the same process class, and reproduced the resulting test failures on origin/main rather than only in a fixture. The failure direction is the dangerous one: a cut landing before `--role` leaves a line the scan never recognises as watcher-shaped, so it is skipped and the lane reports a CONFIDENT zero rather than `unknown` - #917 reports `unknown` when the `--wave` field is unreadable and cannot help here, because there is nothing left to flag. An armed worker reads as deaf, and `watch=DEAD(0 watchers)` is a BLOCKER signal in `/flow:wave`'s own hazards, so an orchestrator refuses to assign to a worker that is in fact listening
- flow-wave-mailbox: the live variable is `$COLUMNS` x prefix length, not "a long path" (#904) - with `-ww` the two #845 lane tests pass at COLUMNS 40, 60 and 120; without it they fail at 40 and pass at 120. Path length matters only because it consumes the width budget before the match token, so a short checkout masks the defect and a long one exposes it - which is why this presented as an environment-dependent flake and why it reproduced in some worktrees and not others. `-ww` overrides `$COLUMNS` outright, so the scan stops depending on the environment it happens to run in. With `COLUMNS` UNSET `ps` does not truncate at all (max line 2576), which is the trap for anyone testing this: a test relying on the ambient width is INERT wherever `COLUMNS` is unset, so `tests/test_flow_wave_mailbox.py::TestPsLaneArgvTruncation` sets `COLUMNS=60` itself and asserts, as a precondition, that the cut really did land before `--role`
- flow-wave-mailbox: the portability objection dissolves, and the ancestry walk is deliberately untouched (#904) - `-ww` looks like it narrows portability and does not: `--no-headers` is a procps-ng long option that BSD and macOS `ps` lack and busybox lacks along with `-eo`, so this invocation was procps-ng-only before `-ww` was added and `-ww` claims no surface `--no-headers` had not already claimed. The six `ps -o ppid= -p <pid>` ancestry-walk sites are NOT widened, measured rather than assumed: that form prints one ppid and is byte-identical at `COLUMNS=20` with and without `-ww`, so it has no argv to widen and gains nothing. Three argv copies changed (the script plus its two generated codex mirrors, regenerated with `make codex-skills` rather than hand-edited); nine sites matched the initial grep and six of them were correctly left alone
- flow-wave-mailbox: `-ww` does NOT retire the `unreadable` conservatism, ruled and recorded beside the branch (#937, ADR 0009) - the three #904 bullets above read as though widening the `ps` view removed the reason for reporting `unknown` on a watcher-shaped line whose `--wave` could not be read, which would make the surviving `unreadable=1` a mitigation outliving its cause. It is not, and the reason is that `-ww`'s protection and this lane's REACHABILITY are disjoint sets: `watcher_roles_live` selects `watcher_roles_ps_fallback` only when `[ -d /proc ]` is false, so the lane is dead code on Linux (this file already said so at the #845 bullet); and a host with no `/proc` is a host where `ps` is not procps-ng, while `-ww` - like the `--no-headers` in the same invocation, per the bullet above - is a procps-ng guarantee. `-ww` therefore retires the ambiguity only on the hosts where the branch never runs. Measured rather than argued, one planted no-`--wave` watcher, same host and instant: the `/proc` lane answered `0` for a NAMED wave while the forced `ps` lane answered `unknown` - so the `unknown`-floods-the-fleet cost that argued for removal is paid on the forced lane only. TWO SIDED, so it carries its reversal trigger next to the setting per ADR 0009, and deliberately not the rate the issue proposed (`unknown` above some share of real arms) - that keys on a currently EMPTY population and a trigger that cannot fire is the blind instrument one level up; the committed trigger is the lane becoming reachable WITHOUT `FLOW_WAVE_WATCHER_SCAN=ps` on a host that runs waves, measured there. The asymmetry the issue asked to stop - absence of `--wave` read as a FACT when our wave is `default` and as an AMBIGUITY when it is named - is documented as deliberate rather than removed: measurement showed both routes already emit `unknown` (the match route via #845's guard, which makes this lane two-valued, `0` or `unknown`, never a positive count), so the symmetric spelling looks free and is not - the fall-through is forward-compatible with #845's guard being lifted, where it would yield a real count, while an unconditional `unreadable=1` would stay needlessly blind. The default-wave direction had NO committed case before this, so the one-line edit that resolves the asymmetry the obvious way reded nothing; `test_a_no_wave_watcher_on_the_default_wave_is_also_unknown` closes that, and three mutations were run to prove the battery discriminates rather than merely goes red (that edit reds the new case alone, deleting the named-wave `unreadable=1` reds its sibling alone, a bare `continue` reds both)

- flow-wave-mailbox - the wave DELIVERY lane (#676), sibling to the #638 registry and sharing its wave dir, lifetime and host-local scope. #638 and its follow-ups built a reliable address book; none of it delivers, and on 2026-08-11 the harness rejected every orchestrator->worker `SendMessage` (it routes only to subagents the calling session spawned), so a fully-written assignment sat undelivered ~2h while both sessions correctly stood by and the only working transport was the user typing a pointer into the worker's terminal. `send`/`read`/`watch`/`list` over `$XDG_RUNTIME_DIR/cc-flow-wave/<wave>/`: orchestrator->worker writes `outbox-<role>.md`, worker->orchestrator writes `inbox-<role>.md` - one box per WRITER, so two workers reporting at once never contend and the orchestrator watches all inboxes with one `--role orchestrator`. Addressed by ROLE, the same declared identity the registry keys on, so the registry-address-only rule is obeyed rather than bypassed. Sends APPEND a rev-stamped block (a deliberate deviation from the issue's "rewrite-in-place", ruled at the #676 gate: overwriting an unread assignment with the verdict that follows it IS the delivery-loss failure the issue exists to remove); `--replace` opts into overwrite and still bumps the rev, so a replace can never read as already-consumed. Revs are per-box and monotonic under flock - pinned by an 8-way concurrent-sender test, since a shared rev is a dropped message. **`watch` is the half that makes this a lane rather than the ad-hoc 2026-08-11 workaround**: it BLOCKS until mail passes the read cursor, prints it and exits 0, so a session that arms it as a background call is re-invoked by the harness on arrival - a mailbox an idle session never reads is not a lane, which is why the workaround still needed a human to say "go read your outbox". Bounded (default 30m) so a wave cannot leave watchers spinning; timeout is exit 5 and the message explicitly refuses to read that as "the counterpart is gone". `list` surfaces per-box rev/cursor/unread, so an assignment a worker has NOT consumed is visible instead of being invisible until someone asks. Honestly scoped: HOST-LOCAL, exactly like the registry - two sessions on different machines still have no transport
- flow-wave-mailbox watch heartbeat (#778) - `watch` was the mandatory step whose ABSENCE was undetectable: an unarmed watch looks identical to an armed one from outside, so the roster could show a live, verified, brief-current worker that nothing would ever wake (the 2026-09-05 `kyle-completion` hour). Now `watch` stamps `.watch-<role>` in the wave dir with the current epoch - one integer, exactly the shape of `.cursor-<box>` - ON ARM AND ON EVERY POLL, not just on arm, because only a REFRESHING stamp separates a watch that was KILLED from one that is merely blocking; the stamp re-reads the clock each poll rather than reusing the start-of-script value, or a 30m watch would age out underneath itself and report the very false `stale` it exists to distinguish. Three states: `armed` (stamped within `FLOW_WAVE_WATCH_STALE_SECS`, default 300), `stale` (older - dead watch, or a session busy between wakes; deaf either way, and the age is always printed so the reader judges which), `absent` (never armed - the unambiguous case, and the one actually observed). The stamp is deliberately NOT removed on exit, since "died" and "never armed" are different operational answers and erasing it would flatten them back into one; `read` does not stamp, because the heartbeat is about the WAKE and an advancing cursor is separately visible. Written outside the mailbox flock on purpose - a single-writer, whole-file, last-write-wins stamp with no read-modify-write, where taking the lock ~600 times per watch would make the wake path contend with every send for no correctness gain. `list` gains a `reader` per box (outbox -> that worker, inbox -> the orchestrator), an ISO `mtime` in `--json`, and a `watches` array covering every role with a box OR a heartbeat - the second disjunct matters, since arming before the orchestrator sends anything is the HEALTHY order and a box-only scan would miss exactly the roles doing it right. `FLOW_WAVE_NOW` is honored for age computation so the states are testable without sleeping. SUPERSEDED IN PART by #801: these three states read the stamp ALONE, and a stamp is only as fresh as the last wake - `armed` was therefore reported for a watch that had already exited; the state is now fused with the live watcher count
- flow-wave-mailbox confident-wrong reporting (#792, follow-on to #778) - seven defects found in one night of an 8-worker wave, each by a session hitting it rather than by reading the script, all sharing one shape: a channel that failed quietly and reported confidently rather than erroring. (1) `watch` used to consume by default - arming as orchestrator with 42 unread across six inboxes printed one message and advanced every cursor to the end, so 41 messages were marked read without ever being shown. There is no default now: `watch` REQUIRES an explicit `--peek` or `--consume` (usage error otherwise), and the two are mutually exclusive. (2) The arm/read ordering flips depending on which was chosen, and nothing said so: with `--consume`, arm THEN read (the wake itself advances the cursor); with `--peek`, read THEN arm (the cursor never moves, so arming first on an unread backlog spin-fires on the very message just read) - found independently by three sessions within minutes of each other. Now, if a watch fires on its very first poll - mail was already unread the instant it armed, not a fresh wake - it prints a `flow-wave-mailbox: NOTE -` line ahead of the message body saying so, pinned by a test that a genuinely fresh wake (mail arrives while already blocking) prints no such line. (3) A watch is one-shot, so a bare unread count is undiagnosable - zero is both the healthy transient (just woke, re-arm pending) and the failure state (blind), and nothing outside the session can tell which. `watch --status --role <r> [--wave W]` reports the heartbeat state/age plus a `re-armed: yes/no` verdict instead. (4) Duplicate watchers accumulated silently - a role is single-owner by construction, so a second live watcher is always a mistake, competing for the same mail rather than each getting a copy; the common trigger is bundling a watch onto the tail of another command (`... register ; ... watch`). `watch` now refuses to start (exit 4, `duplicate`) when a live watcher already holds the same role in the same wave. (5) The counting logic itself double-counted: a `pgrep -cf`-style flattened-string match over `ps -eo args` matches a background launcher's `/bin/bash -c "<text>"` wrapper (whose one `-c` argument IS the inner command's text, so it structurally carries the same pattern as the process it wraps) AND the measuring pipeline's own invocation - a fleet-wide alarm on 2026-09-05 published counts uniformly 2x reality, and the tell was that every number was even. `count_watchers()` (the function's name then; #1228 inlined it into `watch`, and the scan is `watcher_roles_live` today) reads each candidate's REAL argv from `/proc/<pid>/cmdline` (falling back to `ps` on a host with no `/proc`) and requires `argv[1]` to BE the script path - never a substring of a `-c` blob - which excludes a wrapper structurally rather than by trying to pattern-exclude text that could just as easily be legitimate. Self-exclusion walks the FULL ancestor chain (`/proc/<pid>/status`'s `PPid:`, from `$BASHPID` up to PID 1), not one PID: the scan runs inside a `$(...)` subshell, and the subshell's PARENT - the real, currently-alive top-level process, legitimately blocked waiting on this very check - carries the identical argv under a different pid, since `$$` keeps reporting that parent's pid even from inside the subshell. Verified empirically while building the fix: excluding only `$BASHPID` still found "1 live watcher" for a role that had none. (6) A watcher launched from a since-removed worktree prints its mail, then a HARNESS wrapper's trailing `pwd -P` (run after this script has already exited 0) fails with `getcwd: cannot access parent directories` and the WRAPPER reports exit 1 - misdiagnosed twice as "the watcher died" when the mail had in fact arrived. This is outside the script's control (the trailing command runs in the caller's shell after the script exits), so the fix is documentation: the discriminator is in the captured OUTPUT, not the exit code - `FLOW_MAILBOX: mail` (or any body) present means delivered regardless of what runs after; a bare pwd error with no prior output means genuinely lost. Generalizes to any monitor launched from a removed worktree. (7) `read --role orchestrator` had no way to read one correspondent's box, and draining all of them non-interactively through a filter destroyed 13 messages' content in one command. `read --from <role>` (orchestrator only) narrows to one inbox; a CONSUMING orchestrator-wide read (no `--from`, no `--peek`) run non-interactively (`[ -t 1 ]` false, e.g. any subprocess-captured or piped invocation) now refuses without `--out FILE` - a durable copy of the drained body taken before the drain - while a worker's ordinary single-box `read` is unaffected, since it never had this multi-box hazard. 65 tests total; the seven new fixtures are `TestWatchRequiresExplicitChoice`, `TestWatchStatus`, `TestDuplicateWatchers`, and `TestReadFromAndDestination`, plus additions to `TestWatchIsTheWake`
- flow-wave-mailbox fused watch state (#801, follow-on to #778/#792) - `watch --status` printed `(state: armed); 0 live watcher process(es)` - two halves of one line contradicting each other, with the reassuring half leading. The state came from the `.watch-<role>` heartbeat STAMP alone, and a stamp is only as fresh as the last WAKE, while the watch is ONE-SHOT: it delivers one message and exits. So for the whole `FLOW_WAVE_WATCH_STALE_SECS` window after a watch fires and dies, every surface reported `armed` about a role that was deaf. Not theoretical - on the `docker-list` wave (2026-09-07) the orchestrator broadcast "check `--status`; if it is still holding, do nothing" to three workers on the strength of that word: all three were deaf, worker-C held a Step-3 gate request unheard for ~50 minutes and was found only because a human asked "what about worker C", then went deaf a SECOND time straight after reporting a PR done and self-reported "standing by idle" while its next assignment sat unseen in its box; worker-A sat BLOCKED on a ruling already written; and the orchestrator's own watch died repeatedly, twice leaving a worker blocked on a ruling it had already made. The state is now FUSED from the live watcher count and the stamp: `armed` (watcher live, stamp fresh), `stale` (watcher live, stamp NOT refreshing - hung or SIGSTOPped, a different repair from gone), `dead` (stamp, NO live watcher - the case that read `armed`), `absent` (never armed), `unknown`. The heartbeat AGE is still reported in every state, because separating "died just now" from "died an hour ago" is what the stamp is genuinely good for and all it was ever trustworthy for. `unknown` is the #800 convention arriving in this helper - an un-enumerable process table is never rounded down to 0, which would report `dead` for healthy watches and drive re-arms that then collide with the watcher the count could not see (exit 4). The two consumers fail in DELIBERATELY OPPOSITE directions: the #792 duplicate-arm guard treats `unknown` as 0 and lets the arm proceed (a wave that cannot start because its duplicate guard is unavailable is worse than an occasional false duplicate), while reporting treats it as `unknown` and says so loudly. `list` gains a `WATCHERS` column and `watches[].watchers` in `--json` (null, never 0, when unreadable) plus separate `NOT LISTENING:` and `UNKNOWN:` advisories - kept apart because `unknown` is not a claim that nobody is listening, it is the refusal to make either claim - and the #638 roster renders `watch=DEAD(0 watchers)` / `watch=UNKNOWN` and counts both into `FLOW_WAVE_WATCH_UNARMED` and the `WATCH:` summary, where only `absent`/`stale` counted before. TWO COUNTING DEFECTS fell out of making the count load-bearing, both the #792 item-5 failure in new clothes: a `watch --status` query shares the watcher argv shape but watches nothing, so it was counted as a live watcher - the instrument perturbing its own reading, and enough to make a concurrent real arm refuse as a `duplicate` against a process that was only a question; and a command-substitution subshell is FORKED, not exec'd, so it inherits the watcher's argv verbatim and one live watcher read as up to FOUR while it ran its own poll (nondeterministically, since the subshells are transient). Both are excluded structurally rather than by pattern: `--status` in argv disqualifies, and any match whose PARENT also matched is a subshell of a watcher, never a second one. `FLOW_WAVE_WATCHER_SCAN=proc|ps|none` is a test hook that makes the `unknown` lane reachable on a host with a working /proc and exercises the `ps` fallback, which is otherwise dead code everywhere the suite runs - an unverified guard against confident wrong answers being the obvious hazard
- flow-wave-mailbox explicit acknowledgement (#815) - `read`/`watch` advanced a read cursor as a SIDE EFFECT of printing output, conflating "surfaced" with "received": a dropped tool response, a truncated batch, or a `--out` destination that failed to write all silently and permanently lost the message, because the cursor had already moved past it - the next ordinary read reported empty while the caller had never actually received anything. `.cursor-<box>` is retired for `.ack-<box>`, a SET of acknowledged revs (not a watermark), so an out-of-order or partial-batch ack cannot silently imply an earlier, unseen message was received. A new `ack --role <role> [--from <role> | --box NAME] (--revs R[,R...] | --all-unacked)` verb is the only thing that records a receipt, and refuses (exit 2, all-or-nothing on a batch) a rev that does not exist yet in the box - acknowledging a message you could not have received. `read --peek` / `watch --peek` now print WITHOUT acknowledging anything, so a dropped response after a peek leaves the message exactly as unread as if it had never been shown; `read` (bare) and `watch --consume` keep the pre-#815 print-and-acknowledge-immediately behavior as a NAMED legacy convenience (the issue's explicit allowance), unchanged in observable timing and still carrying the same best-effort caveat it always silently had. `read --out` now writes its destination BEFORE any acknowledgement (was: cursor advanced first, so a failed write still consumed the message) - the ordering bug the issue's evidence #3 reproduced directly. `list`'s `CURSOR` column/JSON key becomes `ACKED`/`acked` - the count of revs a box's reader has explicitly acknowledged, not a read position - which required a companion rename in `flow-wave-registry.sh` (`mailbox_box_field ... cursor` -> `acked`, its `mailbox.cursor` JSON key -> `mailbox.acked`, and `mailbox_never_read`'s "cursor 0" check -> "acked 0"), since the registry joins the mailbox's own `list --json` output rather than reimplementing the parse. No migration tooling: wave dirs are ephemeral (`$XDG_RUNTIME_DIR`, wiped at reboot), so a box touched before this fix simply has no `.ack-<box>` file yet, and its absence means "nothing acknowledged" - the safe direction, never "everything up to the old cursor was implicitly acknowledged" - with `ack --all-unacked` available as the explicit, deliberate way to close that gap for a caller who has already durably processed a pre-#815 backlog by other means
- flow-wave-mailbox supervision + route readiness (#814) - `watch` delivers one message (or a timeout) and exits by design, so every wake needs a NEW `watch`, armed by whoever is listening - and "whoever" was always the conversational agent. Three sessions hit this building #814 and #815 in ~90 minutes (see the incident comment on issue #815): a watch backgrounded with `&` into `/dev/null`, a watch that died with no output, and a 25-minute forgotten re-arm that left seven messages waiting, caught only because a different session noticed the silence from outside. New verb `supervise --role <role> [--wave W] [--timeout SEC] [--interval SEC]` makes "a listener for this role exists" independent of any agent remembering anything: the INVOCATION returns promptly with its own verdict line (`supervising` or `duplicate`, exit 4), like every other verb; a DETACHED daemon it forks is what persists, repeatedly re-arming `watch --role <role> --wave <wave> --consume` so each inner watch still exits and still triggers the harness notification for whichever session is separately listening for it - `supervise` guarantees a listener always EXISTS, it does not and cannot replace arming one, and the code says so rather than promising delivery no script can force. Single ownership is a LIFETIME `flock` on `.supervise-<role>.lock`, held for the daemon's entire life - NOT a PID file checked with `kill -0`, which was the first draft and was corrected in review: PIDs are reused by the kernel, so a dead daemon's PID recycled to an unrelated process would make `kill -0` report "alive" and refuse a real supervisor, reproducing #821's argv-collision defect one layer up (an identity check that distinguishes "a process" from "no process" but not "MY process" from "some process"). The kernel releasing a flock the instant its holder dies makes "the lock is free" and "the previous holder is dead" the same fact, with no reclaim logic to get wrong - PROVIDED nothing else inherits that same fd (issue #1033 item 1): the daemon's own inner `watch` child used to inherit fd 8 like any other backgrounded subprocess, so a SIGKILLed daemon's still-running child (reparented to init) kept the lock held until IT exited, making a fresh `supervise` refuse as `duplicate` against a lock its owner no longer existed to hold. The inner invocation now closes it explicitly (`8>&-`), verified directly: SIGKILL the daemon, then `supervise` again immediately - it succeeds at once, with the orphaned child still alive and irrelevant. `.supervise-<role>.pid` still records the PID, but only for a human to read, never as the liveness test. Shutdown polls the sibling `flow-wave-registry.sh get <role> --wave <wave>` (positional role - that script has no `--role` flag, unlike the mailbox's own parser, a real bug caught only by testing the actual invocation, not by reading the code) and exits cleanly within one `--timeout` of `FLOW_WAVE_LIVENESS=released` - not the moment it is released (issue #1033 item 4): the check sits at the top of the loop, whose body then blocks in the inner `watch --timeout`, and the identical bound applies to a TERM/INT signal sent directly to the daemon, since bash defers a trapped signal until that blocking foreground command returns (measured landing at t+4.0s against `--timeout 4`, claude-power-pack Nit Store #864). `watch --status` reports the daemon's own `--timeout` as `FLOW_MAILBOX_SUPERVISE_TIMEOUT` so a reader can compute the bound instead of assuming zero latency. Deliberately NOT triggered by `get`'s `free` verdict alone, which also covers "never registered at all", a legitimate standalone use of `supervise` without the registry that must not self-terminate on its very first loop check (an earlier draft conflated the two and killed itself in exactly that case, caught by tests that omitted registration). Argument validation happens ONCE at daemon start, not per loop iteration, so a bad role/wave name is a clean immediate failure rather than a restart storm; `$0` is likewise resolved to an ABSOLUTE path once, by `supervise` before it launches the daemon, rather than left for the daemon to re-resolve later against a cwd that may not survive it (issue #1033 item 2: two daemons were found pinned at `rc=127` for 13h48m because their re-arm, `bash "$0" watch ...`, depended on a relative `$0` and the worktree cwd it was launched from had since been removed) - the constant-rc-at-cap terminal case above is that exact incident's own shape; a crashed inner watch (any exit other than 0/delivered or 5/timeout) gets exponential backoff, capped (`FLOW_WAVE_SUPERVISE_BACKOFF_BASE`/`_CAP`, default 2s/60s), so a persistently failing cause cannot spin the daemon at full speed; a cap reached with a CONSTANT rc for several consecutive cycles (`FLOW_WAVE_SUPERVISE_TERMINAL_STREAK`, default 3) is treated as terminal rather than retried forever (issue #1033 item 2, a deliberate behaviour change - the `$0`-relative-path incident below is exactly this shape, and nothing about waiting longer changes an unchanging cause). `.supervise-<role>.log` records only structured, sanitized evidence - timestamp, event kind, exit code - NEVER message bodies, which stay in the mailbox's own files with their own access boundary; the inner watch child's stdout, which DOES carry bodies on delivery, is discarded, not relayed anywhere new. Separately, `route_state()` (also #814) answers a DIFFERENT question than watch state: not "is a process polling" (#821-tainted, unchanged) but "has anything actually been acknowledged" (#821-immune, built on #815's ack evidence instead of the process table). FOUR states, not three: `confirmed` (an ack recorded since the last surface - positive evidence), `pending` (unacked, younger than `FLOW_WAVE_ROUTE_UNCONFIRMED_SECS`, default 900s - no verdict yet), `unconfirmed` (unacked, older than the bound - the alarm), `unknown` (no messages at all, or unreadable - nothing to check, and so NEVER `confirmed`; an empty box being reported as a working route was the exact "reports success by checking nothing" defect found the same day in #816's tripwire, #821's counter and #828's helper loop). The readiness clock reuses each message's own send `ts=` (#676) rather than persisting a new "first surfaced" timestamp - deliberately conservative, since it can only flag a route unconfirmed EARLIER than a stricter clock would, never later. Reported as `list`'s `routes` array, a SIBLING of `watches`, never merged into it - the #801 lesson (`(state: armed); 0 live watcher process(es)`, one line contradicting itself) enforced in the JSON schema this time, not only the prose - with a matching `flow-wave-registry.sh` join (`mailbox_route_state`, a `route:{state}` object beside `watch:{...}`, and a text `route=` column beside `watch=`) for the same reason `acked` joined the registry in #815: visible from a roster sweep, not only from asking one mailbox directly. `register.md`/`wave.md` Step 4 now launch `supervise` by default (a bare, manually re-armed `watch` remains documented as the fallback) - opt-in was considered and rejected: the sessions who most need a supervisor are precisely the ones who will forget to reach for it, which is an opt-in guarded by the thing it guards against. What this does NOT promise, and why it is a choice rather than an impossibility (corrected under #898): the code and the PR both said no script could make the harness re-invoke a specific agent's conversation on a background process's completion. That absolute was wrong and carried no harness version. #868 measured (2.1.266, 2026-09-13) that a correctly-formed write to a session's inbox socket DOES render as a turn - 5/5 from a writer whose parent chain still reached the session - and that delivery is gated on process LINEAGE, not on holding the credential: writers reparented to init were accepted by the socket and never delivered, 0/4, matching `verifiedPeerPid`/`expectPeerProcStart` in the installed binary. Inheriting `CLAUDE_CODE_MESSAGING_SOCKET`/`_TOKEN` is not sufficient and was never the question - both survive into a `setsid`-detached grandchild and the write is still dropped. `supervise`'s daemon detaches precisely so it outlives the launching turn, which makes it the orphaned shape BY CONSTRUCTION, so the one process that would do the waking is the one that cannot be delivered from - this lane's own design in tension with itself, not a capability the harness withholds. `supervise` therefore still guarantees only that a listener keeps existing, never that the agent behind it is told, and `route: unconfirmed` remains the honest report of that residual gap. Two bounds keep it that way regardless: the socket RETURNS NOTHING, so a successful write is not evidence of delivery even where delivery works, and across containers the identity problem is upstream of lineage (#945/#947)
- flow-wave-mailbox watcher identity across wave directories (#821) - the watcher count (`count_watchers()` at the time) could not distinguish a live watcher from an orphaned command-substitution subshell of a dead one, measured 12/12 (10 clean, 2 runs at 4 and 5 orphaned survivors, no exceptions): `watcher.kill()` genuinely reaps the direct child, but that child's OWN subshells are forked (not exec'd), carry byte-identical argv, are unreached by a signal to the parent, and reparent to init to live until their own `--timeout`. #792 item 5's Phase-2 parent-filter cannot catch this - its own stated invariant, "a subshell's parent is always the watcher", holds only while the watcher is alive, so an orphan survives the filter BY VIRTUE of having been orphaned. This surfaced as `TestWatchStatus`/`TestDuplicateWatchers` (mailbox) and `TestWatchColumn` (registry, which has no scanner of its own - it consumes the mailbox's fused `list --json` verdict) failing intermittently, "passes in isolation" being FALSE for this one specifically because the orphan leak crosses invocations, not just runs. The trap for anyone investigating: `pgrep -f` (or any tool matching argv as a flattened substring, `/proc`-based scans included) manufactures the exact phantom under investigation, because the pattern searched for is present in the searcher's own command line - already documented as the reason `pgrep -cf` was replaced, and still re-derived the expensive way live during this repo's own gate-process hunting.
