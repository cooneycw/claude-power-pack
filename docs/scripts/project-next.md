# `project-next` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `project-next`

- project-next - CPP's thin extension boundary around the pinned vendored engine: it normalizes GitHub-native relationship evidence BEFORE the engine and appends `cpp_extensions` after it, never re-ranking, filtering, or correcting a `RecommendationResult`
- project-next ledger decision routing (#1398) - a spec's own `.specify/specs/*/ledger.md` "## A. Owner decisions" table is a SECOND registry of the same kind of object as a Wayfinder `DNNN` decision: a named, owner-held gate with a stated blocking effect, each row headed `### QN - <status>`. Before this, an issue citing a pending `QN` (`**Blocked on Q8**`) read as an ordinary, resolvable `uncertain` - the engine's dependency parser cannot resolve `Q8` to a local issue or task, so the reason said "the blocker names no issue or spec task" for a decision this repository's own ledger actually enumerates. `planning_routes()` now reads every discovered ledger and routes a `QN`-referencing issue to `/project:init` the same way a `DNNN`-linked one already was, naming the specific ledger path and decision id in the reason. A RESOLVED row (anything whose status text says so) routes nothing - the decision no longer blocks. An UNREADABLE ledger must not read as "no open decisions" - the exact false-clean this issue is about - so every `QN`-referencing issue is routed conservatively, naming the parse failure, rather than silently finding zero pending rows in a ledger that could not be parsed at all. CPP-local (`scripts/project-next.py`), no engine contract bump - the absorbed Nit Store comment named this half explicitly as CPP's own, separate from the engine's dependency-parser overload
- project-next premise staleness (#770) - WSJF ranks value, effort, and unblocking, all properties of the issue itself, so an issue whose parent specification was written under a premise a later decision retired still ranks as small, well-formed, and safe (observed on kyle `flow:auto #443`: a top-3 safe start whose spec assumed multiple Discord humans, months after the single-owner decision merged; only the ELI5 gate plus owner memory caught it, one step before implementation). The adapter now reads `docs/decisions|adr|adrs/NNNN-*.md`, keeps only records whose status still reads `Accepted` (a superseded or rejected record states no live decision, and the successor that replaced it carries its own date), and pairs each against the parent spec's as-of date - the later of its `Created` and `Amended` headers, so an amended spec is never accused of predating a decision it already absorbed. Domain evidence is declared domains on both documents first, shared significant terms second, with the matched term and which of the two produced it named in every flag. Output is a flag plus a reason in all three render modes and in `cpp_extensions.premise_flags` - deliberately NOT the WSJF penalty the issue floated, which would contradict the adapter's never-re-rank invariant; `/flow:eli5` stays the necessity decision point
- project-next worktree delivery (#1257) - the engine's cleanup candidate for a worktree whose branch maps to no open issue said "it may be merged, closed, or abandoned" in two opposite states: a leftover whose work already landed, and a tree holding work that exists nowhere else. Ancestry cannot separate them - after a squash merge `--is-ancestor` says no and `rev-list --count` says 1 for fully delivered work (nit store #864). `cpp_extensions.worktree_delivery` now annotates every such candidate by BLOB IDENTITY: the paths the branch changed since its merge-base, intersected with the paths that still differ between `origin/<default>` and HEAD; an empty intersection plus a clean tree with no untracked files is `delivered`, anything else `not-proven` (never "undelivered" - the base may have edited those files since), and any git failure `unknown`. The tree state is re-read rather than taken from the collector, which AT THE TIME turned a failed `git status` into clean (closed registry-wide by #1398, below) - the re-read survives as its own defense in depth, not made redundant by that fix; the remote branch is asked of `ls-remote` because the collector fetches without `--prune`, and the same answer confirms the local `origin/<default>` is the remote's current tip - a stale or unconfirmable base is `unknown`, since a failed fetch is only a collector warning. Status and diff pass `--untracked-files=all` and `--ignore-submodules=none`, because `status.showUntrackedFiles=no` or `diff.ignoreSubmodules=all` would otherwise make an excluded population read as clean (counter-model review). The real-git controls skip in the git-less CI image; the runner-injected unknown/positive-control cases run there
- project-next routing and classification correctness, contract v1.5 (#1398, four fixes behind one repin):
  - the rendered start command is `/flow:auto N`, Claude Code's own skill syntax (`lib/project_next/rank.py`) - codex-power-pack's leftover `$flow-auto N` never resolved on this surface and was never a route Claude Code could execute. `scripts/project-next.py`'s wayfinder-override regex (`_apply_route_rendering`) tracks the literal text and was updated in lockstep, or a wayfinder-routed issue's command would have silently stopped being overridden
  - `lib/project_next/collect.py`'s `_parse_worktrees` turned a FAILED `git status --short` call into `dirty=False` - a worktree nothing could examine read identically to one examined and found clean, and fed the "it may be merged, closed, or abandoned" cleanup text the LESS cautious "Review with $flow-cleanup" action (the removal-leaning one) instead of "Inspect uncommitted changes; do not remove automatically". `Worktree.dirty` is now `bool | None`, with a new `status_unknown_reason` field; the four decision sites that read it (rank.py's resume-top-action and off-open-issue warning and cleanup-action text, classify.py's in-flight evidence text) each treat `None` as "unknown is never clean" rather than falling through to the clean branch, and render.py prints `unknown (git status failed: <reason>)` rather than silently choosing "clean". Registered as `controls/project-next` (ADR 0008 census row 23, previously unregistered) - the row lets work THROUGH to `/project:next`, whose command document declares the JSON authoritative, so nothing downstream re-derives a startability lie
  - the dependency-text classifier (`lib/project_next/classify.py`) recognizes `owner/repo#N` as a reference to a DIFFERENT repository's issue, not merely "an issue reference present but not attached to the phrase" - the classification is unchanged (still `uncertain`: this repo's inventory cannot check another repository's state), only the reason text, which now names the external reference explicitly. Deliberately does NOT look it up via `gh` across repositories - the acceptance bullet asked for recognition, not a live cross-repo check, and widening to one is an explicit under-scope recorded on the issue
