# `flow-driver-retirement-check` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `flow-driver-retirement-check` (#1017)

- flow-driver-retirement-check - may a lifecycle driver command be DELETED? (#1017, executing the trigger #934 committed.) `--driver <name>` answers it across every wave, with three outcomes and three exit codes: `clear` (0), `blocked` (1), `unknown` (3). `unknown` IS NOT `clear` - that is the whole instrument. Deleting a driver removes the lifecycle instructions any session running on it is mid-way through executing, which #934 called "not a merge conflict; it is three in-flight PRs losing their driver mid-run", so the verdict authorises a destructive action nothing downstream re-derives (ADR 0008's bound).
- flow-driver-retirement-check WHY IT IS A SCRIPT AND NOT THE PARAGRAPH IT REPLACES - #934 committed the procedure as prose beside the command it governed, and #1017 asked for it to be RUN. Running it showed what re-reading it could not: its first guard was `raw=$(flow-wave-registry.sh list --wave "$W" --json) || { unknown; }`, and `list` EXITS 0 WITH AN EMPTY ROSTER when the registry does not exist (verified against `FLOW_WAVE_REGISTRY_DIR=/nonexistent`: the `merge_starvation` metadata block, `FLOW_WAVE: listed`, exit 0). So the branch that existed to say "I could not look" was unreachable, and a host with no registry read `RETIREMENT: clear` - the precise "no output, therefore nobody is there" collapse the prose spent three paragraphs warning against. A text search for the word `unknown` finds that check in perfect health. The registry FILE is therefore read directly, and its absence, unreadability or unparseability is `unknown`
- flow-driver-retirement-check TWO WRONG DIRECTIONS AT ONCE, which is why the four-value liveness vocabulary is load-bearing - an unreadable registry or an absent helper produces no matching output, and counting that as absence authorises deleting the command out from under a live session; while `list` renders RELEASED and STALE roles with their drivers too, so a substring scan counts sessions that ended months ago and blocks the retirement FOREVER (`worker-A` in `cpp-completion` is exactly that: `liveness: released`, `driver: flow:auto_codex`). Only `released` and `stale` are conclusively inactive
- flow-driver-retirement-check WAVES ARE ENUMERATED, NOT SUPPLIED - the registry helper has no verb that lists waves, so #934's procedure was per-wave by construction and left "a wave nobody thought to check" as a standing hole in a gate whose entire subject is the difference between looking and finding nothing. The wave set is derived from the registry's own top-level keys, so the denominator cannot silently exclude one; `--wave` still narrows it, but ONLY to a wave the registry carries - a misspelt name is `unknown`, because `list --wave <typo>` returns an empty roster and exits 0, and the narrowing flag would otherwise recreate the empty-population failure the gate exists to prevent (counter-model finding, 2026-09-16). Every run prints `RETIREMENT_WAVE:` per wave and a `RETIREMENT_SCOPE:` denominator (#952), and the `matched=` count is the load-bearing half - a green from a blind query and a green from a working one look identical
- flow-driver-retirement-check CONTROLLED (`controls/flow-driver-retirement-check/`, ADR 0008) - four committed cases: a `live` role must block, an `unknown` one must block, an ABSENT REGISTRY must read unknown (the blindness above), and a wave of `released`/`stale` roles must clear. The process table is pinned through the registry helper's own documented `FLOW_WAVE_LIVE_PIDS`/`FLOW_WAVE_UNKNOWN_PIDS` hooks so no case depends on a pid that happens to exist, and `FLOW_WAVE_HOST` is pinned too - an entry whose host is not this host reads `unknown other-host` regardless of its pid (`stale other-host` until #1014), so an unpinned hostname would quietly turn the live case into an unknown one. The ANCHOR is not an earlier revision of the gate (there is none) but the check that was really run while #1017 was filed: one pointed at `~/.claude/daemon/roster.json`, the wrong object, which reports clear on every input. #934's own prose procedure was considered and rejected as the anchor - it correctly catches the live and undetermined cases, so it would score the control INERT on two of three
- flow-driver-retirement-check INACTIVITY IS A TERMINAL SET, NEVER "NOT LIVE" (counter-model finding, 2026-09-16) - the first cut counted `live` and `unknown` by name and let the remainder fall through to inactive, so an entry with NO `liveness` field, or one carrying a state this gate has never heard of, read as conclusively inactive and CLEARED the retirement. Only `released` and `stale` establish inactivity; everything else is undetermined. The same not-pending-therefore-done shape the gate's own header warns about, one level in. Two further fixes from that pass: the jq extraction's exit status is checked under `pipefail` and the result must be exactly one JSON array, because jq prints a complete `[]` for a valid prefix and THEN dies on trailing garbage - a non-empty stdout is not evidence the parse succeeded; and an unreadable WAVE is counted apart from an undetermined ROLE, since one counter for both reported "1 role(s) of undetermined liveness" where no role had been read at all
- flow-driver-retirement-check first verdict (2026-09-16) - `RETIREMENT: clear` for `flow:auto_codex` across 6 waves, `matched=4`, all four in `cpp-completion` and none live or undetermined; `/flow:auto_codex` and `codex/skills/flow-auto_codex/` retired on the strength of it. The `--driver` argument is why the instrument outlives that deletion: the next retirement inherits it instead of improvising one
- flow-driver-retirement-check migrated onto gate-lib (#1127), and this is where the collision mattered most - `${2:?...}` exits 1 under bash and 1 is this gate's `blocked` code, so a dangling `--driver` reported as "at least one LIVE role drives on it", THE VERDICT THAT REFUSES A RETIREMENT. A usage error rendering as the safe-side answer is the worst direction to be wrong in, because nobody investigates a refusal that agrees with caution: the operator sees blocked, does not delete, and never learns the gate never ran. USAGE EXIT MOVED, {1 under bash, 2 under sh} -> 64; clear=0, blocked=1, unknown=3 unchanged. `--driver ""` is now accepted and caught by `[ -n "$DRIVER" ]` as `RETIREMENT: unknown`, exit 3 - measured, and it does NOT reach `clear`
