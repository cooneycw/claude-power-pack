# `check-oscillation` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `check-oscillation` (#936)

- check-oscillation - reports knobs that have been moved BACK (#936). The pattern is the owner's: an approach choice "runs down the middle of two trade-offs, and we inevitably oscillate back and forth to each side in a futile attempt to satisfy diametrically opposing desires." Each swing is locally correct - it fixes the pain actually present - and the pain on the OTHER side is invisible at that moment because it was fixed last time. The structural sibling of ADR 0008: that one says name the input that makes an instrument report the other verdict; this one says name the observation that would move a SETTING back. Same epistemics, different object. The directive half lives in the owner's own `~/.claude/CLAUDE.md`, outside this repo; what ships here is `docs/decisions/0009-oscillation-control.md`, the detector, and its controls
- check-oscillation THE SIGNATURE IS "CHANGED BACK", NOT "CHANGED TWICE". A knob tightened 60 -> 30 -> 10 is three edits to one threshold and is not oscillation; 30 -> 60 -> 30 is. The issue names the second half as the one that matters - "a detector that flags every threshold edit is noise, and it will be disabled, which is itself an oscillation" - so every test in `tests/test_oscillation_control.py` comes in pairs, and `test_the_corpus_contains_BOTH_verdicts` asserts the corpus is not all-positive, because the natural way to extend a corpus later is with more positives and a corpus of those cannot detect a detector wedged at `found`
- check-oscillation IT REPORTS, IT DOES NOT FAIL THE BUILD (owner ruling, 2026-09-15), and that is deliberately not the same as an exit code that cannot fail. `found` / `none` exit 0 - a verdict about the KNOBS; `unknown` exits 3 - a verdict about THIS RUN's ability to look. A population of zero is `unknown`, never `none` (#952): "I examined 400 knob changes and none reversed" and "I examined nothing" are different facts and share neither a word nor an exit code. `--exit-on-finding` exists ONLY so `controls/check-oscillation` can register a real two-sided case, because the framework decides a case from the exit code (`GOOD = exit == good_exit`) and a detector exiting 0 for both verdicts has its known-BAD case scored GOOD - the control would have been blind in exactly the way the framework exists to catch. Its committed reversal trigger is that the build must NEVER pass it
- check-oscillation THE POPULATION IS DERIVED FROM HISTORY; THERE IS NO KNOB LIST. Knobs are discovered by walking `git log --unified=0 -p` and pairing removed/added lines within a hunk by shared setting NAME, so a knob introduced next month is watched from its first edit. A hardcoded list of "the knobs worth watching" is a coverage enumeration, and this repository has repeatedly found those stale
- check-oscillation TWO OPPOSING EDITS IN ONE COMMIT ARE NOT AN OSCILLATION - a swing is across time, not within a single change. The first cut had no such rule and reported a lockfile's package sizes, both "moves" carrying the same sha; found by running the detector against this repository's real history rather than only against fixtures. The test pinning the rule was itself VACUOUS on its first cut: it built a two-revision fixture, which yields ONE move, and one move cannot form a pair - so the assertion passed with the rule deleted. Caught by mutation, not by reading, and the fixture now asserts it holds a pair of opposing moves before saying anything about shas
- check-oscillation `--window` is a threshold, which is one of the issue's own tells, so its reversal trigger is committed beside it in the source rather than in a PR body the next person to touch the line will not read. A control that exempts itself from its own directive is the most conspicuous possible way to fail. `test_the_window_actually_BOUNDS_which_pairs_are_reported` exists because the trigger is unsatisfied by a setting nothing reads: deleting the window comparison left every other test green, so the threshold carried a rationale and no behaviour
- check-oscillation THE EXTRACTOR WAS BLINDEST WHERE THE RULE IS STRONGEST, and this was found by probing it rather than by reading it. ADR 0009's strongest tell is "the diff touches a line whose adjacent comment exists to explain why it is set that way" - and the first cut required a value to be followed by `,;)]` or end-of-line, so `timeout = 30  # seconds, see ADR 0009` extracted NOTHING. The trailing context is now a negative lookahead `(?![\w.])`, which keeps the reason the delimiter class existed (`version = 1.2.3` and `sha = 3f2a` still match nothing) and lets any trailing text follow. Two siblings found in the same probe: `timeout: int = 30` keyed on `int`, so every annotated knob in a file collapsed onto one key and unrelated settings could appear to swing against each other - a finding pointing at the wrong line is worse than a missed one; and `exit N` was unanchored, so prose about exit codes became a knob named `exit` whose value swung between paragraphs, in a repository whose documentation discusses exit codes constantly. `exit` is now whole-line anchored, which deliberately gives up `[[ -n $x ]] && exit 3` - noise is not a neutral failure for a reporting detector, because being ignored is how it fails
- check-oscillation FOUR WAYS TO FAIL TO LOOK, one verdict, one exit code, four reasons - `not-a-git-repository`, `range-unresolvable`, `range-empty`, `no-knob-changes`, on an `OSCILLATION_REASON` line. The #953 convention one level down: a different CONCLUSION earns a new verdict, the same conclusion reached for a different cause earns a reason field. Folded together at first, so a range git REFUSED (`HEAD~200..HEAD` on a 90-commit history) printed the same line as a real history holding no knob edits, and a reader chasing the first would have gone hunting for knobs that were never the problem
- check-oscillation `(path, key)` IS NOT AN IDENTITY, and this was the sharpest of seven findings from the Codex pre-PR pass. One file can hold two call sites spelling the same setting: tighten `first(timeout=60 -> 30)`, and much later loosen `second(timeout=10 -> 20)`, and keyed on the name alone they form one series that appears to swing though neither site changed back - detector-contract question 2 (can a non-zero tell OUR thing changing from a NEIGHBOUR's) failing on the detector itself. The fix needs no language parsing: a real swing is CONTINUOUS, so a pair is required to satisfy `b.before == a.after`. The same requirement is what rejects two branches moving a shared base in opposite directions. Three siblings from the same pass: `--first-parent` is now the lineage, because `--no-merges` alone lists BOTH sides of every merge and interleaves them; any `+++` line is a file boundary, because matching only `+++ b/` left a git-QUOTED path (tabs, or non-ASCII under the default `core.quotePath`) pointing at the PREVIOUS file and credited its hunks to a neighbour that never reversed; and `--timeout 1m` / `60s` / `2m` read as 1 / 60 / 2 without a value boundary, so an unchanged-then-grown duration reported as a reversal
- check-oscillation THE SECOND CODEX PASS FOUND FOUR DEFECTS IN THE FIRST PASS'S FIXES, which is the argument for the second pass existing. (a) The annotation regex allowed a top-level comma, so `def f(timeout: int, retries=3)` read as `{"timeout": 3}` AND - because ANNOT claims the value span - suppressed the correct `retries` reading: moving retries 3 -> 5 -> 3 reported an oscillation against `timeout`, which never changed. (b) `(?![\w.])` is not a terminator; an operator or a unit may follow it, so `timeout = 60 * 60` read as 60 and `delay = "1 minute"` as 1 - `60 * 60` / `120 * 30` / `60 * 120` reported a reversal of a timeout that never moved, and quoted durations walked straight through the exclusion this detector claims for them. The value now requires a real terminator. (c) `--first-parent` paired with `--no-merges` drops every change DELIVERED BY a merge commit, not merely merge-resolution ones: on a repo that merges PRs rather than squashing, two PRs taking a setting 30 -> 60 -> 30 produced NO moves at all, total blindness reading as `none`. Now `--first-parent --diff-merges=first-parent`, no `--no-merges`. (d) Continuity checked between ADJACENT moves silences a real swing the moment anything lands between its halves - first 60 -> 30, second 10 -> 20, first 30 -> 60 - so moves are threaded into per-site CHAINS before the direction test rather than filtered pairwise after it. Without (d)'s test, the fix for a false positive is indistinguishable from a wedge at `none`
- check-oscillation ONE MUTATION DELIBERATELY SURVIVES AND IS RECORDED AS SUCH - deleting the explicit `--diff-merges=first-parent` kills no test, because git has implied it from `--first-parent` since 2.36 and this host runs 2.43. It is load-bearing only on git 2.31-2.35, so the behaviour cannot be produced here at all; `test_the_explicit_diff_merges_flag_is_present` asserts on argv text and says in its own docstring that it is a guard on INTENT, weaker than every other test in the file, and that a reader taking it for a behavioural check will over-trust it. The same shape as any check whose input is host state: load-bearing in one environment, inert in another
- check-oscillation THE CONTROL'S CASES ARE CAPTURED `git log -p` OUTPUT BECAUSE GIT IS NOT IN THE CI IMAGE, and this was learned the expensive way. The first cut registered committed BARE REPOSITORIES as the cases; it was green through `make verify`, `check-negative-controls --strict`, 16 killed mutations and two Codex passes, and then CI reported `FileNotFoundError: [Errno 2] No such file or directory: 'git'` -> `expected=BAD observed=UNSIGNALLED (exit 1)` -> the framework's own verdict non-zero. A NEW control took down the gate that every OTHER control is read through. Precisely the hazard `check-negative-controls.py`'s header already documents about its anchors ("a `git show` anchor would have worked where it was written and been INERT where it gates"), reproduced one layer up by someone who had read that paragraph. The detector grew `--from-log`, both paths share one `parse_log` so the control cannot demonstrate something other than what ships, and a parity test asserts agreement on BOTH verdicts - a parity test on the reversed case alone passes for a parser that finds everything. Reproduced locally afterwards under `env -i PATH=<no-git>`, which is the only way this failure is visible off CI
- check-oscillation git ABSENT is now `OSCILLATION_REASON: git-unavailable`, UNKNOWN, exit 3 - not an unhandled `FileNotFoundError`. A traceback exits non-zero, and to anything reading exit codes that is indistinguishable from a detection, which is what the framework's UNSIGNALLED verdict exists to say. The test asserts `Traceback` is absent from stderr as well as the exit code, since a crash handler could reach exit 3 and still dump one. A second guard inside `collect_moves` covers DIRECT library callers: through the CLI the `git rev-parse` probe catches absence first, so narrowing that guard killed no test until one was written at the level where it is reachable - an unreachable guard is not defence in depth, it is an untested claim
- check-oscillation `!controls/*/cases/*/history.log` sits AFTER `*.log` in `.gitignore`, the second time this exact placement trap has been hit in one day (the #953 `anchor.log` negation was the first). Untracked, the framework reported the control as not existing in a clean clone. The negation was probed two-sided inside the repo afterwards: the two `history.log` captures are trackable, while `some-stray.log`, `logs/x.log`, `scripts/debug.log` and even a sibling `other.log` in the same cases directory stay ignored. The first probe of the negative side aimed at `/tmp/x/some.log`, outside the repository, where `git check-ignore` correctly says nothing at all - a control pointed at a target that could not answer
- check-oscillation KNOWN MISSES, all of them chosen over a wrong attribution - a renamed or moved knob starts a new series; a guarded `[[ -n $x ]] && exit 3` is not seen; a unit-bearing value is not a number; two sites changed inside ONE hunk collapse in `flush()`'s dict, so the second hides the first; a reversal introduced by merge RESOLUTION is dropped with the merge commit. And the one that was a false CLAIM rather than a limit: the module header used to list "allowlist membership" among what it derives, which `_knobs` never extracted - so an allowlist entry added and later removed yielded no moves, and any unrelated numeric move in range still printed `none`. A clean-looking verdict about a population that never contained the thing, sitting in the documentation of the control built for that defect class. The header now states the scope and `tests/test_oscillation_control.py::test_a_STRING_allowlist_entry_is_outside_the_detector` pins it. That test carries NO text assertion: the first cut grepped the header for the retired phrase and fired immediately, because the header now DISCUSSES membership in order to disclaim it - documenting a limit well makes a text guard about that limit more false-positive, not less
- check-oscillation IS WIRED INTO `make verify`, NOT INTO CI, AND THAT IS THE DESIGN (#987). The detector needs git and the CI image has none; `verify` is a LOCAL gate and `.woodpecker.yml` runs no make targets at all (`grep -c 'make verify'` is 0). So the INSTRUMENT runs locally, where git exists, and the CONTROL runs in CI, where `controls/check-oscillation` feeds it committed `git log` captures via `--from-log` and needs no git. CI proves the detector CAN discriminate; the local runs prove it IS used. Neither alone is enough, and a reader finding the detector absent from CI would otherwise assume it was forgotten
- check-oscillation TWO REVERSAL TRIGGERS SIT BESIDE THE TARGET AND BOTH ARE NOW CHECKABLE. (1) `--exit-on-finding` must never appear in a build recipe, or the detector has become blocking - which the owner ruled against. `scripts/check-oscillation.py` had CLAIMED since #936 that a test asserted this, and no such test existed: the claim was unbackable then, because there was no build target, and it was still a claim. The test exists now and reads RECIPE LINES ONLY, because a substring search over the Makefile matches the reversal trigger written there in prose - the fourth text guard in two days to fire on its own documentation. (2) the wiring is safe only while `verify` is local, so a test asserts no CI step runs `make verify`; if one ever does, the git dependency becomes a CI failure and the target needs a git-bearing image or comes out of verify
- check-oscillation THE DEFAULT RANGE RESOLVES rather than being a fixed string (#987). `HEAD~200..HEAD` written as a literal reported `range-unresolvable` UNKNOWN on any checkout with fewer than 200 commits - a fresh clone, a young project, a shallow CI checkout - and putting the detector in `verify` would have failed those builds for a reason that is not about knobs. It now falls back to the whole history when `HEAD~200` does not exist. NOT a softening, and the pair of tests says so: a young repository is EXAMINED, while a range the CALLER asked for that does not resolve is still UNKNOWN. The range actually taken is printed as `OSCILLATION_SOURCE` on every run
- check-oscillation THE FALLBACK IS REFUSED ON A SHALLOW CLONE, and the first cut of it shipped the softening it was written to avoid. `HEAD~200` failing to resolve has TWO causes that look identical from inside the script: a repository with fewer than 200 commits, and one whose earlier commits were never fetched. Walking "everything" is honest for the first and a LIE for the second - measured, not imagined: a depth-2 clone of `timeout 30 -> 60 -> 30` saw ONE move and reported `none`, exit 0, for a history that reversed, while the complete repository reported `found`. Shallow plus no bounded range is now `OSCILLATION_REASON: shallow-history`, UNKNOWN, exit 3. Caught by the counter-model, in the change whose stated purpose was to avoid exactly this
- check-oscillation THE WIRING GUARDS LIVE IN `tests/test_verify_wiring.py` AND CARRY NO SKIP, deliberately. They started in `test_oscillation_control.py`, whose module-level `pytestmark` skips everything when git is absent from `/usr/bin:/bin` - which is the CI environment, so both guards would have been inert in exactly the place they protect. They read text out of `Makefile` and `.woodpecker.yml` and shell out to nothing, so they have no reason to need git. A guard inert where it gates is the defect this repository keeps finding, and this one was two files from shipping
- check-oscillation detects the repository by ASKING GIT (`git rev-parse --git-dir`) rather than looking for a `.git` entry - the control fixtures are bare repos and have none, so a path assumption would have reported them `unknown` and made the control unregistrable for a reason unrelated to the gate. Live on this repo at `HEAD~120..HEAD`: 120 commits, 19 knob moves, 15 distinct knobs, one finding - `tests/test_flow_wave_mailbox.py:timeout 60 -> 10 -> 20`
