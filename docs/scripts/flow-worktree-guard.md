# `flow-worktree-guard` - script reference

Per-script history, indexed from [the scripts inventory](../scripts.md).

## `flow-worktree-guard`

- flow-worktree-guard - leaked-edit detector: warns when a `/flow:auto` edit landed in the MAIN tree instead of the worktree (#486)
- flow-worktree-guard `--strict` - BLOCKING at both `/flow:auto` call sites (Step 4 implement, Step 6 pre-commit) since #576: exit 3 is a STOP, because a live leak means every further edit compounds and the commit about to be made does not contain the work. Strict failure is gated on FRESHNESS (`FLOW_LEAK_FRESH_MIN`, default 30m) in BOTH branches - the #573 total-leak check and, new in #576, the overlap check - so pre-existing uncommitted dirt in main on a shared file the run also edits (CLAUDE.md, a template) warns without stopping the run; only an edit written to main DURING the run blocks
- flow-worktree-guard (#1014) SAYS WHICH OF FOUR THINGS HAPPENED. It was the only flow helper with no contract line, and every could-not-look path - git missing or failing, an unresolvable git dir, an unreadable main tree, a FAILED `git status` read through a process substitution that discarded its exit - ended in the same silent `exit 0` as a clean pass, which `/flow:auto` Steps 4 and 6 read as "no edit leaked into main". It now always prints `FLOW_WORKTREE_GUARD: no-leak | leak | unknown | not-applicable - <detail>` through gate-lib's `gate_emit`, and under `--strict` exits per gate-lib's `gate_map` (no-leak 0, leak 3, unknown 4, not-applicable 5) so no could-not-look answer shares the good exit. `not-applicable` is the main checkout (the current-branch lane) or not being in a work tree - nothing to examine - and is kept apart from `unknown`, could not examine. Callers STOP only on 3 and PROCEED-AND-REPORT on 4 and 5 (ruling RB, with every caller audited). Advisory mode (no `--strict`) still always exits 0 and now also prints the verdict. Registered control `controls/flow-worktree-guard`: two BAD cases forcing the third states, one GOOD, and a HISTORICAL anchor - the guard as it stood at `40f771c` - that misses both BAD cases because it exited 0 on all three. The convention's written home is the "third state: unknown" section of `docs/agents/detector-contracts.md`
- flow-worktree-guard `--help` printed a fixed line range (#1726; Nit Store #864 seq 634, third file). `sed -n '2,36p'` of a 100-line header stopped before the Usage section, so `--help` did not say how to run the script. It now prints the header to its first blank line, as `flow-start-resolve.sh` does since #1713, and `tests/test_flow_helper_help.py` fails against a line range (add a header line and it must be printed). The same issue added tests for eight `unknown` verdicts nothing had fired: no git, a worktree of a bare repository, a main tree that resolves to the worktree itself, no temporary file, main's status failing, no merge base, the diff of this run's commits failing, and an idle worktree with a file deleted in main (`tests/test_merge_tail_refusals.py`)
- flow-worktree-guard leak control (#1726) - `controls/flow-worktree-guard` covers the could-not-look and nothing-to-look-at verdicts; the verdict the guard exists for, `leak` (exit 3), had no committed case, and could not join that control: its historical anchor (pre-#1014) already caught a real leak, and the harness scores a control INERT when its anchor catches a known-bad case. `controls/flow-worktree-guard-leak` is a second registration: a fresh overlap is a leak, a clean main and a years-old overlap are not. Its anchor is CONSTRUCTED: a guard that establishes it is in a linked worktree and never reads the main tree's status
