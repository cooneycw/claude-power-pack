## `gh-pr-merge`

- gh-pr-merge - layout-aware PR squash-merge used by `/flow:auto` + `/flow:merge`; polls mergeability to wait out a transient `UNKNOWN` right after push (#485); bounded refetch+retry when the squash fails on `Base branch was modified` (sibling merge race, #502); opt-in `--admin` flag plus a single admin-gated auto-retry when a squash is rejected by branch protection on an owner merge (#517)
- gh-pr-merge `--admin` narrowing + required-check wait (#577, ADR 0004) - before the squash it resolves the BASE branch's required status-check contexts and polls the PR head until they are green (bounded, `GH_PR_MERGE_CHECK_ATTEMPTS` x `GH_PR_MERGE_CHECK_DELAY`); a red required check, and one that never reports, are hard stops. A required-check block is EXCLUDED from the #517 `--admin` auto-retry - auto-overriding it would defeat the required check on every run - while a review block (#517's actual case, and #579's) is unchanged; an explicit `--admin` from the caller still skips the wait, the documented break-glass
- gh-pr-merge required-context resolution reads BOTH protection mechanisms and believes only a 2xx (#610) - the #577 resolver read classic branch protection alone and discarded gh's exit code, so a 404 body (`{"message":"Branch not protected"...}`, which `gh api` prints on STDOUT with `--jq` unapplied) became a "required context" that could never report, and the wait timed out into a refusal. It fired both when a repo had no protection AND when `main` was guarded by a repository RULESET, which the legacy endpoint cannot see. Resolution now unions `/branches/{b}/protection/required_status_checks` with `/repos/{o}/{r}/rules/branches/{b}` and reports one of three states: `declared` (wait, exactly as #577), `none` (a source answered, nothing required -> skip the wait outright), `unresolved` (neither readable -> fall back to the checks the PR itself reports: green merges, RED is a hard stop, pending waits then FAILS OPEN). Enumeration failure no longer outranks observed reality, and the client-side wait is defence in depth - GitHub enforces a ruleset server-side at squash time, so a plain `gh pr merge --squash` cannot bypass the posture. Cost before the fix: 25 flow:auto runs, ~4h of wall-clock, every one worked around by hand
- gh-pr-merge review gate + exit-3 clean stop (#579) - a required human review is a handoff, never an automated bypass: before the squash the helper reads `reviewDecision` and on `REVIEW_REQUIRED`/`CHANGES_REQUESTED` exits 3 (a FIRST-CLASS CLEAN STOP: PR left open/current/green, message prints the PR URL + "approve or merge on GitHub, then /flow:merge"); a review-family rejection at squash time hits the same stop as belt-and-braces. This retires the #517 auto-`--admin` retry for review blocks - the retry survives only for the residual ADMINISTRATIVE family (protected-branch/push-authorization/base-branch-policy), so automation now bypasses neither a required check (#577) nor a required review; an explicit human-typed `--admin` remains the break-glass and skips both gates. Fail-open on an empty/unreadable `reviewDecision` (GitHub enforces server-side). `auto.md` Step 7 + `merge.md` document exit 3 as not-a-failure (leave worktree/branch intact, no cleanup, never self-escalate to `--admin`)
- gh-pr-merge explicit squash subject/body (#655) - the squash always passes `--subject "<PR title> (#N)" --body "<PR body>"` derived from the PR, because with no `--subject` GitHub may title the squash from the branch's FIRST commit and #635's commit-first discipline makes WIP-first branches routine (a 1045-line feature landed on main as "WIP: ..."); fail-open - an unreadable or empty title omits BOTH flags together and merges exactly as before, so the merge is never hostage to a metadata read; the #517 --admin retry inherits the flags via BASE_FLAGS
- gh-pr-merge deletion surfacing + post-merge completeness (#657) - a collapse onto a moved base (`reset --soft origin/main` + commit, the #655-thread workaround, now marked superseded) silently records deletions of a sibling's merged work with a conflict-free merge and honestly-green CI, so before the squash the helper prints `GH_PR_MERGE_DELETIONS: <n> <paths...>|0|skipped` (opt-in `GH_PR_MERGE_STRICT_DELETIONS=1` turns any deletion into a clean exit-4 pre-squash stop, PR untouched) and after a confirmed merge prints `GH_PR_MERGE_COMPLETENESS: ok|violation|skipped` (landed squash vs the PR's own file list; violation is loud but never flips the exit code - the merge landed); both fail open per component, all reads ref-scoped `git -C <root>` with full refs (never bare relative pathspecs, the #657 companion trap); honestly scoped: completeness catches base-race/squash contamination, NOT collapse damage inside the file list - that guard is the auto.md Step-6 safe-collapse recipe (merge-base target + staged-deletion check)
- gh-pr-merge tested-tree trailer (#716) - poker-measure's push-to-`main` pipeline re-runs the full suite on every squash because its shared 2-worker Woodpecker agent leaves effective PR-verification concurrency at roughly one (poker-measure#236); when this PR's branch was up to date with its base at squash time (`git merge-base --is-ancestor origin/<base> HEAD`), the squashed tree is provably identical to the PR head CI already tested, so the helper appends `Woodpecker-Tested-Tree: <sha1 of HEAD^{tree}>` to the squash body (via `--body` alone when the #655 title-derived path is empty). Deliberately NOT a boolean trailer - an unrelated commit's stray `Woodpecker-Skip-Full-Test: true` text would otherwise propagate into any squash body gh composes and silently skip a real full run; the tree hash is self-verifying, since the consumer recomputes the same hash locally on what it actually checked out and only skips on an exact match. Fail-open per component (unreadable base, unresolvable ancestry, or a branch behind base all omit the trailer - the push pipeline then runs the full suite, the safe default)
- gh-pr-merge Woodpecker queue-wait (#717) - the required-check poll's fixed 60-attempt window counts from when polling starts, not from when the pipeline is actually picked up, so a PR queued behind others on the same shared 2-worker Woodpecker agent burns the same budget as one that is genuinely stuck (measured: 8 of 8 poker-measure merges one night needed exactly one retry, a deterministic tax). GitHub's classic commit-status API - what Woodpecker posts as `ci/woodpecker/pr/woodpecker` - has no queued-vs-running distinction in its `state` field (only GitHub Check Runs expose that), so instead of trying to read that distinction off the rollup, the helper asks Woodpecker's OWN pipeline API: when `WOODPECKER_API_TOKEN` is set (the same credential `/flow:auto` Step 8 already uses for post-merge CI verification), it waits out a `pending` (queued) pipeline on its own bounded budget (`GH_PR_MERGE_QUEUE_WAIT_ATTEMPTS` x `GH_PR_MERGE_QUEUE_WAIT_DELAY`) before the existing check-poll budget starts counting. Entirely fail-open and additive: no token, no `curl`/`jq`, an unresolvable repo id, or no matching pipeline all fall straight through to the unchanged pre-#717 poll, and an explicit `--admin` skips the queue wait exactly as it already skips the required-check wait
- gh-pr-merge base-move guard across the required-check wait (#767) - snapshots the fetched `refs/remotes/origin/<base>` tip before the non-admin queue/check wait and re-fetches it after checks turn green; unchanged tips and moved tips already contained in `HEAD` proceed, while unreadable snapshots print `GH_PR_MERGE_BASE_MOVED: skipped` and fail open. A new base tip not contained in `HEAD` prints the old/new marker and exits 6 as a clean pre-review, pre-squash stop, leaving the PR untouched so the branch can be synced, re-gated, pushed, and merged again; `--allow-base-move` is the loud per-invocation override, and explicit `--admin` skips the guard with the waits
- gh-pr-merge negated close-keyword refusal (#726) - GitHub's literal issue-linking matcher still auto-closes `#N` when close/fix/resolve prose is negated (for example, "does not close #N"), so immediately before either squash path the helper scans the assembled title and body and makes any such match a clean exit-5 stop with the issue number and surrounding text printed, leaving the PR untouched; `--allow-negated-close` is the conscious per-merge escape hatch, but stays loud by printing the same detection plus an override-consumed audit line before proceeding
- gh-pr-merge stacked-child retarget before branch deletion (poker-measure#405) - during the 2026-08-20 poker wave merge drain, squash-merging PR #375 through this helper deleted its branch and GitHub auto-closed open stacked PR #382, whose base was that branch, in the same second; the automatic retarget happens only in GitHub's web-UI merge flow, not through the API/CLI squash-and-delete path used here. Before any squash attempt, the helper now lists every open PR based on the parent branch, resolves the repo's real default branch, and runs `gh pr edit <child> --base <default>` before deletion can occur; the child's temporarily inflated diff self-corrects after the parent's squash lands because only its base pointer changed. It prints `GH_PR_MERGE_STACKED_RETARGET: <n> <PRs...>|0|skipped`; enumeration or default-branch lookup failure is `skipped`, and an individual edit failure warns while the remaining edits and merge continue, preserving the #610 fail-open posture

## `flow-start-resolve`

- flow-start-resolve - deterministic `/flow` Step-1 resolver + `--verify` gate (#581): target-repo resolution (#578), issue fetch + state check, issue-anchored branch derivation, existing-work triage (`current-branch|fresh|resume|remote-pickup|cross-repo`), wraps the #503 live-driver guard + shipped-PR hazard, performs git-lane worktree creation (honoring `FLOW_WORKTREE_BASE`, #584), and emits a `key=value` contract - extracts the compound Step-1 bash the permission matcher could never auto-allow
- flow-start-resolve `COMPOSE_PROJECT_NAME` pin (#626) - the resolver emits a canonical compose-project pin in its contract so the WHOLE flow run inherits it, not just the Step-9 deploy #535 guarded. docker compose derives its project name from the cwd basename when unset, so any compose call from a worktree (the Step-4 test-loop `make docker-up`, a hand-run `make docker-*`) forks a parallel stack that collides on the published port and leaks `<basename>_*` orphans. Value precedence matches Step 9: an explicit `.claude/deploy.yaml compose_project_name:` override, else `basename "$TARGET_REPO"` lowercased - never the worktree basename; `auto.md` Step 1/Step 4 and `start.md` instruct pinning it in the same shell call as any `docker compose`
- flow-start-resolve shipped-PR probe on both lanes (#742) - the `PR_HEAD` probe was resume-lane-only, so a remote-pickup of a pushed branch with an OPEN PR reported `PR_HEAD=none` and sailed past the #503 hazard unconfirmed (the 2026-08-31 agentic-actuary run discovered PR #211 only when `gh pr create` errored at Step 6). The probe is now a shared `probe_pr_head()` run on the resume AND remote-pickup lanes, and names the target repo explicitly (`gh pr list --repo <owner>/<repo>`, parsed from origin's URL; cwd-based fallback for non-owner/repo remotes) so a cross-repo run can never let gh's cwd resolution drift
- flow-start-resolve `--session-cwd` - the session cwd is DECLARED, not inferred (#592): the Bash tool's cwd persists across calls and drifts on any earlier `cd`, so `CROSS_REPO` (and, with no PROJECT arg, `TARGET_REPO` itself) and the `current-branch`/`resume` lane detection are resolved from the path `auto.md`/`start.md` pass verbatim. `GIT_LANE` is always 1 now (worktrees are out-of-repo, issue #627), so omitting `--session-cwd` only risks a misdetected `current-branch`/`resume` lane, never a wrong-repo `EnterWorktree`; it still emits `SESSION_CWD_INFERRED=1` so the gap is visible

## `flow-worktree-claim`

- flow-worktree-claim - cross-session OWNERSHIP claim on a flow worktree (#597), the half #503 could not cover: the live-driver guard protects a session ENTERING a worktree, but nothing protected an active worktree from being REMOVED by a sibling session, whose Step-7 cleanup deleted an issue-N checkout by name and destroyed uncommitted work with no signal but the user noticing. Rides git's own `git worktree lock --reason "flow-claim issue=N pid=... session=... host=... ts=..."`, so the claim is a real barrier (`git worktree remove --force` refuses a locked worktree) rather than an advisory note, and is readable from `git worktree list --porcelain`. `claim`/`check`/`release` verbs; ownership is pid + session, liveness is `kill -0` trusted only when the recorded host matches, and a claim whose owner is gone is STALE and auto-taken-over so the mechanism can never wedge a repo. A lock this family did not write is FOREIGN and never stolen. Staked in `flow-start-resolve.sh --verify` - the hook point running INSIDE the worktree on every lane - and read by resolve mode via `check --issue N` BEFORE any worktree is created, so two sessions handed the same issue stop instead of racing. Fail-open everywhere except the case it exists for: claiming against a live owner exits 1

## `flow-wave-registry`

- flow-wave-registry - role -> address registry for multi-session flow waves (#638, companion to the #637 wave loop): `register`/`list`/`get`/`verify`/`release`/`self-address` verbs over a flock-atomic, wave-namespaced JSON roster at `$XDG_RUNTIME_DIR/cc-flow-wave/registry.json` - OUTSIDE any repo (never shared mutable repo state, the #635 hazard class) and outside transcripts (survives a worker `/clear`; the runtime dir dies at reboot, exactly when every session socket dies too). Self-derived sockets (ancestor-pid walk) are bootstrap only: `verify --from` reconciles against the transport-observed `from=`, and the OBSERVED address replaces the self-derived one as canonical - never the reverse. The non-matching outcomes are SPLIT (#674): a recorded `unknown` filled in by observation is the documented fallback succeeding and reports `address_filled` unflagged (`list` renders `filled`, a fully verified state and not a lesser grade than `verified`), while only a recorded REAL address contradicted by the observed one is flagged `mismatch-corrected`; both exit 0. Role conflicts against a LIVE session refuse (exit 1) without `--force`; dead owners read stale and are taken over, mirroring #597 claim semantics. `list` warns on lane overlap only for the useful signal (same repo + same issue, same branch, same/nested worktrees among LIVE entries) - same repo alone is the normal wave shape and stays info-level, and roles that DECLARED NO LANE are exempt from the pairwise checks entirely (#683: the `orchestrator`, plus any live role with no issue, no branch and a shared-parent cwd; announced in the roster, never silent, and lapsing the moment a lane is declared). `list` also reconciles `flow-claim` worktree locks (#687), since registration is opt-in and orthogonal to `/flow:auto`: a LIVE lock no live registry entry accounts for renders as a claim-derived row and PARTICIPATES in overlap detection (contactable but never a role - separate `unregistered_claims` key in `--json`, never a `verify`/`release` target), its address OBSERVED rather than derived from the pid, and coverage bounded to repos the wave already knows about plus an explicit `--repo` - a host with nothing registered has nothing to scan
- flow-wave-registry loud default + cross-wave visibility (#671) - an omitted `--wave` lands in wave `default` with a clean verdict while every named-wave roster stays empty, the #638 silent-addressing-failure class one namespace level up (both sides read success; the 2026-08-11 incident took a raw-JSON dig to diagnose). Now `register`/`get`/`verify` into `default` without an explicit `--wave` print one advisory stderr line, `register` names the likely intended wave when exactly one other wave has a LIVE orchestrator (suggestion only - never auto-join), and `list` appends a `note:` line for LIVE entries parked in OTHER waves (stderr in `--json` mode so stdout stays parseable). Advisory only: verdicts and exit codes are byte-for-byte unchanged
- flow-wave-registry honest address bootstrap (#672) - the 2026-08-11 wave deadlocked with every session recording `socket: unknown` while the helper reported that the orchestrator's `verify` would supply it later; it could not, because `verify` needs an observed `from=`, which needs a delivered message, which needs an address somebody already holds - so the promise named a fallback that was structurally dead, and ~2h were lost to both sessions standing by on a healthy-looking verdict. Three properties close it. Failure NAMES its cause (`FLOW_WAVE_SOCKET_REASON`): `no-sock-dir` (the socket dir is created LAZILY - the same host had none at 07:52 and self-derived successfully at 10:27, so `unknown` is point-in-time, not a permanent verdict, and a re-register adopts the real address) vs `no-match` (dir present, no ancestor pid owns a socket - a retry alone will not fix it). `FLOW_WAVE_BOOTSTRAP: ok|deadlock` on register/get/list says blocked-not-pending and prints the three lanes that do not depend on self-derivation (re-register, `register --socket <addr>` - which already shipped in #638 but was documented nowhere - and a user-relayed hello). And a failed derivation NEVER downgrades a recorded address to `unknown` (`SOURCE=preserved`): re-registering is the documented cheap re-brief, so the #638 trust model read in its other direction - a known address outranks a failed assertion, since `unknown` cannot be messaged. `FLOW_WAVE_SOCKET_SOURCE` (`explicit|self|preserved|unknown`) reports which lane produced the address; the ancestor walk now starts at `CLAUDE_PID` (`$PPID` alone starts a hop low and was reached only by luck). Companion to #670's order-independent registration, which named this gap as the residual it could not cover
- flow-wave-registry wave-policy tiers (#699) - the registry recorded a role, an address and a lane; everything else a wave RUNS ON - implementation authority, gate policy, who judges, the ledger format, the authority model, merge and deploy policy, and the per-worker FILE LANE - lived in prose the orchestrator retyped into every message, which is both where the 2026-08-11 wave's orchestration errors happened and the one thing that does NOT survive a worker's `/clear` (the registry's stated purpose). Now declared data in two tiers: wave-level via `policy set` (a MERGE that bumps `rev`, so amending one field is a one-flag call; `--authority` implement|file-issues-only and `--authority-model` orchestrator-only|user-and-orchestrator are enum-validated because a typo there reads as declared and answers 'may this wave write code?' with garbage, the rest free text) and role-level on `register` (`--model`, `--permission-mode`, `--files`, `--capacity` - preserved across the omit-everything re-brief, cleared only by an explicit empty value). A DECLARED POLICY NOBODY READS IS DECORATION, so four readers are pinned by test: `register` REPRINTS the policy (the compaction-proof re-brief - a `/clear`ed worker recovers the protocol by re-registering), an undeclared policy reports `FLOW_WAVE_POLICY=absent` instead of passing silently (the failure where implementation authority took a user round-trip and both workers correctly refused to infer it from an issue number), a role briefed on a superseded rev reads `brief=STALE` in `list`/`get` and is named at `policy set` time, and declared FILE LANES join the ONE `report_overlap` predicate - exact-match on declared paths, below the branch/worktree arms and above the shared-repo info, so the collision class that was 100% of the reference wave's real conflicts stops being checked by hand. `policy_absent` is a STATE and exits 0 (#674's rule: a new verdict is never a new exit code); `list --json` gains a `wave_policy` sibling key only when one is declared, so a policy-less wave is byte-identical to pre-#699. Covers declared STATE; #701 covers the state TRANSITIONS
- flow-wave-registry jq-1.6 update trap (#699) - a `?` anywhere inside a `|=` body makes jq evaluate the update as a backtracking path expression, and `_modify` then DELETES the key it was told to update: exit 0, no stderr, the whole policy object gone, `with_lock` reporting success. The same `$pid | tonumber? // $pid` coercion is safe in the object CONSTRUCTOR `register` uses (a plain `=` assignment) and unsafe in `policy set`'s `|=` - exactly the difference that gets copied across by hand, so it is commented at both sites and pinned by a test asserting the STORED object rather than the verdict

## `flow-wave-mailbox`

- flow-wave-mailbox - the wave DELIVERY lane (#676), sibling to the #638 registry and sharing its wave dir, lifetime and host-local scope. #638 and its follow-ups built a reliable address book; none of it delivers, and on 2026-08-11 the harness rejected every orchestrator->worker `SendMessage` (it routes only to subagents the calling session spawned), so a fully-written assignment sat undelivered ~2h while both sessions correctly stood by and the only working transport was the user typing a pointer into the worker's terminal. `send`/`read`/`watch`/`list` over `$XDG_RUNTIME_DIR/cc-flow-wave/<wave>/`: orchestrator->worker writes `outbox-<role>.md`, worker->orchestrator writes `inbox-<role>.md` - one box per WRITER, so two workers reporting at once never contend and the orchestrator watches all inboxes with one `--role orchestrator`. Addressed by ROLE, the same declared identity the registry keys on, so the registry-address-only rule is obeyed rather than bypassed. Sends APPEND a rev-stamped block (a deliberate deviation from the issue's "rewrite-in-place", ruled at the #676 gate: overwriting an unread assignment with the verdict that follows it IS the delivery-loss failure the issue exists to remove); `--replace` opts into overwrite and still bumps the rev, so a replace can never read as already-consumed. Revs are per-box and monotonic under flock - pinned by an 8-way concurrent-sender test, since a shared rev is a dropped message. **`watch` is the half that makes this a lane rather than the ad-hoc 2026-08-11 workaround**: it BLOCKS until mail passes the read cursor, prints it and exits 0, so a session that arms it as a background call is re-invoked by the harness on arrival - a mailbox an idle session never reads is not a lane, which is why the workaround still needed a human to say "go read your outbox". Bounded (default 30m) so a wave cannot leave watchers spinning; timeout is exit 5 and the message explicitly refuses to read that as "the counterpart is gone". `list` surfaces per-box rev/cursor/unread, so an assignment a worker has NOT consumed is visible instead of being invisible until someone asks. Honestly scoped: HOST-LOCAL, exactly like the registry - two sessions on different machines still have no transport

## `flow-wave-lexicon`

- flow-wave-lexicon - reserved vocabulary for wave STATE TRANSITIONS (#701), the transitions half of #699's declared state and the fourth sibling in the wave dir (#638 says who, #676 says it arrived, #699 says the rules, this says what a message DOES). The wave protocol was strict machine-to-machine and free prose agent-to-agent, and every miscommunication in the 2026-08-11 reference wave happened in the prose layer while `FLOW_WAVE:` markers never once misfired: a LANE grant read as a GATE approval (an unjudged gate stopped only by a worker's caution), a lane FENCE read as its own inverse, four state broadcasts accurate when composed and wrong when read, a merge predicate retyped ad hoc four times. Tokens cover ONLY transitions with a wrong-answer cost - `GATE: GO|HOLD|GO-WITH-CONDITIONS #N`, `LANE: GRANT|EXTEND|REVOKE <role> <paths>`, `MERGE: AUTHORIZED #N when <named check>`, `STATE: as-of <commit>`, `RATIFY`/`OVERRULE`, `PUSHBACK`, `LEDGER` - line-anchored (the #607 rule, so a mention is never a declaration) and each requirement traceable to a specific failure; the reasoning stays prose by design, since the reference wave's highest-value messages were a worker's design rulings and its catch of the crossed lane/gate message, none of which survive schematisation. **The anti-decoration contract** (the issue's own kill condition - a reflexive `GATE: GO` prints what a considered one prints): two readers, both load-bearing. `flow-wave-mailbox.sh send` validates every body, so a malformed transition cannot be DELIVERED (exit 6, `refused`, box untouched) - while a message with NO token always delivers and a missing/broken validator FAILS OPEN, since a wave stalling on its own linter is the #676 failure in a different hat; and `record` DERIVES the #645 ledger entry from the parsed `GATE:` token (ruling, `holds_behind`, `serializes:` -> `adds_serialized`) instead of accepting a hand-written one, so a gate cannot be recorded as judged without a parseable verdict. ## `flow-ci-status`

- flow-ci-status - SHA-anchored CI verification as ONE audited allowlistable helper (#766, the #581 pattern): `/flow:auto` Step 8 was the last un-helpered step, inlining a `curl`+`jq` Woodpecker lookup gated on `WOODPECKER_API_TOKEN` already being exported - which it usually is not, since the token lives in an AWS secret rather than a shell profile.
