# `scripts/` inventory - per-script history

Relocated from `CLAUDE.md` by issue #711: the root memory file loads into every
session, so it keeps exactly one line per script (the #501 line-granularity
convention) and the accumulated per-script history lives here. Entries are
verbatim moves - nothing was reworded or dropped.

See also `docs/commands-reference.md` (the command-surface half of the same move).

The **population** of this file is derived and checked - `make scripts-inventory-check`
(`scripts/scripts-inventory-check.py`, issue #1013) fails when a file in `scripts/`
has no entry here, or when a section names no file in `scripts/`. The prose per
entry stays hand-written; only the set is mechanical. A section that is
legitimately about something other than one script is declared on the marker
below, and an undeclared one turns the gate red rather than passing quietly.

## `check-test-binary-guards` (#831 inversion)

- check-test-binary-guards inverted DIRECT lane (#831) - the gate enforced CLAUDE.md's "a test that shells out to a real binary must use a `shutil.which` skip guard" for exactly FOUR names (`git`, `docker`, `gitleaks`, `jq`), so every other binary was not under-detected but OUTSIDE what it examined: the DIRECTIVE was broad, the GATE was narrow, and the gate is what a reader trusts. #830 is the bill - a test ran `subprocess.run(["pgrep", ...])`, `make verify` passed, the gate said ok, and CI went red on `FileNotFoundError` because `pgrep` ships in procps and `uv:python3.11-bookworm-slim` omits it. The tell that this was a defect rather than a missing entry: `ps` was not on the list either, yet `tests/test_flow_wave_mailbox.py` carried a `requires_ps` guard - it existed because someone REMEMBERED, not because anything checked. The default is now inverted against `CI_IMAGE_BINARIES`, a list of what the validate image PROVIDES, so a bare argv[0] outside it needs a guard and "a binary nobody thought about" becomes a state the check can represent; `CI_IMAGE` is pinned against the image named in `.woodpecker.yml`, because the exempt list is a claim about ONE image and nothing else in the repo would notice the pipeline moving. `GUARDED_BINARIES` survives as the script-hop scan list and as an explicit always-guard override (the union decides), which is what keeps #838's `timeout` oracle - a widening harness that substitutes that constant - measuring the direct lane rather than only the hop
- check-test-binary-guards: the inversion is NOT applied to the script hop, and the reason is measured (#831) - in shell text a binary and a shell FUNCTION occupy the same "command position", and so do many variable and heredoc fragments. Scanning this repo's own `scripts/*.sh` for any command-position token and subtracting a generous exempt list leaves 141 uses of `jq` beside 107 of `usage_fail`, 116 of `s` and 75 of `issue`. Telling those apart needs a shell parser, which this file states outright it is not, so the hop keeps an explicit list - widened past the original four to `pgrep`, `ps`, `tmux`, `flock`, `curl`, which is only safe now because #833 and #838 fixed the case-label and quoted-text false positives that widening exposes. A guess that cries wolf costs more than the false negative it removes
- check-test-binary-guards KNOWN RESIDUAL: a fail-soft script use (#831, not fixed) - the hop drops a binary when every use in the script is fail-soft (stderr silenced, in a condition, or with a `||` fallback), because such a script genuinely survives the binary's absence. That is the right answer to the question the hop asks - *can the SCRIPT do its job without this binary?* - and a reader takes it for *can the TEST pass without this binary?*. They diverge exactly when a script degrades gracefully and a test asserts the degraded-versus-not distinction, which is a GROWING pattern here since every `unknown`-vs-`clear` lane produces one. Live in tree: `scripts/flow-wave-mailbox.sh` reaches `ps` only as `$(ps -eo pid,ppid,args --no-headers 2>/dev/null)` so the hop drops it, while `tests/test_flow_wave_mailbox.py` needs `ps` to exercise that lane and carries a hand-written `requires_ps`. Measured: widening `GUARDED_BINARIES` to include `ps` AND deleting those guards still yields ZERO findings, so #831's inversion does not close this. Deliberately not fixed by widening - believing the fail-soft declaration is what keeps the hop from crying wolf (scanning for mere mentions produced 266 findings, ~250 false), so per `docs/agents/detector-contracts.md`'s "when widening is not the remedy" the larger question needs its own channel. Pinned as a property by `tests/test_test_binary_guards.py::test_a_fail_soft_script_use_is_a_known_blind_spot`

## `check-negative-controls` (#924)

- check-negative-controls - runs every gate's registered NEGATIVE CONTROL and proves the control can fail (#924). Seven open CPP issues are one defect in different gates: an instrument returning a confident verdict it is not entitled to, where a green from a blind gate and a green from a working gate are the same bytes. The catching PRACTICE already existed - a hand-run mutation at review time, performed on every merge of 2026-09-13 (#912, #913, #914, #917, #920) - and left NO ARTIFACT: no registered control, no CI step, nothing that reddens when a control stops discriminating. The reviewer's own words: "if I stop doing it, nothing notices"
- check-negative-controls asserts three things per control. DISCRIMINATION - `gate(known-bad) == BAD` **and** `gate(known-good) == GOOD`, both directions, because a gate wedged at "fail" passes the known-bad half alone. ANCHOR - the control run against a vendored blind artifact must FAIL, i.e. the artifact must MISS the known-bad input; that is acceptance step 4 executed on every run instead of once by hand, and an anchor that CATCHES the bad input proves the control is not load-bearing. ANCHOR SANITY - the anchor must agree with the current gate on the known-GOOD input, or it differs for reasons beyond the blindness under test. Each of the three reads the gate's OUTPUT as well as its exit code: a non-zero exit counts as detection only when the manifest's `detect_signal` is present, since a crash exits non-zero too (#946)
- check-negative-controls contract - `NEGATIVE_CONTROL_GATE` / `_SOURCE` / `_DETAIL` (repeatable) / `_PROVENANCE` / `_VERDICT`. Six verdicts: `PASS`; `BLIND` (the gate stopped discriminating - an alarm about the GATE); `INERT` (the anchor did not miss the known-bad input, so the control would not notice a regression); `UNRESOLVED` (a path the registration names is not in this checkout, the manifest is incomplete, or an anchor cannot be CONFIRMED to have missed the known-bad input - NOT a gate failure, and it presents identically to `BLIND` while needing the opposite response); `UNPROVEN` (registered and discriminating but carrying no anchor, so nothing has demonstrated it can fail); `UNSIGNALLED` (the gate exited like a finding and said nothing that identifies one - also an alarm about the GATE, but a different one from `BLIND`, which sends a reader into detection logic for a gate that is throwing, #946). `--strict` exits non-zero on anything that is not `PASS`
- check-negative-controls treats UNPROVEN as the load-bearing state, and it is what makes step 4 MECHANICAL rather than remembered. A control with no anchor does not go quiet, it reddens the build - so forgetting to demonstrate that a control can fail produces a red instead of a silence. Without that the framework is only the reviewer's habit relocated into a script nobody runs
- check-negative-controls vendors its anchors instead of fetching them with `git show`, because **git is not in the CI image**. `CI_IMAGE_BINARIES` in `check-test-binary-guards.py` does not list it, and that file's own header records the rule as "forgotten three times (#451, #489, #577)" and structurally invisible locally, since the dev box HAS git and `make verify` can never reproduce the failure. A `git show <sha>^:<gate>` anchor would have worked where it was written and been INERT where it gates - this issue's own defect class, inside the tool built for it. Verified by running the step under `env -i PATH=<no-git>`: `PASS`, provenance `unverified`
- check-negative-controls keeps PROVENANCE on a separate axis from the verdict and never folds it in: `ok` only after a byte comparison of the vendored anchor against its recorded sha via git history, `unverified` when git was unavailable, `MISMATCH` when the bytes disagree. `unverified` must never print as `ok` - the same rule as "unknown is not 0" (#903, #569)
- check-negative-controls reads the CHECKOUT and never `~/.claude/scripts`. Measured 2026-09-13: of 54 installed helpers 51 were byte-identical to main, 3 were not, 0 were dead mounts - so `st_nlink == 0` corpse-checking reports clean while stale helpers serve. `check-test-binary-guards.py` was one of the three and was byte-identical to `c6df826`, the very pre-fix artifact used here as an anchor, so a control pointed at the installed copy would have produced a REAL RED that looked like a successful demonstration: right about the file it read, silent about main. Every output line carries `NEGATIVE_CONTROL_SOURCE: worktree-at-<sha>`
- check-negative-controls registration is ONE line in the gate itself - `#: NEGATIVE-CONTROL: <control dir>` - so deleting the gate deletes the registration, and a directive naming a directory that is not there is `UNRESOLVED` rather than a skip. The manifest's `gate` field is authoritative for what is INVOKED; the directive's location only says how the control was DISCOVERED, and a registration living beside a different gate than it declares is refused. Reading the discovered file instead was a real defect in the first cut, caught by this script's OWN negative control, which reported `BLIND` for an absent gate - the exact collapse the verdict vocabulary exists to prevent
- check-negative-controls first consumer is `check-test-binary-guards` against #906, whose fix (1fa3560, parent c6df826) was written by someone who had never heard of this control - a control tuned against a fix being written in parallel proves much less. The known-bad fixture's helper HARD-REQUIRES `jq` with no `command -v` preflight, deliberately: a fail-soft helper is dropped by the hop ON PURPOSE (the #831 residual the gate's header documents as a remaining, accepted blindness), so a control written against that residual would fail against main while looking like a demonstration
- check-negative-controls manifest - `control.json`, one per control directory, is the half of the registration that does not fit on the directive line, and this is its whole schema. `gate` - repo-relative path to the instrument, and AUTHORITATIVE for what is invoked; the directive's location only says how the control was DISCOVERED, and a manifest declaring a gate other than the file carrying the directive is refused. `invocation` - the argv, with `{gate}` and `{case}` substituted and cwd at the repo root; use `python3` from PATH and never `sys.executable` or an absolute interpreter, because this manifest is read inside the CI image as well as on a dev box. `good_exit` - the exit code meaning GOOD. `detect_signal` - REQUIRED since #946, a regex (multiline) the gate's own stdout-plus-stderr must carry for a non-zero exit to count as detection; without it a crash and a finding are the same evidence, and a control that omits the field is `UNRESOLVED` rather than silently scored on the exit code alone. Anchor the pattern on something a CLEAN run cannot print - `^binary-guards: [0-9]+ unguarded test` includes the count for exactly that reason. Declaring the field is not enough and the harness refuses two ways of declaring it uselessly, both of which restore the old blindness while wearing the fix's own field name: a pattern that matches EMPTY output (`.*`, a trailing `|`, a bare `^`) makes every non-zero exit a detection again, and one that ALSO matches the gate's known-GOOD run identifies a clean run as readily as a finding. The second is checked against that run's real output rather than the author's intention, and only when the gate exited clean - a gate WEDGED at "fail" prints its finding line on the good input too, and that is `BLIND`, a fact about the gate, not about the regex. `cases[]` - `{name, input, expect}` where `input` is a directory relative to the control dir and `expect` is `GOOD` or `BAD`; register at least one of each, since the GOOD case is the only thing separating a working gate from one wedged at "fail"
- check-negative-controls anchors - `anchors[]` entries are `{kind, sha, origin, path, sha256}`. `sha` and `origin` name the historical commit and the path within it, `path` is the vendored copy relative to the control dir, and `sha256` is the digest of the HISTORICAL BYTES (`git show <sha>:<origin>`), NOT of the vendored file - hashing the vendored copy into its own manifest would only prove nobody edited it since someone wrote the digest down, which is not the claim provenance makes. Omitting `anchors` is legal and yields `UNPROVEN`, which `--strict` refuses: that is the state that makes acceptance step 4 mechanical rather than remembered
- check-negative-controls scored a CRASHING gate as detection until #946: the verdict came from the exit code alone, so a gate that fell over on the known-bad fixture was indistinguishable from one that reported it whenever the crash exited with anything but `good_exit` - and `check-test-binary-guards` exits 1 both ways, so for the one control that existed they were not separable at all. The harness printed `PASS`, exit 0, and "1 control(s) discriminate" for a gate that discriminated nothing, with the CI step green while it happened. Closed by making the manifest declare `detect_signal`: a non-zero exit is detection only when the gate also SAID something, otherwise the verdict is `UNSIGNALLED`. The same misscore lived on the anchor side and is fixed with it - an anchor that crashes on the known-bad input was reported as having CAUGHT it (`INERT`, which accuses a healthy anchor of not being blind) and is now `UNRESOLVED`, the narrower and honest claim. The committed control is `tests/test_negative_controls.py::test_a_gate_that_crashes_on_the_known_bad_input_is_not_a_pass`, which reports `PASS` on the pre-#946 harness
- check-negative-controls does NOT yet prove a mutation landed on an EXECUTED path. That matters only for a MUTATION anchor; a historical anchor is a real artifact that really was blind, so the "mutation that did not mutate" failure mode cannot arise. Every one of the seven first consumers has fix history, so no v1 consumer would exercise a mutation anchor - and shipping an unexercised fallback inside the framework for unexercised instruments is the thing this issue forbids. Recorded as a named gap: stdlib `trace`/`sys.settrace` for Python gates (`coverage` is not in the dev extras), `BASH_XTRACEFD` for shell

## `counter-model-receipt` (#934)

- counter-model-receipt - records ONE counter-model review run (#934), one JSON file per run under `docs/measurements/counter-model/`. The stage it records moved out of `/flow:auto_codex` (retired in #1017, once its committed trigger was actually evaluated) and into `/flow:auto` Step 6, where it runs BY DEFAULT: measured over merged PRs #585..#1000, the opt-in stage ran on **0 of 170** across two months, then 21 of 30 in two days because a wave orchestrator declared `driver: flow:auto_codex` in policy. Adoption tracked an external mandate that dies with the wave, not anyone's per-run judgement - so the thesis is not "nobody wants it" but "an opt-in stage exists exactly as long as someone with authority keeps re-imposing it"
- counter-model-receipt A RECEIPT, NOT A MARKER, and PR #1000 is the argument. That PR ran two review passes and fixed eleven findings, and greps as having had NO cross-model review - because its author rewrote the PR body by hand under the heading `## Codex: 11 findings across two passes` instead of the prescribed `## Codex pre-PR review`. A marker is written by the thing being measured and is therefore defeated by whoever writes it; the PR block is now a RENDERING of the receipt rather than the record. The receipts live in the repository because evidence about an instrument that does not live in the tree cannot be re-derived by anyone else - a count held outside the repo is a green nobody can audit
- counter-model-receipt A SKIP WRITES A RECEIPT TOO, with one of a CLOSED set of reasons - since #1015 exactly two, `codex-absent` and `reviewer-unavailable`, and BOTH are an inability to run the reviewer (owner ruling 2026-09-16: "the only condition for skipping a codex review is the inability to run codex"). A skip with a receipt is a state; a skip without one is indistinguishable from a stage that was never wired in, which is exactly the condition #934 was opened about - nothing anywhere recorded that the stage had not run, for two months. The two are kept apart because "the reviewer binary is missing" and "the reviewer was invoked and returned nothing usable" say different things about whether the stage works. `no-diff` and `explicit-opt-out` were removed: an empty diff now gets an ordinary review and an ordinary `ran` receipt, and there is no discretionary skip at all. The trigger that would bring `no-diff` back is committed beside `SKIP_REASONS`; `explicit-opt-out` is excluded from that trigger by name, because re-adding a discretionary skip is the swing it exists to catch
- counter-model-receipt ENFORCES THE PROPERTY RATHER THAN DOCUMENTING IT - `reviewer != implementer`, refused at write time with a non-zero exit and no file written. Issue #934 item 2 asks for the rule to be stated as a property, not a tool name ("the reviewing model must not be the implementing model"), so a qwen or gemma lane inherits it with no edit. A run whose reviewer IS the implementer is the author agreeing with themselves recorded as independent evidence, which is worse than no receipt because it is counted. `red_cases.already_covered > proposed` is refused for the same reason: it makes the diversity ratio exceed 1 and corrupts the only measurement that can tell an excellent reviewer from an uncritical author
- counter-model-receipt `parse_review` HAS THREE OUTCOMES, NOT TWO - `findings`, `clean`, `unparseable`. A transcript that is absent, truncated mid-finding, or written in some other shape contains zero finding headings, which is byte-identical to a clean review for anything counting headings. `clean` is returned ONLY when the reviewer says so in the prescribed words; everything else with no findings is `unparseable` and exits non-zero, so a caller that forgets to read the verdict still stops. #952's denominator convention applied to a review
- counter-model-receipt an EMPTY receipt directory is `unknown`, never `ok`. "No receipts" and "no receipts with problems" are different facts, and conflating them is how 0 of 170 went unnoticed for two months
- counter-model-receipt is NOT a gate and carries no committed negative control: `validate` checks SHAPE only and its failure is caught by `tests/test_counter_model_review.py`, which is the ADR 0008 bound working as intended. Reading the accumulated counts is a documented `jq` query in ADR 0007 rather than a summarising instrument, deliberately - a number that decides whether the stage becomes blocking should be derived in the open by whoever is deciding
- counter-model-receipt THE STAGE'S OWN RED CASE IS A PAIR OF RECORDED TRANSCRIPTS, not a live call: the same nine-line file reviewed twice by `codex exec` on 2026-09-15, once with a seeded defect (the reviewer named the exact bug) and once without (the prescribed clean statement). Neither `codex` NOR `git` is in the CI image - verified by loading `CI_IMAGE_BINARIES` rather than grepping around it - a live call spends the user's quota, and the reviewer is not deterministic. What CI checks is the STAGE's handling of a reviewer's output; that limit is stated in ADR 0007 and the fixture README rather than implied by the absence of a network call
- counter-model-receipt `--implementer` IS ALSO DERIVED NOW, not the literal `claude/opus-5` every run used to copy from the doc example (#1047 - the exact shape #1048 already fixed on the reviewer side). Claude Code keeps its own session transcripts at `~/.claude/projects/<project>/<session-id>.jsonl` (verified against a real live transcript, 1292 genuine `"model":"..."` entries found), so the writer derives from `$CLAUDE_CODE_SESSION_ID` (or `--implementer-session-id`) the same way the reviewer derives from a codex exec log - found by exact filename match, never the newest transcript on the host. The model value is SHAPE-CHECKED (must not start with `<` - a real identifier, never an angle-bracketed sentinel like `<synthetic>`), never denylisted by name, and the LATEST matching entry wins, because a session can switch models mid-conversation and the receipt should record what was implementing at write time (what counts as a "matching entry" was narrowed in #1109 - see the next line - because it originally meant any `"model"` anywhere in the file). This runs on `--status skipped` too, which is a real behaviour change from #1046: a skip in an environment with no derivable session now REFUSES where it previously succeeded with the literal - fail closed, deliberately, per #1047's own scope
- counter-model-receipt AN IDENTITY COMES FROM THE ASSISTANT, NOT FROM WHAT IT ASKED FOR (#1109). #1047's derivation regex-scanned the whole transcript for `"model": "..."` and kept the last hit, which treats a session log as a bag of strings. It is not: it also records every tool call the assistant made, arguments included, and some of those arguments are themselves named `model` - on this host `mcp__substrate__add_worker` carries `input.model: "opus"`, found in 7 records across a 60-transcript survey. So a session whose last action was spawning a worker recorded `claude/opus` as its own implementer: an identity taken from a REQUEST rather than from the responder. The sharper half is that DELETING the real `message.model` changed nothing - the decoy answered either way, so "the transcript says who wrote this" and "the transcript does not" produced byte-identical receipts, and the field that exists to prove `reviewer != implementer` could be filled from either. The extractor now PARSES each JSONL line and reads `message.model` only from records whose `type` is `assistant`; nested tool arguments, tool results and bare metadata records cannot supply an identity at all, and there is deliberately NO fallback to the old scan - a fallback would restore the fabrication on the path reached when something has already gone wrong. Unparseable lines are COUNTED rather than pattern-matched, and the refusal names its population (`read N record(s); M unparseable; K eligible assistant message(s)`), so a truncated transcript and a transcript with no assistant turns stop looking alike - #952's denominator convention at the extraction seam. Sentinel handling is unchanged: `<synthetic>` and blanks are eligible records without an identity, counted but never overwriting a real value. VERIFIED BOTH WAYS: the five new cases in `tests/test_counter_model_review.py` were run against a copy of the pre-#1109 source and all five failed there (the nested-argument, deleted-model, non-assistant-record, truncated-record and extraction-seam specimens), and the new parser derives real, DIFFERING identities (`claude-opus-5` / `claude-sonnet-5`) from six real host transcripts, so it is neither blind nor uniform. Two adjacent shapes were deliberately NOT widened into and went to the Nit Store instead: `_derive_reviewer_from_exec_log` has the same broad-text-search shape but no reproduced defect, and subagent (`isSidechain`) assistant records could in principle declare a different model - zero of ~25,700 assistant records surveyed carried that flag, so an exclusion for it would be untested speculation

## `counter-model-uniformity-check` (#1091)

- counter-model-uniformity-check UNIFORMITY IS AN OBSERVATION, NOT A DEFECT. A sweep once found 13 of 13 counter-model receipts recording the identical reviewer `codex/gpt-5.5` - the signature of a copied literal, not 13 independent observations (#1048, now fixed at the writer). But if one model genuinely reviewed every change in a period, "N of N identical" is the *correct* reading of a correct corpus. This checker distinguishes the two by cross-verifying a uniform corpus against independently supplied exec-log evidence, rather than treating uniformity itself as a finding
- counter-model-uniformity-check THE EVIDENCE LINK IS SUPPLIED, NEVER GUESSED, deliberately not a schema change to `scripts/counter-model-receipt.py`: real receipts carry no EXEC-LOG or thread_id field, so the manifest route cannot reach anything already on disk, and adding provenance now would help nothing already landed. NOTE (#1048): "structurally impossible" was how this read until 2026-09-20, and it was wrong - a receipt's `branch` names the worktree a rollout records as its own `cwd`, which is an association real receipts do carry. `counter-model-reviewer-attribution.py` uses it; the 13 are attributed in `docs/measurements/counter-model-reviewer-attribution.md`. The premise blocked that disposition for as long as it stood, which is the cost of writing an impossibility claim where a limitation was meant (filed to the Nit Store, claude-power-pack#864, rather than fixed here - re-touching #1048's shipped schema for a benefit that helps nothing on disk was judged out of scope). An `X.evidence.json` manifest is the only way a receipt becomes cross-verifiable, and nothing populates one for the real corpus today
- counter-model-uniformity-check FIVE VERDICT STATES, not two, checked in a fixed order: a disagreement between a stored reviewer and independently-derived evidence is a FINDING regardless of diversity (the strongest signal); a corpus that genuinely varies is OK; a uniform corpus verified against at least one piece of evidence with no disagreement is OK; a uniform corpus with zero verifiable evidence is UNKNOWN (today's real state for the actual corpus, and the case a gate wedged at "always trust uniformity" or "always distrust it" cannot separately pass); an empty population is UNKNOWN. The denominator - `examined=<n> verifiable=<m> distinct=<k>` - is printed on every verdict including the clean ones, so `0 mismatches` is never read next to an unstated population
- counter-model-uniformity-check ADVISORY, NOT GATING, and not wired into any Makefile target or CI step in this repository: a gating version would block on the 13 landed receipts' disposition, which is an OWNER decision this checker does not make, act on, or annotate (`docs/measurements/counter-model/` is read-only to it). ADR 0008 row 83 registers it as class X regardless - the operator eventually reading its verdict when deciding the 13's disposition will not independently re-derive the fact, which is what the bound turns on, not whether a machine currently blocks on it
- counter-model-uniformity-check REUSES `scripts/counter-model-receipt.py`'s own `_derive_reviewer_from_exec_log` via `importlib` rather than a second implementation of the thread_id -> rollout -> model lookup, so the two cannot silently drift apart on how a reviewer is derived
- counter-model-uniformity-check `--selftest` reads the FIVE COMMITTED CASES straight out of `controls/counter-model-uniformity/control.json` and asserts each one's exact exit code and output, so the self-test and the registered negative control cannot drift apart into two things that used to agree

## `counter-model-reviewer-attribution` (#1048)

- `counter-model-reviewer-attribution` ATTRIBUTES A LANDED RECEIPT TO THE ROLLOUT THAT PRODUCED IT, using the association real receipts actually carry: a receipt records `branch`, and a Codex rollout records its own `cwd` - the per-issue worktree, named for that branch - plus a start timestamp. This is what falsified the `structurally impossible` premise recorded one section above, which had blocked the disposition of the 13 landed `codex/gpt-5.5` receipts since #1091
- `counter-model-reviewer-attribution` IS AN INFERENCE, NOT AN IDENTITY, and the distinction is the point. The WRITER's derivation (#1059) anchors on a thread_id and is an identity; this anchors on a directory name and a time window. Its error rate is MEASURED rather than assumed: against the 16 post-#1059 receipts whose reviewers were independently derived, it agrees with 15, disagrees with 0, and cannot link 1. That control is inside its own output as `agreed=`, not a separate claim

## `slate-reconcile` (#1099)

- slate-reconcile REBUILDS AN INSTRUMENT LOST TO A SCRATCHPAD, not the same file: an orchestrator built the same kind of open-vs-claimed check earlier in this project, and it lived only in a session scratchpad, a path keyed to one Claude Code conversation's UUID. A resume made the directory unreachable, so the tool and every measurement it would have made afterward disappeared with no warning anywhere. This ships the check as a repository instrument instead, with committed tests and a committed negative control, so it survives the session that wrote it
- slate-reconcile TWO SIDES WITH INDEPENDENT ORIGINS, or the check confirms itself: the OPEN set is MEASURED (`gh issue list`, or `--open-set-capture PATH` for offline/tests), never something this tool or the claimed file controls. The CLAIMED set is DECLARED, read only from a hand-maintained file (`docs/slate-lanes.json`), never derived from mailbox history or anything else this tool infers - an instrument whose input is another agent's prose is not an instrument
- slate-reconcile DUPLICATE NEEDS NO OPEN-SET LOOKUP AND MUST GO RED WHILE THE TOTALS STILL BALANCE: it is checked entirely within the claimed file (one issue number appearing in more than one lane or bucket), which is precisely why it catches double-counting a naive sum cannot see - a claimed file can have exactly as many total entries as there are open issues while one issue is counted twice and another counted zero times, and a totals-only check would score that clean. The committed `bad-duplicate-while-balanced` case constructs exactly this and asserts both the DUPLICATE finding and the UNACCOUNTED finding it produces in the same run
- slate-reconcile THREE DISTINCT "COULD NOT TELL" STATES, never collapsed to "0 claimed" or read as a clean run: a missing claimed file, a claimed file that exists but fails to parse (loudly, not silently), and an unusable open-set source (a failed `gh` call, or an unreadable capture) each get their own message and exit 2. A lane or bucket key present with an empty list is a verified "nothing here", which is a different fact from the key being absent - the membership floor applies at the level of individual lanes and buckets, not only to the whole file
- slate-reconcile THE LIVE OPEN-SET QUERY OVERRIDES `gh`'S SMALL DEFAULT `--limit` DELIBERATELY (`OPEN_LIMIT`) and additionally refuses a result that reaches that override limit exactly, reporting it UNKNOWN rather than a possibly-truncated open set as complete - found by measurement, not designed in from the start: an early manual check against the real repository silently returned only 30 of 41 actual open issues because `gh issue list`'s undocumented default page size cut the rest, which is exactly the kind of silent undercount this instrument exists to prevent happening to someone else
- slate-reconcile A BACKLOG BUCKET IS REQUIRED FOR THE VERDICT TO KEEP ITS TEETH: without one, every open issue nobody has classified yet reports UNACCOUNTED on day one, which for this repository's ~40 open issues against 2-3 active lanes would be dozens of findings nobody acts on - exactly the noise that trains a reader to ignore a check. `backlog` (open, seen, nobody assigned) is a bucket like any other and stays a deliberate act, not a default; PHANTOM polices it from the other side, since a closed issue left in backlog starts reporting PHANTOM, so the file cannot rot silently in either direction
- slate-reconcile A DOCUMENTED LIMITATION IS THE POINT, NOT AN OMISSION: `docs/slate-lanes.md` states plainly, using the real case that motivated this issue as the worked example, that the reconciler will NOT catch #1033's remaining item 3 being the same work as the separately filed #1094 - those are two legitimately different issue numbers at the granularity GitHub gives, so DUPLICATE (which fires only on one number claimed twice) passes them. An instrument that looks like it covers a case it does not is worse than one that admits the gap, because the gap then gets trusted; finding that kind of duplicate still requires a person reading scope items against each other

## `check-oscillation` (#936)

- check-oscillation - reports knobs that have been moved BACK (#936). The pattern is the owner's: an approach choice "runs down the middle of two trade-offs, and we inevitably oscillate back and forth to each side in a futile attempt to satisfy diametrically opposing desires." Each swing is locally correct - it fixes the pain actually present - and the pain on the OTHER side is invisible at that moment because it was fixed last time. The structural sibling of ADR 0008: that one says name the input that makes an instrument report the other verdict; this one says name the observation that would move a SETTING back. Same epistemics, different object. The directive half lives in the owner's own `~/.claude/CLAUDE.md`, outside this repo; what ships here is `docs/decisions/0009-oscillation-control.md`, the detector, and its controls
- check-oscillation THE SIGNATURE IS "CHANGED BACK", NOT "CHANGED TWICE". A knob tightened 60 -> 30 -> 10 is three edits to one threshold and is not oscillation; 30 -> 60 -> 30 is. The issue names the second half as the one that matters - "a detector that flags every threshold edit is noise, and it will be disabled, which is itself an oscillation" - so every test in `tests/test_oscillation_control.py` comes in pairs, and `test_the_corpus_contains_BOTH_verdicts` asserts the corpus is not all-positive, because the natural way to extend a corpus later is with more positives and a corpus of those cannot detect a detector wedged at `found`
- check-oscillation IT REPORTS, IT DOES NOT FAIL THE BUILD (owner ruling, 2026-09-15), and that is deliberately not the same as an exit code that cannot fail. `found` / `none` exit 0 - a verdict about the KNOBS; `unknown` exits 3 - a verdict about THIS RUN's ability to look. A population of zero is `unknown`, never `none` (#952): "I examined 400 knob changes and none reversed" and "I examined nothing" are different facts and share neither a word nor an exit code. `--exit-on-finding` exists ONLY so `controls/check-oscillation` can register a real two-sided case, because the framework decides a case from the exit code (`GOOD = exit == good_exit`) and a detector exiting 0 for both verdicts has its known-BAD case scored GOOD - the control would have been blind in exactly the way the framework exists to catch. Its committed reversal trigger is that the build must NEVER pass it
- check-oscillation THE POPULATION IS DERIVED FROM HISTORY; THERE IS NO KNOB LIST. Knobs are discovered by walking `git log --unified=0 -p` and pairing removed/added lines within a hunk by shared setting NAME, so a knob introduced next month is watched from its first edit. A hardcoded list of "the knobs worth watching" is a coverage enumeration, and this repository has repeatedly found those stale
- check-oscillation TWO OPPOSING EDITS IN ONE COMMIT ARE NOT AN OSCILLATION - a swing is across time, not within a single change. The first cut had no such rule and reported a lockfile's package sizes, both "moves" carrying the same sha; found by running the detector against this repository's real history rather than only against fixtures. The test pinning the rule was itself VACUOUS on its first cut: it built a two-revision fixture, which yields ONE move, and one move cannot form a pair - so the assertion passed with the rule deleted. Caught by mutation, not by reading, and the fixture now asserts it holds a pair of opposing moves before saying anything about shas
- check-oscillation `--window` is a threshold, which is one of the issue's own tells, so its reversal trigger is committed beside it in the source rather than in a PR body the next person to touch the line will not read. A control that exempts itself from its own directive is the most conspicuous possible way to fail. `test_the_window_actually_BOUNDS_which_pairs_are_reported` exists because the trigger is unsatisfied by a setting nothing reads: deleting the window comparison left every other test green, so the threshold carried a rationale and no behaviour
- check-oscillation THE EXTRACTOR WAS BLINDEST WHERE THE RULE IS STRONGEST, and this was found by probing it rather than by reading it. ADR 0009's strongest tell is "the diff touches a line whose adjacent comment exists to explain why it is set that way" - and the first cut required a value to be followed by `,;)]` or end-of-line, so `timeout = 30  # seconds, see ADR 0009` extracted NOTHING. The trailing context is now a negative lookahead `(?![\w.])`, which keeps the reason the delimiter class existed (`version = 1.2.3` and `sha = 3f2a` still match nothing) and lets any trailing text follow. Two siblings found in the same probe: `timeout: int = 30` keyed on `int`, so every annotated knob in a file collapsed onto one key and unrelated settings could appear to swing against each other - a finding pointing at the wrong line is worse than a missed one; and `exit N` was unanchored, so prose about exit codes became a knob named `exit` whose value swung between paragraphs, in a repository whose documentation discusses exit codes constantly. `exit` is now whole-line anchored, which deliberately gives up `[[ -n $x ]] && exit 3` - noise is not a neutral failure for a reporting detector, because being ignored is how it fails

The #953 convention one level down: a different CONCLUSION earns a new verdict, the same conclusion reached for a different cause earns a reason field. Folded together at first, so a range git REFUSED (`HEAD~200..HEAD` on a 90-commit history) printed the same line as a real history holding no knob edits, and a reader chasing the first would have gone hunting for knobs that were never the problem

- worktree-remove
- worktree-remove `--steal` + claim owner check (#597) - refuses with exit 4 to remove a worktree claimed by another LIVE session (printing the owning pid/session), releases a self-owned or stale claim and proceeds otherwise, and takes `--steal` as the deliberate override. One change covers `/flow:auto` Step 7, `/flow:merge` and `/flow:cleanup`, since all three route removal through this script
- worktree-remove live-occupancy guard (#888, follow-on to #597) - the #597 claim protects a worktree only where one was STAKED, and `flow-worktree-claim.sh check` has seven states while the removal `case` handled two pairs: `held|foreign` stopped, `self|stale` released, and `free`, `unsupported` and `unknown` fell through it silently. `free` is not evidence of an idle checkout - it is simply what any worktree created outside the /flow lane reports - so an unclaimed worktree was removed like an abandoned one, and the uncommitted-changes backstop could not catch it either because `--force` skips that check and `/flow:auto` Step 7 always passes `--force`. Occupied AND dirty is a hard stop (exit 5) that `--force` does NOT suppress, since a guard `--force` silences never fires where the damage happens; `--steal` overrides as it does for a claim. Deliberately NOT the obvious fix of refusing every unclaimed removal - `free` being the normal state of most worktrees, that converts a rare data-loss bug into an everyday blocker, and `test_idle_and_dirty_still_removed_with_force` pins the ordinary Step-7 path against exactly that over-correction. Occupied-but-clean still removes: with nothing unsaved there is nothing unrecoverable to lose. Path matching is boundary-aware (`<wt>` vs `<wt>-2`) rather than a bare prefix, which is not hypothetical - `kyle-issue-1142` is a real prefix of `kyle-issue-1142-container-spec-superseded` - and the scan excludes its own PID and full ancestor chain, since `/flow:auto` invokes the script from a shell whose cwd may still be the worktree. A host with no readable `/proc` prints `WORKTREE_REMOVE_OCCUPANCY: unknown` and falls open: unchecked must never render as clean, which is the failure the guard exists to remove. `WORKTREE_REMOVE_PROC_ROOT` is a test seam that makes that unscannable lane reachable on a host with a working /proc
- worktree-remove branch attribution + the recycled-pid reading (#1032) - a worktree directory is NAMED for the issue it was created for, but the name is a string and nothing keeps it in step with what is checked out inside. Observed on this host: `...-issue-971-...` (CLOSED, PR #1004 merged) holding branch `issue-980-lexicon-quoted-token` (OPEN) - a cleanup trusting the path would have read "closed, merged, safe" about an open lane's checkout, and survived only because #980 had no commits yet. Confirmed against the pre-fix script, which exited 0 and deleted issue #980's branch when handed the #971 path. Comparison is on the issue NUMBER alone, never the slug - a branch legitimately keeps an older title's slug while the issue is renamed (#793), so matching full names would fire on the ordinary case, and a guard that fires on the normal case is one everybody learns to pass with the override. `--force` does NOT override it (Step 7 passes `--force` every run); `--steal` does. The refusal is deliberately the LAST check reached: every other refusal means "do not remove this at all", while this one means only "do not also delete the branch" and its remedy still removes the directory - reached earlier it would hand that remedy to a caller whose tree the occupancy or claim guard had already refused. It also relays the claim's new `identity` field, so `stale` from a recycled pid is distinguishable from `stale` because the owner exited

## `flow-worktree-sweep`

- flow-worktree-sweep (#887) - nobody owned worktree teardown, and the gap is structural rather than an oversight: in a wave the party that CAN remove a worktree has finished by the time the party that DISCOVERS it exists gets there. `gh pr merge --delete-branch` deletes the remote branch, then tries `git branch -d`; git refuses while a worktree holds the branch, and `gh` has no notion of worktrees, so it stops - leaving the worktree holding a branch that no longer exists on the remote. Measured on cooneycw/kyle after ONE wave: 33 registered worktrees and 3.1G, of which 25 held merged branches and 21 were removable by every test at once; cleaning them took the tree to 12 worktrees and 1.1G. The disk was never the defect. The `git branch -d` error appeared on EVERY merge of that wave - roughly a dozen times - and was correctly ignored each time, because the merge had succeeded and the message described a local-branch deletion nobody needed; a warning that is right to ignore twelve times is one nobody will act on the thirteenth. Of the three owners #887 named, the worker on PR open cannot work (the worktree must survive review feedback and re-merges - several PRs took three pushes) and the merging session was rejected for two reasons: its population is only merges IT performs, so a PR closed rather than merged, one merged in the web UI, or a worktree orphaned when its session died are all structurally out of reach (six worktrees on the measured host held branches with no PR at all), and more importantly a refusal is EXPENSIVE for it - it has a merge to finish, so a guard that blocks it is an obstacle to route around, which is the documented history of this exact helper (Step 7 passes `--force` on every call, and #888 exists because `--force` silences the dirty check). A sweep pays nothing to skip, so it can afford to believe its own test. Full argument, including why the cross-session-mutation objection is DISCHARGED rather than inapplicable, in `docs/decisions/0006-worktree-teardown-ownership.md`
- flow-worktree-sweep was INERT in production from #905 landing until #916 fixed it, and the shape is worth keeping. The sweep's entire population is worktrees whose PR merged and whose remote branch is therefore gone; `worktree-remove.sh`'s #905 unpushed check refused exactly that state with exit 7, reading "no remote-tracking ref" as "these commits exist nowhere" when a SQUASH had put them on main under a different sha. Measured end to end - `candidates=1 removable=1 removed=0 refused=1`, `FLOW_WORKTREE_SWEEP: partial`. The sweep applied all five conditions correctly, concluded correctly, and removed nothing. NOT an argument against #905: the refusal was the safe direction, and an inert sweep loses a directory rather than work. The interaction had no owner - #905 was correct and green, #887 was correct and green - and it was found only by running the suite against main AFTER both merged, which nothing in the flow asks anyone to do. #916 closes it with a second signal that can say LANDED rather than a looser first one: `gh-pr-merge.sh` records `branch.<name>.cpp-merged-head` inside its MERGED block, before the `push --delete` destroys the only other evidence, and `worktree-remove.sh` accepts that record ONLY when it equals HEAD exactly. The recorded OID is the PR's `headRefOid` from GitHub - the commit `MERGED` actually proves landed - and is written only when the PR's `headRefName` is this branch; NEVER the local tip (cross-model review): a local branch can sit one unpushed commit past its merged head, and a record of the local tip would have marked that commit landed and let the helper delete the only copy - the #899 data-loss path reopened by the fix for its false refusal. A branch that advanced past the recorded head no longer equals it and is refused, which is the protection working. The OID equality is the guarantee, not the cleanup: `git branch -D` clears the section but `git update-ref -d` does not, so a record can outlive its branch and is harmless anyway because a surviving record names an OID that genuinely landed. The fix is FUTURE-ONLY by nature - nothing can retroactively record a merge that already happened without asking the network which merges happened - so a branch squash-merged some other way, or merged before #916, still reads `unpushed` and stays refused. `tests/test_worktree_sweep.py::test_the_sweep_removes_a_real_post_merge_worktree` was the characterization test that pinned the broken behaviour and is now flipped to assert removal; the rest of that file builds worktrees with `git worktree add -b` and never pushes, so no branch has a `branch.<name>.remote` at all - a fixture that never pushes cannot exercise a check whose subject is a branch's relationship to its remote, which is why the suite could not see this
- flow-worktree-sweep safety test and delegation - the five #887 conditions (PR MERGED, or CLOSED under `--include-closed`; `git status --porcelain` empty; nothing unpushed; no `/proc/<pid>/cwd` at or under the worktree; no `locked` line) are re-read for a worktree IMMEDIATELY BEFORE that worktree's own removal, never from a list built earlier, because the state moves while a wave runs - which is also why `--apply` re-derives rather than executing the dry-run report, and why the default is a dry run at all. Every removal goes through `worktree-remove.sh` with NO flag but `--delete-branch` - every other flag the helper accepts overrides a refusal, and the sweep is the one caller that would apply one to every worktree on the host, so the sweep's largest contribution to safety is what it does not pass. Originally stated as "without `--force` and without `--steal`", which #899 overtook by splitting `--force` into `--force`, `--allow-dirty` and `--allow-unpushed`: the uncommitted-changes check is now armed unconditionally and `--allow-dirty` disarms it. The decision was unchanged by that, but the PIN was not - `tests/test_worktree_sweep.py` enumerated the two flags that existed when #887 landed, so the sweep could have begun passing `--allow-dirty` with all 25 tests green (measured, not hypothetical). It now asserts an allowlist (`{--delete-branch}`), which covers a sixth flag on the day it lands. The #597 claim at exit 4 and the #888 in-use refusal at exit 5 remain final. A non-zero exit is recorded against that worktree as `refused` and the sweep moves on: never retried, never re-attempted with an override, because doing either in a loop over every worktree on a host is the data-loss path #889 closed, reopened at scale. `tests/test_worktree_sweep.py` pins the argv contract directly against a recording stub, since the argv IS the contract. Verification is per-worktree and carried from classification to removal one at a time, and `dirty` plus `unpushed` are re-read as the LAST statements before the removal call, because a `/proc` walk and a GitHub round trip sit between the first read and the invocation. `unpushed` is singled out because it is the only condition with nothing beneath it: `dirty` is backstopped by the helper's own check, `locked` by git and the #597 claim, `occupied` by #889's exit 5 - but a session that COMMITS without pushing reports a clean `git status` and, if paused between tool calls, has no live process for either occupancy scan to find. The residual window is the helper's own startup (spawn + claim check + /proc scan), accepted because the commit objects survive in the common object database and stay reachable via `git fsck --lost-found` until gc, and because a lock held across the whole sweep would block the sessions the sweep exists to stay out of the way of. Both window cases are pinned behaviourally by a `git` wrapper that mutates the worktree after a chosen read, making the race deterministic rather than timed
- flow-worktree-sweep undecidable-vs-skip - `pr-unknown`, `unpushed-unknown` and `occupancy-unknown` are reported as UNDECIDABLE and counted separately from skips, making the run `partial` (exit 3): "I looked and it must stay" and "I could not tell" are different facts, and a sweep that renders the second as the first claims a clean tree it never established. `no-candidates` is likewise distinct from `nothing-to-do` - a repo with no linked worktrees examined an empty population and must not report the same word as one that examined nine and correctly kept them all. `pr-none` is a SKIP and never a reason to remove: two of the skips on the measured host were a deliberately preserved WIP branch and a wayfinder research branch, which by design never gets a PR, and a sweep keyed on "no PR" would have destroyed both. Unpushed is answered by two mechanisms that share no input (#888's lesson that two guards on one signal degrade to one): `git log @{u}..`, which is git-native and exact but unavailable once `git fetch --prune` drops `refs/remotes/origin/<branch>` - the normal state after `--delete-branch` - and the PR's own head OID, which survives the prune and doubles as an IDENTITY check that this local branch is the thing that merged rather than a same-named branch recreated since. Population comes from `git worktree list`, never a path glob: #627 puts worktrees beside the repo as `<parent>/<repo>-<branch>`, so an unrelated checkout sits in the same directory and only git can tell them apart. Stricter than `worktree-remove.sh` in two places on purpose - occupied-but-clean is skipped rather than removed, and an unreadable `/proc` skips rather than falling open - because the helper serves a caller who named one path and asked for it, while the sweep is choosing its own targets. `FLOW_WORKTREE_SWEEP_PROC_ROOT` is a test seam, not a knob. Deliberately NOT added to `templates/claude-settings-permissions.json` (the installer array may be a superset): an allow rule for `worktree-remove.sh` pre-approves a command whose target is visible in the line an operator reads, while one for the sweep would pre-approve a command whose target SET is not, and `git worktree remove` is DESTRUCTIVE by `scripts/classify-tool-risk.py`'s own classification

## `gh-pr-merge`

- gh-pr-merge - layout-aware PR squash-merge used by `/flow:auto` + `/flow:merge`; polls mergeability to wait out a transient `UNKNOWN` right after push (#485); bounded refetch+retry when the squash fails on `Base branch was modified` (sibling merge race, #502); opt-in `--admin` flag plus a single admin-gated auto-retry when a squash is rejected by branch protection on an owner merge (#517)
- gh-pr-merge `--admin` narrowing + required-check wait (#577, ADR 0004) - before the squash it resolves the BASE branch's required status-check contexts and polls the PR head until they are green (bounded, `GH_PR_MERGE_CHECK_ATTEMPTS` x `GH_PR_MERGE_CHECK_DELAY`); a red required check, and one that never reports, are hard stops. A required-check block is EXCLUDED from the #517 `--admin` auto-retry - auto-overriding it would defeat the required check on every run - while a review block (#517's actual case, and #579's) is unchanged; an explicit `--admin` from the caller still skips the wait, the documented break-glass
- gh-pr-merge required-context resolution reads BOTH protection mechanisms and believes only a 2xx (#610) - the #577 resolver read classic branch protection alone and discarded gh's exit code, so a 404 body (`{"message":"Branch not protected"...}`, which `gh api` prints on STDOUT with `--jq` unapplied) became a "required context" that could never report, and the wait timed out into a refusal. It fired both when a repo had no protection AND when `main` was guarded by a repository RULESET, which the legacy endpoint cannot see. Resolution now unions `/branches/{b}/protection/required_status_checks` with `/repos/{o}/{r}/rules/branches/{b}` and reports one of three states: `declared` (wait, exactly as #577), `none` (a source answered, nothing required -> skip the wait outright), `unresolved` (neither readable -> fall back to the checks the PR itself reports: green merges, RED is a hard stop, pending waits then FAILS OPEN). Enumeration failure no longer outranks observed reality, and the client-side wait is defence in depth - GitHub enforces a ruleset server-side at squash time, so a plain `gh pr merge --squash` cannot bypass the posture. Cost before the fix: 25 flow:auto runs, ~4h of wall-clock, every one worked around by hand
- gh-pr-merge review gate + exit-3 clean stop (#579) - a required human review is a handoff, never an automated bypass: before the squash the helper reads `reviewDecision` and on `REVIEW_REQUIRED`/`CHANGES_REQUESTED` exits 3 (a FIRST-CLASS CLEAN STOP: PR left open/current/green, message prints the PR URL + "approve or merge on GitHub, then /flow:merge"); a review-family rejection at squash time hits the same stop as belt-and-braces. This retires the #517 auto-`--admin` retry for review blocks - the retry survives only for the residual ADMINISTRATIVE family (protected-branch/push-authorization/base-branch-policy), so automation now bypasses neither a required check (#577) nor a required review; an explicit human-typed `--admin` remains the break-glass and skips both gates. ## `flow-worktree-claim`

- flow-worktree-claim - cross-session OWNERSHIP claim on a flow worktree (#597), the half #503 could not cover: the live-driver guard protects a session ENTERING a worktree, but nothing protected an active worktree from being REMOVED by a sibling session, whose Step-7 cleanup deleted an issue-N checkout by name and destroyed uncommitted work with no signal but the user noticing. Rides git's own `git worktree lock --reason "flow-claim issue=N pid=... session=... host=... ts=..."`, so the claim is a real barrier (`git worktree remove --force` refuses a locked worktree) rather than an advisory note, and is readable from `git worktree list --porcelain`. `claim`/`check`/`release` verbs; ownership is pid + session, liveness is `kill -0` trusted only when the recorded host matches, and a claim whose owner is gone is STALE and auto-taken-over so the mechanism can never wedge a repo. A lock this family did not write is FOREIGN and never stolen. Staked in `flow-start-resolve.sh --verify` - the hook point running INSIDE the worktree on every lane - and read by resolve mode via `check --issue N` BEFORE any worktree is created, so two sessions handed the same issue stop instead of racing. Fail-open everywhere except the case it exists for: claiming against a live owner exits 1
- flow-worktree-claim pid-IDENTITY witness (#1032) - liveness was `kill -0 <pid>`, which answers "some process has this number", not "the owning session is alive". Linux recycles pids - the space wraps in hours on a busy host - so a dead session's claim read HELD forever, and `FLOW_CLAIM_MAX_AGE_HOURS` aged out only claims from ANOTHER host, so a same-host claim on a recycled pid had no bound at all. That fails in the UNSAFE direction: the reading that BLOCKS recovery, leaving `--steal` - the override meaning "I am overriding a genuinely live owner" - as the only way to clean up after a dead one, at which point the safe path and the deliberate override are the same flag. The claim now records `start=<ticks>`, field 22 of `/proc/<pid>/stat`: a pid can be reused, a pid paired with its start instant cannot. `FLOW_CLAIM_OWNER_WITNESS` reports HOW liveness was decided - `matched` (alive, decisive), `mismatched` (the pid exists but is a DIFFERENT process -> stale, the reading that fixes this), `absent`/`unreadable` (identity could not be established). The witness may only DEMOTE on a positively read CONFLICTING value; an unreadable one never yields `stale`, because a check that cannot read identity has not disproved it. The age bound now applies to any claim whose identity could NOT be established, same-host included, so nothing can wedge a repo permanently - and NOT to a matching witness, so a session legitimately working one worktree for days is never evicted by the clock. That asymmetry is what makes the threshold change one-sided: the case that would argue for moving it back cannot occur, and `test_a_verified_owner_is_never_aged_out` pins it. Field 22 is read by consuming through the LAST `') '` rather than splitting the line, because `comm` is process-controlled and may contain spaces - measured on this host, a process named `npm exec tavily` yields 11 from `awk '{print $22}'` and the true start-time from this extraction. `FLOW_CLAIM_PROC_ROOT` is the test seam making both witness lanes reachable on a host whose /proc works. Sibling gap, deliberately NOT widened into here: `flow-wave-registry.sh` liveness is pid-identity-blind the same way, and #1033 item 3 owns it by name

## `check-test-binary-guards` (#906 direct-invocation hop)

- check-test-binary-guards direct-invocation hop (#906) - the #789 one-hop scan required argv[0] to be `bash` or `sh`, so a test that ran a repo script DIRECTLY on its shebang (`subprocess.run([str(HELPER), ...])`) entered no hop at all and the script was never scanned. Every helper in `scripts/` is executable and carries `#!/usr/bin/env bash`, so direct invocation is the NATURAL spelling: a test author following the repo's own conventions got no coverage, while one writing the less natural `["bash", SCRIPT]` did - reinstating, for the commonest shape, exactly the local invisibility the gate exists to remove. The trigger now also fires when argv[0] itself resolves to an executable file inside the checkout, reusing the existing resolver and scanner. Only the TRIGGER widens: the scan it feeds is the same `binaries_in_script()` against the same explicit `GUARDED_BINARIES`, so the function-versus-binary collision that made inverting the hop unworkable (#831) stays out of reach - a shell function is mistakable for a binary only when scanning for arbitrary tokens, and nothing here does. Bounded by an ownership boundary (argv[0] resolving OUTSIDE the checkout is ignored - a system script is not ours to scan) and by executability (the shape covered is "run on its shebang"; a non-executable path cannot run, so scanning it would read a file the test never executes). Verified by control rather than assertion: on a synthetic tree with a script that hard-requires `jq`, the pre-#906 checker finds 1 of 3 invocation shapes and the new one finds 3 of 3
- check-test-binary-guards: #906's own 11-of-12 is TWO stacked gaps, and only one is closed (#906, #831) - the issue attributes its measurement (11 of 12 `curl` tests in `tests/test_lane_serveability.py` invisible) to the trigger alone. Reproduced exactly, then re-measured WITH the trigger fixed: still 1 of 12. The trigger fires; `binaries_in_script(scripts/lane-serveability-check.sh)` returns empty, because that script preflights `command -v curl` and reports `unknown` when it is absent - it genuinely degrades, so the hop CORRECTLY drops curl. That is the #831 residual by name: the hop answers "can the SCRIPT do its job without this binary?" while a reader takes it for "can the TEST pass without this binary?", and they diverge wherever a test FORCES the degraded lane, as these twelve do by stubbing a server and asserting real HTTP outcomes. #906's acceptance criterion is met (it is correctly worded, "where the script hard-requires a guarded binary"); its narrative attribution is not. Those twelve keep their hand-written `requires_curl` and the header's caveat list now names this case
- check-test-binary-guards heredoc masking (#906, cascade step six) - widening the trigger took the tree from `ok` to 31 findings, ALL false, ALL from ONE line of prose. `scripts/delegated-run-check.sh` embeds a Python program at lines 225-442 via `python3 - <<'PYEOF'`, and a docstring inside it reads "a model that tries \`git commit\` once and moves on is behaving exactly as designed". Those are MARKDOWN backticks - but a backtick opens a command substitution in shell, and `SHELL_BINARY_RE` counts one as a command-position separator, so the sentence read as an invocation of `git`. `_mask_noncode` resolves comments, quoting, arithmetic and command substitution and had NO heredoc handling. A quoted-delimiter heredoc body is now blanked before the shell-quoting pass: it is literal text the shell hands to another program and never executes as shell, and a nested interpreter's needs are a SECOND hop this checker states outright it does not follow - so this is consistent with the existing depth rule rather than a new exception. Only QUOTED delimiters: an unquoted `<<EOF` body IS parameter-expanded and command-substituted by the shell itself, so its `$(...)` really are this script's invocations and masking them would be the undercount direction. This is `#831 -> #833 -> #838 -> #840 -> #841` one step further, and it could not fire before #906 because that script is only ever invoked directly by its tests - the gap masked the bug. The coupling is not a choice: removing the mask reddens the two existing #838 widening oracles, so the trigger change cannot land without it

## `flow-pr-watch`

- flow-pr-watch - the post-clearance watch (#788): in a wave the merge-queue critic clears a PR's queue position, the PR's next pipeline runs, and NOTHING watches the result. On the kyle-completion wave (2026-09-05) the owner noticed a red pipeline on a cleared PR before the critic did, and the clearance stood unrevised over a red run - issuing the clearance is where the critic's attention ended. Run it as a BACKGROUND call after a clearance: it blocks until the pipeline is terminal, then exits, so the harness re-invokes the critic with a verdict in hand - the same wake shape as `flow-wave-mailbox.sh watch`
- flow-pr-watch classification - pipeline colour is not the answer, because a red on a cleared PR is one of three things whose right responses are opposite: `cancelled` (a superseding push killed the run - re-pushing it only lengthens the queue), `flake` (a test already on the wave's declared list - blaming the PR stalls a clean merge), `red` (a real failure - retrying until it wins hides the defect). Each has a mechanical signature, which is why the triage that was done by hand all evening is automatable at all
- flow-pr-watch cancellation is CONJUNCTIVE - a superseding run must exist AND the watched run must carry the kill signature (server state `killed`/`cancelled`, or every stopped step sharing one `Stopped` timestamp with no pytest summary in the log). Either half alone would excuse a genuine defect that merely happened to be re-pushed over, which is the expensive direction of this error; a superseded run whose log reached a real pytest summary is classified on its failures instead, and `tests/test_flow_pr_watch.py` pins that
- flow-pr-watch resolves through the check rollup, NOT `pipeline ls` - for a `pull_request` event Woodpecker records the TARGET branch, not the head, so a branch grep finds the wrong run or none. The rollup's `targetUrl` on the PR head is the only link from "this PR right now" to "that pipeline number" that cannot drift; the `woodpecker-cli` lane is a fallback and anchors on the exact head SHA, never on list position (the #766/#516 lesson). Supersession is detected two ways: the PR head moving (needs no CI provider at all) and a higher-numbered pipeline appearing for the same head
- flow-pr-watch baseline - the helper does NOT decide what a flake is; that stays a human/critic judgment recorded in a plain list of test ids (`#` comments, blank lines ignored) passed via `--baseline`, defaulting to `<checkout>/.claude/flow-flake-baseline.txt`. An entry may be a full id (`tests/test_x.py::test_y`) or a bare test name, which matches any id whose last `::` component equals it. The match is all-or-nothing - one id outside the set makes the whole run red - and the verdict always prints the ids it excused, because a baseline entry left in after its flake is fixed would otherwise silently downgrade a real regression
- flow-pr-watch contract - `FLOW_PR_WATCH_PR` / `_HEAD` / `_PIPELINE` / `_URL` / `_SUPERSEDED_BY` / `_FAILED` / `_BASELINE` / repeated `_ASSERT` detail lines, then `FLOW_PR_WATCH: green|cancelled|flake|red|timeout|unknown`. Exit 0 for green, cancelled, flake and unknown; 1 for red; 2 usage; 5 timeout - no new exit code for a new verdict (the #674 rule). Fail-open like every other advisory helper: no `gh`, no CLI, no pipeline for the head all report `unknown` and exit 0, because a watch that cannot see must never be the reason a wave stops. Without `woodpecker-cli` a red is still reported as red, with no ids and an explicit NOTE, rather than guessed at

- lane-serveability-check - can a local-model lane actually SERVE, as opposed to having the model registered (#895, the #581/#613 pattern). `/qwen:auto` and `/gemma:auto` gated delegation on `GET /api/version` plus `GET /api/tags`, which answer *is the daemon up* and *is the model in the manifest*. - lane-serveability-check probes `/api/generate`, and the tidier story for why is wrong. It prints "unchecked, not clean" and `/qwen:status` renders it as a third summary state, `UNVERIFIED`, which may only ever weaken a `true` - a missing harness is a decided NOT READY and uncertainty must not soften it into a maybe

## `delegated-core-vendor`

- delegated-core-vendor - one shared lifecycle for `/codex:auto`, `/qwen:auto` and `/gemma:auto` (#1011). The three described the SAME eight-step lifecycle three times - 367-454 non-blank lines shared per pair - and the cost is on the record: #774 found all three printing a Step 2 plan report that "reads exactly like a checkpoint and was not one", one defect present in three documents simultaneously, found on a six-worker wave where three workers described a halt that did not exist. By the time this landed the drift was real, not hypothetical: codex's Steps 6-8 carried ~60 lines qwen's and gemma's never received. Step 4 (the model invocation), Environment, the capability contract and Notes stay per-driver and are never generated
- delegated-core-vendor contract - `check` (default) exit 1 on any problem, `--write` re-renders, `--root DIR` points both at another tree (which is what makes the control's fixture cases possible). Verdicts: `MISSING` (a driver file, a values file, or a region's marker pair is absent), `ORPHAN` (a values file declares a slot the core never uses), `UNRESOLVED` (`{{...}}` residue no slot rule claimed), `DRIFT` (a rendered region's bytes differ from the render). Stdlib-only, offline and git-free, so the slim CI image gives the same verdict as a dev box - which is why it runs in BOTH `make verify` (via `delegated-core-check`) and the `delegated-core-check` Woodpecker step, unlike `oscillation`, which needs git and is local-only
- delegated-core-vendor slot rules - a placeholder ALONE on a line is a block slot and its value's lines replace it, an EMPTY value removing the line entirely so an optional paragraph leaves no blank behind; a placeholder inside a line is inline and its value must be one line. A slot's value is the EXACT text between its marker and the next in `templates/delegated-driver-values/<driver>.md` - nothing is stripped, so a trailing blank line there is the paragraph break its surroundings need. Two refusals worth naming, both because the silent version ships into three prompt documents: an INDENTED block slot is refused rather than reinterpreted as inline (its value's lines would not inherit the indent), and `UNRESOLVED` uses a deliberately LOOSER pattern than the slot matcher, because `{{driver}}` is not a slot by the upper-case rule and would otherwise render as literal text with nothing complaining
- delegated-core-vendor is a gate that lets work THROUGH, so it carries a committed negative control (ADR 0008): `controls/delegated-core-vendor` holds whole miniature fixture TREES, one with every region rendered and one with a single line of qwen's region B edited in place, markers intact. The anchor is `constructed` rather than historical - the gate is new, so the honest "before" is "no check at all", which cannot be run against a case - and is the plausible weaker thing somebody would write instead: confirm the marker pair is present and call that vendored. It catches deleted markers and is blind to a region edited in place, which is the failure that actually happens

## `delegated-run-check`

- delegated-run-check - the verdict on whether a DELEGATED-model run actually succeeded (#798, the #581/#613 pattern). Every local/delegated lane (`/qwen:*`, `/gemma:*`, `/codex:*`) decided a run's fate by testing `$?` against zero, and in all six command documents that test could not observe the CLI's exit status. Two structural reasons, and a third that no exit-code fix reaches: `... | tee "$OUT"` makes `$?` the status of `tee` (`pipefail` was set nowhere - grepped, zero hits across all three lanes - so the documented `exit 124 = timeout` branch was literally unreachable); in the three `auto` files the invocation and the check sat in SEPARATE fenced blocks with prose between them, hence separate shells, so `$?` reflected whatever ran last in the new shell; and the Qwen CLI reports success on a failed run outright - verified 2026-09-07 against an unreachable endpoint (`@qwen-code/qwen-code` 0.15.10): `EXIT=0`, `subtype: "success"`, `is_error: false`, `num_turns: 1`, with the only evidence of failure being `[API Error: Request timeout after 154s...]` inside the terminal `result` string. So a dead endpoint read as a completed task and `/*:auto` marched into review, quality gates, `/flow:finish` and `/flow:merge` on an empty diff. Found while diagnosing why `/qwen:*` was pointed at an offline MacBook (corrected to `proxvmqwen45`): the endpoint had been wrong long enough to matter and nothing surfaced it, because the harness reported success throughout
- delegated-run-check contract - `DELEGATED_RUN_LANE` / `_FILE` / `_EXIT` / repeated `_SIGNAL` / `_DETAIL` / `_TOOL_ERRORS` (#836), then `DELEGATED_RUN_STATUS: success|failure`. Exit 0 success, 1 failure, 2 usage. Signals: `exit-nonzero`, `timeout` (124), `output-missing`, `output-empty`, `output-unreadable`, `api-error`, `error-payload`, `no-turns`, `no-tool-use`. Written DEFENSIVELY across all three harness formats rather than assuming they share the Qwen behaviour - the issue verified the false-success only for Qwen Code and explicitly declined to assume it of OpenCode or the Codex CLI, so signals absent from a format simply never fire
- delegated-run-check: an `item.type: "error"` fails only in CONJUNCTION with nothing having run (#892) - when the Codex CLI cannot start its execution tool it announces that as an item whose OWN `type` is `"error"`, and `is_fatal` judges only the TOP level of an event, where that event is just `{"type":"item.completed"}`. So the helper never saw it and a lane where nothing ran reported `DELEGATED_RUN_STATUS: success` at exit 0. The fix is deliberately NOT recursive and deliberately separate from `is_fatal`: a `state.status == "error"` NESTED inside a tool call is a denied OR independently failed call, which is `TOOL_ERRORS` business and the `/gemma:auto` fence working as designed, and making `is_fatal` recursive to reach the item case would re-break it. The broader wording is deliberate and the source insists on it: denial and independent failure are indistinguishable at that level without matching each harness's deny-rule WORDING, so the counter is named `TOOL_ERRORS` rather than `DENIED` because "the narrower name would claim more than the input supports". An error ITEM is the harness talking about itself - and codex emits that same item for `ConfigWarning`, `DeprecationNotice` and `ModelRerouted`, all of which continue running, so an error item ALONE is worth surfacing and not worth failing over. A genuinely critical error takes a different shape, a top-level `{"type":"error"}`, which `is_fatal` already catches. What makes #892 a failure is the conjunction: the harness announced an error AND nothing ever ran - the difference between "the run did nothing" and "the run could not do anything", which is also the difference between re-running the prompt and installing a missing binary. `item_error_message` surfaces the payload for exactly that reason, because the only prior signal was `no-tool-use`, which this helper's own documentation gives a benign reading
- delegated-run-check states its denominator, and `error` was absent from the item enumeration because the enumeration came only from runs that WORKED (#892) - `EVENTS` counts JSON lines parsed and `RECOGNIZED` the subset carrying a recognizable event shape, because a helper whose whole defect was "reports success when nothing ran" must be able to say how much it actually looked at; 0 recognized means the verdict was computed over nothing, which is UNKNOWN rather than clean, and `output-unrecognized` is the signal that says so. The item-type list this helper documents was "verified against real streams on disk" - five captures of successful runs - and an enumeration drawn only from successful runs cannot contain the failure item, while nothing about the list looks incomplete. Treat it as a floor, not a census: a membership list is only as complete as the population it was drawn from. Found while adding the denominator: `TOOL_ERRORS` was initialized INSIDE the parse branch, so an empty output file skipped it and the script died on `TOOL_ERRORS: unbound variable` part way through the contract - after SIGNAL and DETAIL, before STATUS - so a caller parsing `DELEGATED_RUN_STATUS` got NO status line at all. Measured on `c7297c2~1` against an empty file: exit 1, contract truncated after `DETAIL`. The merged commit's own comment says this case "exits 0" and that "a run that produced no stream at all reported success"; that does not reproduce, and the line above states what does. Recorded because the overstatement is instructive rather than as a correction for its own sake: an inventory line derived from a merged artifact is only as good as the artifact's PROSE where it relies on prose, and a comment is a claim while the code is the behaviour. The real defect is still real and still this issue's class - a contract that stops mid-emission leaves the field the caller branches on undefined - it is a missing verdict rather than a false one
- delegated-run-check tool-error channel - `DELEGATED_RUN_TOOL_ERRORS: <n>`, the count of tool calls that reported an error, in any of the three harnesses' shapes (#836, widened to all three lanes in #1054). `DELEGATED_RUN_STATUS` answers *did the delegated PROCESS run cleanly*; its readers take it for *did the delegated WORK happen*, and a denied tool call separates the two: it still counts as `tool_use`, the payload stays well formed and the exit code stays 0, so a run whose every command was refused reported `success` - one did, returning a fabricated empty `docker` inventory that nothing downstream could have questioned. The remedy is a new channel, NOT a wider `is_fatal`: the recursive version existed, made every fenced `git commit` a failed run and was reverted, and the header says so in as many words - a guard against false success that manufactures false failure is not an improvement. So the count never enters `signals`, never reaches `is_fatal` and never changes the verdict; `test_a_denied_tool_call_is_not_a_failed_run` passes UNMODIFIED and is the regression pin for the whole change. ALWAYS emitted including `0`, unlike `_SIGNAL`/`_DETAIL`, because a count that appears only when non-zero cannot distinguish "I looked and found none" from "this version does not look" - and telling those apart is the entire reason the line exists. Named for its real population: separating a DENIED call from a tool that failed on its own means matching each harness's deny-rule wording, a guess about format that the script's own header forbids, so it says `TOOL_ERRORS` and means exactly that. Counting is scoped to tool-ish events - a `state.status` error nested under a non-tool event would inflate it, the counter's own ownership boundary, pinned by `test_a_non_tool_error_state_is_not_counted_as_a_tool_error` rather than left as a TODO. The success prose changed with it: "the run looks clean" was the sentence being read as "the work happened", and now states the narrow claim and disclaims the broad one
- delegated-run-check counted one harness's shape and reported `0` for the other two (#1054) - `TOOL_ERRORS` matched a tool call's nested `state.status == "error"`, which is the OpenCode/gemma shape and no other, so on `--lane codex` and `--lane qwen` the counter was STRUCTURALLY incapable of returning non-zero whatever happened. The Codex CLI emits no `state` at all: it reports a failed call on the item, `{"type":"item.completed","item":{"type":"command_execution","exit_code":3,"status":"failed"}}`. The Qwen CLI emits a `tool_result` block carrying `is_error: true` two levels down inside `message.content[]`, where `is_fatal`'s deliberately TOP-LEVEL-only read cannot see it. Measured on a real `/codex:auto 1224` run against cooneycw/kyle: four commands exited non-zero, two of them the delegated model's own `make lint` and `make test-file` which a blocked dependency download meant never ran, and the helper printed `TOOL_ERRORS: 0`, `STATUS: success` and the sentence "no tool call reported an error" - an affirmative claim, not a silence, and the #836 false-clean reappearing one lane over. Codex reports ONE call across several events sharing an `item.id`, so codex items are deduped by id - inflation is this defect's mirror image and only one of the two looks wrong. The count still never enters `signals`, never reaches `is_fatal` and never changes the verdict. Two consequences worth stating rather than discovering: a benign non-zero exit is counted (an `rg` that matches nothing exits 1), which the name `TOOL_ERRORS` already claims and no more; and `isinstance(True, int)` is True in Python, so a `"exit_code": true` is excluded explicitly rather than read as a non-zero status. A counter-model reviewer raised two further shapes and they were resolved differently, which is the distinction worth keeping: `status: "declined"` is matched, because measuring the shipped binary put it in the camelCase app-server protocol rather than the snake_case exec JSONL - so it is speculative, but missing it would be a false zero while matching it spuriously requires a payload that literally says `declined`, and asymmetric risk is the only case where matching an unobserved string belongs in a file committed to verified format facts; `collab_tool_call` is NOT, because admitting it means editing `TOOL_TYPES`, which also drives `saw_tool` and therefore the VERDICT, and the enumeration carrying it (`collab_agent_tool_call`, `dynamic_tool_call`, `sub_agent_activity`) is a different protocol's list from the exec one - nit-stored rather than guessed at. The review also caught a test that passed for the wrong reason: `test_a_non_tool_codex_item_is_not_counted` was declined by the EVENT-level gate at the call site, not by the item-level scope it named, found by deleting the inner check and seeing the test stay green. WHY it survived #836 and #892 is the reusable part: the counter had a negative control for the shape it could see - both non-zero assertions in the suite were `--lane gemma` - and none for either shape it could not, while every codex-lane assertion in the file expected `0`. A per-format recognizer's always-emitted `0` is only as good as its list of formats, so a new lane owes a committed case ON THAT LANE. The codex case is a real `codex exec --json` capture (`tests/fixtures/delegated_runs/codex-command-failed.jsonl`, a command that really exited 3); the qwen shape is read out of the installed CLI's `emitToolResult` source, and its case is synthetic - a difference in provenance the tests state rather than imply
- delegated-run-check is NOT fail-open, and that is the one deliberate departure from every other advisory in the flow family. Those shrug off what they cannot assess, because a guard that cannot see must not stop a run. This one inverts that: it exists because an unassessable run was being reported as a success, so an unreadable or empty stream reports `failure` - "the delegated model produced no output" is the failure, not an inconclusive reading of one

- delegated-run-check format facts are VERIFIED, never guessed (#798 cross-model review) - the first cut recognized only `tool_use`-shaped events, so every SUCCESSFUL `/codex:auto` run would have scored `no-tool-use` and failed under the `--expect-tools` its own lane passes. - delegated-run-check `no-terminal-event` (truncated or killed stream) fails only under `--expect-tools`, and the gating is empirical rather than tidy: `turn.completed` was absent from 2 of 5 real codex captures, one of them a run still executing when it was sampled. ## `deletion-accounting` (#1031)

- deletion-accounting - accounts for every line a diff DELETES, before you push it (#1031). It exists because worktrees share the object store AND the refs: a sibling session's `git fetch` in ANY worktree advances `origin/main` for EVERY worktree with no signal in yours, so `git reset --soft origin/main` moves HEAD to a base your tree has not seen and the resulting commit's diff renders the sibling's merged work as DELETIONS authored by you. Caught once in a real branch before pushing - a commit touching 10 files reported 22 files, 1022 insertions, 861 deletions, the extra 12 being another worker's merged PR. Nearly invisible: `git log --oneline origin/main..HEAD` shows ONE commit with your message; two-dot and three-dot diffs are IDENTICAL, because after the reset `origin/main` IS the merge base, so the merge-base remedy for the reviewer hazard does not detect this one; and `make verify` passed green on 3500 tests over a tree with the sibling's work reverted, because a suite cannot object to work that is simply absent. The tell is the FILE COUNT, which is why it prints first
- deletion-accounting DOES NOT PATTERN-MATCH THE DIFF, and that is the fix. The check adopted to catch the above was `git diff "$MERGE_BASE" | grep -E '^-[^-]' | sort | uniq -c`; `^-[^-]` requires a character after the `-`, so it cannot match a bare `-` (a deleted BLANK line) or a line beginning `--` (a deleted MARKDOWN BULLET, because `- item` renders as `-- item`). Measured on a merged documentation PR: 88 matched, 24 bare `-` invisible, 7 `--` invisible, 119 actual - and the seven silently dropped were deleted verdict definitions and a deleted guidance line. The issue's own corrected one-liner, `grep -E '^-' | grep -v '^---'`, is better and still not right: a deleted line whose CONTENT begins `---` renders as `----`, matches `^---`, and is discarded with the file headers - measured on this branch at 3 of 4 where the blind form saw 1 and the shipped parser saw 4. So it parses hunks instead - and TEXT-MATCHING THE HEADERS IS NOT ENOUGH EITHER, which the counter-model review of this change proved on its first cut. Recognising `--- `/`+++ ` by their text, narrowed to git's `a/`/`b/` prefixes on the belief that shape was unfakeable, still ended a hunk early on a deleted `-- a/foo` followed by an added `++ b/bar`: 0 deletions where git reports 2, the same content-dependent blindness one level down. The parser now CONSUMES the line counts the hunk header declares and looks for a header only once both are exhausted, so nothing inside a hunk can be mistaken for one whatever it spells
- deletion-accounting COUNTS ITS OWN COVERAGE, because the first cut answered confidently over input it had never parsed - five ways, all reported as `ok - 0 deleted`: a diff taken under `color.ui=always` (escape sequences hide every hunk; 19 real deletions read as 0), a file of bytes that is not a diff at all (`fatal: upstream diff generation failed`), a directory passed to `--diff-file` (`-r` is true for one and `cat`'s status was discarded), a truncated patch whose hunk header declares more lines than it holds, and a deleted BINARY file, which has no lines to count and vanished entirely. A SECOND review pass found four more of the same shape after those were fixed: a combined merge hunk (`@@@`) the parser does not read, a patch truncated after its file headers, a hunk whose counts UNDERFLOW (`@@ -1,0 +1,1 @@` spends them on a context line, so the deletion below falls outside the hunk and the end-of-input check sees nothing left over), and a deleted binary in `git diff --binary` form, which says `GIT binary patch` and never mentions `/dev/null`. Coverage is therefore counted PER FILE SECTION, not per input - accepting the whole input because something in it parsed is how one valid patch masks an unreadable neighbour, which is precisely what `--root` does. All nine are now UNKNOWN or a finding; the `--base` lane additionally pins `color.ui=false --no-color --no-ext-diff --no-textconv`, so a presentation setting cannot switch the instrument off. A genuinely empty `git diff` stays CLEAN, and so does a rename-only or mode-only patch, which legitimately carries no hunk - those distinctions are what keep the coverage check from reporting UNKNOWN on ordinary correct input, which is how a check gets switched off inside a week (ADR 0009)
- deletion-accounting IS MEASURED AGAINST `git diff --numstat`, not against its author's arithmetic. `--numstat` comes from git's own diff machinery rather than from reading the textual patch, so agreement between the two is evidence about the parser; `tests/test_deletion_accounting.py` asserts it on a repo built to hold every shape the one-liners trip on - front-matter delimiters that must NOT count because they survive as context, a deleted `---`, a deleted bullet, a deleted blank line, and ordinary code. Verified on a real 31-file diff of this repository: 276 deletions across 31 files, identical to `--numstat`, of which 18 were invisible to the retired form
- deletion-accounting EXIT 1 IS NOT AN ACCUSATION. It cannot know which deletions are yours - only you can - so its job is to put every one in front of you with nothing filtered out: 0 = nothing deleted, 1 = deletions to review, 2 = UNKNOWN. Exit 2 is why `detect_signal` keys on the FINDING line rather than the exit status: an unresolvable ref, an unreadable input or an EMPTY population must not score as a run that found something, and `controls/deletion-accounting` would otherwise be unable to tell a detection from a failure to look. An empty `--root` is UNKNOWN rather than clean for the same reason
- deletion-accounting REPORTS MULTIPLICITY AND REFUSES TO INTERPRET IT. The companion heuristic propagated alongside the retired grep - "every deletion appears exactly twice" - would have fired on 63 distinct lines with zero real findings; measured multiplicities were 1x/2x/3x/4x/6x/24x. A multiplicity is a finding only against the KNOWN FAN-OUT of the source file it came from, and that map has to be derived, not hand-listed, so the census prints counts and says nothing about what a count means
- deletion-accounting's negative control is `controls/deletion-accounting`, whose anchor is the retired `^-[^-]` form itself, committed as a blind artifact. Its two BAD cases are chosen so the anchor MISSES both: deletions that are only a markdown bullet and a blank line, and a deleted `---`. A second anchor for the corrected one-liner cannot coexist with them - that form CATCHES the first case - so the one-liner's residual is pinned by a unit test instead, which is the honest place for a blindness no single anchor can demonstrate against this case set

## `bandit-audit` (#962)

- bandit-audit - the repository's own Python static security analysis over `lib/` and `scripts/` (#962). CPP ran none: `grep -rn "bandit" Makefile .woodpecker.yml pyproject.toml` returned nothing across 113 tracked Python files, while `lib/security/` is CPP's deterministic secret and policy scanner and `lib/creds/` handles credential retrieval and injection. A repository shipping security tooling that runs no static analysis over that tooling is the gap, independent of what the scan finds. `lib/security/modules/` carries nine adapters and no Python SAST, so `/security:scan` could not produce this verdict either
- bandit-audit DID NOT INHERIT codex-power-pack's skip list, and that re-decision is the whole of #962. CxPP runs `bandit -r lib scripts -ll --quiet --skip B104,B108,B310,B602`; measured on this tree at adoption, that list removes **10 of 11** MEDIUM+ findings, because B602 (`shell=True`) and B108 (hard-coded `/tmp`) are precisely what a repository of shell-out helpers and deploy locks does. The issue named the hazard in advance - "inheriting a suppression without re-deciding it is how CPP's four disabled mypy error codes ended up load-bearing in two repos" - and the measurement confirmed it rather than discovering it
- bandit-audit replaced the MECHANISM, not merely the contents of the list. A `--skip` turns a rule off across the whole tree, forever, invisibly, and has no direction in which it can go stale. `.bandit-audit-allow` carries one line per (file, rule) - `finding <path> <test-id> <count> <issue>` - so three distinctions a blanket skip cannot draw all become reds: a new site in a file that already has one (the count), a new site in a fresh file (the path), and a recorded site that gets FIXED (the line now accepts more than the run reported, `BANDIT-STALE`, exit 1). Today: 10 lines covering 11 findings, every one dispositioned by #1113. KNOWN BLIND SPOT, bounded rather than widened (counter-model review of #962): a count is not a per-site identity, so fixing one accepted site and adding a different one in the same file leaves the count unchanged and the gate green - the REPLACEMENT is invisible. Deliberate: a line number is invalidated by every edit above it and a snippet hash by every reformat, and a ledger that reddens on unrelated edits gets switched off (ADR 0009). Whether an accepted site is still the same site is answered by review of the diff that moved it and by #1113, and `tests/test_bandit_audit.py::test_a_same_count_site_replacement_is_a_known_blind_spot` pins the bound. Whole-line comments only, for the reason the sibling gate learned the expensive way - `#` opens a comment and also opens every issue reference on a record
- bandit-audit refuses BOTH inline routes around that ledger, and they are DIFFERENT FIELDS - a fact the first cut got wrong and the counter-model review measured. On bandit 1.9.4: a bare `# nosec` increments `metrics.<file>.nosec`, a rule-scoped `# nosec B307` increments `metrics.<file>.skipped_tests` and leaves `nosec` at 0. The two comments are one character apart in source, so reading `nosec` alone missed the rule-scoped form entirely - which is the form a careful author is MORE likely to write, since it suppresses less. Both are read, per file, so the finding names where to look. Either way a tracked, counted, printed ledger could otherwise sit beside an untracked, uncounted, unprinted one in the source, which is what ADR 0008's "suppressions are visible or they do not happen" rules out
- bandit-audit's `skipped_tests` guard does NOT detect a CLI `--skip`, and the correction is recorded rather than quietly swapped. The first cut read that field as "a `--skip`/`-s` reached the tool" and said so in its own message; measured, `--skip B307` yields `skipped_tests=0` and simply omits the finding, so the guard was blind to the exact thing #962 is about, and the registered case that "proved" it declared `skipped_tests=4` - a report bandit never emits, a fixture built to the author's belief rather than to the tool. It was deleted and replaced by `bad-rule-scoped-nosec`. Ambient config was checked too and is not a route on this version: a `.bandit` at the repository root and a `pyproject.toml [tool.bandit]` section both had NO effect (bandit needs an explicit `-c`), recorded with its date rather than asserted as a property. The CLI-flag question now lives where it can fail: `BANDIT_FLAGS` is ONE tuple shared by the audit and by `--selftest`, so a suppression flag reddens the live fixture first - though only for the rule that fixture exercises, which is why `tests/test_bandit_audit.py` also PINS the tuple as a literal. An exact-token screen was the pass-1 fix and pass 2 defeated it with `--skip=B104` and `-sB104`; an equality assertion has no spelling to miss, and a normalized-option check sits beside it so the pin cannot be edited into a hole
- bandit-audit inherits ADR 0008's third-party-tool shape from `shellcheck` (#960), the shape that ADR states #961 and #962 take. The scan ROOTS are hardcoded so the enumeration cannot silently narrow itself; the MEMBERS under them are derived by walking with a declared prune list, never globbed. The denominator - files examined, loc, and the ROOTS themselves - prints on EVERY run including the clean one, so the claim is bounded rather than silently narrow: `tests/`, `extras/` and the generated `codex/skills/` copies are outside the population (the root-level `*reddit*.py` scripts this note used to name were deleted by #1041), and widening is a decision rather than an omission (bandit over `tests/` is thousands of B101 `assert_used` findings and nothing else)
- bandit-audit checks COVERAGE, not merely membership, and the distinction is measured. A file bandit cannot parse still appears in `metrics` with a `loc` count - a file containing `def broken(:` produced `metrics["probe/c.py"] = {"loc": 1, ...}` AND an entry in `errors` - so presence in `metrics` proves a file was READ, never that it was ANALYSED. Both are required: every enumerated file must appear in `metrics` AND `errors` must be empty, or the run is UNKNOWN. Same shape as pip-audit's `skip_reason` one gate over (#961), where a single skipped dependency produced `ok - 1 package(s), 0 findings`
- bandit-audit hands bandit the ENUMERATED FILES rather than `-r lib scripts`, because two traversals that can disagree eventually will (counter-model review). `discover()` prunes `.venv`, `venv` and the caches; bandit's own recursion prunes nothing, so `lib/.venv/site-packages/dep.py` appeared in the report and not in the population and the gate reported UNKNOWN because a neighbour's installed dependency had changed. An explicit file list makes the two populations identical BY CONSTRUCTION, with no second exclusion list to keep in sync
- bandit-audit refuses an enumeration that failed PARTWAY, which `os.walk` otherwise hides (counter-model review pass 2). `os.walk` swallows directory-read errors and omits the subtree: injecting a `PermissionError` for `lib/security/` took the population from 113 files to 94 and the audit still printed `ok`, exit 0 - a zero that cannot tell clean security code from security code it could not enumerate, and invisible downstream because the coverage check compares bandit's report against that already-short list. An `onerror` handler now raises UNKNOWN, and a declared root that is absent or unreadable is refused for the same reason: "the root is not there" and "the root is clean" are not the same fact
- bandit-audit posture: an unaccounted MEDIUM+ finding exits 1, a stale allowlist line exits 1, a `# nosec` or a `--skip` exits 1, and UNKNOWN exits 2 - bandit unavailable, a file it could not parse, a file missing from the report, a finding outside the enumerated population, a zero-file population, or an unreadable ledger. **Unknown is never a pass**, the same rule the shellcheck gate holds for a missing binary, and the two outcomes are distinguishable by construction: `bandit-audit: ok` is a statement about the tree, `BANDIT-UNKNOWN:` is a statement about this run, and the two never print together
- bandit-audit gates at severity >= MEDIUM and COUNTS the band below it rather than discarding it. 136 LOW findings across 40 files at adoption, 119 of them B603 + B607 + B404 - the same observation stated three times, that this repository shells out on purpose, everywhere. Gating there would fail 40 of 113 files on day one, and a gate that fails everything on day one is switched off inside a week (ADR 0009). The count prints on every run and is tracked by #1114, so "below the gate" never reads as "not examined". #972 is the same residual one tool over, for `shellcheck`
- bandit-audit is PINNED IN THE DEV EXTRA rather than fetched with `uvx`, and `make bandit-audit` runs through `uv run --extra dev` so the tool is the one `uv.lock` names. A linter's ruleset moves between releases; `.woodpecker.yml` already records what that costs for shellcheck - "running the gate under two different linters would make the control's verdict depend on which container reached it" - and a Python tool cannot be pinned by image digest the way a static binary can. The `uvx` fallback exists for a caller with no synced venv and says so on stderr rather than pretending to parity
- bandit-audit IS in `make verify` while `dep-audit` is NOT, and the asymmetry is the reason rather than an inconsistency. `dep-audit` is excluded because it REQUIRES THE NETWORK and verify is the gate a developer runs on a plane; bandit is a local analyser, so after `uv sync` this needs nothing but the checkout. `dep-audit`'s pre-committed reversal trigger - "if `verify` ever acquires another target that REQUIRES the network, the reason for this exclusion is gone" - is deliberately NOT fired by this target, and `tests/test_bandit_audit.py` pins both halves
- bandit-audit has three inputs because a control must be valid where the harness runs (ADR 0008). ## `stash-worktree-guard`

- stash-worktree-guard - a git `reference-transaction` hook that refuses `git stash push` from a LINKED WORKTREE (#1056). A worktree isolates the working tree and NOT the refs: `refs/stash` lives in the repository's common git dir, so every worktree plus the main checkout share ONE stack, and `git stash pop` takes whatever is on top rather than what you put there. Measured three times here - #521/#635 (two `/flow:auto` runs swapping each other's work), a `/cpp:update` auto-stash orphaned on the shared stack for sixteen days, and a `/codex:auto` worker on #1032 whose pop restored 67 lines of a different session's #1027 work while its own entry vanished from the reflog. #635 fixed this by writing "never stash here" into `.claude/commands/flow/{auto,finish}.md`, which binds only a caller reading one of those two documents at that moment; the #1056 worker was producing a RED case against pre-fix code, a task no flow command covers, so it never passed the place where the rule was written. This lives in git instead, so it binds a human, Claude, Codex, Qwen and a shell script equally
- stash-worktree-guard guards `push` ONLY, and that bound is structural rather than unfinished work. Measured on git 2.43.0: on `push` the `refs/stash` transaction reaches `prepared` BEFORE the working tree is touched, so refusing aborts cleanly - exit 128, working tree byte-identical, no entry created; on `pop` git applies the stash and prints `Dropped refs/stash@{0}` FIRST and the veto fires afterwards, leaving the tree mutated AND the entry gone, which is strictly worse than not guarding; `drop` has the same shape. So it acts only on entry CREATION, whose signature at `prepared` is unambiguous - `old` is the null OID. A future editor who "completes" it by acting on deletions would be adding a refusal that fires after the damage, and `tests/test_stash_worktree_guard.py::test_pop_is_not_guarded` pins that so the edit reds instead of reading as an improvement. Its silence on a pop is not approval, and the header, the refusal message, `docs/agents/shared-stash-stack.md` and that test all say so
- stash-worktree-guard is FAIL-OPEN everywhere else, because it fires on every ref update in the repository - every commit, fetch and branch, in every worktree - so a bug here breaks git for every session. Another ref, another transaction state, a malformed line or a git too old to resolve its own dirs all exit 0, and it does no work at all until a line's ref is already known to be `refs/stash`. `CPP_ALLOW_WORKTREE_STASH=1` permits the deliberate uniquely-tagged stash that is restored by `git stash apply <sha>`. Installation is ON BY DEFAULT (owner decision, 2026-09-19): `flow-start-resolve.sh --verify` arms it on every worktree of every lane - the moment a linked worktree makes `refs/stash` shared is exactly when the hazard appears - and `/cpp:init` Tier 1 and `/cpp:update` Step 5b.1 install it too. All three are advisory and fail-open; none can fail the step it runs in. `--install [REPO]` / `--check` / `--uninstall` / `--enable`, verdict `STASH_GUARD: installed | current | stale | absent | foreign | unsupported | disabled | error`. The OPT-OUT PERSISTS, which is what makes it one: `--uninstall` removes the hook and records `cpp.stashGuard=false`, `--install` then reports `disabled` and changes nothing, and `--enable` is the deliberate way back on. Without that record the next automatic install would silently undo the user's choice, so the prompt would return on every update - the oscillation ADR 0009 predicts. `disabled` and `absent` are separate verdicts because they are opposite facts: nobody installed it, versus somebody turned it off. `--quiet` suppresses the prose on a no-op and NEVER the verdict line - silencing that marker made a real `disabled` read as `unknown` in the resolver, caught by `test_verify_honours_the_stash_guard_optout` - and one install covers the whole worktree family because hooks resolve through the same common dir the stack does. It COPIES rather than symlinks: a symlink into a checkout later moved or deleted leaves a dangling hook in every worktree, where a stale copy is merely reported by `--check`. The location comes from `git rev-parse --git-path hooks`, so an ABSOLUTE `core.hooksPath` is honoured; a RELATIVE one is refused as `unsupported`, because each worktree resolves it against its own top-level and no single install could cover the family that shares the stack - measured, and reporting success there would claim coverage that does not exist. `--check` also requires the installed copy to be EXECUTABLE before saying `current`: git silently ignores a non-executable hook, so identical bytes establish nothing about enforcement. All three came from the counter-model review on this branch. `foreign` refuses to overwrite a different `reference-transaction` hook rather than chaining it on a guess, and `unsupported` names a git below 2.28 rather than reporting an install that enforces nothing
- stash-worktree-guard is NOT registered in `controls/`, and the reason is the registry's own contract rather than an omission. Its negative control needs a real repository with a real linked worktree, and git is absent from the `negative-controls` CI image by design (the anchors are vendored precisely because of that); a git-dependent control there reports UNSIGNALLED and fails the pipeline. Its control lives in `tests/test_stash_worktree_guard.py` instead, carrying both halves issue #1056 names - a worktree push refused with the tree byte-identical, and the same push from the main checkout succeeding - plus `test_blind_guard_fails_the_known_bad_case`, which runs the identical known-bad input against an always-exit-0 hook and asserts the outcome flips. Verified by mutation before shipping: blinding the hook lane reddens exactly the two refusal tests and leaves the other twelve green, which is the correct signature since a blind guard permits everything

## `pytest-workers` (#1086)

- pytest-workers - resolves the pytest worker cap for `make test` and the CI `validate` step, and REFUSES `auto` (#1086, executing the convention #640 shipped). Precedence is `PYTEST_WORKERS` then `CPP_TEST_WORKERS` then a default declared in the script, identical to `resolve_pytest_workers()` in `lib/cicd/steps.py` - #640 built that precedence FOR CONSUMER PROJECTS, naming this very host's contention as the reason, and CPP never applied it to itself, so CPP's own suite was the one on the box with no cap at all. The integer goes to stdout so the whole call site is `-n "$(sh scripts/pytest-workers.sh)"`; the human line goes to stderr so the cap is IN the run's output rather than reconstructed from the yaml by a reader
- pytest-workers REFUSES rather than clamps, and that is the decision rather than a default. `-n auto` is one worker per core, `nproc` is 24 on this host, one Woodpecker agent serves it with `WOODPECKER_MAX_WORKFLOWS=2` and no per-step CPU limit, and flow sessions run full suites from worktrees beside the pipeline - nine were live while #1086 was measured. Multiplied by the invocations actually in flight, the first symptom is not a slow machine but intermittent reds that read as regressions in whatever changed most recently. Clamping would make the caller's stated intention silently untrue; refusing (exit 2, `pytest-workers: REFUSED`) makes them state a real one. Non-integers and every all-zero spelling are refused on the same grounds - `0`, and also `00` and `000`, which the counter-model review caught being ACCEPTED because the first cut matched the literal `0` and so tested the value's spelling rather than its value; leading zeros are normalised after validation, so `-n 08` reaches pytest as `8`. The stripping is a POSIX loop rather than `$((10#$workers))`: that is a bashism, the CI image has no bash, and under `sh` it is an arithmetic error that aborted the script for EVERY value, valid ones included - caught only by re-running the known-good case after fixing the known-bad one. A cap above the core count is a NOTE rather than a refusal - oversubscription is a legitimate choice for a suite that waits rather than computes, which this one does
- pytest-workers has its committed two-sided case in `tests/test_pytest_worker_cap.py` rather than in `controls/`, and the reason is the registry's shape, not an omission: the negative-control harness hands a gate a case DIRECTORY, and this gate's entire input is an environment variable. The test module carries both directions - `auto` refused with the message, an integer accepted with the line - plus all three precedence orderings, so the guard cannot quietly stop refusing
- pytest-workers declares the DEFAULT and CI declares its OVERRIDE, which are different statements and live in different places. The dev-box default is 4 rather than the 8 where #1086 measured 5.34x, because that measurement was of ONE suite: this box routinely carries four to nine concurrent CPP suites from flow worktrees, and 9x4=36 workers on 24 cores is already oversubscribed where 9x8=72 is threefold. CI overrides to 8 on the `validate` step because `WOODPECKER_MAX_WORKFLOWS=2` bounds that host to two pipelines

## `pytest-parallel-differential` (#1086)

- pytest-parallel-differential - compares a SERIAL and a PARALLEL JUnit report of the SAME commit node by node (#1086). The acceptance question for a parallelism change is not "is it green" but "did the same tests run, and did they reach the same verdicts": a test whose isolation broke does not usually fail, it passes for the wrong reason because a sibling worker created the resource it asserts on. The speedup is visible on every run and the weakening is visible on none of them, so this is the instrument that separates them
- pytest-parallel-differential decides three things separately, because they are different diagnoses. MEMBERSHIP FLOOR - the two runs collected the same SET of node ids; a count comparison is not enough, since a substituted node keeps the count and changes the population, and a green over 3,900 tests and a green over 4,263 print the same colour. DANGEROUS - a node that FAILS serially and PASSES in parallel, which blocks: whatever made it pass was not the code under test. QUARANTINE - a node that passes serially and fails in parallel, a flake to triage rather than a reason to abandon the change, but still a DIFFERENCE and therefore still non-zero; calling it agreement because it is the safe direction would be the same overclaim pointed the other way
- pytest-parallel-differential exits 2 with `DIFFERENTIAL-UNKNOWN:` on a missing file, unparseable XML, a duplicated node id, or a report carrying zero test cases. Zero is a denominator, not a result: two empty reports have identical node-id sets and agree perfectly, which is the most flattering wrong answer available here. Node identity is `classname::name`, not the `file` attribute, which some pytest versions omit - an identity that depends on the writer's version is not an identity
- pytest-parallel-differential is CONTROLLED (`controls/pytest-parallel-differential/`, ADR 0008), and BOTH bad cases carry an IDENTICAL TALLY on purpose. The anchor is a constructed tally-only comparator - the first framing of the problem, and exactly what a human does glancing at two summary lines - so a bad case whose totals differed would be caught by it, the control would report INERT, and the demonstration would establish nothing about the distinction this gate exists to draw. `bad-substituted-node` keeps 3 passes on both sides while a different test ran; `bad-dangerous-flip` keeps 1 pass and 1 failure on both sides with the pass and the failure swapped between two tests. The GOOD case carries a failure present in BOTH runs, mirroring the real #1086 measurement, so the accept-an-agreeing-failure path is exercised rather than left unproven by an all-green pair
